### Кейс 5: Призрак изменения (*Hibernate Dirty Checking*)

### Обновится ли запись в базе данных?
```Java
@Service
public class ProfileService {

    @Transactional
    public void updateUsername(Long userId, String newName) {
        User user = userRepository.findById(userId).orElseThrow();
        user.setName(newName);
        
        // ВНИМАНИЕ: Мы забыли вызвать userRepository.save(user);
    }
}
```

**Что произойдет:** Имя пользователя в базе данных **успешно изменится**, несмотря на то, что метод `save()` не был вызван.

### Почему:
1. Метод помечен как `@Transactional`, поэтому при входе открывается сессия Hibernate.    
2. Метод `findById` извлекает сущность из БД и помещает её в Persistence Context (*кэш первого уровня*). Сущность переходит в состояние _Managed_ (*управляемая*).    
3. При вызове сеттера `setName()` меняется состояние объекта в оперативной памяти. 
4. В момент завершения метода прокси Spring пытается закоммитить транзакцию. Перед коммитом Hibernate автоматически вызывает механизм **Dirty Checking** (проверка "грязных" объектов).    
5. Hibernate сравнивает текущее состояние объекта `User` в памяти с его начальным снимком (снапшотом), видит, что поле `name` изменилось, и сам генерирует SQL-запрос `UPDATE`.

Какой из этих механизмов кажется вам наиболее непредсказуемым при отладке чужого кода?

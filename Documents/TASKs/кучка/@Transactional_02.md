


```java
@Transactional
public void proxySaveUser() {
    try {
        User user = new User();
        persistensContext.save(user); // Ошибка: несоответствие типов полей
    } catch (Exception e) {
        // NOP - проглотили
    }
    // Метод завершается без исключения
    // Что будет?
}
```

---
### Пошагово, что произойдет:
В этом коде произойдет одно из двух, но результат будет один: **исключение всё равно будет выброшено, а транзакция — откатана.** Проглотить ошибку таким образом не получится.

Вот как это работает под капотом (в зависимости от того, когда именно генерируется ошибка):

### Сценарий 1: Ошибка происходит отложенно (при `flush`) — Самый частый случай

По умолчанию в Hibernate метод `save()` (или `persist()`) не отправляет SQL-запрос в базу данных немедленно (если только не требуется сразу получить сгенерированный базой ID типа `IDENTITY`). Он просто помещает сущность в Persistence Context.

1. `save(user)` отрабатывает **без ошибок**.
    
2. Блок `catch` вообще не срабатывает.
    
3. Ваш метод `proxySaveUser()` завершается штатно.
    
4. В дело вступает прокси `@Transactional`. Он видит, что метод завершился успешно, и начинает процедуру `commit`.
    
5. Перед коммитом Hibernate делает автоматический `flush` (отправляет накопившиеся SQL-запросы в БД).
    
6. Возникает ошибка на уровне БД (несоответствие типов).
    
7. **Итог:** Исключение вылетает на этапе коммита, уже **за пределами** вашего `try-catch`. Вызывающий код получит исключение (например, `DataException` или `TransactionSystemException`).
    

### Сценарий 2: Ошибка происходит прямо внутри `save()`

Если ошибка типов отлавливается на уровне самого Hibernate еще до отправки в БД, или если SQL отправляется немедленно, то:

1. Вызывается `save(user)`, внутри него выбрасывается исключение.
    
2. Но прежде чем выбросить исключение, Hibernate помечает текущую транзакцию меткой **`rollback-only`** (только для отката), так как считает, что контекст скомпрометирован.
    
3. Ваша программа перехватывает ошибку в блоке `catch` и "проглатывает" её.
    
4. Метод завершается штатно.
    
5. Прокси `@Transactional` пытается сделать `commit`, так как из метода не вылетело исключений.
    
6. Spring проверяет статус транзакции, видит метку `rollback-only` и понимает, что коммитить нельзя, хотя метод сказал, что всё хорошо.
    
7. **Итог:** Spring сам выбросит исключение **`UnexpectedRollbackException`** с сообщением вроде _"Transaction silently rolled back because it has been marked as rollback-only"_.
    

### Резюме

В Spring с `@Transactional` нельзя просто «проглотить» исключение от JPA/Hibernate, если оно нарушает целостность работы с БД.

Если вы действительно хотите попытаться сохранить данные, а в случае неудачи продолжить работу (например, записать в лог или сохранить что-то другое), вам нужно вынести этот `save` в **отдельный метод** с аннотацией `@Transactional(propagation = Propagation.REQUIRES_NEW)` и оборачивать в `try-catch` уже вызов этого нового метода.

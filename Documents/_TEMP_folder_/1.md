Для запуска на одной машине и демонстрации уровня **Middle+** оптимально разделить систему ровно на **3 микросервиса**.

Меньшее количество (2 сервиса) выглядит как искусственно распиленный монолит, а 4 и более сервиса перегрузят оперативную память ноутбука. При этом **Apache Kafka здесь не утяжелит систему, а станет ключевым козырем**, если запустить её в современном режиме **KRaft** (без тяжелого Zookeeper) и ограничить память контейнеров. Весь стенд (3 Java-сервиса + Kafka + PostgreSQL) уложится в **2.5–3 ГБ ОЗУ** и запустится одной командой `docker-compose up`.

### 2. Подробное описание каждого микросервиса

#### 1. Сервис курсов валют и котировок (`currency-rates-service`)

- **Роль понятным языком:** «Поставщик рыночных данных». Единственный сервис, который знает о существовании внешнего интернета, ЦБ РФ и бирж.
    
- **Что делает:**
    
    - По расписанию (и по ручному вызову) ходит в реальный **SOAP API Центробанка РФ**, забирает курсы валют, ключевую ставку и цены на драгметаллы.
        
    - Ходит в **REST API Московской биржи** за текущими ценами акций и облигаций.
        
    - Хранит историю котировок в своей БД (`rates_db`, таблицы секционированы по годам).
        
- **Интерфейсы:**
    
    - _Отдает REST API:_ позволяет другим сервисам синхронно запросить курс конкретной валюты на конкретную дату (с кэшированием в памяти через Caffeine).
        
    - _Пишет в Kafka (Producer):_ как только загружены свежие курсы за день, публикует событие в топик `currency.rates.updated`.

#### 2. Сервис учета сделок и портфеля (`portfolio-service`)

- **Роль понятным языком:** «Бухгалтерская книга / Кошелек». Отвечает за то, сколько денег и активов есть у пользователя и какие операции он совершил.
    
- **Что делает:**
    
    - Принимает от пользователя через REST API операции: покупка/продажа активов, зачисление дивидендов, уплата комиссий, обмен валюты.
        
    - Гарантирует **идемпотентность**: проверяет `idempotency_key` каждой сделки, чтобы при повторном нажатии кнопки деньги не списались дважды.
        
    - Ведет актуальные остатки по счетам в своей БД (`portfolio_db`).
        
- **Интерфейсы:**
    
    - _Принимает REST API:_ создание портфеля, добавление сделки, просмотр текущих балансов.
        
    - _Пишет в Kafka (Producer):_ при сохранении новой сделки записывает событие в таблицу `outbox_events` в той же транзакции БД, а фоновый процесс отправляет его в топик `portfolio.trades` (паттерн **Transactional Outbox**).

#### 3. Сервис расчета налогов и отчетов (`tax-report-service`)

- **Роль понятным языком:** «Налоговый калькулятор и генератор справок». Самый сложный по бизнес-логике сервис, внутри которого живет чистое ядро на Java Core.
    
- **Что делает:**
    
    - Слушает события о новых сделках из Kafka и формирует у себя налоговые партии (лоты) в БД (`tax_db`).
        
    - Считает финансовый результат по методу **FIFO** с **валютной переоценкой** (пересчитывает каждую покупку, продажу и комиссию в рубли строго по курсу ЦБ на дату операции).
        
    - Считает пени и проценты по ключевой ставке ЦБ за любой период.
    
- **Интерфейсы:**
    
    - _Читает из Kafka (Consumer):_ подписан на `portfolio.trades` (пересчитывает налоговую базу при новой сделке) и на `currency.rates.updated` (обновляет локальный справочник курсов для автономности расчетов).
        
    - _Ходит по REST в `currency-rates-service`:_ если пришла сделка за прошлый год, а курса на эту дату еще нет в локальном кэше, дозапрашивает его синхронно (под защитой **Resilience4j Circuit Breaker**).
        
    - _Отдает REST API:_ выдает красивый JSON-отчет по налогам для веб-интерфейса.
        
    - _Отдает SOAP API (Сервер):_ публикует WSDL-контракт и принимает XML-запросы от корпоративных систем (например, 1С) на выгрузку налоговых регистров.

### 3. Как устроены данные и взаимодействие (уровень Middle+)

|**Аспект архитектуры**|**Как реализуем**|**Зачем это нужно на собеседовании**|
|---|---|---|
|**Базы данных (Database per Service)**|В `docker-compose.yml` поднимается **один** контейнер PostgreSQL 18, но при старте init-скрипт создает три независимые базы (`rates_db`, `portfolio_db`, `tax_db`) с разными пользователями.|Соблюдаем главный принцип микросервисов (никаких общих таблиц и JOIN между сервисами), но не тратим лишнюю память на 3 контейнера Postgres.|
|**Гарантия доставки в Kafka**|В `portfolio-service` используем паттерн **Transactional Outbox** (запись сделки + запись события в таблицу `outbox` в одной локальной транзакции).|Показываем понимание проблемы «двойной записи» (Dual Write): что делать, если в БД сделка сохранилась, а Kafka в этот момент упала.|
|**Защита от дублей в Kafka**|В `tax-report-service` храним таблицу `processed_events(event_id)` (паттерн **Idempotent Consumer**).|В распределенных системах Kafka гарантирует доставку _At-least-once_ (сообщение может прийти дважды). Эта таблица защитит от двойного начисления налога.|
|**Синхронное vs Асинхронное**|Запрос недостающего курса на историческую дату — **синхронный REST**. Уведомление о новой сделке и рассылка свежих курсов — **асинхронная Kafka**.|Демонстрируем умение выбирать правильный протокол под задачу, а не пихать Kafka или REST везде подряд.|

### 4. Как уместить всё на одном ноутбуке (настройки Docker)

Чтобы вся система не «положила» компьютер при демонстрации, в `docker-compose.yml` закладываются три инженерных приема:

1. **Kafka в режиме KRaft (без Zookeeper):** Используем официальный образ `apache/kafka:3.9.0` (или `4.0.0`). Вместо двух тяжелых контейнеров работает один, который стартует за 3 секунды.
    
2. **Ограничение памяти JVM (Heap tuning):** Для каждого из трех Spring Boot сервисов задаем переменную окружения `JAVA_TOOL_OPTIONS: "-Xms128m -Xmx320m -XX:+UseG1GC"`. Современная **Java 25** с виртуальными потоками отлично чувствует себя в 320 МБ памяти на пет-нагрузке.
    
3. **Единая точка документации (опционально):** Вместо тяжелого Spring Cloud Gateway можно добавить крошечный контейнер **Swagger UI** (или Nginx на 15 МБ памяти), который агрегирует OpenAPI-спецификации всех трех сервисов на одной странице `http://localhost:8080/docs`, чтобы удобно показывать работу системы на созвоне.

### 5. Что этот вариант добавит в ваше резюме

Помимо закрытия всех требований исходной вакансии (**Java Core, REST, SOAP, PostgreSQL, Liquibase, статические анализаторы безопасности**), такая архитектура автоматически делает ваше портфолио релевантным для **90% остальных Middle/Middle+ Java-вакансий**, где в требованиях почти всегда стоят:

- Опыт работы с **Apache Kafka** (Spring Kafka, настройка топиков, обработка ошибок / Dead Letter Topic).
    
- Понимание паттернов микросервисной архитектуры (**Transactional Outbox**, **Idempotent Consumer**, **Database per Service**, **Circuit Breaker**).
    
- Умение проектировать контракты (OpenAPI для REST, WSDL/XSD для SOAP, JSON Schema / Avro для событий Kafka).

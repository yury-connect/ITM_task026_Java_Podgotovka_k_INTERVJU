**1. Что такое Spring?**

**Spring** — это не просто фреймворк, а целостная экосистема для разработки enterprise-приложений на Java 🚀

Он предоставляет готовую инфраструктуру (управление объектами, подключение к БД, безопасность, веб-слой, транзакции), берет на себя рутину и позволяет разработчику фокусироваться строго на бизнес-логике.

**2. Что такое фреймворк и чем он отличается от библиотеки?**

- **Фреймворк** — это готовый архитектурный каркас приложения, который диктует структуру и полностью управляет потоком выполнения программы.
    
- **Главное отличие (Inversion of Control)**:
    
    - Когда вы используете **библиотеку**, ваш код сам вызывает методы библиотеки.
        
    - Когда вы используете **фреймворк**, он сам вызывает ваш код в нужные моменты времени (_"Принцип Голливуда: Не звоните нам, мы сами вам перезвоним"_).
        

**3. Что такое IoC (Inversion of Control)?**

**Inversion of Control (Инверсия управления)** — это архитектурный принцип, при котором управление созданием объектов, их конфигурацией и жизненным циклом передается от кода приложения внешнему контейнеру (**Spring IoC Container**).

Вместо того чтобы вручную делать `new ServiceImpl()`, вы делегируете эту задачу контейнеру.

**4. Что такое DI (Dependency Injection)?**

**Dependency Injection (Внедрение зависимостей)** — это конкретный паттерн проектирования, реализующий принцип IoC 🧩

Суть: объект не создает свои зависимости сам, а получает их извне от IoC-контейнера.

**Способы внедрения в Spring**:

- **Через конструктор** (Best Practice — гарантирует неизменяемость/immutability и упрощает unit-тестирование).
    
- **Через сеттер** (для необязательных зависимостей).
    
- **Через поля (Field Injection)** через `@Autowired` (Не рекомендуется: сложно тестировать, скрывает зависимости, провоцирует циклические ссылки).
    

**5. Стереотипные аннотации Spring**

Стереотипы говорят контейнеру, что класс является Spring-бином, и задают его роль в архитектуре:

- **`@Component`** — базовая аннотация для любого управляемого Spring-компонента.
    
- **`@Service`** — обозначает класс со слоем бизнес-логики.
    
- **`@Repository`** — класс слоя доступа к данным (DAO). Автоматически включает трансляцию исключений БД.
    
- **`@Controller` / `@RestController`** — компоненты веб-слоя для обработки HTTP-запросов (`@RestController` = `@Controller` + `@ResponseBody`).
    
- **`@Configuration`** — класс, содержащий методы с аннотацией `@Bean` для явной конфигурации контекста.
    

**6. Зачем в Repository отлавливать и транслировать исключения?**

Аннотация `@Repository` автоматически подключает пост-процессор `PersistenceExceptionTranslationPostProcessor`.

- **Зачем это нужно**: Разные технологии и вендоры БД бросают свои специфичные проверяемые исключения (например, `SQLException` у JDBC, `HibernateException` у ORM).
    
- **Результат**: Spring перехватывает их и переводит в единую, понятную для всего приложения иерархию **непроверяемых (unchecked)** исключений — **`DataAccessException`** (например, `DataIntegrityViolationException`). Это полностью изолирует бизнес-код от деталей реализации БД.
    

**7. В чем разница между @Repository и @Service?**

- **`@Service`**: Предназначен для **бизнес-логики**, управления доменными транзакциями и координации вызовов нескольких репозиториев.
    
- **`@Repository`**: Предназначен строго для **работы с хранилищем данных** (CRUD, выполнение SQL/HQL/JPQL запросов). Содержит механизмы трансляции низкоуровневых ошибок БД.
    

**8. Можем ли мы заменить @Controller на @Component?**

**Да, технически можем**, потому что `@Controller` является мета-аннотацией поверх `@Component` и Spring IoC подтянет данный класс как бин ⚙️

**Но есть важный нюанс**: Чтобы обработчик HTTP-запросов корректно заработал, вам придется вручную навесить `@RequestMapping` на класс/методы. Без этого или без аннотации `@Controller` сканер `HandlerMapping` в Spring MVC может пропустить этот компонент при построении карты эндпоинтов. Кроме того, теряется читаемость кода.

**9. Путь HTTP-запроса до контроллера в Spring MVC**

```
[ HTTP Request ] 
       │
       ▼
[ DispatcherServlet ] ──(1. Поиск хэндлера)──► [ HandlerMapping ]
       │
       ▼
[ HandlerInterceptor (preHandle) ]
       │
       ▼
[ HandlerAdapter ] ──(2. Вызов метода)──────► [ @RestController ]
       │                                              │
       ├◄─────────────────(3. Возврат результата)─────┘
       ▼
[ HandlerInterceptor (postHandle & afterCompletion) ]
       │
       ▼
[ HTTP Response ]
```

**10. Что такое интерцепторы (HandlerInterceptor)?**

**`HandlerInterceptor`** — это компонент Spring MVC, который позволяет перехватывать HTTP-запросы до и после их обработки контроллером 🛑

Имеет 3 метода:

1. **`preHandle()`**: Выполняется **ДО** вызова метода контроллера. Может вернуть `false` и заблокировать дальнейшую обработку (удобно для авторизации, проверки токенов).
    
2. **`postHandle()`**: Выполняется **ПОСЛЕ** метода контроллера, но до рендеринга View.
    
3. **`afterCompletion()`**: Выполняется после полного завершения запроса и отдачи ответа (удобно для логирования таймингов и очистки `ThreadLocal`).
    

_Отличие от Servlet Filter_: Фильтр работает на уровне Servlet API до Spring, а Интерцептор работает внутри контекста Spring MVC и знает всё про аннотации и хэндлеры.

**11. Когда вызывается конструктор бина?**

Конструктор вызывается на самом первом этапе жизненного цикла бина — во время **инстанцирования (Instantiation)**.

> ⚠️ **Критический момент**: В момент выполнения конструктора внедрение зависимостей через `@Autowired` на поля еще **НЕ произошло**! Все внедряемые поля равны `null`. Для логики инициализации, требующей готовые зависимости, нужно использовать метод с аннотацией **`@PostConstruct`**.

**12. Жизненный цикл бина (Bean Lifecycle)**

```
1. Instantiation (Вызов конструктора)
       │
2. Populate Properties (Внедрение зависимостей)
       │
3. Aware Interfaces (BeanNameAware, ApplicationContextAware)
       │
4. BeanPostProcessor: postProcessBeforeInitialization()
       │
5. Initialization (@PostConstruct -> InitializingBean -> custom init-method)
       │
6. BeanPostProcessor: postProcessAfterInitialization()  <-- (Здесь создаются ПРОКСИ!)
       │
7. Бин готов к использованию (Ready)
       │
8. Destruction (@PreDestroy -> DisposableBean -> custom destroy-method)
```

**13. Транзакции: параметры и ограничения @Transactional**

**Параметры `@Transactional`**:

- `propagation`: Стратегия распространения транзакции.
    
- `isolation`: Уровень изоляции (например, `READ_COMMITTED`, `REPEATABLE_READ`).
    
- `readOnly`: Флаг оптимизации для операций только на чтение.
    
- `timeout`: Максимальное время выполнения транзакции в секундах.
    
- `rollbackFor` / `noRollbackFor`: Указывает, при каких исключениях делать или не делать откат.
    

> 💡 **Важно**: По умолчанию Spring делает rollback **ТОЛЬКО при `RuntimeException` и `Error`**. Если метод выбросит checked exception (`IOException` и т.д.), транзакция **НЕ откатится**, если явно не указать `rollbackFor = Exception.class`.

**Главные ограничения**:

- Работает только для **`public`** методов (при стандартном AOP проксировании).
    
- Не работает при внутреннем вызове метода из того же класса (**Self-invocation**).
    

**14. Виды прокси в Spring и их ограничения**

Spring AOP использует два вида динамических прокси:

- **JDK Dynamic Proxy**:
    
    - Применяется, если целевой класс реализует **хотя бы один интерфейс**.
        
    - Создает прокси-объект, реализующий тот же интерфейс.
        
    - _Ограничение_: Проксирует **только методы, объявленные в интерфейсе**.
        
- **CGLIB Proxy** (по умолчанию в Spring Boot 2+):
    
    - Создает новый класс-наследник (subclass) поверх вашего класса прямо в байткоде.
        
    - _Ограничения_: Не может переопределить и спроксировать `final` классы, а также `final` или `private` методы.
        

**15. Задачка на Dynamic Proxy**

_Условие_: Класс реализует интерфейс с 1 методом, но сам класс содержит еще 2 дополнительных метода. Сколько методов будет проксироваться при использовании **JDK Dynamic Proxy**?

_Ответ_: Проксироваться будет **ровно 1 метод** (тот, что объявлен в интерфейсе) 🎯

Два дополнительных метода класса прокси-объекту просто неизвестны, так как JDK Dynamic Proxy генерирует класс только на базе контракта интерфейса. Если попытаться вызвать эти методы через ссылку на интерфейс — код не скомпилируется, а каст к классу выбросит `ClassCastException`.

**16. Виды Propagation (Распространения транзакций)**

1. **`REQUIRED`** (default): Использует текущую транзакцию. Если её нет — создает новую.
    
2. **`REQUIRES_NEW`**: Всегда создает новую независимую транзакцию. Если есть текущая — приостанавливает её.
    
3. **`NESTED`**: Создает вложенную транзакцию с помощью Savepoints (точка сохранения), если текущая существует.
    
4. **`SUPPORTS`**: Выполняется в транзакции, если она есть. Если нет — выполняется без транзакции.
    
5. **`NOT_SUPPORTED`**: Выполняется всегда без транзакции. Если есть текущая — приостанавливает её.
    
6. **`MANDATORY`**: Требует наличия активной транзакции. Если её нет — выбрасывает `TransactionRequiredException`.
    
7. **`NEVER`**: Требует выполнения без транзакции. Если активная транзакция есть — выбрасывает исключение.
    

**17. Разбор задачи на Self-Invocation и транзакции**

**Сценарий A**: В одном классе вызываем `private` метод с `REQUIRED`, а из него `public` с `REQUIRES_NEW`. Сколько транзакций будет?

- **Ответ**: **0 транзакций** (если внешний вызов идет напрямую на private метод) или **1 транзакция** (если изначально вызвали public метод).
    
- _Почему_:
    
    1. Spring AOP прокси полностью **игнорирует** аннотацию `@Transactional` на `private` методах.
        
    2. Внутренние вызовы методов в рамках одного и того же класса (`this.method()`) идущие в обход прокси-объекта (**Self-invocation**), не перехватываются Spring AOP. Вызов `REQUIRES_NEW` сработает как обычный вызов метода без создания новой транзакции.
        

**Сценарий B**: А если первый метод сделать `public`? Сколько создастся транзакций?

- **Ответ**: Будет создана **ровно 1 транзакция**!
    
- _Почему_: Внешний клиент вызывает Первый `public` метод через Прокси -> Прокси открывает Транзакцию 1.
    
- Затем Первый метод вызывает Второй `public` метод **напрямую через `this.secondMethod()`**. Этот вызов идет **внутри целевого объекта мимо Прокси**. Вторая аннотация `@Transactional(propagation = REQUIRES_NEW)` просто не будет прочитана прокси-слоем!
    

**Сценарий C**: Как реально заставить Spring создать 2 транзакции?

Есть 4 решения этой проблемы 🛠️:

1. **Вынести второй метод в отдельный Spring-бин** и заинжектить его (Самый чистый подход).
    
2. **Self-Injection (Инжекция самого себя)**:    
```Java
@Service
public class OrderService {
	@Autowired 
	@Lazy
	private OrderService self; // Внедряем ПРОКСИ самого себя

	@Transactional
	public void methodA() {
		self.methodB(); // Вызов ИДЕТ через прокси -> создастся новая транзакция!
	}

	@Transactional(propagation = Propagation.REQUIRES_NEW)
	public void methodB() { ... }
}
```
    
3. **Использование `AopContext.currentProxy()`**: `((OrderService) AopContext.currentProxy()).methodB();` (требует флага `exposeProxy=true`).
    
4. **Переход на AspectJ weaving**: Компиляционная или load-time модификация байткода вместо динамических Spring AOP прокси.

**18. Через что работает @Transactional?**

Аннотация `@Transactional` работает через механизм **Spring AOP (Aspect-Oriented Programming)** и цепочку служебных компонентов ⚙️

1. **AOP Proxy**: При старте приложения Spring создает прокси-объект вокруг вашего бина.
    
2. **TransactionInterceptor**: При вызове метода интерцептор перехватывает управление и обращается к **`PlatformTransactionManager`** (например, `DataSourceTransactionManager` или `JpaTransactionManager`).
    
3. **Открытие транзакции**: Менеджер транзакций берет соединение (Connection) из пула (HikariCP), переводит его в режим `setAutoCommit(false)` и связывает это соединение с текущим потоком через **`TransactionSynchronizationManager`** (хранит соединение в `ThreadLocal`).
    
4. **Выполнение метода**: Все DAO/Repository методы внутри текущего потока используют одно и то же привязанное соединение.
    
5. **Завершение**:
    
    - Если метод завершился успешно — вызывается `connection.commit()`.
        
    - Если выброшено `RuntimeException` или `Error` (по умолчанию) — вызывается `connection.rollback()`.
        
    - В конце соединение возвращается в пул HikariCP.
        

**19. gRPC vs REST**

- **gRPC**:
    
    - **Транспорт**: Работает строго поверх **HTTP/2** (поддерживает мультиплексирование и дуплексный стриминг).
        
    - **Формат данных**: Бинарный протокол **Protocol Buffers (Protobuf)**.
        
    - **Контракт**: Строго задается в `.proto` файлах. Код клиентов и серверов под разные языки генерируется автоматически.
        
    - **Скорость**: В 5–10 раз быстрее REST за счет компактности бинарного формата и эффективности HTTP/2. Ideal для межсервисного взаимодействия (In-cluster Service-to-Service).
        
- **REST**:
    
    - **Транспорт**: Обычно HTTP/1.1 (редко HTTP/2).
        
    - **Формат данных**: Текстовый **JSON** или XML.
        
    - **Контракт**: Опционален (OpenAPI/Swagger), слабосвязанный.
        
    - **Применение**: Идеальный стандарт для публичных API, фронтенда и мобильных клиентов за счет простой отладки и читаемости человеком.
        

**20. Преимущества бинарного формата перед JSON**

1. **Компактность (Payload Size)**: В JSON передаются текстовые ключи, кавычки и скобки (`{"user_id": 123}`). В бинарном формате (Protobuf/Avro) передаются только теги полей и их сырые байты, что сокращает размер сетевого пакета на 60–80%.
    
2. **Скорость сериализации/десериализации**: JSON требует тяжелого парсинга строк и символов процессором. Бинарные данные маппятся напрямую в структуры памяти без лишних аллокаций строк.
    
3. **Строгая типизация и обратная совместимость**: Схема данных валидируется на этапе компиляции, а нумерация полей в `.proto` позволяет безопасно добавлять новые поля без поломки старых клиентов.
    

**21. Чем REST отличается от HTTP?**

- **HTTP** — это **сетевой протокол прикладного уровня**, определяющий правила передачи сообщений (методы GET/POST, заголовки, статусы ответов).
    
- **REST (Representational State Transfer)** — это **архитектурный стиль** проектирования распределенных систем.
    
- **Суть**: REST использует HTTP в качестве транспорта, накладывая на него концептуальные ограничения:
    
    - Ориентация на ресурсы (URI — это сущность: `/users/123`).
        
    - Использование стандартных HTTP-глаголов по смыслу (`GET` — чтение, `POST` — создание, `DELETE` — удаление).
        
    - Отсутствие состояния на сервере (Statelessness).
        
    - Единообразие интерфейса (HATEOAS).
        

**22. TCP и HTTP: что поверх чего работает?**

**HTTP работает ПОВЕРХ TCP** 🌐

По модели OSI / TCP/IP:

- **TCP** — протокол **транспортного уровня (L4)**. Отвечает за надежную доставку байт, виртуальное соединение, повтор потерянных пакетов и контроль порядка.
    
- **HTTP** — протокол **прикладного уровня (L7)**. Использует готовое TCP-соединение для отправки структурированных текстовых/бинарных запросов и ответов.
    

**23. Расшифровка HTTP**

**HTTP** — **H**yper**T**ext **T**ransfer **P**rotocol (Протокол передачи гипертекста).

**24. Монолит vs Микросервисы**

- **Монолит**:
    
    - _Что это_: Приложение, собранное и задеплоенное как единый исполняемый модуль (JAR/WAR), использующее общую базу данных.
        
    - _Плюсы_: Простой старт, легкая отладка, единая кодовая база, честные ACID-транзакции в БД, нет сетевых задержек между модулями.
        
    - _Минусы_: Сложно масштабировать отдельные фичи, высокая связность кода, долгая сборка, падение одного модуля валит весь процесс.
        
- **Микросервисы**:
    
    - _Что это_: Набор независимых, слабосвязанных сервисов, разбитых по бизнес-доменам, каждый со своей собственной БД (Database-per-service).
        
    - _Плюсы_: Независимый деплой и масштабирование, изоляция сбоев, возможность использовать разные стеки технологий.
        
    - _Минусы_: Сложность инфраструктуры, задержки сети, проблема распределенных транзакций (Saga, Outbox), сложность сквозной отладки и трейсинга.
        

**25. Стратегия перехода с монолита на микросервисы**

Переход выполняется по паттерну **Strangler Fig Pattern ("Паттерн Душитель")** 🌳

1. **Анализ домена (DDD)**: Выделение bounded contexts (ограниченных контекстов).
    
2. **Проведение границ в коде**: Разделение монолита на четкие модули внутри единой базы.
    
3. **Выделение сервисов с наименьшими связями**: Постепенный "выпил" отдельного сервиса.
    
4. **Разделение данных (Database Decomposition)**: Вынос таблиц выделяемого сервиса в отдельную БД. Синхронизация данных через события (Change Data Capture / Debezium / Kafka).
    
5. **Перенаправление трафика**: Настройка API Gateway так, чтобы запросы к выделенной фиче уходили на новый микросервис, а остальные — на монолит.
    
6. Повторение цикла до полного усыхания монолита.
    

**26. DDD (Domain-Driven Design)**

**DDD** — подход к проектированию ПО, при котором архитектура системы строго строится вокруг доменной модели и бизнес-логики 🎯

- **Стратегический DDD**:
    
    - **Ubiquitous Language (Единый язык)**: Общий словарь терминов, используемый разработчиками и бизнес-экспертами.
        
    - **Bounded Context (Ограниченный контекст)**: Явная граница, в рамках которой термины доменной модели имеют строго определенное значение (например, "Заказ" в контексте Доставки и в контексте Оплаты — это разные сущности).
        
- **Тактический DDD (Компоненты)**:
    
    - **Entity (Сущность)**: Объект с уникальным идентификатором, меняющий состояние (User, Order).
        
    - **Value Object (Объект-значение)**: Измеряет или описывает что-то, не имеет ID, неизменяем (Money, Address).
        
    - **Aggregate (Агрегат)**: Кластер связанный сущностей и VO, управляемый через единственный корень — Aggregate Root.
        
    - **Repository**: Абстракция для сохранения и извлечения Агрегатов.
        
    - **Domain Event**: Событие, произошедшее в домене ("OrderPaidEvent").
        

**27. Что такое Kubernetes (K8s)?**

**Kubernetes** — это open-source платформа для **оркестрации контейнеризированных приложений**.

Он автоматизирует развертывание, масштабирование, самовосстановление (Self-healing), балансировку нагрузки и управление конфигурациями контейнеров в кластере серверов.

**28. Основные сущности Kubernetes**

- **Pod**: Минимальная единица деплоя. Содержит один или несколько тесно связанных контейнеров (например, приложение + sidecar Envoy).
    
- **Deployment**: Декларативное описание желаемого состояния подов (какой образ, сколько копий, как обновлять).
    
- **ReplicaSet**: Нижнеуровневый контроллер, гарантирующий запуск строго заданного количества копий (реплик) подов.
    
- **Service**: Абстракция (L4), предоставляющая стабильный IP-адрес и DNS-имя для группы подов, а также балансирующая трафик между ними.
    
- **Ingress**: Правила маршрутизации внешнего HTTP/HTTPS трафика (L7) к внутренним сервисам кластера.
    
- **ConfigMap / Secret**: Хранилища конфигурационных данных и секретов.
    
- **StatefulSet**: Контроллер для развертывания приложений с сохранением состояния (Stateful: БД, Kafka) с гарантией порядка и уникальными сетевыми именами.
    

**29. Для чего нужны Deployment и ReplicaSet?**

- **ReplicaSet**: Отвечает только за **поддержание количества подов**. Если под упал — ReplicaSet поднимет новый.
    
- **Deployment**: Управляет самими **ReplicaSet**. Он добавляет функционал управления версиями приложения: позволяет без простоя раскатывать новые версии (Rolling Update), откатываться на предыдущие версии (Rollback) и масштабировать ReplicaSet.
    

**30. Стратегии обновлений в Kubernetes**

1. **RollingUpdate (По умолчанию)**: Постепенная замена старых подов новыми. Старые поды гасятся по одному только после того, как новые успешно стартовали. **Downtime = 0**.
    
2. **Recreate**: Все старые поды одновременно принудительно убиваются, после чего создаются новые. Есть простоя (Downtime), но нет конфликта разных версий с БД.
    
3. **Canary / Blue-Green**: Реализуются внешними средствами (Argo Rollouts, Service Mesh Istio, Ingress). Позволяют плавно перенаправлять % пользователей на новую версию.
    

**31. Зачем нужен ConfigMap и его минусы**

**Зачем нужен**: Соблюдение принципа **12-Factor App** (Разделение кода и конфигурации). Один и тот же образ Docker используемся на Dev, Stage и Prod, а настройки передаются через внешние ConfigMap.

**Почему не писать в манифест Deployment**:

- Изменение одной переменной потребует правки всего описания инфраструктуры Deployment.
    
- ConfigMap можно переиспользовать сразу в нескольких Deployment.
    

**Минусы ConfigMap**:

- Хранит данные в **открытом незашифрованном виде**.
    
- Если ConfigMap смонтирован как файл, его обновление внутри пода происходит с **задержкой (до 1 минуты)**.
    
- Изменение ConfigMap **НЕ перезапускает поды автоматически**. Приложению нужен механизм hot-reload или сторонний контроллер (Reloader).
    

**32. В чем отличие Service от Ingress?**

- **Service (Level 4 - Транспортный)**:
    
    - Работает на уровне IP-адресов и портов (TCP/UDP).
        
    - Балансирует внутренний трафик кластера между подами.
        
    - Типы: `ClusterIP` (внутри кластера), `NodePort` (открывает порт на ноде), `LoadBalancer` (запрашивает внешний облачный балансировщик).
        
- **Ingress (Level 7 - Прикладной)**:
    
    - Работает на уровне HTTP/HTTPS протокола.
        
    - Выступает единой точкой входа для внешнего трафика.
        
    - Умеет маршрутизировать трафик по доменам (`api.example.com`) и URL-путям (`/users` -> Service A, `/orders` -> Service B), терминировать TLS-сертификаты.
        

**33. Как зашифровать K8s Secret?**

По умолчанию K8s Secret просто кодируется в **Base64**, что **НЕ является шифрованием**! 🔓

Способы защиты:

1. **Encryption at Rest в etcd**: Включение KMS-провайдера (Key Management Service) в API-сервере Kubernetes для шифрования данных перед записью в etcd.
    
2. **Sealed Secrets (Bitnami)**: Асимметричное шифрование. В Git хранится зашифрованный публичным ключом Secret, а расшифровать его может только контроллер внутри кластера своим приватным ключом.
    
3. **External Secrets Operator + HashiCorp Vault / AWS Secrets Manager**: Секреты хранятся во внешнем защищенном хранилище и динамически монтируются в кластер.
    

**34. Istio и Istio Ingress Controller**

- **Istio (Service Mesh)**: Архитектурная прослойка управления коммуникацией между сервисами.
    
    - Подсаживает к каждому поду **sidecar-прокси (Envoy)**.
        
    - _Возможности_: Автоматический mTLS (шифрование трафика между сервисами), Circuit Breaking, Retries, Canary-деплой, глубокий сплит трафика, сбор метрик и распределенный трейсинг.
        
- **Istio Ingress Gateway**: Входной контроллер трафика на базе Envoy, заменитель стандартного Ingress Controller. Он принимает внешний трафик и включает его в общую сеть безопасности и наблюдаемости Istio Service Mesh.
    

**35. Пробы (Probes) в Kubernetes**

Пробы — это проверки состояния контейнера контроллером Kubelet 🩺

**Виды проб**:

1. **Startup Probe**: Проверяет, запустилось ли приложение. На время ее работы остальные пробы отключаются. Нужна для медленно стартующих приложений.
    
2. **Liveness Probe**: Проверяет, **живо ли приложение**. Если проба не прошла -> K8s **убивает и перезапускает** контейнер (Restart Policy).
    
3. **Readiness Probe**: Проверяет, **готово ли приложение принимать сетевой трафик**. Если проба не прошла -> K8s **удаляет под из списка Endpoints сервиса**, и на него перестают идти HTTP-запросы.
    

**Как осуществляются (Механизмы)**:

- `httpGet`: Запрос на указанный порт и path (ожидает код 200-399).
    
- `tcpSocket`: Проверка открытия TCP-порта.
    
- `exec`: Выполнение команды внутри контейнера (код возврата `0` = OK).
    
- `grpc`: Вызов встроенного gRPC Health Checking протокола.

**93. Функциональный интерфейс и его роль в Java**

**Функциональный интерфейс (Functional Interface)** — это интерфейс, который содержит **ровно один абстрактный метод** (Single Abstract Method — SAM) 🎯

- **Аннотация `@FunctionalInterface`**: Не обязательна, но крайне рекомендуется. Она заставляет компилятор проверить, действительно ли интерфейс имеет ровно один абстрактный метод (методы `default`, `static` или методы класса `Object` не идут в этот зачет).
    
- **Зачем нужен**: Служит базовым типом для **лямбда-выражений** и **ссылок на методы (Method References)**. Это позволяет передавать поведение (функции) в качестве аргументов методов, делая Java языком с поддержкой элементов функционального программирования.
    

**94. Отличия lambda-выражения от анонимного класса**

1. **Контекст ссылки `this`**:
    
    - В **анонимном классе** `this` указывает на экземпляр самого анонимного класса.
        
    - В **лямбде** `this` указывает на экземпляр внешнего обрамляющего класса (Enclosing class).
        
2. **Компиляция и байткод**:
    
    - **Анонимный класс** создает отдельный `.class` файл на диске во время компиляции (например, `OuterClass1.class`).
        
    - **Лямбда** не создает новый класс на этапе компиляции. Она генерирует инструкцию `invokedynamic` (INDY), которая при первом вызове в runtime динамически создает фабрику и класс через `LambdaMetafactory`.
        
3. **Выделение памяти и состояние**:
    
    - Создание **анонимного класса** — это всегда выделение нового объекта в Heap (`new`).
        
    - Бессостояниевые (Stateless) **лямбды** могут переиспользоваться JVM без повторного выделения памяти в куче.
        
4. **Ограничения интерфейсов**:
    
    - **Анонимный класс** может наследоваться от абстрактных/обычных классов и реализовывать интерфейсы с любым количеством методов.
        
    - **Лямбда** работает только с функциональными интерфейсами.
        

**95. Method References: типы, плюсы и минусы**

**Method Reference (Ссылка на метод)** — это компактный синтаксис для записи лямбды, которая просто вызывает существующий метод 🔗

**4 вида ссылок на методы**:

- Статический метод: `Math::max` вместо `(a, b) -> Math.max(a, b)`
    
- Метод конкретного объекта: `obj::getValue` вместо `() -> obj.getValue()`
    
- Метод произвольного объекта известного типа: `String::toLowerCase` вместо `(s) -> s.toLowerCase()`
    
- Конструктор: `ArrayList::new` вместо `() -> new ArrayList()`
    
- 🟢 **Когда улучшает код**:
    
    - Когда лямбда является простейшим "транзитом" и не содержит никакой дополнительной логики или преобразований аргументов (например, `.map(User::getName)`).
        
- 🔴 **Когда ухудшает читаемость**:
    
    - При перегрузке методов, когда непонятно, какая именно перегрузка вызывается.
        
    - Если для понимания контекста приходится постоянно смотреть на сигнатуру целевого метода.
        

**96. Требование effectively final для захватываемых переменных**

Локальная переменная считается **effectively final**, если после инициализации ее значение больше нигде в коде не меняется (даже если ключевое слово `final` не написано) 🔒

**Причины этого ограничения**:

1. **Разница жизненных циклов Стека и Кучи**:
    
    - Локальная переменная живет на **Стеке** и уничтожается сразу при выходе из метода.
        
    - Лямбда-выражение может быть передано в другой поток или выполнено позже, выжив после завершения метода.
        
2. **Захват по значению (Capture by Value)**:
    
    - Чтобы использовать переменную, лямбда создает себе её **копию**.
        
    - Если бы Java разрешала менять значение переменной во внешнем коде, возникло бы рассинхронизация между копией в лямбде и оригиналом на стеке. Создалась бы ложная иллюзия передачи по ссылке (Pass-by-reference).
        

**97. Замыкания (Closures) в контексте Java**

**Замыкание** — это функция, которая запоминает окружение (переменные) из своего лексического контекста создания 📦

- **Как работает в Java**:
    
    - Java поддерживает замыкания **по значению (Closure over values)**, а не по переменным.
        
    - Лямбда "замыкает" в себе значения локальных примитивов и ссылки на объекты.
        
    - Если лямбда захватывает поле класса-владельца, она на самом деле захватывает ссылку `this`. Так как объект `this` находится в Heap, изменение его полей внутри лямбды разрешено.
        

**98. Stream в Java vs Коллекция**

- **Хранение данных**:
    
    - **Коллекция** — это структура данных в памяти, которая физически хранит элементы.
        
    - **Stream** — это поток данных. Он не хранит элементы, а забирает их из источника (коллекция, массив, I/O канал).
        
- **Модификация**:
    
    - **Коллекция** позволяет добавлять и удалять элементы.
        
    - **Stream** не изменяет свой источник данных.
        
- **Вычисление (Evaluation)**:
    
    - **Коллекция** вычисляется жадно (Eager): все элементы должны находиться в памяти перед использованием.
        
    - **Stream** вычисляется лениво (Lazy): элементы обрабатываются по запросу.
        
- **Переиспользование**:
    
    - **Коллекцию** можно обходить сколь угодно раз.
        
    - **Stream** можно исполнить и прочитать **строго один раз**.
        

**99. Stream Pipeline и ленивость промежуточных операций**

**Stream Pipeline** состоит из 3 частей:

1. **Источник (Source)**: Коллекция, массив, генератор.
    
2. **Промежуточные операции (Intermediate operations)**: `filter`, `map`, `flatMap` (может быть 0 или больше).
    
3. **Терминальная операция (Terminal operation)**: `collect`, `forEach`, `reduce` (ровно одна).
    

- **Почему промежуточные операции ленивые**:
    
    - Вызов `stream.map(...).filter(...)` не выполняет никакой реальной обработки данных. Он лишь конструирует цепочку связанных объектов стадий (Sink-цепочку).
        
    - Обработка данных начинается **только в момент вызова терминальной операции**.
        
- **Зачем нужна ленивость**:
    
    - **Loop Fusion (Слияние циклов)**: Позволяет пройтись по данным за один единый проход, выполнив все трансформации для каждого элемента разом.
        
    - **Short-circuiting**: Позволяет досрочно прекратить обработку (например, при вызове `findFirst()`).
        

**100. Intermediate и Terminal операции**

- 🔄 **Intermediate (Промежуточные)** — всегда возвращают новый `Stream<T>`:
    
    - `filter()`, `map()`, `flatMap()`, `distinct()`, `sorted()`, `peek()`, `limit()`, `skip()`.
        
- 🏁 **Terminal (Терминальные)** — запускают обработку и возвращают конкретный результат или `void`:
    
    - `collect()`, `forEach()`, `reduce()`, `count()`, `findFirst()`, `findAny()`, `anyMatch()`, `allMatch()`, `noneMatch()`, `min()`, `max()`, `toArray()`.
        

**101. Stateless и Stateful intermediate operations**

- **Stateless (Без состояния)**:
    
    - Элемент обрабатывается независимо от других элементов.
        
    - Не требует сохранения информации о ранее прошедших элементах.
        
    - _Примеры_: `filter()`, `map()`, `flatMap()`, `peek()`.
        
- **Stateful (С состоянием)**:
    
    - Требуют накопления или знания обо всех/предыдущих элементах потока для выполнения операции.
        
    - _Примеры_: `sorted()` (нужны все элементы для сортировки), `distinct()` (хранит кэш увиденных элементов), `limit()`, `skip()`.
        

**102. Влияние sorted() и distinct() на стоимость Pipeline**

`sorted()` и `distinct()` ломают идеологию однопроходной стриминговой обработки элементов:

- **`sorted()`**: Является **барьером пайплайна**. Чтобы отсортировать поток, JVM вынуждена приостановить стриминг, вычитать **абсолютно все** элементы из источника в промежуточный буфер, отсортировать его за O(N log N) и только потом проталкивать элементы дальше. Приводит к всплеску расхода памяти и задержкам.
    
- **`distinct()`**: Вынужден создавать и поддерживать внутренний `HashSet` для отслеживания уже встреченных элементов. Это влечет overhead по памяти O(N) и нагрузку на Garbage Collector.
    

**103. map() vs flatMap()**

- **`map(Function<T, R>)`**:
    
    - Преобразование **"Один в Один" (1 -> 1)**.
        
    - Применяет функцию к каждому элементу типа `T` и возвращает элемент типа `R`.
        
    - _Результат_: `Stream<R>`.
        
- **`flatMap(Function<T, Stream<R>>)`**:
    
    - Преобразование **"Один ко Многим" (1 -> N)**.
        
    - Применяет функцию, которая превращает каждый элемент `T` в отдельный `Stream<R>`, а затем **сплющивает (объединяет)** все полученные подпотоки в один единый `Stream<R>`.
        

**104. Однопроходная обработка (Sink chain) и причина одноразовости Stream**

- **Как работает под капотом**:
    
    - При вызове терминальной операции конструируется цепочка объектов `Sink` (по одному на каждую промежуточную операцию).
        
    - Данные берутся из источника через `Spliterator` и начинают протекать сквозь цепочку `Sink` поштучно: элемент 1 проходит через `filter` -> `map` -> `collect`, затем элемент 2 делает то же самое.
        
- **Почему Stream одноразовый**:
    
    - Внутри объекта `Stream` при вызове терминальной операции выставляется служебный флаг `linkedOrConsumed = true`.
        
    - При повторной попытке вызвать любую операцию на этом же экземпляре стрима, JVM проверяет этот флаг и бросает `IllegalStateException`. Поток — это курсор, данные из которого уже утекли.
        

**105. reduce() vs collect()**

- **`reduce()` (Иммутабельная редукция)**:
    
    - Сворачивает элементы в **одиночное неизменяемое значение** путем применения ассоциативной функции: `(a, b) -> a + b`.
        
    - На каждом шаге создает **новый объект**. Собирать элементы в `List` через `reduce` крайне неэффективно, так как придется создавать новый список на каждом шаге.
        
- **`collect()` (Мутабельная редукция)**:
    
    - Накапливает элементы в **мутабельный контейнер-результат** (например, `ArrayList` или `StringBuilder`).
        
    - Изменяет существующий контейнер на месте (`list.add(elem)`), что работает в разы быстрее и не замусоривает Heap.
        

**106. Состав Collector: supplier, accumulator, combiner, finisher**

Интерфейс `Collector<T, A, R>` определяет 4 ключевых компонента для мутабельной редукции 🧩

1. **`supplier()`**: Фабрика, создающая новый пустой контейнер аккумулятора (`() -> new ArrayList<T>()`).
    
2. **`accumulator()`**: Функция, добавляющая входной элемент в контейнер аккумулятора (`(list, item) -> list.add(item)`).
    
3. **`combiner()`**: Функция, объединяющая два контейнера аккумулятора в один (используется при параллельной обработке: `(list1, list2) -> { list1.addAll(list2); return list1; }`).
    
4. **`finisher()`**: Финальное преобразование промежуточного контейнера `A` в итоговый результат `R` (например, приведение `StringBuilder.toString()`).
    

**107. Характеристики Collector'а**

- **`CONCURRENT`**: Указывает, что аккумулятор может вызываться параллельно из нескольких потоков над **одним и тем же** объектом контейнера без необходимости вызова `combiner`. Требует потокобезопасного контейнера (например, `ConcurrentHashMap`).
    
- **`UNORDERED`**: Результат редукции не зависит от порядка элементов в источнике (дает свободу оптимизациям при параллельной сборке).
    
- **`IDENTITY_FINISH`**: Указывает, что функция `finisher` является тождественной (Identity) и промежуточный контейнер `A` можно просто привести к типу `R` без дополнительных вычислений.
    

**108. groupingBy(), partitioningBy() и Downstream collectors**

- **`groupingBy(classifier)`**: Группирует элементы в `Map<K, List<T>>` на основе функции-классификатора.
    
- **`partitioningBy(predicate)`**: Частный случай группировки, разбивающий элементы на две группы по булеву условию. Возвращает `Map<Boolean, List<T>>`.
    
- **Downstream Collectors (Вложенные коллекторы)**: Вторая передаваемая функция в `groupingBy`, определяющая, как обрабатывать элементы _внутри_ каждой сформированной группы (например, посчитать количество `groupingBy(User::getRole, counting())` или собрать в сет `toSet()`).
    

**109. Опасность побочных эффектов (Side-effects) в Stream API**

**Side-effect** — это изменение внешнего состояния программы изнутри лямбд стрима (например, добавление элементов во внешний список через `.peek(list::add)`).

**Почему это опасно**:

1. **Race Conditions в `parallelStream()`**: При вызове в параллельном потоке несинхронизированная внешняя структура данных будет повреждена.
    
2. **Нарушение порядка и ленивости**: Из-за ленивости или short-circuiting оптимизаций побочный эффект может выполниться не полностью, не в том порядке или не выполниться вовсе.
    

> 💡 **Золотое правило**: Лямбды в Stream API должны быть **чистыми функциями (Pure Functions)**, не меняющими внешнее состояние.

**110. Short-circuit, parallelStream() и роль Spliterator**

- **Short-circuit (Короткое замыкание)**:
    
    - Операции, которые прекращают обработку, не вычитывая поток до конца (`findFirst()`, `findAny()`, `anyMatch()`, `limit()`).
        
    - Реализованы через вызов `Sink.cancellationRequested()`, останавливающий проталкивание новых элементов по цепочке.
        
- **`parallelStream()` — когда помогает, а когда вредит**:
    
    - 🟢 _Помогает_: Вычислительно сложные CPU-bound задачи на больших объемах данных ($N \ge 10000$), со структурой данных, легко делящейся на части (`ArrayList`, массивы).
        
    - 🔴 _Вредит_: Простые I/O задачи, маленькие объемы данных, плохо делимые источники (`LinkedList`), наличие stateful операций (`sorted`), использование общего `ForkJoinPool.commonPool()`, где одна долгая задача может заблокировать приложения.
        
- **Роль `Spliterator` (Splittable Iterator)**:
    
    - Ключевой механизм для параллельных стримов.
        
    - Метод `tryAdvance()` обрабатывает один элемент по аналогии с `Iterator`.
        
    - Метод `trySplit()` делит текущий источник **пополам**, создавая новый `Spliterator` для передачи другому потоку из `ForkJoinPool`.

**51. Иерархия Throwable в Java**

Все исключения и ошибки в Java образуют единую иерархию классов, где верховным предком является `java.lang.Throwable` 🌳
```Text
                   +-------------------+
                   |     Throwable     |
                   +-------------------+
                     /               \
                    /                 \
       +---------------+           +-------------------+
       |     Error     |           |     Exception     |
       +---------------+           +-------------------+
                                     /               \
                                    /                 \
                     +-------------------+      +------------------+
                     | RuntimeException  |      | Checked Exceptions|
                     |   (Unchecked)     |      | (IOException etc)|
                     +-------------------+      +------------------+
```

**52. Ошибки и исключения: Error, Exception и RuntimeException**

- 🛑 **`Error` (Фатальные ошибки)**:
    
    - Сигнализируют о критических проблемах на уровне виртуальной машины (JVM) или системы.
        
    - Приложение не должно пытаться их перехватывать или обрабатывать.
        
    - _Примеры_: `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError`.
        
- ⚠️ **`Exception` (Checked / Контролируемые исключения)**:
    
    - Предсказуемые внешние сбои, которые могут возникнуть во время корректной работы программы.
        
    - Приложение **обязано** либо обработать такое исключение в блоке `catch`, либо декларировать его в сигнатуре метода через `throws`.
        
    - _Примеры_: `SQLException`, `IOException`, `FileNotFoundException`.
        
- 💥 **`RuntimeException` (Unchecked / Неконтролируемые исключения)**:
    
    - Ошибки в логике самого кода (баги программиста) или состояния приложения.
        
    - Не требуют обязательной обработки или объявления в сигнатуре метода.
        
    - _Примеры_: `NullPointerException`, `IndexOutOfBoundsException`, `IllegalArgumentException`.
        

**53. Checked vs Unchecked исключения на практике**

- **Практическая разница**:
    
    - **Checked**: Проверяются компилятором на этапе сборки. Если метод может выбросить checked-исключение, вызывающий код не скомпилируется без его явной обработки.
        
    - **Unchecked**: Не проверяются компилятором. Пролетают вверх по стеку вызовов до ближайшего обработчика или гасят поток.
        
- **Когда Checked исключения полезны**:
    
    - Когда вы проектируете публичный API библиотеки и хотите **принудительно обязать** пользователя обработать критический восстановимый сценарий (например, временное отсутствие сети).
        
- **Почему в современном Java-коде Checked исключения мешают**:
    
    1. **Нарушение инкапсуляции**: Изменение внутренней реализации метода (например, переход с JPA на сетевой клиент) заставляет протаскивать новое checked исключение через сигнатуры всех вышележащих методов.
        
    2. **Несовместимость с Lambdas & Streams API**: Функциональные интерфейсы из `java.util.function` (`Function`, `Consumer`, `Supplier`) не декларируют checked исключений. Их вызов внутри стримов требует громоздкого обертывания в `try-catch`.
        
    3. **Замусоривание кода**: Часто приводят к пустым блокам `catch` от ленивых разработчиков.
        

> 📌 **Современный стандарт**: Фреймворки (Spring, Hibernate) полностью отказались от checked exceptions в пользу unchecked.

**54. Правила переопределения методов с Checked Exceptions**

При переопределении (`@Override`) метода в классе-потомке действуют строгие правила безопасности типов 📐

- **Нельзя**: Объявлять **новые** checked исключения или ставить исключения **шире** (выше по иерархии), чем объявлены у родительского метода.
    
- **Можно**:
    
    1. Вообще не объявлять исключений в сигнатуре потомка.
        
    2. Объявлять **подтипы** (сужать) исключений, указанных у родителя (ковариантность исключений).
        
    3. Объявлять любые `RuntimeException` (Unchecked), независимо от сигнатуры родителя.
        

**55. Разница между throw и throws**

- 🎯 **`throw`**:
    
    - Инструкция (оператор) внутри тела метода.
        
    - Используется для непосредственного выбрасывания конкретного объекта исключения.
        
    - Пример: `throw new IllegalArgumentException("Invalid ID");`
        
- 📜 **`throws`**:
    
    - Ключевое слово в сигнатуре (заголовке) метода.
        
    - Предупреждает компилятор и вызывающий код о том, что данный метод **может выбросить** указанные checked исключения.
        
    - Пример: `public void readFile() throws IOException`
        

**56. Порядок выполнения try, catch и finally (включая return)**

1. Выполняется блок `try`.
    
2. Если в `try` произошло исключение, его выполнение прерывается, и управление передается в соответствующий блок `catch`.
    
3. **Блок `finally` выполняется ВСЕГДА** после завершения `try` или `catch`, независимо от того, произошло исключение или нет.
    

- **Поведение с оператором `return`**:
    
    - Если `return` находится внутри `try` или `catch`, выражение в `return` вычисляется, результат сохраняется во временную переменную, **затем исполняется блок `finally`**, и только после этого происходит фактический возврат из метода.
        
    - ⚠️ **Критический нюанс**: Если в самом блоке `finally` написать еще один `return`, он затрет (перекроет) результат или выброшенное исключение из блоков `try`/`catch` и вернет значение из `finally`.
        

**57. Подводные камни блока finally**

1. **Затирание исключений (Swallowing / Masking exceptions)**:
    
    - Если в `try` выбросилось `NullPointerException`, а внутри `finally` сработает `return` или выбросится новое исключение (например, `IOException` при закрытии файла), исходный NPE полностью исчезнет из стек-трейса.
        
2. **Когда `finally` НЕ выполнится вообще**:
    
    - Вызов `System.exit(status)`.
        
    - Падение самой JVM (Fatal Crash, Segfault, `OutOfMemoryError`).
        
    - Принудительное завершение процесса ОС (`kill -9`).
        
    - Бесконечное зависание или блокировка потока внутри блока `try` или `catch`.
        

**58. Try-with-resources, Suppressed Exceptions и AutoCloseable vs Closeable**

Конструкция `try-with-resources` (Java 7+) автоматически закрывает ресурсы, реализовавшие интерфейс `AutoCloseable` 🛠️
```Java
try (InputStream is = new FileInputStream("file.txt");
     OutputStream os = new FileOutputStream("out.txt")) {
    is.transferTo(os);
}
```

- **Очередность закрытия**: Ресурсы закрываются в порядке, **обратном их объявлению** (сначала `os`, затем `is`).
    
- **Suppressed Exceptions (Подавленные исключения)**:
    
    - Если исключение произошло и в блоке `try`, и в момент вызова скрытого метода `.close()`, приоритет отдается исключению из `try`.
        
    - Исключения, произошедшие при закрытии ресурсов, не теряются: они добавляются в список **подавленных** к основному исключению (доступны через `e.getSuppressed()`).
        
- **`AutoCloseable` vs `Closeable`**:
    
    - **`AutoCloseable`** (Java 7): Базовый интерфейс. Метод `close()` декларирует `throws Exception`.
        
    - **`Closeable`** (Java 5): Наследует `AutoCloseable`. Метод `close()` декларирует более специфичный `throws IOException` и строго требует **идемпотентности** (повторный вызов метода `.close()` не должен иметь побочных эффектов).
        

**59. Стратегии обработки: Заворачивание vs Пробрасывание**

- 🎁 **Заворачивание (Exception Wrapping)**:
    
    - _Когда использовать_: При переходе между слоями архитектуры.
        
    - _Пример_: Нижний слой доступа к данным выбрасывает low-level `SQLException`. Сервисный слой должен поймать его и обернуть в высокоуровневое доменное исключение `RepositoryException`, **обязательно сохранив исходную причину**: `throw new DataAccessException("Failed to fetch user", sqlException);`
        
- ↗️ **Пробрасывание как есть (Rethrowing)**:
    
    - _Когда использовать_: Если текущий слой не может обработать ошибку и не добавляет никакой ценной контекстной информации.
        

**60. Проектирование кастомной иерархии исключений**

Хорошая архитектура исключений четко разделяет сбои приложения на две категории 🏛️

1. **Доменные исключения (Domain Exceptions)**:
    
    - Отражают нарушение бизнес-правил приложения.
        
    - Всегда наследуются от единого базового `DomainException` (наследующего `RuntimeException`).
        
    - _Примеры_: `UserNotFoundException`, `InsufficientBalanceException`, `OrderAlreadyPaidException`.
        
2. **Инфраструктурные исключения (Infrastructure Exceptions)**:
    
    - Отражают сбои внешних систем, БД, сети, сторонних REST API.
        
    - Наследуются от `InfrastructureException`.
        
    - _Примеры_: `DatabaseConnectionTimeoutException`, `PaymentGatewayUnavailableException`.
        

> 💡 **Правило**: Не создавайте отдельные классы исключений под каждый чих. Если обработка одинакова — достаточно одного класса с понятным сообщением или кодом ошибки (Error Code).

**61. Антипаттерн "Log and Rethrow"**
```Java
// ❌ ПЛОХО
catch (NoSuchUserException e) {
    log.error("User not found", e);
    throw e;
}
```

- **Почему это плохая практика**:
    
    - Приводит к **дублированию логов**. Вызывающий метод наверняка тоже поймает это исключение, опять залогирует его и пробросит выше.
        
    - В итоге один и тот же сбой будет замусоривать логи огромными одинаковыми стек-трейсами на каждом уровне вызова.
        
- **Золотое правило**: **Или залогируй и обработай, или пробрось дальше.** Никогда не делай и то, и другое одновременно.
    

**62. Область применения Optional**

`Optional<T>` создан исключительно как явный сигнальный тип для **возвращаемых значений методов**, где значение может отсутствовать 🔍

- 🟢 **ГДЕ ИСПОЛЬЗОВАТЬ**:
    
    - Только в качестве возвращаемого типа методов: `public Optional<User> findById(Long id)`.
        
- 🔴 **ГДЕ НЕ ИСПОЛЬЗОВАТЬ**:
    
    - **В полях классов/сущностей**: `Optional` не реализует `Serializable`, увеличивает расход памяти и осложняет работу ORM (Hibernate).
        
    - **В параметрах методов**: Создает неудобство для вызывающей стороны (`method(Optional.of("val"))`). Используйте обычную перегрузку методов или аннотации `@Nullable`.
        
    - **В коллекциях**: Не пишите `List<Optional<User>>`. Коллекции сами по себе отлично выражают отсутствие элементов через пустой список (`Collections.emptyList()`).
        
    - **В DTO и классах запросов**: Затрудняет JSON-сериализацию/десериализацию (Jackson).
        

**63. Разбор методов Optional: map, flatMap, orElse, orElseGet, orElseThrow**

- **`map(Function)`**: Если значение есть, применяет функцию и оборачивает результат в новый `Optional`.
    
- **`flatMap(Function)`**: Применяет функцию, которая **сама возвращает `Optional`**, предотвращая создание вложенного `Optional<Optional<T>>`.
    
- **Критическое отличие `orElse` vs `orElseGet`**:
    
    - **`orElse(T other)`**: Значение `other` **вычисляется всегда**, даже если `Optional` содержит внутри валидный объект!        
```Java
// ❌ Плохо: DB-запрос выполнится ДАЖЕ ЕСЛИ userOptional НЕ пустой!
User user = userOptional.orElse(fetchUserFromDatabase());
```
        
- **`orElseGet(Supplier other)`**: Вычисление происходит **лениво** — лямбда вызовется ТОЛЬКО если `Optional` пуст.        
```Java
// ✅ Отлично: DB-запрос выполнится только при отсутствии значения
User user = userOptional.orElseGet(() -> fetchUserFromDatabase());
```
        
- **`orElseThrow()`**: Возвращает значение, а если его нет — выбрасывает `NoSuchElementException` (или кастомное исключение через `orElseThrow(Supplier)`).
    

**64. Records и Sealed Classes в Java**

**Records (Записи)** — специальный вид классов для неизменяемых (immutable) данных (Data Carriers) 📦

- **Что генерируется автоматически**: Все поля `private final`, конструктор со всеми аргументами, геттеры без приставки `get` (`user.name()`), методы `equals()`, `hashCode()` и `toString()`.
    
- **Ограничения Records**:
    
    - Не могут наследоваться от других классов (уже неявно наследуют `java.lang.Record`).
        
    - Все поля строго `final`.
        
    - Не могут хранить дополнительные нестатические поля экземпляра.
        

**Sealed Classes (Запечатанные классы)** — позволяют ограничить круг классов, которые могут от них наследоваться 🔐
```Java
public sealed class Shape permits Circle, Square, Rectangle {}
```

- **Ограничения Sealed Classes**:
    
    - Классы-наследники должны находиться в том же модуле/пакете и обязаны явно объявить свой статус: `final`, `sealed` или `non-sealed`.
        
- **Зачем нужны в сумме**:
    
    - Создают паттерн **Algebraic Data Types (ADT)**.
        
    - В сочетании с **Pattern Matching в `switch`** позволяют компилятору проверять полноту условий (Exhaustive check):
        
        
        
```Java
double area = switch (shape) {
	case Circle c -> Math.PI * c.radius() * c.radius();
	case Square s -> s.side() * s.side();
	case Rectangle r -> r.a() * r.b();
	// Ветка default НЕ нужна! Компилятор знает все возможные подтипы Shape.
```

**1. В чем разница между JDK, JRE и JVM?**

- **JVM (Java Virtual Machine)** — виртуальная машина, которая непосредственно выполняет байткод на конкретной операционной системе (Windows, Linux, macOS). Обеспечивает кроссплатформенность ("Write once, run anywhere").
    
- **JRE (Java Runtime Environment)** — среда выполнения. Состоит из JVM + стандартного набора библиотек (например, `java.base`). Нужна исключительно для **запуска** готовых Java-приложений.
    
- **JDK (Java Development Kit)** — комплект разработчика. Содержит JRE + инструменты для **разработки и сборки** (`javac`, `jar`, отладчики, профилировщики).    

Аналогия: JVM — это двигатель, JRE — готовый автомобиль, а JDK — полный автозавод с цехами и чертежами. 🚗

**2. Состав JDK и их использование при разработке, сборке и запуске**

- **При разработке**: используются стандартные библиотеки JDK (API), компилятор `javac` (IDE использует его на лету для проверки ошибок) и утилиты докуметирования (`javadoc`).
    
- **При сборке**: работает компилятор `javac` (переводит `.java` в `.class`), утилита `jar` (упаковывает файлы в `.jar` / `.war` архивы), а также `jlink` (для сборки кастомного минимального runtime).
    
- **При запуске**: используется утилита `java` (стартует процесс JVM), сама **JVM** (JIT-компилятор и Garbage Collector) и базовые модули runtime (`java.base`).    

**3. Путь Java-кода от .java файла до выполнения на процессоре**

1. **Исходный код (`.java`)**: пишется разработчиком.
    
2. **Компиляция (`javac`)**: компилятор проверяет синтаксис и превращает `.java` в машинно-независимый байткод (`.class`).
    
3. **Загрузка и связывание (Class Loading & Linking)**: JVM загружает `.class` файл в память Metaspace, валидирует его и подготавливает статические ресурсы.
    
4. **Интерпретация**: JVM начинает исполнять байткод поинструкционно с помощью интерпретатора.
    
5. **JIT-компиляция (Just-In-Time)**: JVM отслеживает "горячие" (часто вызываемые) участки кода. JIT-компилятор (C1/C2) на лету скомпилирует их в чистый машинный код конкретного процессора и применит оптимизации.
    
6. **Выполнение процессором**: CPU исполняет сгенерированные нативные команды. ⚡
    

**4. Байткод и структура .class файла**

- **Байткод** — это высокоуровневый, машинно-независимый набор инструкций (опкодов), предназначенный для выполнения виртуальной машиной JVM.
    
- **Структура `.class` файла**:
    
    - **Magic Number**: первые 4 байта `0xCAFEBABE` для валидации формата файла.
        
    - **Версия формата**: Major/Minor версии компилятора.
        
    - **Constant Pool (Пул констант)**: таблица имен классов, методов, полей, типов и строковых констант.
        
    - **Access Flags**: модификаторы доступа (`public`, `final`, `abstract` и т.д.).
        
    - **Class Info**: данные о текущем классе, его суперклассе и реализуемых интерфейсах.
        
    - **Fields & Methods**: описания полей и методов (их сигнатуры, аннотации).
        
    - **Attributes (Code)**: сам байткод методов, таблицы обработки исключений и отладочная информация (номера строк в исходнике).
        

**5. Механизм Class Loading (Загрузка классов)**

Загрузка классов работает по **модели делегирования (Delegation Model)**:

1. Когда требуется класс, текущий ClassLoader перенаправляет запрос наверх своему **родительскому (parent)** загрузчику.
    
2. Запрос поднимается по цепочке вверх до самого верхнего — Bootstrap ClassLoader.
    
3. Bootstrap загрузчик пытается найти класс у себя. Если находит — загружает.
    
4. Если родитель не нашел класс, управление возвращается вниз дочернему загрузчику.
    
5. Дочерний ClassLoader пытается найти файл `.class` в своей зоне ответственности (`classpath`).
    
6. Если класс не найден ни одним загрузчиком, выбрасывается `ClassNotFoundException` или `NoClassDefFoundError`.
    

Этот механизм предотвращает подмену системных классов (например, нельзя подменить `java.lang.String`).

**6. Стандартные Class Loader'ы в JVM**

1. **Bootstrap ClassLoader**: базовый загрузчик, написанный на C/C++. Загружает ключевые классы JVM (`java.lang.*`, `java.util.*` из модуля `java.base`).
    
2. **Platform ClassLoader** (ранее Extension ClassLoader): загружает платформенные модули и расширения.
    
3. **Application (System) ClassLoader**: загружает классы приложения и библиотеки из `classpath` (из ваших JAR-файлов).
    
4. **Custom ClassLoaders**: пользовательские загрузчики, создаваемые разработчиками или фреймворками (Spring, Tomcat) для Hot Swap, загрузки классов по сети или изоляции библиотек.
    

**7. Разница между Loading, Linking и Initialization**

- **Loading (Загрузка)**: поиск `.class` файла, чтение массива байт и создание объекта `java.lang.Class` в памяти Metaspace.
    
- **Linking (Связывание)** состоит из трех шагов:
    
    - _Verification_: проверка байткода на соответствие спецификации и правилам безопасности.
        
    - _Preparation_: выделение памяти под **статические поля** и их заполнение дефолтными значениями (0, `null`, `false`).
        
    - _Resolution_: замена символьных ссылок из пула констант на прямые указатели в памяти.
        
- **Initialization (Инициализация)**: исполнение метода `<clinit>` — присвоение статическим полям их реальных значений из кода и выполнение `static`-блоков.
    

**8. Моменты фактической инициализации класса**

Инициализация класса происходит **лениво** — только при **первом активном использовании** (First Active Use):

- Создание экземпляра класса (через `new`, `Class.newInstance()` или рефлексию).
    
- Вызов статического метода класса.
    
- Чтение или изменение неконстантного статического поля.
    
- Запуск метода `main()` данного класса.
    
- Инициализация его дочернего класса.
    

_Важная деталь:_ обращение к `static final` константам базовых типов или строк (Compile-time constants) **не** приводит к инициализации класса, так как компилятор подставляет их значение непосредственно в место вызова.

**9. Порядок выполнения static-полей, static-блоков и инициализации родительских классов**

Порядок строгий и выполняется сверху вниз по иерархии:

1. **Инициализация родительского класса (Parent)**:
    
    - Статические поля и `static`-блоки родителя в порядке их объявления в коде.
        
2. **Инициализация дочернего класса (Child)**:
    
    - Статические поля и `static`-блоки дочернего класса в порядке их объявления в коде.
        
3. **Создание объекта (`new Child()`)**:
    
    - Нестатические поля и блоки инициализации родителя -> Конструктор родителя.
        
    - Нестатические поля и блоки инициализации дочернего класса -> Конструктор дочернего класса.

**10. Что такое JAR-файл и чем обычный JAR отличается от executable JAR?**

- **JAR (Java ARchive)** — это по сути обычный ZIP-архив, сгруппированный со специальной директорией `META-INF`. Содержит скомпилированные `.class` файлы, ресурсы (картинки, YAML/properties конфиги) и метаданные 📦
    
- **Обычный JAR (Library JAR)**:
    
    - Служит библиотекой (зависимостью) для других проектов.
        
    - Не имеет объявленной точки входа (`main` метода).
        
    - Нельзя запустить напрямую через `java -jar lib.jar`. Его можно использовать только подключив в `classpath`.
        
- **Executable JAR (Исполняемый JAR)**:
    
    - Готовое к запуску автономное приложение.
        
    - Содержит указание на главный класс в файле `META-INF/MANIFEST.MF` (заголовок `Main-Class`).
        
    - Запускается напрямую одной командой `java -jar app.jar`.
        
    - Часто собирается как **Fat JAR / Uber JAR** (когда внутри содержатся не только файлы текущего проекта, но и все распакованные зависимости других библиотек).
        

**11. Роль MANIFEST.MF, Main-Class и classpath при запуске приложения**

- **`MANIFEST.MF`**:
    
    - Служебный текстовый файл текстовых метаданных, лежащий внутри JAR по пути `META-INF/MANIFEST.MF`.
        
    - Хранит ключевую информацию о сборке: версию спецификации, кем собран архив, параметры безопасности, список зависимостей и точку входа.
        
- **`Main-Class`**:
    
    - Атрибут (ключ) внутри `MANIFEST.MF`.
        
    - Указывает полного названия класса с пакетом (FQCN), содержащего метод `public static void main(String[] args)`.
        
    - Пример строки в файле: `Main-Class: com.example.app.Application` 🚀
        
- **`classpath`**:
    
    - Путь (список директорий и JAR-архивов), где JVM ищет сторонние классы и ресурсы во время выполнения.
        
    - **Важный нюанс:** Если приложение запускается через `java -jar app.jar`, флаг `-classpath` из командной строки полностью игнорируется JVM. В этом случае JVM берет пути из атрибута `Class-Path` внутри самого `MANIFEST.MF`.
        

**12. Classpath vs Module Path, зачем появился JPMS и проблемы классического classpath**

- **Главное отличие**:
    
    - **Classpath**: Плоский список архивов/папок без проверки структуры. JVM ищет класс по цепочке "первый попался — тот и взял".
        
    - **Module Path**: Иерархический граф модулей (содержащих файл `module-info.class`), с явными правилами экспорта и импорта.
        
- **Зачем появился JPMS (Java Platform Module System, Java 9+)**:
    
    - **Проблема "JAR Hell"**: В `classpath` легко получить дублирование одного и того же класса в разных библиотеках. Ошибки всплывают только в runtime в виде `NoClassDefFoundError` или `NoSuchMethodError`.
        
    - **Отсутствие сильной инкапсуляции**: В `classpath` любой `public` класс из сторонней библиотеки доступен вашему коду, даже если авторы библиотеки хотели сделать его чисто внутренним (например, пакеты `com.sun.*`).
        
    - **Размер и монолитность runtime**: До Java 9 файл `rt.jar` тянул за собой всё API платформы разом. С JPMS саму JDK распилили на модули (`java.base`, `java.sql`, `java.desktop`), что позволяет собирать кастомные компактные JRE с помощью `jlink`.
        

**13. Strong Encapsulation модулей и ее влияние на Reflection**

- **Strong Encapsulation (Сильная инкапсуляция)**:
    
    - В JPMS по умолчанию код из модуля A **не имеет доступа** к `public` типам модуля B, если модуль B явно не экпортировал данный пакет через ключевое слово `exports` в своем `module-info.java`.
        
- **Влияние на Reflection (Рефлексию)**:
    
    - До Java 9 вызов `field.setAccessible(true)` позволял прочитать или обновить абсолютно любое приватное поле любого класса в JVM.
        
    - Начиная с JPMS, рефлексия подчиняется правилам инкапсуляции. Если пакет не открыт для рефлексии с помощью директивы `opens` в `module-info.java`, попытка вызвать `setAccessible(true)` из другого модуля выбросит `InaccessibleObjectException` 🛑
        
    - Это обезопасило внутренности самого JDK (например, класс `Unsafe` или внутренние массивы `String`), сделав работу JVM стабильнее.
        

**14. Зачем нужны системы сборки (Maven / Gradle), если есть javac?**

Использовать голый `javac` в промышленной разработке невозможно по ключевым причинам:

- **Управление зависимостями**: `javac` не умеет ходить в интернет, выкачивать нужные версии библиотек из репозиториев (Maven Central), проверять их контрольные суммы и решать конфликты версий.
    
- **Автоматизация жизненного цикла**: Сборка — это не только компиляция. Это еще генерация кода, прогон тестов, сборка отчетов, обработка ресурсов, packaging (упаковка в JAR/WAR) и публикация артефактов.
    
- **Воспроизводимость (Reproducible Builds)**: Система сборки гарантирует, что проект одинаково скомпилируется и соберется у любого разработчика на любой ОС и на CI/CD сервере.
    
- **Мультимодульность**: Автоматическое управление связями и порядком компиляции десятков внутренних модулей одного крупного проекта.
    

**15. Как работают системы сборки и что они делают помимо компиляции**

Системы сборки работают на базе построения **графа задач (Directed Acyclic Graph)** и прохождения четких фаз жизненного цикла ⚙️

**Функционал помимо компиляции:**

- **Download & Caching**: Загрузка транзитивных зависимостей и их локальное кэширование.
    
- **Code Generation**: Запуск аннотационных процессоров для генерации исходного кода (Lombok, MapStruct, gRPC) перед компиляцией.
    
- **Resource Filtering**: Подстановка нужных переменных окружения в файлы конфигураций (`application.properties`).
    
- **Testing & Reporting**: Автоматический запуск JUnit/TestNG тестов, формирование отчетов покрытия кода (JaCoCo).
    
- **Code Quality & Security**: Проверка стиля кода и уязвимостей (Checkstyle, SpotBugs, SonarQube).
    
- **Packaging & Publishing**: Сборка Fat-JAR, создание Docker-образов и отправка артефактов в Nexus/Artifactory.
    

**16. Разрешение транзитивных зависимостей и конфликтов версий**

Когда библиотека A тянет библиотеку C (версии 1.0), а библиотека B тянет ту же C (но версии 2.0), возникает конфликт. Инструменты решают его по-разному 🔀

- **Подход Maven (Nearest Definition — Ближайшая декларация)**:
    
    - Выбирается та версия библиотеки, которая находится **ближе к корню** графа зависимостей (то есть ближе к `pom.xml` вашего проекта).
        
    - Если длина пути одинакова, побеждает та зависимость, которая **объявлена первой** по тексту в `pom.xml`.
        
    - _Управление_: Переопределение версий фиксируется через блок `<dependencyManagement>` или с помощью тэгов `<exclusions>`.
        
- **Подход Gradle (Latest Version — Самая свежая версия)**:
    
    - Gradle по умолчанию выбирает **наивысшую (самую новую)** версию из найденных в графе транзитивных зависимостей.
        
    - _Управление_: Зафиксировать или жестко ограничить версию можно через `strictly` правила или резолюшн-стратегии (`configurations.all { resolutionStrategy ... }`).
        

**17. Annotation Processing и этап его работы**

- **Что это такое**:
    
    - Механизм (`javax.annotation.processing.Processor`), позволяющий перехватывать аннотации во время компиляции, анализировать структуру кода и **генерировать новые файлы кода (`.java`) или ресурсов**.
        
    - Используется библиотеками для исключения runtime-накладных расходов на рефлексию (Lombok, MapStruct, Dagger 2, JPA Metamodel).
        
- **На каком этапе работает**:
    
    - Работает **внутри самого компилятора `javac` ДО перевода кода в байткод**.
        
    - Процесс проходит циклично (в несколько раундов):
        
        1. `javac` строит синтаксическое дерево (AST) исходных файлов.
            
        2. Аннотационные процессоры сканируют AST и генерируют новые `.java` файлы.
            
        3. `javac` компилирует сгенерированные файлы. Если в процессе рождаются новые аннотированные файлы, начинается следующий раунд.
            
        4. Когда новые файлы больше не создаются, весь итоговый массив кода компилируется в `.class` файлы.
            

**18. Зачем нужен JIT-компилятор, если код уже скомпилирован в байткод?**

- **Слабость байткода**:
    
    - Байткод — это набор универсальных инструкций для виртуальной машины. Физический процессор (x86 или ARM) не умеет выполнять байткод напрямую.
        
    - Выполнение байткода через **Интерпретатор** работает медленно, так как каждая инструкция декодируется на лету.
        
- **Зачем нужен JIT (Just-In-Time) компилятор**:
    
    - JIT отслеживает частые "горячие" участки кода (Hot Spots) прямо во время работы приложения.
        
    - Он переводит этот байткод в **нативный машинный код** конкретного процессора и сохраняет его в специальной области памяти (Code Cache).
        
    - **Главный плюс JIT перед обычным C++ компилятором**: JIT имеет доступ к профилю выполнения в Runtime (какие ветки `if` срабатывают чаще, какие типы реально передаются) и может применять агрессивные динамические оптимизации, недоступные при статической компиляции 🔥
        

**19. Profiling, Tiered Compilation, Inlining, Devirtualization и Escape Analysis**

- **Profiling (Профилирование runtime)**:
    
    - JVM ведет счетчики вызовов методов и циклов, собирая статистику о типе данных, пройденных ветках и частоте вызовов.
        
- **Tiered Compilation (Многоуровневая компиляция)**:
    
    - Старт программы происходит мгновенно на **Интерпретаторе (Level 0)**.
        
    - При разогреве подключается быстрый компилятор **C1 / Client (Level 1-3)** для получения нативного кода без долгих оптимизаций.
        
    - Для самых "горячих" участков подключается тяжелый компилятор **C2 / Server (Level 4)**, производящий максимально глубокие оптимизации.
        
- **Inlining (Встраивание)**:
    
    - JIT убирает сам вызов небольшого метода, подставляя его тело непосредственно в место вызова. Это устраняет расходы на создание стек-фрейма.
        
- **Devirtualization (Девиртуализация)**:
    
    - Если интерфейсный/абстрактный метод в реальности имеет только одну реализацию (мономорфный вызов), JIT заменяет медленный вызов через таблицу виртуальных методов (vtable) на прямой вызов конкретной функции.
        
- **Escape Analysis (Анализ сбегания)**:
    
    - JIT проверяет, выходит ли создаваемый объект за пределы локального метода.
        
    - Если объект не сбегает: JVM производит **Scalar Replacement** (разбирает объект на примитивные поля и хранит их на стеке или в регистрах CPU), полностью избегая выделения памяти в Heap и снижая нагрузку на Garbage Collector 🧠
        

**20. Что такое JMH и почему микробенчмарки “на коленке” дают ложные выводы?**

- **JMH (Java Microbenchmark Harness)**:
    
    - Специализированный фреймворк от разработчиков OpenJDK, предназначенный для написания корректных и математически точных бенчмарков производительности на уровне отдельных методов.
        
- **Почему замеры "на коленке" (через `System.currentTimeMillis()`) всегда врут**:
    
    1. **Dead Code Elimination (Удаление мертвого кода)**: Если JIT видит, что результат работы метода никуда не сохраняется и не выводится, он просто полностью удаляет весь код из финальной машинной сборки. Время выполнения станет равно 0.
        
    2. **Constant Folding**: JIT может заранее посчитать результат выражения с константами во время компиляции и подставить готовое значение.
        
    3. **Отсутствие прогрева (Warmup)**: Замер захватывает фазу интерпретации и работы JIT-компилятора, а не реальную скорость работы готового нативного кода.
        
    4. **GC Паузы и Safepoints**: В момент вашего замера может сработать Garbage Collector или пауза операционной системы, что исказит результат в сотни раз.
        
    5. **Ошибки On-Stack Replacement (OSR)**: Компиляция прямо внутри замеряемого цикла вносит погрешность.
        

_JMH решает все эти проблемы: он проводит фазу прогрева, защищает от DCE через `Blackhole` объекты и собирает правильную статистику._**10. Что такое JAR-файл и чем обычный JAR отличается от executable JAR?**

- **JAR (Java ARchive)** — это по сути обычный ZIP-архив, сгруппированный со специальной директорией `META-INF`. Содержит скомпилированные `.class` файлы, ресурсы (картинки, YAML/properties конфиги) и метаданные 📦
    
- **Обычный JAR (Library JAR)**:
    
    - Служит библиотекой (зависимостью) для других проектов.
        
    - Не имеет объявленной точки входа (`main` метода).
        
    - Нельзя запустить напрямую через `java -jar lib.jar`. Его можно использовать только подключив в `classpath`.
        
- **Executable JAR (Исполняемый JAR)**:
    
    - Готовое к запуску автономное приложение.
        
    - Содержит указание на главный класс в файле `META-INF/MANIFEST.MF` (заголовок `Main-Class`).
        
    - Запускается напрямую одной командой `java -jar app.jar`.
        
    - Часто собирается как **Fat JAR / Uber JAR** (когда внутри содержатся не только файлы текущего проекта, но и все распакованные зависимости других библиотек).

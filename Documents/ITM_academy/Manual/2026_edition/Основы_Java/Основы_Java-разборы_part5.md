**65. Иерархия коллекций и почему Map не наследуется от Collection**

Иерархия Java Collections Framework делится на две принципиально разные ветви 🌳

- **Ветвь `Collection`**:    
    - Корневой интерфейс — `Iterable<E>`, от него наследуется `Collection<E>`.
        
    - Далее идут основные интерфейсы: `List<E>`, `Set<E>`, `Queue<E>` (и `Deque<E>`).
        
    - Работает с одиночными элементами данных.
        
- **Ветвь `Map`**:    
    - `Map<K, V>` стоит изолированно и **не наследуется от `Collection`**.
        

**Почему `Map` не является `Collection`**:

- **Разная модель данных**: `Collection` хранит одиночные элементы (`E`), а `Map` хранит ключевые пары "ключ-значение" (`Key-Value`).
    
- **Несовместимость контрактов**: Методы `Collection` не применимы к парам. Например, что должен делать метод `add(E)` у Map — добавлять ключ или значение? Как должен работать `iterator()`?
    
- **Представления (Views)**: `Map` не является коллекцией сам по себе, но предоставлять доступ к своим данным через коллекции: `keySet()` (возвращает `Set<K>`), `values()` (возвращает `Collection<V>`) и `entrySet()` (возвращает `Set<Map.Entry<K, V>>`).
    

**66. Массив vs Коллекция: принципиальные отличия и выбор**

- **Принципиальные отличия**:
    
    - **Размер**: Массив имеет строго фиксированную длину после создания. Коллекции динамически увеличиваются и уменьшаются.
        
    - **Типы данных**: Массивы могут напрямую хранить примитивы (`int[]`, `byte[]`). Коллекции хранят **только ссылочные типы** (`List<Integer>`).
        
    - **Проверка типов**: Массивы **Reified** (проверяют типы элементов в Runtime). Коллекции используют **Type Erasure** (проверка типов идет на этапе компиляции).
        
    - **Память и накладные расходы**: Массив представляет собой непрерывный кусок памяти без overhead на заголовки оберток, что делает его максимально производительным.
        
- **Когда использовать массив**:
    
    - Высоконагруженные / low-latency участки кода, где критичны накладные расходы на память и Garbage Collection.
        
    - Работа с сырыми бинарными данными (`byte[]` при I/O и сетевых протоколах).
        
    - Алгоритмы с заранее известным фиксированным размером буфера.
        
- **Когда использовать коллекцию**:
    
    - Во всех остальных задачах бизнес-логики, где размер данных заранее неизвестен и требуется богатый API (сортировка, фильтрация, быстрая дедупликация).
        

**67. Immutable collection vs Unmodifiable collection**

- 🛑 **Unmodifiable collection (Немодифицируемая обертка)**:
    
    - Создается через `Collections.unmodifiableList(existingList)`.
        
    - Это **лишь поверхностный виджет (View)** над базовой мутабельной коллекцией.
        
    - Само представление запрещает мутирующие вызовы (`add`, `remove`), выбрасывая `UnsupportedOperationException`.
        
    - **Ловушка**: Коллекция **НЕ является истинно неизменяемой**! Если кто-то изменит исходный `existingList`, эти изменения мгновенно отобразятся и в вашей "unmodifiable" коллекции.
        
- 🛡️ **Immutable collection (Истинно неизменяемая коллекция)**:
    
    - Создается через `List.of()`, `Set.of()`, `Map.of()` (Java 9+) или `List.copyOf()`.
        
    - Это **автономная копия данных**. Она гарантирует, что внутреннее состояние коллекции не может быть изменено ни прямо, ни через сторонние ссылки.
        
    - Попытка передать `null` при создании вызывает `NullPointerException`.
        
    - Бонус: Оптимизирована по памяти в JVM (не создаются лишние обертки-делегаты).
        

**83. Спец-коллекции Java: особенности и сценарии применения**

- **`LinkedHashSet`**: `HashSet` + двусвязный список. Сохраняет **порядок вставки (insertion order)** элементов.
    
    - _Сценарий_: Дедупликация элементов с сохранением порядка их поступления.
        
- **`EnumSet`**: Невероятно быстрая реализация `Set` для enum-типов. Внутри представлена в виде битовой маски (`long` или массив `long[]`).
    
    - _Сценарий_: Хранение наборов флагов, прав доступа или статусов. Работает быстрее и компактнее обычных битовых операций.
        
- **`EnumMap`**: `Map`, у которого ключами выступают значения Enum. Внутри реализована как обычный массив, где индексом служит `enum.ordinal()`.
    
    - _Сценарий_: Высокопроизводительная группировка или маппинг данных по Enum-ключам.
        
- **`WeakHashMap`**: `Map`, в котором ключи оборачиваются в `WeakReference`.
    
    - _Сценарий_: Кэширование метаданных. Если на объект-ключ больше нет сильных ссылок (`Strong Reference`) в приложении, бакет с этим ключом автоматически удаляется сборщиком мусора.
        
- **`IdentityHashMap`**: Нарушает контракт `Map` — сравнивает ключи не через `.equals()`, а через **`==` (по ссылке)**.
    
    - _Сценарий_: Сериализация, построение графов объектов, обход глубоких структур (tracking visited objects во избежание циклических ссылок).
        
- **`ConcurrentSkipListMap`**: Потокобезопасный отсортированный `NavigableMap` на базе структуры данных **SkipList (Список с пропусками)**.
    
    - _Сценарий_: Замена `TreeMap` в многопоточной среде. Обеспечивает O(log N) для поиска и записи без глобальных блокировок.
        
- **`BlockingQueue`**: Интерфейс очередей для многопоточности, поддерживающий блокировки при попытке взять элемент из пустой очереди или добавить элемент в полную.
    
    - _Сценарий_: Реализация паттерна "Producer-Consumer".
        
- **`DelayQueue`**: Unbounded блокирующая очередь элементов типа `Delayed`.
    
    - _Сценарий_: Элемент можно извлечь только тогда, когда истекло время его задержки (`getDelay() <= 0`). Применяется для таймаутов, планировщиков задач и очистки сессий.
        
- **`SynchronousQueue`**: Очередь с **нулевой емкостью**. Операция `put` одного потока блокируется до тех пор, пока другой поток не вызовет `take`.
    
    - _Сценарий_: Прямая передача задач "из рук в руки" между потоками (активно используется в `Executors.newCachedThreadPool()`).
        

**84. Изменяемый ключ в HashMap или элемент в HashSet**

Если изменить состояние объекта-ключа после того, как он был помещен в `HashMap` или `HashSet`:

1. **Искажение Хэш-кода**: Вычисление `hashCode()` от измененного объекта начнет возвращать **другое значение**.
    
2. **Потеря элемента**: При вызове `map.get(key)` или `set.contains(elem)` JVM пересчитает хэш-код, пойдет не в тот бакет и **не найдет элемент**, хотя он физически лежит в памяти таблицы.
    
3. **Утечка памяти**: Элемент невозможно корректно удалить через `.remove()`. Он навсегда зависает в куче.
    

> ⚠️ **Вывод**: Ключи для `HashMap` и элементы `HashSet` **обязаны быть неизменяемыми (Immutable)**.

**85. Iterator vs ListIterator**

- **`Iterator`**:    
    - Применим к любой коллекции `Collection`.        
    - Обход только в **одну сторону** (вперед: `hasNext()`, `next()`).        
    - Позволяет только **удалять** элементы (`remove()`).
        
- **`ListIterator`**:    
    - Доступен **только для списков (`List`)**.        
    - Двунаправленный обход (вперед и назад: `hasPrevious()`, `previous()`).        
    - Умеет получать текущие индексы (`nextIndex()`, `previousIndex()`).        
    - Позволяет не только удалять, но и **заменять** (`set(E)`), а также **вставлять** элементы (`add(E)`) прямо во время обхода.
        

**86. Почему legacy-коллекции (Vector, Stack) — плохой выбор**

- **`Vector`**:
    
    - Все методы помечены ключом `synchronized`. Это создает дикий overhead на блокировки даже в однопоточном коде.
        
    - В многопоточности потокобезопасность отдельных методов не дает атомарности составным операциям (например, комбинация `if (!vec.isEmpty()) vec.get(0)` все равно требует внешней синхронизации).
        
    - _Замена_: `ArrayList` (однопоток) или `CopyOnWriteArrayList` / `ConcurrentHashMap` (многопоток).
        
- **`Stack`**:
    
    - Наследуется от `Vector` — это архитектурная ошибка дизайна (нарушение принципа Liskov Substitution). Из-за наследования `Stack` получил методы доступа по индексу и вставки в середину, что полностью разрушает концепцию LIFO (Last In, First Out).
        
    - _Замена_: `ArrayDeque` (реализует интерфейс `Deque`).
        

**87. Принцип работы subList() и его подводные камни**

Метод `list.subList(from, to)` **не создает новый список в памяти**. Он возвращает специальное **представление (View)** оригинального списка 🔍

- **Взаимосвязь**: Все изменения внутри `subList` мгновенно отражаются на исходном списке и наоборот.
    
- **Подводные камни**:
    
    1. **`ConcurrentModificationException`**: Если после создания `subList` структурно изменить (добавить/удалить элемент) **исходный** список напрямую, а затем обратиться к `subList`, произойдет моментальное падение с `ConcurrentModificationException`.
        
    2. **Утечки памяти (Memory Leaks)**: `subList` держит сильную ссылку на **весь** исходный список. Если отрезать `subList` из 2 элементов у `ArrayList` на 10 млн элементов и сохранить этот `subList`, весь гигантский список на 10 млн элементов будет висеть в памяти Heap.
        

**88. Обертки Collections.synchronizedList() и их ограничения**

Обертка декорирует обычный список, оборачивая вызовы методов в блоки `synchronized (mutex) { delegate.method(); }` 🔒

- **Главные ограничения**:
    
    1. **Итерация не защищена**: Проход по коллекции через `for-each` или `Iterator` **не атомарен**. Чтобы избежать `ConcurrentModificationException`, разработчик обязан вручную синхронизироваться по самому объекту коллекции:
        
        Java
        
        ```
        synchronized (syncedList) {
            for (Item item : syncedList) { ... }
        }
        ```
        
    2. **Плохая масштабируемость**: Использует грубую блокировку (Coarse-grained lock) на весь список. При высокой конкуренции потоки встают в затор.
        

**89. Отличия List.of(), Set.of(), Map.of() от старых методов**

1. **Настоящая Иммутабельность**: Создают полностью изолированные структуры, а не декораторы поверх мутабельного списка (`Collections.unmodifiableList`).
    
2. **Запрет на `null`**: Фабричные методы `of()` моментально выбрасывают `NullPointerException` при попытке передать или найти `null`.
    
3. **Запрет дубликатов**: При попытке передать одинаковые элементы в `Set.of()` или ключи в `Map.of()` выбросится `IllegalArgumentException` на этапе создания.
    
4. **Эффективность по памяти**: Под капотом используются специализированные компактные типы (например, `ListN`, `List12`), избегающие создания лишних массивов для 1-2 элементов.
    

**90. Порядок элементов в коллекциях**

- **Insertion order (Порядок вставки)**: Элементы итерируются строго в том порядке, в котором их добавляли.
    
    - _Примеры_: `ArrayList`, `LinkedList`, `LinkedHashSet`, `LinkedHashMap`.
        
- **Access order (Порядок доступа)**: Порядок перестраивается при каждой операции чтения/обращения. Недавно запрошенные элементы перемещаются в конец.
    
    - _Примеры_: `LinkedHashMap` (с включенным флагом `accessOrder = true` — идеальная база для LRU-кэша).
        
- **Natural / Custom order (Сортированный порядок)**: Порядок задается методом `compareTo` (интерфейс `Comparable`) или переданным `Comparator`.
    
    - _Примеры_: `TreeSet`, `TreeMap`.
        
- **Unordered (Отсутствие порядка)**: Порядок элементов не гарантируется и может меняться при перебалансировке/рехашинге таблицы.
    
    - _Примеры_: `HashSet`, `HashMap`.
        

**91. Накладные расходы на память: ArrayList, LinkedList, HashMap, TreeMap**

- 🟢 **`ArrayList` (Минимальные расходы)**:
    
    - Представляет собой плоский массив ссылок `Object[]`.
        
    - Overhead: Точка входа + заголовок массива + около 4 байт (с compressed OOPs) на каждый элемент.
        
- 🔴 **`LinkedList` (Огромные расходы)**:
    
    - Каждый элемент завернут в объект `Node`.
        
    - Overhead на элемент: Заголовок объекта `Node` (12-16 байт) + 3 ссылки (`item`, `next`, `prev` = 12-24 байта). Итого ~40-48 байт служебных данных на **каждый** элемент!
        
- 🟡 **`HashMap` (Значительные расходы)**:
    
    - Массив бакетов + объекты нод `Node`.
        
    - Overhead на элемент: Заголовок `Node` + `int hash` + ссылка `key` + ссылка `value` + ссылка `next` (~32 байта) + неиспользованный запас емкости массива по Load Factor (0.75).
        
- 🔴 **`TreeMap` (Максимальные расходы)**:
    
    - Узлы красно-черного дерева `Entry`.
        
    - Overhead на элемент: Заголовок `Entry` + `key` + `value` + ссылки `left`, `right`, `parent` + `boolean color` (~64 байта служебных данных на каждый элемент).
        

**92. Шпаргалка по выбору коллекции под задачу**

- **Быстрое чтение по индексу**: `ArrayList`.
    
- **Частая вставка/удаление из начала/конца (Двусторонняя очередь)**: `ArrayDeque` (производительнее `LinkedList`).
    
- **Уникальность элементов**:
    
    - Без порядка: `HashSet`.
        
    - С сохранением порядка добавления: `LinkedHashSet`.
        
    - Со сортировкой по значению: `TreeSet`.
        
- **Маппинг "Ключ-Значение"**:
    
    - Стандарт: `HashMap`.
        
    - Сохранение порядка вставки или LRU Cache: `LinkedHashMap`.
        
    - Сортировка по ключам: `TreeMap`.
        
- **Многопоточная среда**:
    
    - Интенсивное чтение, редкая запись: `CopyOnWriteArrayList` / `CopyOnWriteArraySet`.
        
    - Выделенный высококонкурентный Key-Value словарь: `ConcurrentHashMap`.
        
    - Многопоточная сортировка: `ConcurrentSkipListMap`.
        
    - Очереди задач (Producer-Consumer): `ArrayBlockingQueue` или `LinkedBlockingQueue`.

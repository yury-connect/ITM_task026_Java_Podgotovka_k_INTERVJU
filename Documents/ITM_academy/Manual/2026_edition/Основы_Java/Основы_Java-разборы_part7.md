**111. Процесс vs Поток на уровне ОС и в Java**

- **Процесс (Process)**:    
    - Изолированная среда выполнения с собственным адресом в памяти, таблицей файловых дескрипторов и ресурсами ОС.
        
    - Переключение контекста между процессами (Context Switch) — тяжелая операция, требующая смены таблиц страниц памяти (TLB).
        
    - Процессы защищены друг от друга: падение одного не валит другой.
        
- **Поток (Thread)**:    
    - Легковесная единица исполнения внутри процесса.
        
    - Все потоки одного процесса **делят общее адресное пространство** (Heap, Metaspace), но имеют свой отдельный стек (Stack), регистры процессора и счетчик команд (PC).
        
    - Переключение контекста потоков быстрее, чем процессов.
        
- **Отражение в Java**:    
    - Запущенный JVM-процесс — это 1 процесс ОС.
        
    - Многопоточность в Java реализуется внутри одного JVM-процесса. Потоки делят общий Heap, что дает высокую скорость обмена данными, но создает риски состояния гонки (Data Race) и требует синхронизации.
        
    - Падение JVM-процесса (например, по `OutOfMemoryError` или Fatal Crash) моментально уничтожает все потоки внутри него.
        

**112. Platform Threads vs Virtual Threads**

- **Platform Thread (Платформенный поток)**:
    
    - Обертка "1-к-1" над потоком операционной системы (Kernel Thread).
        
    - **Ресурсы**: Жестко зарезервированный стек (~1 МБ), управление полностью отдано планировщику ОС.
        
    - **Лимит**: В системе можно создать единовременно тысячи платформенных потоков (ограничено памятью RAM и переключением контекста ОС).
        
- **Virtual Thread (Виртуальный поток, Java 21+)**:
    
    - Легковесная абстракция JVM, реализующая модель "M-к-N" (миллионы виртуальных потоков исполняются на небольшом пуле платформенных потоков-носителей / Carrier Threads).
        
    - **Ресурсы**: Стек хранится в Heap и динамически растет/сжимается (байты/килобайты).
        
    - **Механизм**: При блокирующем I/O вызове (например, чтение из сокета или БД) виртуальный поток снимается с Carrier Thread (unmount), а Carrier Thread задействуется для работы других виртуальных потоков.
        
- 🟢 **Где реально полезны**:
    
    - В приложениях с **I/O-bound нагрузкой** и моделью "Thread-per-request" (веб-серверы, microservices). Позволяют обрабатывать сотни тысяч одновременных сетевых соединений простым синхронным кодом.
        
- 🔴 **Где НЕ решают проблему**:
    
    - **CPU-bound задачи**: Не добавляют процессорных ядер. Задачи интенсивных вычислений всё так же упрутся в физические ядра CPU.
        
    - **Проблема Pinning (Привязки)**: Если блокирующий вызов выполняется внутри `synchronized` блока/метода или native-кода, виртуальный поток не может сняться и намертво блокирует Carrier Thread.
        
    - **Внешние барьеры**: Не спасают от лимитов сторонних ресурсов (например, размер пула соединений к БД всё равно ограничивает параллелизм).
        

**113. Java Memory Model (JMM) и ее назначение**

**Java Memory Model (JMM)** — это спецификация, определяющая правила того, как потоки взаимодействуют через общую память (Heap/Metaspace) и при каких условиях чтения из памяти гарантированно увидят результаты записей других потоков 🧠

- **Проблема, которую решает JMM**:
    
    - Современные процессоры хранят данные в многоуровневых кэшах (L1, L2, L3) и буферах записи (Store Buffers).
        
    - JIT-компилятор и CPU применяют агрессивные оптимизации: **Instruction Reordering** (изменение порядка инструкций, если они не нарушают однопоточный контекст).
        
    - Без JMM один поток мог бы изменить переменную в своем CPU-кэше, а другой поток никогда бы этого не увидел, или увидел бы изменения в абсолютно хаотичном порядке.
        

JMM задает единый абстрактный контракт для всех ОС и архитектур CPU, гарантируя переносимость и предсказуемость многопоточного кода.

**114. Атомарность, Видимость и Упорядоченность**

- ⚛️ **Atomicity (Атомарность)**:
    
    - Неделимость операции. Операция выполняется полностью или не выполняется вовсе. Никакой поток не может увидеть промежуточное состояние.
        
    - _Пример_: Запись 32-битного примитива `int a = 5` атомарна. Операция `a++` — **не атомарна** (чтение -> изменение -> запись).
        
- 👁️ **Visibility (Видимость)**:
    
    - Гарантия того, что изменение переменной одним потоком становится немедленно "видно" для чтения другими потоками (выталкивание из CPU-кэшей в RAM).
        
- 🔀 **Ordering (Упорядоченность)**:
    
    - Гарантия сохранения последовательности выполнения операций, запрещающая JIT-компилятору и CPU переставлять инструкции местами, если это нарушает логику взаимодействия потоков.
        

**115. Отношение Happens-Before**

**Happens-Before (HB)** — это ключевой фундаментальный отношение-контракт в JMM. Если операция $A$ связана с операцией $B$ отношением $A \rightarrow B$ (Happens-Before), это гарантирует:

1. Результаты выполнения операции $A$ гарантированно видны для операции $B$.
    
2. Операция $A$ логически выполняется строго до операции $B$.
    

- **Ключевые правила HB**:
    
    - **Program Order**: В рамках одного потока каждая инструкция HB для любой следующей за ней по коду.
        
    - **Monitor Lock**: Освобождение блокировки (`monitorexit`) HB для каждого последующего захвата **того же** монитора (`monitorenter`).
        
    - **Volatile Variable**: Запись в `volatile` поле HB для каждого последующего чтения из **этого же** `volatile` поля.
        
    - **Thread Start**: Вызов `thread.start()` HB для первой инструкции внутри запускаемого потока.
        
    - **Thread Join**: Завершение работы потока HB для успешного возврата из `thread.join()`.
        
    - **Transitivity**: Если $A \rightarrow B$ и $B \rightarrow C$, то $A \rightarrow C$.
        

> ⚠️ Если между записью и чтением перекрестной переменной отсутствует связь Happens-Before, программу нельзя считать корректной — возникает неопределенное поведение (Data Race).

**116. Race Condition vs Data Race**

- 🏎️ **Data Race (Гонка по данным)**:
    
    - Техническая ошибка на уровне памяти: ситуация, когда два и более потоков **одновременно обращаются к одной не-volatile ячейке памяти**, при этом **хотя бы одно обращение — запись**, и не используется синхронизация (нет Happens-Before).
        
    - Определяется спецификацией JMM.
        
- 🔀 **Race Condition (Состояние гонки)**:
    
    - Семантическая (архитектурная) ошибка в логике программы. Возникает, когда правильность работы приложения зависит от случайной последовательности или таймингов выполнения потоков (например, паттерн "Check-then-Act").
        
- **Важно**: Data Race можно устранить с помощью `AtomicInteger`, но архитектурный Race Condition останется:    
```Java
// Data Race НЕТ (Atomic), но Race Condition ЕСТЬ!
if (atomicInt.get() == 1) { 
	// Другой поток успеет изменить значение между get() и set()!
	atomicInt.set(2); 
}
```
    

**117. Принцип работы synchronized на концептуальном уровне**

Ключевое слово `synchronized` реализует блокировку по схеме взаимного исключения (Mutual Exclusion Lock / Mutex) на базе встроенного монитора объекта 🔒

- **Объект монитора**:
    
    - `synchronized` метод экземпляра блокируется по объекту `this`.
        
    - `synchronized static` метод блокируется по объекту `Class`.
        
    - `synchronized(obj)` блок блокируется по указанному объекту `obj`.
        
- **Эволюция блокировки в JVM (Lock Inflation)**:
    
    Для исключения сразу тяжелых вызовов ядра ОС, JVM плавно повышает уровень блокировки:
    
    1. **Biased Locking** _(устаревает в новых JDK)_: Блокировка привязывается к первому потоку без атомных операций.
        
    2. **Lightweight Locking**: При минимальной конкуренции потоки пытаются захватить замок в режиме спин-лока через быстрый CAS.
        
    3. **Heavyweight Locking**: При реальном конфликте потоков JVM задействует системный Mutex ОС, а конкурирующие потоки переводятся в состояние `BLOCKED` и уходят в сон.
        

**118. Механика monitor enter и monitor exit**

На уровне байткода Java блок `synchronized` компилируется в пару инструкций: `monitorenter` и `monitorexit` ⚙️

- **`monitorenter`**:
    
    - Поток пытается захватить владение монитором объекта.
        
    - Если счетчик повторных входов (reentrancy counter) равен `0`, поток захватывает монитор и выставляет счетчик в `1`.
        
    - Если этот же поток повторно входит в синхронизированный блок (Reentrancy), счетчик просто инкрементируется (`2`, `3`...).
        
    - Если монитор занят другим потоком, текущий поток приостанавливается до освобождения.
        
- **`monitorexit`**:
    
    - Уменьшает счетчик вхождений на `1`.
        
    - Когда счетчик достигает `0`, поток полностью освобождает монитор, и другие потоки получают шанс его захватить.
        

> 💡 **Компилятор гарантирует**: В байткод всегда вставляются резервные вызовы `monitorexit` в блоках обработки исключений, чтобы монитор не остался заблокированным при выбрасывании Exception.

**119. Гарантии ключевого слова volatile**

Модификатор `volatile` гарантирует 📋:

1. **Прямую видимость (Visibility)**: Чтение переменной всегда происходит из оперативной памяти (RAM), а запись моментально выталкивает данные из CPU-кэша в RAM.
    
2. **Запрет реордеринга (Ordering)**: Вставляет Memory Barriers (барьеры памяти), запрещающие перестановку инструкций записи/чтения `volatile`-поля с предшествующими или последующими операциями.
    
3. **Атомарность чтения/записи 64-битных типов**: Чтение и запись `long` и `double` гарантированно происходят атомарно за одну инструкцию (без них на 32-битных архитектурах возможна запись половинками — Word Tearing).
    

**120. Почему volatile НЕ делает составные операции атомарными**

Операции вида `count++`, `a = a + 1` или `check-then-act` состоят из 3 отдельных шагов байткода:

1. `getfield` — Прочитать значение из памяти.
    
2. `iadd` — Увеличить значение в регистре CPU.
    
3. `putfield` — Записать результат обратно в память.
    

`volatile` гарантирует свежесть данных только на этапах 1 и 3. Но между шагами 1 и 2 другой поток может успеть прочитать то же самое старое значение.
```text
Thread A: Read 5  ---> Increment to 6 --------> Write 6
Thread B:   ---> Read 5 ---> Increment to 6 --------> Write 6 (Потерян 1 инкремент!)
```

**121. Особые гарантии публикации final-полей**

`final` поля обеспечивают **безопасную публикацию (Safe Publication)** объектов без применения блокировок 🛡️

- **Гарантия Freeze**: JMM гарантирует, что к моменту завершения конструктора объекта все его `final`-поля полностью инициализированы ("заморожены").
    
- Любой поток, получивший ссылку на этот объект, гарантированно увидит корректно инициализированные значения его `final`-полей, а не значения по умолчанию (`null`, `0`).
    
- **Условие безопасности**: Ссылка `this` не должна утекать (Escaped) из конструктора до его полного завершения.
    

**122. Synchronized vs ReentrantLock**

- **Используйте `synchronized`**:
    
    - В 90% базовых ситуаций.
        
    - Лаконичный синтаксис, автоматический release при выходе из блока.
        
    - JVM постоянно оптимизирует `synchronized` под капотом.
        
- **Используйте `ReentrantLock`**:
    
    - Нужен попыточный захват блокировки без зависания: `tryLock()`.
        
    - Нужен таймаут на ожидание: `tryLock(100, TimeUnit.MILLISECONDS)`.
        
    - Нужна прерываемая блокировка: `lockInterruptibly()`.
        
    - Нужна честная очередь FIFO (Fairness Lock): `new ReentrantLock(true)`.
        
    - Нужны несколько условий ожидания: `lock.newCondition()`.
        

**123. ReadWriteLock и StampedLock**

- **`ReentrantReadWriteLock`**:
    
    - Разделяет блокировки на Read (shared, могут держать параллельно много читателей) и Write (exclusive, только 1 писатель).
        
    - _Применение_: Read-heavy нагрузки (когда чтений 95%+, а записи редки).
        
    - _Риски_: Голодание писателей (Writer Starvation), если поток читателей непрерывен.
        
- **`StampedLock` (Java 8+)**:
    
    - Вводит **Optimistic Reading (Оптимистичное чтение)**: Чтение вообще не берет блокировку, а получает метку (stamp) и проверяет валидность через `validate(stamp)`.
        
    - _Применение_: Сверхбыстрое чтение, когда конфликты с записью невероятно редки.
        
    - _Риски_: **Не является реинтерабельным** (Reentrant)! Повторный попыточный вызов в том же потоке приведет к дедлоку.
        

**124. Почему wait/notify — это низкоуровневый инструмент**

- **Сложности и риски**:
    
    - Требуют обязательного обертывания в `synchronized(obj)` (иначе `IllegalMonitorStateException`).
        
    - Проблема **Missed Signals** (сигнал `notify()` отправлен до того, как поток вызвал `wait()`, и был навсегда утерян).
        
    - **Spurious Wakeups** (спонтанные пробуждения): `wait()` обязан вызываться только внутри цикла `while (!condition)`.
        
    - Легко перепутать `notify()` и `notifyAll()`, получив зависание программы.
        
- **Чем заменяют**: High-level утилитами из `java.util.concurrent`: `Lock` + `Condition`, `BlockingQueue`, `CompletableFuture`, `CountDownLatch`.
    

**125. Синхронизаторы: CountDownLatch, CyclicBarrier, Semaphore, Phaser**

- ⏱️ **`CountDownLatch`**:
    
    - Один или несколько потоков ждут, пока счетчик событий не опустится до нуля (`countDown()`).
        
    - _Особенность_: Одноразовый инструмент (нельзя сбросить и использовать повторно).
        
- 🔄 **`CyclicBarrier`**:
    
    - N потоков ждут **друг друга** в единой точке синхронизации (`await()`). Как только все N прибудут, барьер рушится и потоки идут дальше.
        
    - _Особенность_: Многоразовый (автоматически сбрасывается для следующего круга).
        
- 🚦 **`Semaphore`**:
    
    - Ограничивает число потоков, одновременно использующих ограниченный ресурс, с помощью выдачи разрешений (permits).
        
- 🎭 **`Phaser`**:
    
    - Продвинутый многофазный барьер. Позволяет динамически регистрировать и снимать потоки прямо во время работы.
        

**126. ThreadLocal: применение и утечки памяти**

**`ThreadLocal`** позволяет хранить переменные, изолированные строго внутри текущего потока 👤

- **Где полезен**: Контекст сессии пользователя, транзакции БД, хранение непротокобезопасных утилит (исторически `SimpleDateFormat`).
    
- ⚠️ **Главная опасность в Пуллах Потоков (Thread Pools)**:
    
    - Потоки в пулах **живут долго и переиспользуются**.
        
    - Каждая запись в `ThreadLocal` сохраняется во внутренней таблице `ThreadLocalMap` текущего объекта `Thread`.
        
    - Если после выполнения задачи не вызвать `threadLocal.remove()`, данные останутся висеть в памяти навсегда, приводя к:
        
        1. **Утечкам памяти (Memory Leaks)**.
            
        2. **Утечкам данных (Security Leak)**: Следующая задача, попавшая на этот же поток из пула, случайно прочитает данные предыдущего пользователя!
            

**127. Иерархия: Executor vs ExecutorService vs ScheduledExecutorService**

- **`Executor`**: Базовый интерфейс. Содержит 1 метод `execute(Runnable)`. Разделяет задачу и способ ее запуска.
    
- **`ExecutorService`**: Расширяет `Executor`. Управляет жизненным циклом пула (`shutdown()`, `awaitTermination()`) и умеет принимать задачи с возвращаемым результатом: `submit(Callable)` -> `Future`.
    
- **`ScheduledExecutorService`**: Расширяет `ExecutorService`. Добавляет возможности выполнения задач с задержкой или периодически: `scheduleAtFixedRate()`, `scheduleWithFixedDelay()`.
    

**128. Расчет размера пула потоков**

- 🧮 **Для CPU-bound задач** (интенсивные вычисления, кодирование, алгоритмы):
    
    $$\text{Threads} = N_{\text{cores}} + 1$$
    
    _(Где $+1$ дается на случай редких падений в page fault или блокировок на уровне ОС)._
    
- 🌐 **Для I/O-bound задач** (сетевые запросы, база данных, чтение файлов):
    
    $$\text{Threads} = N_{\text{cores}} \times \left(1 + \frac{\text{Wait Time}}{\text{Compute Time}}\right)$$
    
    _(Так как потоки большую часть времени стоят в ожидании ответа, число потоков может измеряться сотнями)._
    

> 💡 В современном Java 21+ для I/O-bound задач вычисление размера пула теряет смысл — используется `Executors.newVirtualThreadPerTaskExecutor()`.

**129. Сравнение фабрик пулов потоков**

- **`newFixedThreadPool(n)`**:
    
    - Фиксированное кол-во потоков.
        
    - Использует неограниченную очередь `LinkedBlockingQueue`.
        
    - _Опасность_: Если задачи приходят быстрее, чем обрабатываются, очередь переполнит Heap и вызовет `OutOfMemoryError`.
        
- **`newCachedThreadPool()`**:
    
    - Динамическое число потоков (от `0` до `Integer.MAX_VALUE`).
        
    - Использует очередь с нулевой емкостью `SynchronousQueue`.
        
    - _Опасность_: При всплеске нагрузки мгновенно породит тысячи потоков и положит систему по CPU/RAM.
        
- **`newWorkStealingPool()`**:
    
    - На базе `ForkJoinPool`. Создает параллелизм по числу ядер CPU.
        
    - Каждый поток имеет свою собственную двустороннюю очередь задач (Deque).
        

**130. ForkJoinPool, Work Stealing и опасности Common Pool**

- **`ForkJoinPool`**: Пул, заточенный под задачи, разделяемые по принципу "Разделяй и властвуй" (метод `fork()` разбивает подзадачу, `join()` ждет результат).
    
- **`Work Stealing` (Кража работы)**:
    
    - У каждого потока есть своя локальная очередь (Deque).
        
    - Свои задачи поток берет с головы очереди в режиме LIFO (для локальности кэша).
        
    - Если у потока закончилась работа, он становится "вором" и забирает (стелит) задачи с хвоста очереди другого занятого потока в режиме FIFO.
        
- ⚠️ **Риски `ForkJoinPool.commonPool()`**:
    
    - Это общий статический пул для приложения (используется по умолчанию в `parallelStream()`, `CompletableFuture` без указания executor'а).
        
    - Если заблокировать потоки `commonPool` тяжелыми I/O операциями, остановятся абсолютно все параллельные стримы и асинхронные цепочки во всем приложении!
        

**131. Ограничения обычного Future**

1. **Блокирующее получение**: Метод `future.get()` блокирует вызывающий поток до завершения задачи.
    
2. **Невозможность построения цепочек (Chaining)**: Нельзя сказать "когда завершится задача A, передай результат в задачу B".
    
3. **Нельзя ручного завершить**: Нельзя принудительно завершить `Future` снаружи, просто передав готовое значение.
    
4. **Нет комбинации задач**: Нельзя дождаться выполнения "всех N футур" или "первой из N" без ручной блокирующей обвязки.
    
5. **Нет удобной обработки ошибок**.
    

**132. Преимущества CompletableFuture**

`CompletableFuture<T>` реализует интерфейсы `Future<T>` и `CompletionStage<T>` и предлагает:

- **Реактивный неблокирующий стиль**: Позволяет навешивать коллбэки (`thenApply`, `thenAccept`), которые сработают автоматически при готовности результата.
    
- **Композиция задач**: Возможность объединять асинхронные графы выполнения.
    
- **Явное завершение**: Метод `completableFuture.complete(value)` разрешает вручную отдать результат из любого потока.
    
- **Развитая обработка ошибок**: Операторы `exceptionally()`, `handle()`.
    

**133. Операторы CompletableFuture и выбор Executor**

- **`thenApply(Function<T, R>)`**: Преобразование типа 1-в-1 (аналог `.map()`).
    
- **`thenCompose(Function<T, CompletionStage<R>>)`**: Сплющивание вложенных асинхронных тасок (аналог `.flatMap()`).
    
- **`thenCombine(other, BiFunction)`**: Запускает две независимые футуры параллельно и объединяет их результаты, когда обе завершатся.
    
- **`allOf(futures...)`**: Возвращает новый `CompletableFuture<Void>`, который завершится, когда **все** переданные футуры будут выполнены.
    
- ⚙️ **Почему важен выбор Executor**:
    
    - Если вызывать методы без суффикса `Async` (например, `thenApply`), код коллбэка выполнится **в том же потоке, который завершал предыдущую задачу**.
        
    - Если вызывать `thenApplyAsync(...)` без указания Executor, задача уйдет в общий `ForkJoinPool.commonPool()`, что создает риски его блокировки.
        

**134. Cooperative Interruption (Кооперативное прерывание)**

В Java **не существует безопасных способов насильно убить поток** извне (метод `Thread.stop()` давно deprecated и запрещен, так как оставляет объекты в разрушенных состояниях).

**Принцип работы Cooperative Interruption**:

1. Внешний поток подает сигнал прерывания через `thread.interrupt()`.
    
2. Выставляется внутренний булев флаг прерывания у целевого потока.
    
3. Сам поток **обязан регулярно проверять свой флаг** (`Thread.currentThread().isInterrupted()`) или обрабатывать `InterruptedException` от блокирующих методов.
    
4. Получив сигнал, поток должен корректно освободить ресурсы и завершить выполнение.
    

**135. Thread.interrupt(), Deadlock, Livelock, Starvation**

- **`Thread.interrupt()`**: Не убивает поток моментально. Если поток спал/ждал (`sleep`, `wait`, `join`), метод выбросит `InterruptedException` и сбросит флаг. В противном случае просто выставится флаг `isInterrupted() = true`.
    
- ⛔ **Deadlock (Взаимная блокировка)**:
    
    - Поток A держит Ресурс 1 и ждет Ресурс 2.
        
    - Поток B держит Ресурс 2 и ждет Ресурс 1.
        
    - Потоки заблокированы навечно.
        
- 🔄 **Livelock (Живая блокировка)**:
    
    - Потоки постоянно меняют свое состояние в ответ на действия друг друга, не заблокированы, но **не делают никакого полезного прогресса** (аналог: два вежливых человека пытаются разойтись в узком коридоре, шагая в одну и ту же сторону).
        
- 🪦 **Starvation (Голодание)**:
    
    - Поток готов к выполнению, но не получает процессорного времени или доступа к ресурсу из-за агрессивных/высокоприоритетных соседних потоков.
        

**136. CAS, AtomicLong vs LongAdder, ABA-проблема и False Sharing**

- ⚡ **CAS (Compare-And-Swap)**:
    
    - Атомарная инструкция процессора (`LOCK CMPXCHG`).
        
    - Принимает: адрес памяти, ожидаемое старое значение (Expect) и новое значение (Update).
        
    - Если значение в памяти == Expect, обновляет на Update и возвращает `true`. В противном случае возвращает `false` (поток уйдет на повтор в `while`-цикле).
        
- 📊 **`AtomicLong` vs `LongAdder`**:
    
    - **`AtomicLong`**: Держит одну `volatile` переменную и крутит CAS-цикл. При высокой конкуренции сотни потоков стучатся в одну ячейку, постоянные сбои CAS вызывают жуткий просад производительности.
        
    - **`LongAdder` (Java 8+)**: Разбивает счетчик на массив ячеек (`Cell[]`). Потоки хэшируются и обновляют разные ячейки без конфликтов. При вызове `.sum()` значения ячеек суммируются. В разы быстрее на высокой конкуренции.
        
- 🔄 **ABA-проблема**:
    
    - Поток 1 прочитал значение `A`. Поток 2 изменил `A` -> `B` -> `A`. Поток 1 делает CAS(A, C) — проверка успешна, так как значение снова `A`, хотя состояние системы изменилось.
        
    - _Решение_: Использование `AtomicStampedReference` (версионирование).
        
- ⚡ **False Sharing (Ложное сцепление)**:
    
    - Процессорная кэш-линия (обычно 64 байта) подтягивает из RAM сразу группу переменных.
        
    - Если Поток 1 меняет Переменную X, а Поток 2 меняет Переменную Y, лежащую на **той же кэш-линии**, ядро CPU постоянно инвалидирует кэш соседнего ядра.
        
    - _Решение_: Аннотация `@Contended` (добавляет падинг/отступы байт).

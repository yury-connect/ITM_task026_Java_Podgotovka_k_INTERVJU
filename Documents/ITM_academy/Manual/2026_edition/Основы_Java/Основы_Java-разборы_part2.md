**21. Чем примитивные типы отличаются от ссылочных, почему примитивы не являются полноценными объектами и какие различия между ними реально важны в прод-коде?**

- **Способ хранения в памяти**:
    
    - **Примитивы** хранят чистое значение прямо в выделенной памяти (на стеке метода или внутри структуры объекта в куче).
        
    - **Ссылочные типы** хранят адрес (ссылку), указывающий на сам объект, расположенный в Heap (куче).
        
- **Почему примитивы — не объекты**:
    
    - У них нет метаданных заголовка объекта (Object Header), у них нет методов, они не наследуются от `java.lang.Object`, у них нет идентичности (identity) и они не могут быть равны `null`.
        
- **Что реально важно в прод-коде**:
    
    - **Производительность и память**: Примитивы работают в разы быстрее за счет локальности данных в кэше процессора и отсутствия накладных расходов. Объекты-обертки (например, `Integer`) требуют дополнительно 16-24 байта на служебный заголовок объекта в куче. Массив `int[1000]` занимает около 4 КБ, а `Integer[1000]` — более 20 КБ плюс нагрузка на Garbage Collector.
        
    - **Ограничение Дженериков**: Java Generics работают только со ссылочными типами (`List<Integer>`, но не `List<int>`).
        
    - **Семантика отсутствия значения**: Примитив не может быть `null`. В бизнес-логике (например, значение в БД) `0` и `null` имеют разный смысл: `0` — это число, а `null` — значение не задано.
        

**22. Размеры и диапазоны примитивных числовых типов и их практическая значимость**

- **Целочисленные типы**:
    
    - `byte`: 1 байт (8 бит), от -128 до 127.
        
    - `short`: 2 байта (16 бит), от -32 768 до 32 767.
        
    - `int`: 4 байта (32 бита), от -2.14 млрд до +2.14 млрд.
        
    - `long`: 8 байт (64 бита), от -9_10^18 до +9_10^18.
        
- **Типы с плавающей точкой**:
    
    - `float`: 4 байта (32 бита), точность ~6-7 десятичных цифр.
        
    - `double`: 8 байт (64 бита), точность ~15-17 десятичных цифр.
        
- **Что реально важно на практике**:
    
    - **Генерация ID и счетчиков**: Всегда используйте `long` для первичных ключей в БД, ID пользователей, транзакций или счетчиков. `int` на 2.14 миллиардах заблизит лимит на продуктовой базе быстрее, чем кажется.
        
    - **Работа с бинарными данными**: `byte[]` незаменим при работе с сетевыми протоколами, файловым I/O и передачей файлов.
        
    - **Финансы и деньги**: Никогда не используйте `float` или `double` для финансовых расчетов — только `BigDecimal` или хранение денег в минимальных единицах (копейках/центах) в виде `long`.
        

**23. Переполнение целых чисел в Java и причина отсутствия исключений**

- **Как работает**:
    
    - Целые числа в Java хранятся в **двоичном дополнительном коде (Two's complement)**.
        
    - Знаковый бит находится в самом старшем разряде (`0` — положительное, `1` — отрицательное).
        
    - Когда вы прибавляете `1` к `Integer.MAX_VALUE` (`0x7FFFFFFF`), единичный бит переходит в знаковый разряд (`0x80000000`), и значение превращается в `Integer.MIN_VALUE`. Происходит закольцовывание (wrap-around).
        
- **Почему не выбрасывается исключение**:
    
    - **Производительность**: Проверка на переполнение после каждой арифметической операции потребовала бы дополнительных процессорных инструкций (ветвлений) на уровне CPU, что замедлило бы выполнение любого Java-кода в разы.
        
- **Как защититься в коде**:
    
    - Использовать методы класса `Math` с проверкой: `Math.addExact(a, b)` или `Math.multiplyExact(a, b)` — они выбросят `ArithmeticException` при переполнении.
        
    - Использовать `BigInteger`, если диапазон заранее неизвестен.
        

**24. Работа float/double, 0.1 + 0.2 != 0.3, NaN, Infinity и -0.0**

- **Почему 0.1 + 0.2 != 0.3**:
    
    - `float` и `double` реализуют стандарт IEEE 754. В двоичной системе счисления большинство десятичных дробей (такие как `0.1` или `0.2`) являются бесконечными периодическими дробями (как `1/3` в десятичной).
        
    - При сохранении в ограниченную мантиссу происходит округление. В итоге `0.1 + 0.2` в памяти дает `0.30000000000000004`.
        
- **Специальные значения и их поведение**:
    
    - **`NaN` (Not a Number)**: Результат неопределенных операций (например, `0.0 / 0.0` или `Math.sqrt(-1)`).
        
        - _Сравнение_: `NaN` не равен ничему, даже самому себе! Выражение `Double.NaN == Double.NaN` вернет `false`. Для проверки нужно использовать метод `Double.isNaN(val)`.
            
    - **`Infinity` и `-Infinity`**: Результат деления ненулевого числа на `0.0` (например, `1.0 / 0.0`).
        
        - _Сравнение_: Сравниваются корректно: `Double.POSITIVE_INFINITY == Double.POSITIVE_INFINITY` вернет `true`.
            
    - **`-0.0` (Отрицательный ноль)**: Появляется из-за наличия отдельного знакового бита.
        
        - _Сравнение_: При сравнении через примитивы `0.0 == -0.0` вернет `true`. Однако если обернуть их в объекты: `Double.valueOf(0.0).equals(Double.valueOf(-0.0))` вернет `false`!
            

**25. Boxing, Unboxing и создаваемые ими проблемы**

- **Autoboxing** — автоматическое преобразование примитива в соответствующий объект-обертку (`int` -> `Integer` через `Integer.valueOf()`).
    
- **Unboxing** — обратный процесс (`Integer` -> `int` через метод `.intValue()`).
    
- **Проблемы в продуктиве**:
    
    1. **Скрытые `NullPointerException`**: При попытке распаковать обертку, содержащую `null`, вызывается метод `.intValue()`, что моментально приводит к NPE.
        
    2. **Утечка производительности и падение GC**: В циклах автоупаковка создает миллионы временных объектов в Heap, что вызывает частые паузы сборщика мусора (Stop-the-World).
        
    3. **Логические ошибки сравнения**: Разработчики часто сравнивают обертки через `==`, сравнивая ссылки на объекты вместо их значений.
        

**26. Integer Cache и неявности при сравнении через ==**

- **Что такое Integer Cache**:
    
    - Для оптимизации памяти JVM кэширует экземпляры `Integer` для диапазона значений **от -128 до 127** (верхний порог можно расширить через флаг `-XX:AutoBoxCacheMax`).
        
    - При автоупаковке или вызове `Integer.valueOf(x)` для значений из этого диапазона JVM не создает новый объект, а возвращает ссылочный объект из кэша.
        
- **Почему `==` иногда "работает"**:   
```Java
    Integer a = 100;
    Integer b = 100;
    System.out.println(a == b); // true (один и тот же объект из кэша)
    
    Integer c = 200;
    Integer d = 200;
    System.out.println(c == d); // false (разные объекты в куче!)
```
    
Это создает крайне опасный баг: код отлично работает на тестах с маленькими числами, но ломается на бою при превышении 127. Обертки всегда нужно сравнивать только через `.equals()`.
    

**27. Опасность null при авто-распаковке**

Авто-распаковка происходит неявно в местах, где компилятор ожидает примитив. Компилятор сам вставляет вызов метода распаковки (например, `.intValue()`).

**Главные ловушки в коде**:

- **Тернарный оператор**:    
```Java
    Integer val = null;
    boolean flag = true;
    int number = flag ? val : 0; // NPE! Компилятор приводит к int оба плеча
```
    
- **Цикл for-each по коллекциям**:    
```Java
    List<Integer> list = Arrays.asList(1, null, 3);
    for (int num : list) { ... } // Упадет на втором элементе при попытке unboxing
```
    
- **Передача в методы и условные выражения**:
```Java
    Integer status = null;
    if (status == 1) { ... } // NPE! status распаковывается в int для сравнения
```
    

**28. Фундаментальные методы класса Object, контракт equals/hashCode и toString**

- **Базовые методы**: `equals()`, `hashCode()`, `toString()`, `getClass()`, `clone()`, `wait()`, `notify()`, `notifyAll()`.
    
- **Контракт `equals()`**:
    
    - Рефлексивность (`x.equals(x) == true`).
        
    - Симметричность (`x.equals(y)` и `y.equals(x)` дают одинаковый результат).
        
    - Транзитивность (если `x.equals(y)` и `y.equals(z)`, то `x.equals(z)`).
        
    - Согласованность (многократные вызовы возвращают одно значение, если объект не менялся).
        
    - Проверка на `null` (`x.equals(null)` всегда `false`).
        
- **Контракт `hashCode()`**:
    
    - Если объекты равны по `equals()`, их `hashCode()` **обязаны быть равны**.
        
    - Если `hashCode()` у двух объектов разный, они гарантированно **не равны** по `equals()`.
        
    - Коллизия: Разные объекты могут иметь одинаковый `hashCode()`.
        
- **Почему это критично**:
    
    - Хеш-коллекции (`HashMap`, `HashSet`) используют `hashCode()` для поиска нужного бакета, а затем `equals()` для поиска конкретного элемента внутри бакета. Нарушение контракта ведет к утере элементов из `Set/Map`, дублированию ключей и утечкам памяти.
        
- **Требования к `toString()`**:
    
    - Должен предоставлять понятное информативное представление объекта для логов и отладки, но **не должен раскрывать конфиденциальные данные** (пароли, персональные данные, токены).
        

**29. Идентичность объекта vs Логическое равенство**

- **Идентичность (Identity) — оператор `==`**:
    
    - Проверяет равенство **ссылок в памяти**.
        
    - Возвращает `true` только в том случае, если обе переменные указывают на один и тот же адрес объекта в Heap.
        
- **Логическое равенство (Logical Equality) — метод `.equals()`**:
    
    - Проверяет равенство **состояния (содержимого)** объектов по бизнес-логике.
        
    - Две разные области памяти с одинаковым набором полей (например, два объекта `User` с одинаковым `id`) будут идентифицированы как логически равные.
        

**30. Иммутабельность String, String Pool, суть Immutable-объектов и их роль в многопоточности**

- **Почему `String` immutable (неизменяемый)**:
    
    - Внутренний массив байт (`byte[] value`) объявлен как `private final`, а сам класс `String` — `final` (нельзя унаследовать и переопределить поведение).
        
- **Зачем нужна неизменяемость строк**:
    
    1. **String Pool (Пул строк)**: Позволяет JVM экономить память, храня только один экземпляр одинаковых строковых литералов. Если бы строки были изменяемыми, изменение одной переменной поменяло бы значение у всех, кто ссылается на этот литерал.
        
    2. **Безопасность**: Строки используются как аргументы для открытия файлов, подключения к БД, сетевых адресов. Изменение строки во время работы создаст уязвимость.
        
    3. **Кэширование Хеш-кода**: `hashCode()` вычисляется один раз при первом обращении и кэшируется. Это делает `String` идеальным ключом для `HashMap`.
        
- **Что такое Immutable-объект в целом**:
    
    - Объект, состояние которого невозможно изменить после создания.
        
    - Требования к созданию: все поля `final` и `private`, нет сеттеров, класс `final`, глубокое копирование изменяемых полей при получении через конструктор или геттеры.
        
- **Значение для многопоточности**:
    
    - Иммутабельные объекты **потокобезопасны по умолчанию (Thread-safe by design)**.
        
    - Их можно свободно передавать между потоками без применения синхронизации (`synchronized`, `Lock`), без риска состояния гонки (Data Race) и без проблем с видимостью изменений.

**31. Что такое defensive copying и в каких случаях он нужен?**

**Defensive copying (защитное копирование)** — это паттерн проектирования, при котором класс создает полную независимую копию мутабельного (изменяемого) объекта перед тем, как сохранить его во внутреннее поле или вернуть наружу через геттер 🛡️

- **Зачем это нужно**:
    
    - Если клиентский код передает в ваш объект мутабельный класс (например, `Date`, `ArrayList`, `byte[]`), а вы сохраняете прямую ссылку, этот клиент может изменить внутреннее состояние вашего объекта прямо извне.
        
    - Если геттер возвращает прямую ссылку на внутренний массив или коллекцию, внешний код может очистить или изменить данные в обход всех валидаций вашего класса.
        

> 💡 **Правило применения**:
> 
> - **При приеме данных (Конструктор/Сеттеры)**: Делайте копию входного объекта до валидации его полей.
>     
> - **При отдаче данных (Геттеры)**: Возвращайте копию объекта или необернутую неизменяемую обертку (`Collections.unmodifiableList()`).
>     

**32. Что происходит в памяти при создании объекта в Java?**

При выполнении конструкции `User user = new User("Alice")` JVM проходит 6 строгих шагов ⚙️

1. **Проверка загрузки класса**: JVM проверяет, загружен ли класс `User` в Metaspace. Если нет — запускается цепочка ClassLoader'ов.
    
2. **Выделение памяти в Heap**:
    
    - В куче вычисляется точный размер памяти под объект (заголовок + поля).
        
    - Выделение происходит мгновенно через **TLAB (Thread Local Allocation Buffer)** — собственный маленький кусок кучи, зарезервированный под текущий поток, что исключает блокировки между потоками.
        
3. **Обнуление памяти**: Заглушение выделенной области нулями. Все примитивные поля получают дефолтные значения (`0`, `0.0`, `false`), а ссылочные — `null`.
    
4. **Инициализация заголовка (Object Header)**:
    
    - Записывается **Mark Word** (хэш-код, возрастной порог для GC, данные о блокировках/locks).
        
    - Записывается **Klass Word** (указатель на метаданные класса в Metaspace).
        
5. **Выполнение кода инициализации (`<init>`)**:
    
    - Выполняются блоки инициализации и инициализаторы полей.
        
    - Вызывается конструктор суперкласса (`super()`), а затем конструктор текущего класса.
        
6. **Сохранение ссылки**: Адрес созданного объекта в Heap записывается в локальную переменную `user`, расположенную в стек-фрейме текущего метода.
    

**33. Области памяти в JVM: Общие vs Потоковые**

Память JVM фундаментально разделена на две категории по уровню доступа 🏢

```
+-------------------------------------------------------------+
|                      ОБЩИЕ (Shared)                         |
|   [ Heap ]         [ Metaspace ]       [ Code Cache ]       |
+-------------------------------------------------------------+
|                   ДЛЯ ПОТОКА (Thread-Local)                 |
|   [ Java Thread Stack ]  [ PC Register ]  [ Native Stack ]  |
+-------------------------------------------------------------+
```

- **Общие для всех потоков (Shared / Global Memory)**:
    
    - Создаются при старте JVM и доступны абсолютно любому потоку.
        
    - Требуют механизмов синхронизации при конкурентном доступе.
        
- **Принадлежащие конкретному потоку (Thread-Local Memory)**:
    
    - Создаются вместе с потоком и автоматически уничтожаются при его завершении.
        
    - Доступны только своему потоку, поэтому безопасны без синхронизации.
        

**34. Содержимое областей памяти: Heap, Stack, Metaspace, Code Cache и Native Memory**

- 🟢 **Heap (Куча)** _(Shared)_:
    
    - Все созданные объекты классов и экземпляры.
        
    - Все массивы (примитивные и ссылочные).
        
    - Значения нестатических полей объектов.
        
- 🔵 **Java Thread Stack (Стек)** _(Thread-Local)_:
    
    - Фреймы вызова методов (Stack Frames).
        
    - Локальные примитивные переменные.
        
    - Указатели (ссылки) на объекты в куче.
        
- 🟣 **Metaspace** _(Shared, Off-Heap)_:
    
    - Метаданные классов (структура класса, аннотации, имена полей/методов).
        
    - Таблицы виртуальных методов (vtable).
        
    - Runtime Constant Pool (Пул констант).
        
- 🟠 **Code Cache** _(Shared)_:
    
    - Нативный машинный код, скомпилированный JIT-компилятором из "горячих" методов.
        
- ⚪ **Native Memory (Off-Heap)** _(Shared/Thread)_:
    
    - Память операционной системы за пределами управления JVM.
        
    - Прямые буферы ввода-вывода (`ByteBuffer.allocateDirect()`).
        
    - Память под сами потоки ОС (Native Stacks) и служебные структуры JVM.
        

**35. Что такое Stack Frame и его внутреннее устройство**

**Stack Frame (Фрейм стека)** — это изолированный блок памяти, который JVM выделяет в стеке потока **при каждом вызове метода**. При возврате из метода фрейм мгновенно уничтожается (смещается указатель стека) 🎯

Содержимое фрейма:

1. **Local Variable Table (LVT — Таблица локальных переменных)**:
    
    - Массив, где хранятся аргументы метода и локальные переменные.
        
    - `this` хранится в нулевой ячейке (для нестатических методов).
        
2. **Operand Stack (Стек операндов)**:
    
    - Рабочая область для выполнения вычислительных операций и подготовки аргументов к вызову других методов (например, сложение чисел берет два верхних значения из стека операндов).
        
3. **Frame Data (Данные фрейма)**:
    
    - Ссылка на Пул Констант для динамического связывания.
        
    - Информация о нормальном завершении метода или таблица обработки исключений (Exception Table).
        

**36. Где живут локальные переменные, параметры и ссылки на объекты?**

Локации определяются исключительно тем, **ГДЕ** и **КАК** объявлена переменная, а не ее типом 📍

- **Локальные переменные и параметры методов**:
    
    - Живут **на Стеке** (в `Local Variable Table` текущего стек-фрейма).
        
    - Если переменная примитивного типа — сам примитив лежат на стеке.
        
    - Если переменная ссылочного типа — 32/64-битный адрес (ссылка) лежит на стеке.
        
- **Поля классов (Instance Fields)**:
    
    - Всегда живут **в Куче (Heap)** в составе своего объекта-владельца.
        
    - Даже примитивное поле `int age` внутри класса `User` будет храниться в куче!
        
- **Статические переменные (Static Fields)**:
    
    - Начиная с Java 8, живут **в Куче (Heap)** внутри специального зеркального объекта `java.lang.Class`.
        

**37. Что находится в Heap: сами объекты, массивы, поля или только ссылки?**

В Heap хранятся **ТОЛЬКО сами структуры объектов и массивов**, а также их внутреннее наполнение:

- **Объекты и массивы**:
    
    - Вся тушка объекта хранит служебный заголовок + значения своих полей.
        
- **Примитивные поля внутри объекта**:
    
    - Хранятся непосредственно внутри памяти объекта в куче (например, биты числа `int` или `boolean`).
        
- **Ссылочные поля внутри объекта**:
    
    - Хранят **НЕ сам вложенный объект**, а 32-битный или 64-битный указатель (адрес) на другой объект, находящийся в той же куче.
        

> 📌 **Резюме**: Ссылки как адреса живут и на стеке (локальные), и в куче (как поля объектов). Сами же данные объектов и массивов всегда базируются исключительно в Heap.

**38. Передача по значению в Java и концепция "ссылка передается по значению"**

В Java существует **ЕДИНСТВЕННЫЙ** механизм передачи параметров — **Pass-by-value (Передача по значению)**. Концепции передачи по ссылке (Pass-by-reference) в Java нет ❌

- **Что происходит при передаче примитива**:
    
    - Создается копия значения (например, копия числа `5`). Изменения внутри метода не влияют на исходную переменную.
        
- **Что происходит при передаче объекта**:
    
    - В метод передается **копия адреса (ссылки)** на объект в куче.
        
    - Вы имеете два независимых указателя (внешний и внутренний), смотращих на один и тот же объект в Heap.
```Java
void modify(User u) {
    u.setName("Bob"); // Изменит объект в Heap! Оба указателя смотрят на него.
    u = new User("Charlie"); // Переприсвоит ТОЛЬКО локальную копию ссылки!
}
```

Если бы в Java была передача по ссылке, присвоение `u = new User()` изменило бы переменную во внешнем коде. Но этого не происходит.

**39. Типы ссылок: Strong, Soft, Weak, Phantom**

Жизненный цикл объекта в куче регулируется 4 типами ссылок из пакета `java.lang.ref` 🔗

1. **Strong Reference (Сильная ссылка)**:
    
    - Обычная ссылка: `User user = new User()`.
        
    - **Поведение**: Сборщик мусора **никогда** не удалит объект, пока до него можно добраться по сильной ссылке.
        
2. **SoftReference (Мягкая ссылка)**:
    
    - `SoftReference<User> soft = new SoftReference<>(user)`.
        
    - **Поведение**: Удаляется GC **только при нехватке памяти** перед выбрасыванием `OutOfMemoryError`.
        
    - **Применение**: Кэши в памяти, критичные к объему RAM.
        
3. **WeakReference (Слабая ссылка)**:
    
    - `WeakReference<User> weak = new WeakReference<>(user)`.
        
    - **Поведение**: Удаляется при **ближайшей сборке мусора**, если у объекта больше нет Strong или Soft ссылок.
        
    - **Применение**: `WeakHashMap` (для хранения ключей-метаданных без риска утечек памяти).
        
4. **PhantomReference (Фантомная ссылка)**:
    
    - `PhantomReference<User> phantom = new PhantomReference<>(user, queue)`.
        
    - **Поведение**: Метод `.get()` всегда возвращает `null`. Объект помещается в `ReferenceQueue` после того, как он был полностью финализирован и физически готов к удалению.
        
    - **Применение**: Безопасная очистка off-heap ресурсов вместо устаревшего `finalize()`.
        

**40. GC Roots, достижимость объектов и критерии их удаления**

**GC Roots (Корни сборки мусора)** — это отправные точки, с которых сборщик мусора начинает обход графа объектов для определения их жизнеспособности (Tracing GC) 🌳

**Что является GC Root**:

- Локальные переменные и параметры активных методов в Java-стеке каждого потока.
    
- Статические переменные загруженных классов.
    
- Активные потоки (`Thread` объекты).
    
- JNI Local / Global ссылки в нативном коде.
    

**Модель досягаемости (Reachability)**:

- **Reachability Graph**: GC построит дерево всех объектов, до которых можно дойти по цепочке ссылок от любого из GC Roots.
    
- **Reachable (Достижимый)**: Объект гарантированно считается живым и **не подлежит сборке**.
    
- **Unreachable (Недостижимый / Мусор)**: Если к объекту нельзя построить путь ни от одного GC Root (даже если объекты циклически ссылаются друг на друга), он признается мусором и подлежит уничтожению сборщиком.

GraphQL — это не просто «ещё один способ делать HTTP-запросы», а **язык запросов и среда выполнения на стороне сервера**, которые позволяют фронтенду запрашивать именно те данные, которые ему нужны, и ничего лишнего . В отличие от REST, где вы ходите по разным URL за разными ресурсами, здесь **все операции идут через один эндпоинт** (обычно `POST /graphql`), а «что именно сделать» указывается внутри тела запроса .[](https://graphql.org/learn/introduction/)[](https://developers.buffer.com/guides/graphql-intro.html)

## 📜 Схема и типы (*Контракт*)

Сердце любого GraphQL-сервера — это **строго типизированная схема** (*обычно пишется на SDL — Schema Definition Language*). В ней описываются все типы данных, их поля и связи между ними, а также то, какие операции (*запросы, мутации, подписки*) вообще доступны . Бэкенд-разработчик пишет «резолверы» — функции, которые знают, откуда взять данные для каждого конкретного поля (*из БД, другого сервиса или просто из памяти*) .[](https://graphql.org/learn/introduction/)[](https://developer.overheid.nl/blog/2026/07/30/graphql-1-introductie)

## 🎯 Варианты общения (*Операции*)

Фронтенд общается с бэкендом через три типа операций:

#### **1. Query** (*Чтение*)  
Это аналог `GET` в REST. Клиент отправляет «дерево» полей, которое повторяет структуру желаемого JSON-ответа. Сервер возвращает ровно то, что попросили, без «оверфетчинга» (лишних данных) и «андерфетчинга» (когда нужно делать несколько запросов) . Например, если нужны только имя и email пользователя, вы запрашиваете только их, даже если в базе у пользователя есть еще 20 полей.[](https://graphql.org/learn/introduction/)[](https://docs.aws.amazon.com/ja_jp/appsync/latest/devguide/appsync-dg.pdf#4#151#4)

#### **2. Mutation** (*Запись*)  
Это аналог `POST`, `PUT`, `DELETE`. Мутации используются для создания, обновления или удаления данных . Синтаксис похож на Query, но начинается со слова `mutation`. Важное отличие: если в одном запросе несколько мутаций, они выполняются **последовательно** (одна за другой), в то время как поля обычного Query могут выполняться параллельно . Мутация возвращает результат операции (например, созданный объект), чтобы фронтенд мог сразу обновить кэш или UI .[](https://graphql.org/learn/mutations/)[](https://www.apollographql.com/docs/ios/fetching/mutations.md)[](https://javarush.com/quests/lectures/ru.javarush.java.spring.lecture.level29.lecture05?post=full#discussion#1)

#### **3. Subscription** (*Подписка*)  
Это механизм для **реального времени**. Клиент отправляет подписку, и сервер держит соединение открытым (*обычно через `WebSockets`*), отправляя данные каждый раз, когда происходит соответствующее событие (*например, «создан новый отзыв»*) . Это сложнее в реализации и поддержке, чем `Query`/`Mutation`, но идеально подходит для чатов, лент новостей или обновления статусов в реальном времени.[](https://graphql.org/learn/subscriptions/)

## ⚙️ Как это работает «*под капотом*»

Фронтенд формирует строку запроса (*JSON с полями `query` и `variables`*) и отправляет её *POST*-запросом на единый эндпоинт. Бэкенд (*например, на Spring Boot с библиотекой `graphql-java` или `graphql-kickstart`*) парсит запрос, валидирует его по схеме, а затем вызывает нужные резолверы. Клиент получает JSON, где в поле `data` лежат запрошенные данные, а в поле `errors` — информация об ошибках (*если они были*). При этом HTTP-статус ответа чаще всего будет `200 OK`, даже если внутри произошла бизнес-ошибка .[](https://developers.buffer.com/guides/graphql-intro.html)

## 🆚 Кратко: **GraphQL** vs **REST**
	
- **Endpoint:** REST — много URL, GraphQL — один URL.
    
- **Данные:** REST — сервер решает, что вернуть (*часто лишнее*), GraphQL — клиент указывает точные поля.
    
- **Версионирование:** REST — через URL (`/v1/`, `/v2/`), GraphQL — через эволюцию схемы (*добавление полей, `@deprecated` для старых*) без создания новых версий .[](https://graphql.org/learn/introduction/)[](https://docs.aws.amazon.com/ja_jp/appsync/latest/devguide/appsync-dg.pdf#4#151#4)
    
- **Ошибки:** REST — через HTTP-коды (404, 500), GraphQL — через массив `errors` в теле ответа при статусе 200 .[](https://developers.buffer.com/guides/graphql-intro.html)

Для твоего бэкенда на Java это означает, что тебе нужно будет либо добавить в проект `Spring GraphQL` (*если используешь Spring Boot 3*), либо настроить контроллер, который принимает GraphQL-запросы, и определить схему с типами и резолверами.

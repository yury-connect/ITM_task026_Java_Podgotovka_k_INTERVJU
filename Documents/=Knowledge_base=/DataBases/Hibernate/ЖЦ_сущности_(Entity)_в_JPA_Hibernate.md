Жизненный цикл сущности (Entity) в JPA / Hibernate описывает, как объект взаимодействует с контекстом персистентности (Persistence Context / L1-кэшем) и базой данных.

Сущность может находиться в одном из **4 состояний**, а переход между ними осуществляется вызовом конкретных методов `EntityManager` или `Session`.

### 🎨 4 Состояния Entity
- 🐣 **Transient (New):** Простой Java-объект, созданный через `new`. У него нет идентификатора (Primary Key) в БД, и Hibernate про него ничего не знает.    
- 🟢 **Persistent (Managed):** Объект связан с активной сессией (`EntityManager`). Имеет ID в БД. Включен механизм **Dirty Checking** — любые изменения полей через сеттеры автоматически сформируют SQL `UPDATE` при сбросе сессии.    
- 🟡 **Detached:** Запись в БД существует (есть ID), но сессия Hibernate **закрыта или очищена**. Изменения полей больше не отслеживаются Hibernate.    
- 🔴 **Removed:** Объект помечен на удаление. В БД запись будет физически удалена (SQL `DELETE`) при ближайшем `flush()`.    

### 🔄 Схема переходов между состояниями

#### 1. Переходы в состояние **Persistent** (*Managed*) 🟢
- 🐣 **Из Transient в Persistent:**    
    - **`em.persist(entity)` (*JPA Стандарт*):**        
        - Делает исходный переданный объект `Managed`.            
        - Возвращает `void`.            
        - Не делает мгновенный `INSERT` в БД (за исключением стратегии `GenerationType.IDENTITY`), откладывая запись до `flush()`.
        
    - **`session.save(entity)` (*Hibernate Legacy*):**        
        - Делает объект `Managed` и **мгновенно возвращает его сгенерир-й ID**.   
        - Может вып-ть SQL `INSERT` раньше времени, чтобы получить знач-е ключа.
    
- 🗄️ **Из Базы Данных в Persistent:**    
    - **`em.find(Class, id)`** или **`em.createQuery(...)`**: Загружают данные из БД и сразу возвращают управляемый объект в состоянии `Managed`.        
    - **`em.getReference(Class, id)`**: Возвращает CGLIB-прокси с зафиксированным ID без выполнения SQL-запроса (запрос уйдет при первом обращении к полям).

#### 2. Переходы в состояние **Detached** 🟡
- 🟢 **Из Persistent в Detached:**    
    - **`em.detach(entity)`** (или `session.evict(entity)`): Исключает конкретный экземпляр объекта из текущего L1-кэша сессии.        
    - **`em.clear()`** (или `session.clear()`): Отсоединяет **вообще все** сущности, находящиеся в текущей сессии.        
    - **`em.close()`** (или `session.close()`): При закрытии контекста/сессии все управляемые ею объекты автоматически становятся `Detached`.

#### 3. Возврат из **Detached** в **Persistent** (*Re-attachment*) 🟡 $\rightarrow$ 🟢
- **`em.merge(detachedEntity)` (JPA Стандарт):**    
    - Принимает `Detached`-объект (или `Transient`).        
    - Ищет объект с таким ID в L1-кэше или выполняет SQL `SELECT` в БД.
    - Копирует поля из переданного `detachedEntity` в найденную/созданную управляемую сущность.
    - **Возвращает НОВЫЙ экземпляр в состоянии `Managed`**.
        
    - ⚠️ **Главная ловушка:** Исходная ссылка `detachedEntity`, переданная в параметр метода, **ОСТАЕТСЯ в состоянии `Detached`**! Работать дальше нужно строго с результатом метода: `User managedUser = em.merge(detachedUser)`.
    
- **`session.saveOrUpdate(entity)` / `session.update(entity)` (Hibernate Legacy):**
    - Привязывает **исходный** `Detached`-объект прямо к сессии, делая его `Managed`.
    - _Опасность:_ Выбросит `NonUniqueObjectException`, если в текущей сессии уже загружен другой объект с таким же ID.

#### 4. Переходы в состояние **Removed** 🔴
- 🟢 **Из Persistent в Removed:**    
    - **`em.remove(entity)` (*JPA Стандарт*):**        
        - Принимает **только `Managed`-объект**.
        - Переводит его в состояние `Removed`.
        - Физический SQL-запрос `DELETE` уходит в базу только при `flush()` или коммите транзакции.
            
        - ⚠️ Если передать в `em.remove()` объект в состоянии `Detached`, выбросится `IllegalArgumentException`.
        
- 🟡 **Из Detached в Removed (*через Hibernate Native*):**
    - **`session.delete(entity)` (*Hibernate Legacy*):**        
        - В отличие от JPA `remove()`, нативный метод Hibernate умеет принимать и сразу удалять объекты, находящиеся в состоянии `Detached`.

#### 5. Переход из **Removed** в **Transient** 🔴 $\rightarrow$ 🐣
- Если над объектом в состоянии `Removed` вызвать **`em.persist(entity)`** до того, как произошел `flush()`, операция удаления отменяется, и объект снова возвращается в состояние `Managed`.    
- После выполнения `flush()` и коммита транзакции физическая запись из БД удаляется, а Java-объект в памяти по факту переходит в состояние **Transient** (простой объект без записи в БД).

### ⚠️ Важные нюансы и отладка (Checklist для собеседования)

> 💡 **Что делает `em.flush()`?**
> 
> Метод `flush()` не меняет состояния объектов! Он лишь синхронизирует L1-кэш с БД: физически отправляет накопленный стек SQL-команд (`INSERT`, `UPDATE`, `DELETE`) в сетевой сокет базы данных. Все `Managed` объекты при этом так и остаются `Managed`.

> 💡 **Что делает `em.refresh(entity)`?**
> 
> Запрашивает актуальное состояние строки из БД через SQL `SELECT` и перезаписывает им поля у `Managed`-объекта в памяти, отменяя все нереализованные изменения.

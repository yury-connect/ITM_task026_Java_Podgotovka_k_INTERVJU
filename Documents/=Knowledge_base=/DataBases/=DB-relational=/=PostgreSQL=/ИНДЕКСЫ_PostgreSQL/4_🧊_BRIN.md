### 🧊 BRIN — «для огромных таблиц» (четвёртый по частоте)

**Принцип работы**: **Block Range Index**. Хранит сводную информацию (минимум/максимум) для **диапазона физических блоков** таблицы. Например, для 128 страниц подряд он хранит минимальное и максимальное значение индексируемой колонки в этом диапазоне[](https://git.postgresql.org/cgit/pgweb-static.git/plain/documentation/pdf/10/postgresql-10-US.pdf?id=494b7f9011ca054d7ad4ccf024d12ba2efe8c9ed#494#309).

**Для чего нужен**: Огромные таблицы, где данные **физически упорядочены** (например, по дате вставки). Идеален для логов, событий, временных рядов.

**Сложность**: Поиск **O(1) или O(log n)** для определения диапазона, но затем нужно просканировать все страницы в этом диапазоне (lossy). Вставка очень быстрая.

**Плюсы**:
- **Крошечный размер**: в сотни раз меньше B-tree.    
- Очень быстрая вставка.    
- Идеален для больших таблиц с упорядоченными данными.    

**Минусы**:
- **Lossy**: требует перепроверки всех строк в диапазоне.    
- **Бесполезен**, если данные не упорядочены физически.    
- Не подходит для точечного поиска по случайным значениям.    

**Когда брать**: Для **огромных таблиц** (миллионы/миллиарды строк), где данные **физически упорядочены** (например, по времени), и ты ищешь по диапазону (например, за период)[](https://git.postgresql.org/cgit/pgweb-static.git/plain/documentation/pdf/10/postgresql-10-US.pdf?id=494b7f9011ca054d7ad4ccf024d12ba2efe8c9ed#494#309).

**Когда не следует**: Для небольших таблиц (B-tree справится лучше) или для таблиц, где данные вставляются в случайном порядке.

## 🚀 Инициализация колонки в большой таблице: ранжирование по пригодности на проде

---
### 🥇 1. `ALTER TABLE ... SET DEFAULT` <br>(*идеально для PostgreSQL 11+*)

**Когда:** нужно задать значение по умолчанию для **новых** строк, а существующие — не трогать.
```sql
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'NEW';
```

**Почему топ:** В PostgreSQL 11+ это **мгновенная операция** — значение хранится в метаданных, таблица **не перезаписывается**. Никаких блокировок, никакого bloat.

**Минус:** Существующие строки остаются с `NULL`. Если нужно заполнить их — идём к пункту 2.

---
### 🥈 2. Батчевое обновление (*рабочая лошадка*)

**Когда:** нужно заполнить **существующие** строки, а таблица большая.
```sql
-- Батчами по id
UPDATE orders SET status = 'NEW' 
WHERE status IS NULL AND id BETWEEN 1 AND 10000;

-- Следующий батч
UPDATE orders SET status = 'NEW' 
WHERE status IS NULL AND id BETWEEN 10001 AND 20000;
```

**Почему хорошо:**
- Короткие транзакции → нет долгих блокировок.    
- Меньше WAL, меньше bloat.    
- Можно контролировать прогресс и остановиться в любой момент.    

**Минус:** Нужно писать цикл (в приложении или через `DO $$ ... $$`), и это **медленнее**, чем один `UPDATE`, но безопаснее.

**Совет:** Используй `ctid` вместо `id`, если нет первичного ключа:
```sql
UPDATE orders SET status = 'NEW'
WHERE ctid IN (SELECT ctid FROM orders WHERE status IS NULL LIMIT 10000);
```

---
### 🥉 3. `CREATE TABLE AS` + `RENAME` (*для полной перезаписи*)

**Когда:** нужно перезаписать **всю** таблицу, и есть место на диске.
```sql
CREATE TABLE orders_new AS
SELECT id, COALESCE(status, 'NEW') AS status, ...
FROM orders;
DROP TABLE orders;
ALTER TABLE orders_new RENAME TO orders;
```

**Почему хорошо:** Быстро, одна транзакция, нет bloat (новая таблица без мёртвых строк).

**Минус:** Требует **места** (две копии таблицы), **блокирует** запись на время переименования, и **теряются индексы/констрейнты** — их нужно пересоздавать вручную.

---
### ⚠️ 4. Один `UPDATE` на всю таблицу (*плохо для прода*)
```sql
UPDATE orders SET status = 'NEW' WHERE status IS NULL;
```

**Почему плохо:**
- **Долгая транзакция** → блокировки, рост WAL, риск таймаута.
- **Bloat** → MVCC создаёт новую версию каждой строки.
- **Блокировка таблицы** → другие запросы ждут.
- **Риск отката** → упадёт на 999 999-й строке — всё откатится.

**Когда допустимо:** Только на **маленьких таблицах** (до 10 000 строк) или в **окно обслуживания** (ночь, выходные).

---
### ❌ 5. `UPDATE` без `WHERE` (*катастрофа*)
```sql
UPDATE orders SET status = 'NEW';
```

**Почему нельзя:** Обновит **все** строки, даже те, где значение уже правильное. Двойной bloat, двойная нагрузка, бессмысленная работа.

**Когда допустимо:** **Никогда** на проде.

---
## 🎤 Итог для собеседования

> _«Если нужно инициализировать колонку, я ранжирую так: сначала `ALTER TABLE ... SET DEFAULT` — в PostgreSQL 11+ это мгновенно. Если нужно заполнить существующие строки — батчи по 10 000 через `id BETWEEN` или `ctid`. Если перезапись полная — `CREATE TABLE AS` с переименованием. Один большой `UPDATE` на всю таблицу — плохо: долгая транзакция, блокировки, bloat. `UPDATE` без `WHERE` — вообще нельзя.»_

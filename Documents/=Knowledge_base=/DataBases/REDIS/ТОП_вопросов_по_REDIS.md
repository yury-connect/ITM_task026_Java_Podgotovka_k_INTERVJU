### ⚡ 1. Однопоточность Redis и I/O Multiplexing

- 🧵 **Почему считался и считается однопоточным:**    
    Основной движок выполнения команд Redis исполняет бизнес-логику и команды в **одном главном потоке**. Начиная с Redis 6.0, многопоточность была добавлена _исключительно_ для асинхронного считывания/записи сетевых сокетов и парсинга протокола RESP, но сам процесс выполнения команд остался строго однопоточным.
    
- 🚀 **За счет чего достигается гигантская скорость:**    
    - 🧠 **Операции в OЗУ:** Все данные хранятся в оперативной памяти (RAM). Доступ к RAM занимает наносекунды, устраняя задержки дискового ввода-вывода (I/O).
        
    - 🔄 **I/O Multiplexing (*Мультиплексирование ввода-вывода*):** Использование системных вызовов ядра ОС (`epoll` в Linux, `kqueue` в macOS). Один поток постоянно опрашивает тысячи сетевых сокетов и обрабатывает готовые события по мере их поступления в событиный цикл (Event Loop).
        
    - 🚫 **Отсутствие блокировок и Context Switch:** Нет затрат ресурсов процессора на переключение контекста между потоками и отсутствуют мьютексы/блокировки для защиты внутренних структур данных.        

### 📦 2. Структуры данных Redis и их бизнес-применение

- 🔤 **String (*Строки*):** Базовый тип (до 512 МБ).    
    - _Применение:_ Кэширование HTML-страниц, JSON-ответов API, токены сессий, счетчики с атомарными операциями `INCR` / `DECR`.
    
- 🗂️ **Hash (*Хэш-таблицы*):** Объект с парами поле-значение.    
    - _Применение:_ Хранение объектов (профиль пользователя, корзина товаров), где можно атомарно обновить или прочитать отдельное поле без перезаписи всего объекта.
    
- 📜 **List (*Списки*):** Связанные списки элементов.    
    - _Применение:_ Организация простых очередей задач (`LPUSH` + `RPOP` / `BRPOP`), ленты последних событий или уведомлений.
        
- 🎯 **Set (*Неупорядоченные множества*):** Коллекции уникальных элементов.    
    - _Применение:_ Хранение уникальных тегов, онлайн-пользователей, списков друзей, пересечение множеств (`SINTER`) для поиска общих интересов.
    
- 🏆 **Sorted Set (*ZSet / Упорядоченные множества*):** Множества, где каждый элемент привязан к числовому баллу (Score).    
    - _Применение:_ Лидерборды в играх, приоритетные очереди, алгоритмы Rate Limiter, выборки по диапазонам времени.
    
- 📡 **Streams (*Потоки*):** Лог событий append-only.    
    - _Применение:_ Шина сообщений с логикой групп подписчиков (Consumer Groups), отслеживанием смещений (Offset) и подтверждением доставки (`XACK`).
    
- 📊 **HyperLogLog:** Вероятностная структура данных.    
    - _Применение:_ Подсчет количества уникальных элементов (Uniques / UV) в гигантских объемах данных с погрешностью до $0.81\%$ при фиксированном расходе памятивсего в 12 КБ.

### ⚖️ 3. Redis vs Memcached

- 📦 **Типы данных:** Memcached поддерживает только простые строки/бинарные данные (Key-Value). Redis предлагает богатство структур (Hashes, Sets, ZSets, Streams).
    
- 💾 **Сохраняемость (*Persistence*):** Memcached — строго в оперативной памяти (при перезагрузке данные теряются). Redis поддерживает сброс данных на диск (RDB и AOF).
    
- 📡 **Репликация и Кластеризация:** Memcached не имеет нативной репликации (шардирование реализуется на стороне клиента). Redis поддерживает из коробки Master-Replica, Sentinel и распределенный Redis Cluster.
    
- 🤹 **Многопоточность:** Memcached — многопоточный из коробки. Redis использует один основной поток для выполнения команд.
    
- 🛠️ **Дополнительный функционал:** В Redis есть Pub/Sub, Lua-скрипты, транзакции, модули расширения и гео-индексы. В Memcached этого нет.    

### 🔄 4. Основные стратегии работы с кэшем

- 📥 **Cache-Aside (Lazy Loading / Ленивая загрузка):**    
    - Приложение сначала идет в кэш. Если данных нет (Cache Miss), приложение читает их из БД, пишет в кэш и возвращает пользователю.        
    - _Применение:_ Универсальный стандарт для систем с преобладанием чтения.
    
- 📖 **Read-Through:**    
    - Приложение всегда обращается только к сервису кэша. Если данных нет, кэш сам прозрачно вычитывает их из БД, сохраняет у себя и отдает приложению.    
    - _Применение:_ Изоляция работы с БД внутри слоя кэширования.
    
- ✍️ **Write-Through:**    
    - Приложение пишет данные в кэш. Кэш **синхронно** и атомарно записывает их в БД и только потом подтверждает успех.        
    - _Применение:_ Системы с высокими требованиями к согласованности данных между кэшем и БД.
    
- ⏳ **Write-Behind (Write-Back / Отложенная запись):**    
    - Приложение пишет данные в кэш. Кэш мгновенно отвечает успехом, а затем **асинхронно** батчами сбрасывает накопленные изменения в БД.        
    - _Применение:_ Системы с экстремально высокой нагрузкой на запись (счетчики, аналитика). Есть риск потери данных при падении кэша.        

### 🧹 5. Вытеснение (Eviction) и Очистка ключей по TTL

#### Механизмы удаления ключей с истекшим TTL:
	
- 💤 **Passive Expiration (Пассивный):** Ключ проверяется при попытке доступа к нему. Если TTL истек, он удаляется и отдает `null`.
    
- ⚡ **Active Expiration (Активный):** Раз в 100 миллисекунд Redis случайно берет 20 ключей с установленным TTL и удаляет среди них просроченные. Процесс повторяется, пока доля просроченных ключей в выборке не станет меньше $25\%$.    

#### Стратегии вытеснения при переполнении памяти (`maxmemory-policy`):
	
- 🕒 **`volatile-lru` / `allkeys-lru`:** Вытесняет ключи, к которым дольше всего не обращались (Least Recently Used).
    
- 🔢 **`volatile-lfu` / `allkeys-lfu`:** Вытесняет ключи, к которым обращались реже всего (Least Frequently Used).
    
- 🎲 **`volatile-random` / `allkeys-random`:** Случайное удаление ключей.
    
- ⏰ **`volatile-ttl`:** Удаляет ключи с наименьшим оставшимся временем жизни (TTL).
    
- 🛑 **`noeviction`:** Не удаляет ничего. При попытке записи возвращает ошибку OOM (Out of Memory).    

### 💾 6. Сохраняемость на диске: RDB vs AOF

- 📸 **RDB (Redis Database Snapshots):**
	    
    - _Механика:_ Создает компактные точечные дампы памяти в один файл через системный вызов `fork()` во вспомогательный процесс.
        
    - _Плюсы:_ Высокая скорость восстановления при старте, компактный размер файла.
        
    - _Минусы:_ Потеря данных за весь интервал между снимками при аварийном падении.
    
- 📜 **AOF (Append Only Log):**
	    
    - _Механика:_ Записывает каждую команду изменения в лог-файл (`fsync`: всегда, раз в секунду или средствами ОС).
        
    - _Плюсы:_ Максимальная надежность (минимальная потеря данных).
        
    - _Минусы:_ Файл быстро разрастается (требует периодического фонового сжатия `AOF Rewrite`), медленная загрузка данных при старте.
    
- ⚖️ **Оптимальный компромисс:**
	    
    **Гибридный режим (RDB + AOF rewrite / по умолчанию с Redis 4.0).** Файл AOF при перезаписи формируется из RDB-дампа базового состояния и короткого текстового AOF-лога свежих команд.

### 🐘 7. «Big Keys» и неблокирующее удаление UNLINK

- 🔴 **Что такое и чем опасны:**    
    Ключи, содержащие огромные значения (строки $> 10$ МБ или коллекции с миллионами элементов). Из-за однопоточности Redis выполнение команды `DEL` для Big Key блокирует главный поток на сотни миллисекунд или секунд для высвобождения памяти в ОС, парализуя работу всего кластера.
    
- 🔍 **Как находить:**    
    Использовать утилиту `redis-cli --bigkeys` или команду `MEMORY USAGE key`.
    
- 🧹 **Как правильно удалять:**    
    Использовать команду **`UNLINK`** вместо `DEL`.
    
    `UNLINK` мгновенно удаляет ключ из пространства имен (он становится недоступен для клиентов), а физическое высвобождение тяжелой памяти из RAM передает асинхронному фоновому потоку (Background Thread).    

### 🚨 8. Cache Avalanche (Лавина) и Cache Penetration (Пробивание)

#### 🌊 Cache Avalanche (*Лавина кэша*)

- _Суть:_ Массовое и одномоментное протухание TTL у тысяч ключей, либо падение всего сервера кэша. Вся нагрузка мгновенно сваливается на базу данных, укладывая её.
    
- _Решение:_	    
    - Добавление случайного разброса (Jitter) к TTL (например, 10 минут $+$ случайные $0\text{--}60$ секунд).        
    - Использование отказоустойчивых кластеров Redis (Sentinel / Cluster).        

#### 🥊 Cache Penetration (Пробивание кэша)

- _Суть:_ Злоумышленник или сбоящий клиент запрашивает несуществующие ID (например, `id = -1`), которых нет ни в кэше, ни в БД. Каждый запрос проходит кэш насквозь и загружает БД.
    
- _Решение:_
	    
    - **Кэширование пустых значений (`null`):** Сохранение ключа со значением `null` и коротким TTL (1–2 минуты).
        
    - **Фильтр Блума (Bloom Filter):** Вероятностная структура данных перед кэшем, которая со $100\%$ гарантией отвечает, если элемента **точно нет** в системе, не доводя запрос до БД.        

### 🧱 9. Cache Breakdown и Cache Stampede (Thundering Herd)

- 🎯 **Суть проблемы:**
    
    Один ультра-популярный («горячий») ключ протухает по TTL. В эту же миллисекунду сотни параллельных запросов одновременно получают Cache Miss и разом идут в БД пересчитывать эти данные, генерируя аномальный пик нагрузки (Thundering Herd).
    
- 🛡️ **Способы решения:**
    
    - **Мьютексы / Блокировки (Mutex Locking):** Первый запрос, получивший Cache Miss, захватывает распределенный замок (`SETNX`), рассчитывает значение из БД и пишет в кэш. Остальные запросы ждут освобождения замка и читают готовое значение из кэша.
        
    - **Мягкое устаревание (Logical Expiration / Soft TTL):** Данные сохраняются в кэше без жесткого TTL в Redis. Внутрь JSON-объекта зашивается логическое время протухания. Если запрос видит, что логический TTL истек, он отдаёт клиенту текущие старые данные, а в фоновом потоке асинхронно отправляет запрос в БД на обновление.        

### 💳 10. Транзакции в Redis (MULTI, EXEC, WATCH)

- 🛠️ **Команды:**
	    
    - `MULTI` — начало блока транзакции.
        
    - `WATCH key` — оптимистичная блокировка ключа (если ключ изменился до `EXEC`, транзакция отменится).
        
    - `EXEC` — последовательное выполнение всех накопленных команд.
        
    - `DISCARD` — сброс команд блока.
    
- 🛑 **Почему НЕТ полноценного Rollback:**
    
    Все команды внутри `MULTI` накапливаются в очередь и исполняются строго по очереди.
	    
    1. Синтаксические ошибки отсекаются на этапе накопительной проверки.
        
    2. Ошибки времени исполнения (например, попытка сделать `INCR` на типе List) проигнорируются, а остальные команды транзакции **всё равно выполняятся**.
        
    3. Redis спроектирован для максимальной производительности. Поддержка механики отката транзакций существенно усложнила и замедлила бы базовый движок.        

### 📜 11. Lua-скрипты в Redis

- 🎯 **Зачем нужны:**    
    Для переноса комплексной бизнес-логики на сторону сервера Redis и исключения сетевых задержек (Network RTT).
    
- ⚛️ **Как обеспечивают атомарность:**    
    Redis исполняет весь Lua-скрипт **атомарно в главном потоке**. Во время выполнения скрипта никакие другие команды от других клиентов не могут вклиниться и быть исполнены.
    
- 🛠️ **Вызов:** `EVAL` или `EVALSHA` (вызов по предзагруженному SHA1-хэшу скрипта для экономии сетевого трафика).    

### 🏛️ 12. Схемы масштабирования: Master-Replica, Sentinel, Cluster

- 🔄 **Master-Replica:**
	    
    - Асинхронная репликация с одной Master-ноды (запись) на несколько Replica-нод (чтение).
        
    - _Минус:_ Нет автоматического переключения при падении мастера (No Auto-Failover).
    
- 🛡️ **Redis Sentinel:**
	    
    - Система мониторинга и обеспечения высокой доступности (HA).
        
    - Ансамбль из Sentinel-узлов следит за состоянием Master и автоматически подгоняет одну из реплик до мастера при сбое основного узла, обновляя конфигурацию клиентов.
    
- 🧩 **Redis Cluster:**
	    
    - Полноценное горизонтальное шардирование и высокая доступность.
        
    - Данные распределяются по **16384 хэш-слотам (Hash Slots)**. Номер слота рассчитывается как `CRC16(key) % 16384`. Слой серверов автоматически маршрутизирует запросы на нужный шард.        

### 📡 13. Pub/Sub vs Redis Streams

- 📢 **Pub/Sub (Издатель-Подписчик):**
	    
    - Паттерн «выстрелил и забыл» (Fire and Forget).
        
    - **Нет персистентности:** Данные не сохраняются на диск. Если консюмер был оффлайн в момент отправки, он потеряет сообщение навсегда.
        
    - Нет подтверждения доставки (`ACK`) и групп обработки.
    
- 🌊 **Redis Streams:**
	    
    - Персистентная структура данных (append-only log).
        
    - Поддерживает историю сообщений, группы потребителей (Consumer Groups), отслеживание прочитанных смещений, явное подтверждение обработки (`XACK`) и повторную вычитку зависших сообщений (`XPENDING` / `XCLAIM`).        

### 🔒 14. Распределенные блокировки (Distributed Lock) и Redisson

- ⚠️ **Проблема `SETNX + TTL` в лоб:**
    
    Команда `SET key uuid NX PX 30000` атомарна, но если бизнес-задача выполняется дольше 30 секунд, блокировка протухнет. Друбой узел захватит замок, а первый узел по завершении удалит **чужую** блокировку!
    
- 🐕 **Механизм Watchdog (Redisson):**
    
    Библиотека Redisson захватывает замок через Lua-скрипт с UUID и ID потока. Запускается фоновый фоновый поток (**Watchdog**), который каждые 10 секунд продлевает TTL блокировки (пока жива бизнес-задача).
    
- 🏰 **Алгоритм Redlock:**
    
    Алгоритм распределенной блокировки для защиты от сбоев в кластере из $N$ независимых Master-узлов. Блокировка считается захваченной, если замок удалось взять на большинстве узлов ($N/2 + 1$) за ограниченное время.    

### 🔌 15. Java-клиенты: Jedis vs Lettuce vs Redisson

- 🔌 **Jedis:**
	    
    - Синхронный, блокирующий клиент.
        
    - **Не является потокобезопасным.** Требует обязательного использования тяжелого пула соединений `JedisPool` для параллельной работы.
    
- 🥬 **Lettuce:**
	    
    - Асинхронный и реактивный клиент на базе Netty.
        
    - **Потокобезопасен.** Позволяет множеству потоков использовать одно общее соединение. Является стандартом по умолчанию в Spring Boot.
    
- 🔴 **Redisson:**
	    
    - Высокоуровневый фреймворк поверх Redis. Предоставляет привычные Java-структуры данных (`RLock`, `RMap`, `RQueue`, `RAtomicLong`), абстрагируя разработчика от низкоуровневых команд Redis.        

### 🍃 16. Интеграция со Spring Boot (Spring Data Redis)

- 🎯 **Аннотация `@Cacheable`:**
	    
    Оборачивает метод в AOP-прокси. Перехватывает вызов, запрашивает `CacheManager`. При попадании (Hit) возвращает результат из Redis, при промахе (Miss) исполняет метод и сохраняет результат в Redis.
    
- ⏱️ **Настройка TTL:**
	    
    Задается через конфигурационный класс `RedisCacheManagerBuilderCustomizer` или `RedisCacheConfiguration` отдельно для каждого имени кэша.
    
- ⚙️ **Выбор Сериализатора:**
	    
    - **`JdkSerializationRedisSerializer` (Дефолт):** Бинарный формат Java. Нечитаемый, раздутый по размеру, имеет проблемы с уязвимостями десериализации.
        
    - **`StringRedisSerializer`:** Простая кодировка строк.
        
    - **`GenericJackson2JsonRedisSerializer`:** Сохраняет данные в читаемом JSON-формате и записывает метаданные классов (`@class`) для корректного восстановления типов при обратном чтении.        

### 🚦 17. Реализация Rate Limiter в Redis

- 🪟 **Sliding Window Logs (Забор по временному окну на базе ZSet):**
	    
    - Каждый запрос добавляется в Sorted Set (`ZADD`), где Score и Value — текущий timestamp в миллисекундах.
        
    - Удаляются старые записи за пределами окна: `ZREMRANGEBYSCORE key 0 (currentTime - windowSize)`.
        
    - Считается количество оставшихся элементов через `ZCARD`. Если их больше лимита — запрос отклоняется.
        
    - Все шаги оборачиваются в один атомарный Lua-скрипт.
    
- 🪣 **Token Bucket (Корзина токенов):**
	    
    - Реализуется через Lua-скрипт или модуль `RedisCell`. Хранит текущее количество токенов и timestamp последнего обновления. При запросе рассчитывает досыпку токенов за прошедшее время и списывает один токен.

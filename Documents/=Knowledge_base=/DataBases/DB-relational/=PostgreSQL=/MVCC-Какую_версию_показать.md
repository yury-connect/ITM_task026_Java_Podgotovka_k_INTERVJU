# За счёт чего PostgreSQL понимает, какую версию показать?

---
### ⚙️ 1. Что такое `xmin` и `xmax`?
В PostgreSQL таблицы хранятся в виде неупорядоченного файла — **Heap (Куча)**. Каждая версия строки (кортеж / tuple) содержит не только пользовательские данные, но и служебный заголовок (`HeapTupleHeader`).

В этом заголовке фиксируются два ключевых системных поля:

- 🟢 **`xmin` (Transaction ID Insert):**
	    
    - Идентификатор транзакции (XID), которая **создала (вставила)** эту конкретную версию строки.
        
    - Устанавливается один раз при `INSERT` и больше никогда не меняется для данного кортежа.
    
- 🔴 **`xmax` (Transaction ID Delete/Update):**
	    
    - Идентификатор транзакции (XID), которая **удалила или обновила** эту версию строки.
        
    - Если строка активна и никто не пытался её удалить, `xmax` равен **`0`**.
        
    - _(Примечание: `xmax` также используется при пессимистических блокировках, например `SELECT FOR UPDATE`, но с определенными служебными флагами)._

### 🔄 2. Как `xmin` и `xmax` меняются при INSERT, UPDATE и DELETE

В архитектуре MVCC данные **никогда не перетираются на месте**. Любое изменение создаёт новую физическую версию строки.

- ➕ **`INSERT`:**	    
    - Создаётся новая строка в Heap.
    - `xmin` = ID текущей транзакции.
    - `xmax` = `0`.
    
- ❌ **`DELETE`:**	    
    - Физическая строка **не удаляется** с диска!
    - В существующей строке поле `xmax` меняется с `0` на ID текущей транзакции, выполняющей `DELETE`.
    
- 🔄 **`UPDATE` (это комбинация DELETE + INSERT):
    - У старой версии строки поле `xmax` становится равным ID текущей транзакции (она помечается "умершей" для будущих транзакций).
    - Рядом в Heap создаётся абсолютно новая версия строки, у которой `xmin` равен ID той же самой текущей транзакции, а `xmax` равен `0`.

### 📸 3. За счёт чего PostgreSQL понимает, какую версию показать? (Снимки данных — Snapshots)

Само по себе наличие `xmin` и `xmax` не даёт ответа на вопрос, видна ли строка конкретному читателю. Для этого Postgres использует **Снимок данных (Snapshot)** и статус транзакций из **CLOG (Commit Log / `pg_xact`)**.

#### Что содержит Снимок (*Snapshot*):
Когда ваша транзакция делает `SELECT`, Postgres формирует для неё снимок состояния всей СУБД. В снимок входят 3 ключевых параметра:
	
1. **`xmin` снимка:** ID самой старой транзакции, которая всё ещё была активна в момент создания снимка. Все транзакции с ID меньше этого значения гарантированно либо завершились, либо отменились.
    
2. **`xmax` снимка:** Первый ещё не присвоенный ID транзакции (все транзакции с ID $\ge$ `xmax` начались _после_ создания нашего снимка, поэтому их изменения нам строго не видны).
    
3. **`xip_list` (список активных XID):** Список ID всех транзакций, которые были **активны (ещё не закоммичены)** в точный момент снятия снимка между `xmin` и `xmax`.

### 🔍 4. Алгоритм проверки видимости (Visibility Check)
Когда Postgres читает строку из таблицы, он берет значения `xmin` / `xmax` из её заголовка и сверяет их со **снимком текущей сессии** и статусом транзакции в **CLOG**:

#### Шаг 1: Проверка `xmin` (Кто создал строку?)
	
- Если `xmin` совпадает с ID **нашей же** транзакции $\rightarrow$ строка **ВИДНА** (мы видим свои собственные изменения).
    
- Если `xmin` находится в `xip_list` (была активна во время снятия снимка) или равен еще не начавшейся транзакции $\rightarrow$ строка **НЕВИДНА** (создатель еще не закоммитился).
    
- Если `xmin` закоммичен в CLOG и был завершен **ДО** нашего снимка $\rightarrow$ переходим к проверке `xmax`.

#### Шаг 2: Проверка `xmax` (Кто удалил строку?)
	
- Если `xmax` равен `0` $\rightarrow$ строка **ВИДНА** (её никто не удалял).
    
- Если `xmax` совпадает с ID **нашей же** транзакции $\rightarrow$ строка **НЕВИДНА** (мы сами её только что удалили).
    
- Если `xmax` находится в `xip_list` или принадлежит незакоммиченной транзакции $\rightarrow$ строка **ВИДНА** (удаление еще не закоммичено другими, они нам не мешают).
    
- Если `xmax` закоммичен в CLOG **ДО** нашего снимка $\rightarrow$ строка **НЕВИДНА** (её успешно удалили в прошлом).

### 💡 Пример на пальцах

Представим 3 транзакции:
	
- Транзакция №100 вставляет строку `("User", xmin=100, xmax=0)` и делает `COMMIT`.
    
- Транзакция №101 делает `UPDATE` этой строки: старой строке ставит `xmax=101`, а новой пишет `(xmin=101, xmax=0)`. Но **НЕ коммитится**!
    
- Транзакция №102 делает `SELECT`. Ей создается снимок, где транзакция №101 числится в `xip_list` (как активная).

**Что увидит Транзакция №102?**
	
1. Читает **старую** версию: `xmin=100` (закоммичен, ок), `xmax=101` (транзакция 101 еще в `xip_list` $\rightarrow$ удаление не закоммичено!). Postgres берет эту строку и отдаёт читателю!
    
2. Читает **новую** версию: `xmin=101` (транзакция 101 в `xip_list` $\rightarrow$ вставка не закоммичена!). Postgres игнорирует эту строку.

В результате Транзакция №102 увидит старое корректное значение, совершенно не блокируя параллельный `UPDATE` от Транзакции №101.

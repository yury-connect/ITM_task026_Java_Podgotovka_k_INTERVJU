# Как работает WAL в **PostgreSQL**

В **PostgreSQL** механизм WAL (Write-Ahead Logging) используется для обеспечения транзакционности (свойство ACID — Durability), быстрого восстановления после сбоев и работы репликации.

---
### Архитектура и основные компоненты:

Для работы *WAL* в *PostgreSQL* выделены три ключевые зоны:
- **WAL Buffers**: область в оперативной памяти (*часть Shared Buffers*), куда временно записываются логи изменений.
- **WAL Files**: сегменты на диске (*по умолчанию размером 16 МБ*), хранящиеся в директории `pg_wal`.
- **LSN (*Log Sequence Number*)**: уникальный 64-битный идентификатор (*смещение*) каждой записи в журнале, используемый для синхронизации страниц данных и WAL.

---
### Пошаговый алгоритм работы

Когда клиент выполняет транзакцию (например, `UPDATE`), PostgreSQL действует следующим образом:

```text
[Транзакция] ──> [Изменение страницы в RAM] ──> [Запись в WAL Buffers]
                                                        │
[Подтверждение клиенту] <── [Сброс WAL на диск (fsync)] <─┘
```

1. **Модификация в памяти**: Сервер находит нужную страницу данных в оперативной памяти (`Shared Buffers`) и изменяет её. Страница становится «грязной» (*dirty page*).
2. **Запись в буфер WAL**: Описание сделанного изменения формируется в виде WAL-записи и помещается в `WAL Buffers` в RAM. На измененную страницу данных записывается текущий `LSN`.
3. **Фиксация (COMMIT)**: Когда клиент отправляет команду `COMMIT`, PostgreSQL **не записывает** измененную страницу данных на диск сразу. Вместо этого он принудительно сбрасывает (вызывает `fsync`) накопленный кусок `WAL Buffers` в файл на диске (`pg_wal`).
4. **Ответ клиенту**: Как только WAL-запись гарантированно сохранена на диске, транзакция считается успешной, и клиент получает подтверждение.

> **Главное правило:** Страница данных из памяти ни в коем случае не может быть сброшена на диск фоновыми процессами до тех пор, пока соответствующая ей WAL-запись с тем же или более ранним `LSN` не окажется на диске.

---
### Что происходит при чекпоинтах (*Checkpoints*)

Чтобы файлы WAL не росли бесконечно, существует процесс **Checkpoint** (*контрольная точка*):

- Фоновый процесс `checkpointer` периодически или по достижении лимита объема данных сбрасывает все накопившиеся «грязные» страницы из RAM на диск.
- После успешной записи страниц на диск фиксируется точка, до которой все данные гарантированно сохранены.
- Файлы WAL, созданные _до_ этой контрольной точки, становятся ненужными для восстановления и могут быть удалены или переиспользованы (рециклированы).

---
### Как WAL спасает при сбоях (*Crash Recovery*)

Если сервер внезапно потерял питание, данные из оперативной памяти стерлись, а на диске остались устаревшие таблицы и файлы WAL. При перезапуске PostgreSQL:

1. Читает последнюю успешную контрольную точку (Checkpoint).
2. Начинает сканировать WAL-файлы, созданные _после_ этой точки.
3. Метод **REDO**: Сервер последовательно применяет все операции из WAL к файлам данных. Если `LSN` на странице данных меньше, чем `LSN` в WAL-записи, изменение накатывается заново.

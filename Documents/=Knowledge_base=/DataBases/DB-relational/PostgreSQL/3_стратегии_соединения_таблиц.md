В PostgreSQL есть **три базовые стратегии соединения** (*внутренние джойны*).  
Запомни их как **Nested Loop**, **Hash Join** и **Merge Join**.

---
## 🔄 1. **Nested Loop Join** (*Вложенные циклы*)

#### **Как работает (*алгоритм*):**  
Это самый простой и интуитивный способ. Для каждой строки из первой таблицы («*внешний цикл*») PostgreSQL пробегается по **всем** строкам второй таблицы («*внутренний цикл*») и ищет совпадения по условию.
#### **Визуализация (*эмодзи*):**  
🚶‍♂️➡️🏃 (*Один чел-к идет по списку, а для каждого пункта бегает по второму списку*).
#### **Когда используется:**
- Одна из таблиц **очень маленькая** (*например, 10 строк*).    
- Есть **индекс** на второй таблице по полю соединения (тог*да это называется "Index Nested Loop" и работает очень быстро*).    
- Обычно это **самый медленный** способ для больших таблиц, так как сложность O(N * M) (*произведение размеров таблиц*).    
#### **Пример из жизни:**  
У тебя есть список из 5 клиентов. Ты берешь первого клиента, идешь в таблицу заказов, ищешь все его заказы (*по индексу*), возвращаешься, берешь второго и т.д.

---
## 🧲 2. **Hash Join** (*Хеш-соединение*)

#### **Как работает (*алгоритм*):**  
PostgreSQL берет **меньшую** таблицу, читает её целиком и строит в оперативной памяти **хеш-таблицу** (*как словарь: `ключ = поле соединения`, `значение = вся строка`*). Затем он читает **большую** таблицу, и для каждой её строки делает быстрый поиск *(O(1))* в этой хеш-таблице. Если находит совпадение — возвращает строку.
#### **Визуализация (*эмодзи*):**  
📚➡️🔍 (*Ты берешь маленькую книгу, составляешь по ней быстрый указатель (оглавление), а потом просто сверяешь по нему большую книгу*).
#### **Когда используется:**
- Одна таблица **помещается в память** (у PostgreSQL есть параметр `work_mem`).    
- Нет индекса на поле соединения (*или он не эффективен*).    
- Таблицы большие, но одна существенно меньше другой.    
#### **Пример из жизни:**  
Тебе нужно связать 1000 заказов с 1 миллионом товаров. Ты берешь 1000 заказов, кладешь их в «быстрый словарь» по `product_id`, а потом просто пробегаешь по миллиону товаров и моментально находишь нужный заказ.

---
## 🗂️ 3. **Merge Join** (*Сортировочное соединение*)

#### **Как работает (алгоритм):**  
PostgreSQL сортирует **обе** таблицы по полю соединения (или использует уже готовую сортировку из индекса). Затем он берет два отсортированных списка и проходит по ним **одновременно**, как две застежки-молнии, сравнивая и сдвигая указатели вперед.
#### **Визуализация (эмодзи):**  
🤝 (Два отсортированных списка идут параллельно, как два бегуна на соседних дорожках, и синхронно сравниваются).
#### **Когда используется:**
- Обе таблицы **огромные** (хеш не влезает в память).    
- Данные **уже отсортированы** (например, через `ORDER BY` или есть индекс, дающий сортировку).    
- Обычно чуть медленнее хеш-джойна, но зато **не жрет память**, так как читает данные с диска потоками.    
#### **Пример из жизни:**  
У тебя два отсортированных списка учеников по фамилиям. Ты берешь два списка и двигаешься по ним одновременно: сравниваешь фамилии и, если они совпадают, берешь пару, если фамилия в первом списке меньше, сдвигаешь первый список, и наоборот.

---
### 🏁 Как PostgreSQL выбирает стратегию? (Кратко)

Оптимизатор смотрит на **статистику таблиц** (количество строк, размеры), наличие **индексов** и доступный объем **оперативной памяти**. Он оценивает стоимость каждой стратегии и выбирает самую дешевую.

- Для **маленьких** таблиц или индексированных связей (один-ко-многим) → **Nested Loop**.
    
- Для **больших** несортированных таблиц, где одна помещается в память → **Hash Join**.
    
- Для **очень больших** таблиц, где данных так много, что они не лезут в память, или они уже отсортированы → **Merge Join**.    

### 🎯 Главное для собеседования

На вопрос "Какие стратегии соединения есть у PostgreSQL?" отвечай так:

> _"В PostgreSQL есть три стратегии: Nested Loop (вложенные циклы) — для маленьких таблиц или индексов, Hash Join — когда одна таблица помещается в память и нет индексов, и Merge Join — для больших объемов, когда данные уже отсортированы. Оптимизатор выбирает автоматически, исходя из статистики и размера `work_mem`."_ 🚀

В PostgreSQL выбор правильного индекса — один из главных инструментов оптимизации производительности на уровне базы данных. В своей практике я обычно разделяю тему индексов на две составляющие: 
- **физические структуры данных (алгоритмы)** и 
- **архитектурные шаблоны применения (конструкции)**.

Давайте разберем обе категории.

---
## 1. Алгоритмы и структуры индексов в PostgreSQL

### 🌲 **B-Tree** (*Balanced Tree*)
	
- **Что это:** Сбалансированное дерево поиска. Алгоритм по умолчанию в PostgreSQL.
    
- **Как работает:** Данные хранятся в отсортированном виде в древовидной структуре. Сложность поиска, вставки и удаления — $O(\log N)$.
    
- **Для чего применяется:**
	    
    - Операции сравнения: `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`.
        
    - Сортировки (`ORDER BY`) и поиск по префиксу (`LIKE 'abc%'`).
    
- **Когда выберу:** В 90% стандартных задач (поиск по `id`, `email`, датам, статусам).

### 🔑 Hash
	
- **Что это:** Хеш-таблица.
    
- **Как работает:** Вычисляет хеш-код ключа и отображает его на физический адрес страницы. Поиск за $O(1)$.
    
- **Для чего применяется:** **Только** для оператора точного равенства (`=`). Не поддерживает диапазоны и сортировки.
    
- **Когда выберу:** Редко. Может быть чуточку меньше и быстрее B-Tree на очень длинных строках при поиске строго по `=`, но на практике B-Tree универсальнее. Начиная с PG 10 Hash-индексы стали WAL-logged (*безопасными при сбоях*), но B-Tree все еще остается дефолтом.

### 🌳 GiST (*Generalized Search Tree*)
	
- **Что это:** Обобщенное дерево поиска. Это не просто структура, а фреймворк для построения иерархических индексов с настраиваемым оператором поиска.
    
- **Как работает:** Позволяет инкапсулировать данные в иерархические фигуры (*например, ограничивающие прямоугольники для гео-точек*).
    
- **Для чего применяется:**
	    
    - Геопространственные данные (*PostGIS*).
        
    - Поиск пересечений диапазонов (*операторы `&&`, `@>`, `<@` для `tsrange`, `int4range`*).
        
    - Полнотекстовый поиск (*хотя для него чаще берут GIN*).
    
- **Когда выберу:** Когда нужно проверить, пересекаются ли интервалы времени бронирования или находится ли точка внутри полигона.

### 📑 GIN (*Generalized Inverted Index*)
	
- **Что это:** Инвертированный индекс («*индекс наизнанку*»).
    
- **Как работает:** Разбивает составной элемент (*массив, JSONB, документ*) на отдельные элементы (*лексемы/ключи*) и для каждого элемента хранит список ID строк (*posting list/tree*), где он встречается.
    
- **Для чего применяется:**
	    
    - Поиск внутри `JSONB` (операторы `@>`, `?`, `?&`).
        
    - Работа с массивами (`int[]`, `text[]`).
        
    - Полнотекстовый поиск (`tsvector`).
    
- **Когда выберу:** Запросы вида «найти все заказы, где в `JSONB` атрибутах есть `"category": "electronics"`».
    
- **Нюанс:** GIN очень быстр на чтение, но имеет высокий overhead при записи (`INSERT`/`UPDATE`), так как требует обновления множества элементов в индексе.

### 📦 **BRIN** (*Block Range Index*)
	
- **Что это:** Индекс по диапазонам блоков.
    
- **Как работает:** Не хранит ссылки на каждую строку. Он разбивает таблицу на группы дисковых страниц (по умолчанию 128 блоков) и хранит только **минимальное и максимальное значение** для каждой группы.
    
- **Для чего применяется:** Для гигантских таблиц (*десятки и сотни гигабайт/терабайт*), где данные физически упорядочены на диске в порядке добавления.
    
- **Когда выберу:** Логи, временные ряды (*Time-Series*) с полем `created_at` или таблицы аудита.
    
- **Плюсы:** Занимает считанные мегабайты памяти там, где B-Tree весил бы десятки гигабайт.

## 2. **Виды** применения индексов (*Конструкции*)
	
### 🔗 **Composite Index** (*Составной индекс*)
	
Индекс, построенный сразу по нескольким колонкам.
```SQL
CREATE INDEX idx_users_status_created ON users (status, created_at);
```
	
- **Правило левого префикса:** Запрос обязан использовать самую левую колонку (`status`), иначе B-Tree не сможет выполнить быстрый поиск по дереву.
    
- **Практика:** Колонки с точным совпадением (`=`) и высокой селективностью ставлю левее, а диапазонные условия (`>`, `<`) — в самый конец.

### 🎯 **Partial Index** (*Частичный индекс*)
	
Индекс, содержащий не все строки таблицы, а только те, что подпадают под условие `WHERE`.
```SQL
CREATE INDEX idx_active_orders ON orders (created_at) WHERE status = 'PENDING';
```
	
- **Плюсы:** Экономит память и дисковый ввод-вывод. Не замедляет `INSERT`/`UPDATE` для строк, которые не подходят под условие `WHERE`.
    
- **Применение:** Индексирование неотработанных тасок, необработанных заказов или признака `is_deleted = false`.

### 🔍 **Functional** / **Expression Index** (*По выражению*)
	
Индекс, построенный на результате функции или выражения над колонкой.
```SQL
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
```
	
- **Зачем нужен:** Обычный индекс на `email` проигнорируется, если в SQL написан вызов `WHERE LOWER(email) = 'test@example.com'`. Индекс по выражению позволяет СУБД сопоставить вычисленное значение с деревом индекса.

### 🛡️ **Covering Index** (*Покрывающий индекс*)
	
Индекс, который содержит все поля, запрашиваемые в `SELECT` и `WHERE`, позволяя выполнить **Index Only Scan** без обращения к основной таблице (Heap).
```SQL
CREATE INDEX idx_users_lookup ON users (department_id) INCLUDE (name, salary);
```
	
- **Секция `INCLUDE`:** Позволяет добавить дополнительные колонки в листовые узлы B-Tree без добавления их в само дерево поиска. Это не раздувает глубину дерева, но экономит дисковый I/O при чтении.

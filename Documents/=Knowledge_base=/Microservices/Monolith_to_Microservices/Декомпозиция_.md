## Декомпозиция монолита на микросервисы — пошаговый план

---
### Шаг 1. Понять, зачем это нужно

Прежде чем резать монолит, ответьте на вопрос: **какую проблему вы решаете?** Микросервисы — не серебряная пуля. Они решают одни проблемы (*масштабирование, независимые деплои, изоляция команд*), но создают другие (*сетевые задержки, распределённые транзакции, сложность отладки*).

Если монолит работает и команда справляется — возможно, дробить не нужно.

---
### Шаг 2. Определить границы (*bounded contexts*)

Самый важный этап. Нужно найти **логические границы** в предметной области. Обычно используют подход **Domain-Driven Design (DDD)**:
	
- **Bounded Context** — область, где определённая модель данных имеет чёткое значение. Например, «Заказы», «Платежи», «Склад», «Пользователи».
    
- **Ubiquitous Language** — единый язык внутри контекста. В «Заказах» слово «товар» означает одно, в «Складе» — другое.    

**Как найти границы на практике:**
- Посмотреть на структуру базы данных: какие таблицы связаны, какие нет.    
- Посмотреть на команды: какие группы разработчиков над чем работают.    
- Посмотреть на бизнес-процессы: где заканчивается один процесс и начинается другой.    

**Признак правильно найденной границы:** если два сервиса нужно менять одновременно при каждом изменении требований — граница проведена неверно.

---
### Шаг 3. Выбрать стратегию декомпозиции

Есть несколько подходов:
	
- **По бизнес-возможностям (*business capabilities*)** — самый распространённый. Выделяем сервисы по функциям: управление заказами, управление каталогом, управление пользователями, платежи.
	
- **По поддоменам (*DDD*)** — выделяем core-домены (*то, что даёт бизнесу ценность*), supporting-домены (*вспомогательные*) и generic-домены (*типовые, можно купить готовое*).
	
- **По транзакциям** — там, где нужна атомарность, оставляем в одном сервисе. Границы транзакций — естественные границы сервисов.
	
- **По командам (*Conway's Law*)** — если у вас есть команда «Платежи» и команда «Каталог», логично сделать два сервиса.

---
### Шаг 4. Начать с монолита (Strangler Fig)

Не переписывайте всё сразу. Используйте паттерн **Strangler Fig** (удушающий фикус):
1. Монолит продолжает работать.    
2. Рядом появляется новый сервис.    
3. Постепенно куски логики переносятся из монолита в сервис.    
4. Когда всё перенесено — монолит удаляется.    

**Как это делается технически:**
- Перед монолитом ставится API Gateway или прокси.    
- Запросы на новую функциональность идут в новый сервис.    
- Запросы на старую — в монолит.    
- Постепенно переключаете трафик.    

---
### Шаг 5. Разделить базу данных

Самое сложное. В монолите одна база — все таблицы связаны. В микросервисах **у каждого сервиса своя база**.

**Проблемы:**
- JOIN-ы между таблицами разных сервисов становятся невозможны.    
- Транзакции, которые раньше были атомарными, теперь распределённые.    
- Данные дублируются (например, имя пользователя нужно и в «Заказах», и в «Профиле»).    

**Решения:**
- **API Composition** — сервис-агрегатор собирает данные из нескольких сервисов.    
- **CQRS** — разделение на чтение и запись, отдельные модели для каждого.    
- **Saga** — распределённые транзакции через последовательность локальных транзакций с компенсациями.    
- **Event Sourcing** — хранение событий вместо состояния, другие сервисы подписываются на изменения.    

---
### Шаг 6. Организовать взаимодействие

Сервисы должны общаться. Варианты:

**Синхронно (REST, gRPC)** — просто, но создаёт жёсткую связность. Если один сервис упал — другой тоже может упасть.

**Асинхронно (Kafka, RabbitMQ)** — сервисы обмениваются событиями через брокер. Более гибко, но сложнее отлаживать. Используйте, когда важна отказоустойчивость и слабая связность.

**Гибрид** — синхронно там, где нужен немедленный ответ (например, проверка баланса), асинхронно — где можно подождать (отправка email, обновление статистики).

---
### Шаг 7. Инфраструктура

Микросервисы требуют инфраструктуры:
	
- **Service Discovery** — сервисы должны находить друг друга (Eureka, Consul, K8s DNS). 
- **API Gateway** — единая точка входа (Spring Cloud Gateway, Kong, Nginx).    
- **Config Server** — централизованная конфигурация (Spring Cloud Config, Consul).    
- **Distributed Tracing** — отслеживание запросов через все сервисы (Jaeger, Zipkin).    
- **Centralized Logging** — сбор логов в одном месте (ELK, Grafana Loki).    
- **Metrics & Monitoring** — Prometheus + Grafana.    
- **Circuit Breaker** — защита от каскадных отказов (Resilience4j, Hystrix).    

---
### Шаг 8. Организационные изменения

Микросервисы — это не только технология, но и **организация**:

- **Автономные команды** — каждая команда владеет своим сервисом от кода до продакшена.
    
- **DevOps-культура** — разработчики сами деплоят и мониторят.
    
- **CI/CD** — каждый сервис имеет свой пайплайн.
    
- **Контракты** — API между сервисами версионируются и тестируются.    

---
### Типичные ошибки

**Слишком мелкие сервисы** — если сервис делает одну операцию, это не микросервис, а распределённый монолит. Сервис должен быть достаточно крупным, чтобы владеть своим доменом.

**Общая база данных** — если два сервиса читают и пишут в одну базу, это не микросервисы. Это распределённый монолит.

**Синхронные вызовы везде** — цепочка из 10 синхронных вызовов упадёт, если хотя бы один сервис недоступен.

**Игнорирование данных** — распределённые транзакции сложны. Если данные должны быть согласованы атомарно — возможно, это один сервис.

---
### Пошаговый план для реального проекта

1. **Выделить 1–2 пилотных сервиса** — не начинайте с критичных. Выберите что-то изолированное.
    
2. **Построить инфраструктуру** — Gateway, Service Discovery, мониторинг.
    
3. **Разделить базу** — начать с отдельной схемы для пилота.
    
4. **Настроить CI/CD** — отдельный пайплайн для сервиса.
    
5. **Переключить трафик** — через API Gateway.
    
6. **Оценить результат** — стало ли лучше? Если нет — остановиться.
    
7. **Повторять** — постепенно переносить следующие куски.    

---
### Итог

Декомпозиция монолита — это **эволюционный процесс**, а не революция. Начинайте с границ (DDD), используйте Strangler Fig, разделяйте базы, стройте инфраструктуру, меняйте организацию. И помните: **микросервисы — это компромисс**. Они решают проблемы масштабирования и изоляции команд, но создают сложность распределённых систем.

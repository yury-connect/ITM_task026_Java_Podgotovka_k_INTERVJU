# Гексагональная архитектура

Гексагональная архитектура (также известная как **«Порты и Адаптеры»**) — это архитектурный паттерн, который изолирует вашу бизнес-логику (домен) от технических деталей (баз данных, веб-фреймворков, внешних API). Главная цель — сделать так, чтобы ядро приложения ничего не знало о том, как оно используется и какие технологии его окружают.

Для Java-разработчика это означает, что вы можете менять Spring, базу данных или способ общения с клиентом, не переписывая бизнес-правила.

### 🎯 Основная идея: Инверсия зависимостей

В классической слоистой архитектуре (Controller -> Service -> Repository) бизнес-логика зависит от инфраструктуры. В гексагональной всё наоборот: **зависимости всегда направлены внутрь, к домену** .[](https://www.sfeir.dev/back/architectures-spring-boot-tour-dhorizon/#1)[](https://blog.ndepend.com/hexagonal-architecture/?source=post_page-----db338833d6c2----------------------#respond)

Домен определяет **интерфейсы (порты)**, которые ему нужны для работы (например, «сохрани заказ», «отправь уведомление»). Инфраструктура (адаптеры) реализует эти интерфейсы. Домен не знает, _как_ это будет сделано — через JPA, MongoDB или отправку в Kafka.

### 🧩 Ключевые компоненты

1. **Домен (Ядро)**: Чистая бизнес-логика. Здесь нет аннотаций Spring (`@Service`, `@Entity`), нет зависимостей на JPA или Jackson. Это просто Java-код (POJO).
    
2. **Порты (Ports)**: Интерфейсы, которые определяют, как внешний мир может общаться с доменом.
	    
    - **Входящие (Driving) порты**: Описывают, _что_ приложение умеет делать (Use Cases). Например, `OrderService` с методом `createOrder()`.
        
    - **Исходящие (Driven) порты**: Описывают, _что_ приложению нужно от внешнего мира. Например, `OrderRepository` (сохранить) или `NotificationSender` (отправить).
    
3. **Адаптеры (Adapters)**: Реализации портов, которые связывают домен с технологиями.
	    
    - **Входящие адаптеры**: REST-контроллеры, Kafka-консьюмеры, CLI. Они вызывают методы домена.
        
    - **Исходящие адаптеры**: Реализации репозиториев (JPA, JDBC), клиенты внешних API, продюсеры Kafka. Они реализуют интерфейсы портов.

### 💻 Как это выглядит в коде (Java)

Вместо того чтобы `OrderService` напрямую зависел от `OrderRepositoryJpa`, вы делаете так:

**1. Домен и Порт (Исходящий):**
```java
// Это чистый интерфейс в пакете domain
public interface OrderRepository {
    void save(Order order);
}
// Домен использует этот интерфейс
public class OrderService {
    private final OrderRepository repository; // Зависимость от абстракции
    public void createOrder(Order order) {
        // бизнес-логика
        repository.save(order);
    }
}
```

**2. Адаптер (Инфраструктура):**
```java
// Это реализация в пакете infrastructure
@Repository
public class JpaOrderRepository implements OrderRepository {
    private final JpaOrderDao dao; // Spring Data JPA
    @Override
    public void save(Order order) {
        dao.save(order);
    }
}
```

### ⚖️ Плюсы и минусы (для собеседования)

**Плюсы:**
- **Тестируемость**: Домен можно тестировать юнит-тестами без поднятия Spring-контекста или базы данных (используя моки для портов) .[](https://www.sfeir.dev/back/architectures-spring-boot-tour-dhorizon/#1)
    
- **Гибкость**: Замена базы данных или фреймворка затрагивает только адаптер, а не бизнес-логику .[](https://www.sfeir.dev/back/architectures-spring-boot-tour-dhorizon/#1)
    
- **Явные границы**: Четко видно, где заканчивается «чистый» код и начинается «грязная» инфраструктура.    

**Минусы:**
- **Избыточность**: Появляется много интерфейсов и классов-мапперов (нужно конвертировать DTO в доменные объекты и обратно) .[](https://www.sfeir.dev/back/architectures-spring-boot-tour-dhorizon/#1)
    
- **Overkill**: Для простого CRUD-приложения это лишняя сложность .[](https://stackoverflow.com/revisions/ac80775e-efc7-48c5-911e-2b98bf5293fc/view-source#1)

### 🆚 Отличие от Onion / Clean Architecture

На практике гексагональная, луковая (Onion) и чистая (Clean) архитектуры очень похожи. Главное отличие в акцентах:

- **Гексагональная** фокусируется на симметрии «входов» и «выходов» (порты и адаптеры) .[](https://blog.ndepend.com/hexagonal-architecture/?source=post_page-----db338833d6c2----------------------#respond)
    
- **Onion/Clean** больше говорят о слоях и правилах зависимостей (Use Cases, Entities). В реальном коде разница между ними минимальна и часто зависит от словаря, который использует команда .[](https://www.sfeir.dev/back/architectures-spring-boot-tour-dhorizon/#1)[](http://www.predic8.de/hexagonal-clean-onion-vergleich-fazit.htm)

### 📌 Итог для Java-разработчика

Если вы используете Spring Boot, гексагональная архитектура — это способ сказать: «Мой `@RestController` и мой `@Repository` — это просто адаптеры. Они не содержат бизнес-логики. Бизнес-логика — это отдельный класс, который ничего не знает о Spring». Это усложняет структуру проекта, но дает долгосрочную поддерживаемость, если домен сложный.

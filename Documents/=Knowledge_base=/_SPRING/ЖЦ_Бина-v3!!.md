# 🌱 Жизненный цикл Spring Bean

Удобная схема:
**Создание контекста → BeanDefinition → PostProcessor'ы → Instantiation → DI → Initialization → Proxy → Ready → Destruction**

---
## 🚀 *ЭТАП 0*. Запуск приложения и создание Context

Создаётся `ApplicationContext`:
- `AnnotationConfigApplicationContext`
- в Spring Boot — `SpringApplication`

При запуске контекста вызывается `refresh()`, который запускает основной механизм создания и настройки бинов.

---
## 🔎 *ФАЗА 1*. ОБНАРУЖЕНИЕ И ОПРЕДЕЛЕНИЕ БИНОВ

### 1.1. 🔍 Сканирование
Spring сканирует указ-е пакеты через `@ComponentScan` и находит классы, помеченные:
- `@Component`
- `@Service`
- `@Repository`
- `@Controller`
- `@Configuration`

### 1.2. 📐 Создание `BeanDefinition`
Для каждого найденного компонента создаётся **`BeanDefinition`** — условный «чертёж» будущего бина:
- класс;
- scope;
- зависимости;
- constructor;
- `init-method`;
- `destroy-method`;
- lazy и т.д.

### 1.3. 🗃️ Регистрация
`BeanDefinition` регистрируются в `BeanDefinitionRegistry`.

> ⚠️ Не стоит говорить на собеседовании, что `BeanDefinitionRegistry` — это просто `ConcurrentHashMap`. Это **интерфейс**. В конкретной реализации *Spring* действительно используется внутренняя *map*-структура, но такая формулировка слишком упрощает архитектуру.

---
## ⚙️ *ФАЗА 2*. ОБРАБОТКА `BeanFactoryPostProcessor`

Здесь Spring ещё работает в основном с **описаниями бинов**, а не с самими объектами.

### 2.1. 🛠️ `BeanDefinitionRegistryPostProcessor`
Он выполняется **до** обычного `BeanFactoryPostProcessor`. Может:
- добавлять `BeanDefinition`;
- изменять существующие;
- удалять их.

### 2.2. 📝 `BeanFactoryPostProcessor`
Обрабатывает и модифицирует зарегистрированные `BeanDefinition`.

💡 Главное запомнить:
> **`BeanFactoryPostProcessor` работает с чертежами (`BeanDefinition`), а не с готовыми объектами.**

---
## 🏗️ ФАЗА 3. СОЗДАНИЕ ЭКЗЕМПЛЯРА

Spring создаёт экземпляр бина (**Instantiation**).   
Для обычных *singleton*-бинов это происходит при `refresh()` в процессе предварительного создания singleton'ов.   
Если бин `@Lazy` — его создание откладывается до первого обращения к нему.   

### 🧱 Что происходит?
Вызывается:
- конструктор;  
- либо *factory method* (`@Bean`);  
- либо другой способ создания экземпляра.  

После этого **экземпляр объекта уже существует**, но его зависимости ещё могут быть не внедрены.

### 👨‍🔧 Как выбирается конструктор?
Если есть несколько конструкторов, Spring использует правила выбора конструктора; в частности, явно указанный `@Autowired` конструктор имеет приоритет.

> ⚠️ Если констр-р **один**, в соврем. верс. Spring `@Autowired` для него не требуется.

---
## 🔌 ФАЗА 4. DEPENDENCY INJECTION / POPULATION

Spring заполняет зависимости и свойства бина:
```java
@Autowired
private UserRepository repository;
```

или через:
- **constructor** injection;
- **setter** injection;
- **field** injection;
- `@Resource`;
- `@Value`;
- конфигурацию XML и т.д.

После этой стадии зависимости бина в основном готовы к использованию.

---
## 🔄 ФАЗА 5. ИНИЦИАЛИЗАЦИЯ

Здесь находится самая важная последовательность.

### 5.1. 🧩 `Aware`-интерфейсы
Spring передаёт бину необходимую инфраструктуру:
- `BeanNameAware` → имя бина;
- `BeanFactoryAware` → `BeanFactory`;
- `ApplicationContextAware` → `ApplicationContext`;
- `ResourceLoaderAware` → `ResourceLoader`;
- и другие.

### 5.2. ⏮️ `BeanPostProcessor. postProcessBeforeInitialization()`
Spring вызывает:
```
postProcessBeforeInitialization(bean, beanName)
```

Здесь работают соответствующие `BeanPostProcessor`.

⚠️ **Важное исправление исходного текста:**
`@Autowired` **не следует описывать как обработку именно на этом этапе**.

Внедрение зависимостей через `@Autowired` выполняется раньше, во время **property population**, посредством `AutowiredAnnotationBeanPostProcessor`.

А `@PostConstruct` вызывается уже **внутри initialization phase**, после `postProcessBeforeInitialization`.

### 5.3. 🚦 Методы инициализации
Последовательность:
### 1️⃣ `@PostConstruct`
Вызывается метод:
```java
@PostConstruct
public void init() {
}
```
Здесь зависимости уже внедрены.

### 2️⃣ `InitializingBean.afterPropertiesSet()`
Если бин реализует:
```java
InitializingBean
```

вызывается:
```java
afterPropertiesSet();
```

### 3️⃣ `init-method`
Если указан пользовательский метод:
```java
@Bean(initMethod = "init")
```
или:
```xml
<bean init-method="init">
```
он вызывается следующим.

### 🎯 Итого
```text
@PostConstruct
      ↓
afterPropertiesSet()
      ↓
init-method
```

---
### 5.4. ⏭️ `BeanPostProcessor.postProcessAfterInitialization()`
После init-методов Spring вызывает:
```
postProcessAfterInitialization(bean, beanName)
```

Именно здесь **часто создаётся или возвращается proxy**, например для:
- `@Transactional`
- `@Async`
- `@Cacheable`
- Spring AOP

То есть:
```
оригинальный Bean
      ↓
postProcessAfterInitialization
      ↓
Proxy (если нужен)
```

> ⚠️ Не все прокси обязательно создаются именно одним и тем же *BPP* или строго только на этом этапе, поэтому на собеседовании лучше говорить **«часто/обычно здесь»**, а не «все прокси создаются здесь».

---
## 🟢 ФАЗА 6. READY FOR USE

Бин полностью создан и инициализирован.
Для singleton он помещается в кэш singleton-объектов:
```text
DefaultSingletonBeanRegistry
        ↓
singletonObjects
```

Теперь при обычном обращении:
```java
applicationContext.getBean(UserService.class);
```
Spring возвращает уже готовый объект/прокси.

---
## 💀 ФАЗА 7. УНИЧТОЖЕНИЕ

Когда `ApplicationContext` корректно закрывается:
```java
context.close();
```

Spring уничтожает управляемые singleton-бин'ы.

### Порядок:
```text
@PreDestroy
    ↓
DisposableBean.destroy()
    ↓
destroy-method
```

### 1️⃣ `@PreDestroy`
```java
@PreDestroy
public void cleanup() {
}
```

Обычно:
- закрытие ресурсов;
- остановка потоков;
- освобождение соединений.

### 2️⃣ `DisposableBean.destroy()`
Если бин реализует:
```java
DisposableBean
```

вызывается:
```java
destroy();
```

### 3️⃣ `destroy-method`
Например:
```java
@Bean(destroyMethod = "close")
```
или XML-конфигурация.

Spring также умеет автоматически распознавать методы вроде `close()` / `shutdown()` в определённых случаях конфигурации.

---
# ⚠️ Важное исключение

При:
```text
kill -9
```
процесс завершается **немедленно**.
*Spring* не получает возможности корректно закрыть `ApplicationContext`.

Поэтому:
```text
@PreDestroy
destroy()
destroy-method
```

**не гарантируются**.
Не следует использовать их для критически важных операций, которые обязательно должны быть выполнены.

# 🧠 Вся схема в 30 секунд

```
🚀 ApplicationContext
        ↓
🔎 BeanDefinition
        ↓
⚙️ BeanFactoryPostProcessor
        ↓
🏗️ Instantiation
        ↓
🔌 Dependency Injection
        ↓
🧩 Aware
        ↓
⏮️ postProcessBeforeInitialization
        ↓
1️⃣ @PostConstruct
        ↓
2️⃣ afterPropertiesSet()
        ↓
3️⃣ init-method
        ↓
⏭️ postProcessAfterInitialization
        ↓
🎭 Proxy (если нужен)
        ↓
🟢 READY
        ↓
🗃️ singletonObjects
        ↓
        ...
        ↓
💀 @PreDestroy
        ↓
💀 destroy()
        ↓
💀 destroy-method
```

### 🎯 Самое важное для Middle
Если попросят **«расскажи lifecycle Spring Bean»**, уверенно пройти эту цепочку:
> **BeanDefinition → BeanFactoryPostProcessor → Instantiation → Dependency Injection → Aware → BPP before → `@PostConstruct` → `afterPropertiesSet` → init-method → BPP after → Proxy → Ready → Destruction.**

И отдельно помнить **три ловушки**, на которых часто проверяют Middle:
1. 🔥 `BeanFactoryPostProcessor` работает с **`BeanDefinition`**, а не с экземпляром.
2. 🔥 `@Autowired` выполняется на этапе **population**, а не в `postProcessBeforeInitialization`.
3. 🔥 `@PostConstruct` вызывается **до `postProcessAfterInitialization`**, поэтому при обычном proxy-based AOP вызов `@Transactional`-метода через `this.method()` внутри `@PostConstruct` **не проходит через proxy** и транзакция таким способом не откроется.

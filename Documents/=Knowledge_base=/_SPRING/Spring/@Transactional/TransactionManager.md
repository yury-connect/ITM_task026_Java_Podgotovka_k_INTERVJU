**TransactionManager** в Java — это ==центральный интерфейс или компонент для управления транзакциями (*началом, коммитом и откатом*), который обеспечивает целостность данных при работе с базами данных==. [1](https://javarush.com/quests/lectures/ru.javarush.java.spring.lecture.level06.lecture02), [2](https://struchkov.dev/blog/ru/transaction-jdbc-and-spring-boot/)

### Главные задачи
- **Начало транзакции**: запуск последовательности операций.
- **Фиксация (*Commit*)**: сохранение изменений в БД, если всё прошло успешно.
- **Откат (*Rollback*)**: отмена всех изменений, если произошла ошибка.

### Как это работает (*на примере Spring*)
В экосистеме *Spring Framework* базовым интерфейсом является **`PlatformTransactionManager`** (*или просто `TransactionManager`*). [1](https://struchkov.dev/blog/ru/transaction-jdbc-and-spring-boot/)

- Он скрывает детали работы конкретной технологии доступа к данным (JDBC, JPA/Hibernate, JTA).
- Часто используется вместе с аннотацией `@Transactional`, которая автоматически оборачивает методы в транзакции с помощью механизмов Spring AOP. [1](https://javarush.com/quests/lectures/ru.javarush.java.spring.lecture.level06.lecture03), [2](https://sobes.tech/az/bank/java/3b48a432-ed13-466d-857f-70e09d98a749)

### Разница между **декларативным** и **программным** 
управлением транзакциями заключается в том, **где и как описывается логика** управления (*начало, коммит и откат транзакции*) — в самом коде или через конфигурацию (*аннотации*).

Ниже приведено прямое сравнение этих подходов на примере *Spring Framework*.

| Критерий                         | Декларативное <br>управление                                | Программное <br>управление                                                               |
| -------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **Как <br>реализуется**          | Через аннотацию `@Transactional` или XML.                   | Через код с помощью `TransactionTemplate` <br>или напрямую `PlatformTransactionManager`. |
| **Где <br>находится <br>логика** | Отделена от бизнес-логики (использует Spring AOP / прокси). | Внедрена прямо внутрь <br>методов бизнес-логики.                                         |
| **Гибкость / <br>Гранулярность** | На уровне метода (минимальная единица — целый метод).       | На уровне отдельных строк кода (высокая точность).                                       |
| **Удобство <br>чтения кода**     | Высокое (код чистый, бизнес-логика не загромождена).        | Более низкое (код перегружен инфраструктурным кодом).                                    |
| **Простота <br>тестирования**    | Требует поднятия Spring-контекста для работы прокси.        | Проще тестировать в unit-тестах с помощью mock-объектов.                                 |

Подробный разбор подходов

1. Декларативное управление (`@Transactional`)

Это самый популярный подход. Вы просто говорите фреймворку: «Этот метод должен быть транзакционным», а Spring сам создаёт прокси-объект, который перехватывает вызов, открывает транзакцию, выполняет ваш код и закрывает её.

- **Пример кода:**
```java
@Service
public class UserService {

    @Transactional
    public void createUser(User user) {
        userRepository.save(user);
        notificationService.sendWelcomeEmail(user);
        // Если здесь выбросится RuntimeException, Spring автоматически сделает rollback
    }
}
```

Используйте код с осторожностью.

- **Плюсы:** Максимальная чистота кода (принцип SOLID — разделение обязанностей).
- **Минусы:** Сложнее контролировать транзакцию внутри метода. Нельзя сделать транзакционной только половину метода (для этого придётся дробить код на отдельные методы и сервисы).

2. Программное управление

Вы явно управляете жизненным циклом транзакции в коде. Чаще всего для этого используется `TransactionTemplate`.

- **Пример кода:**
```java
@Service
public class UserService {

    @Autowired
    private TransactionTemplate transactionTemplate;

    public void createUser(User user) {
        // Код до транзакции (например, валидация)
        validateUser(user);

        // Сама транзакция
        transactionTemplate.execute(status -> {
            userRepository.save(user);
            return null;
        });

        // Код после транзакции (например, отправка тяжелой метрики)
        metricService.sendData();
    }
}
```

Используйте код с осторожностью.

- **Плюсы:** Полный контроль. Вы можете запустить транзакцию ровно на две строчки кода посреди огромного метода, что полезно для оптимизации (чтобы не держать соединение с БД слишком долго).
- **Минусы:** Код становится «грязным», бизнес-логика смешивается с инфраструктурной логикой управления данными.

---

Что выбирать на практике?

- **В 95% случаев выбирают декларативный подход (`@Transactional`)**. Он покрывает стандартные требования веб-приложений и микросервисов.
- **Программный подход** используют в редких специфических сценариях: при работе со сложной логикой, где критически важно сократить время удержания транзакции, или при интеграции со сторонними легаси-системами, где поведение АОП-прокси непредсказуемо.

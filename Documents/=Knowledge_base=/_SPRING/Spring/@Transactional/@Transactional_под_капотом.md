### ⚙️ Как работает @Transactional под капотом

Spring управляет транзакциями декларативно с помощью **Spring AOP (Aspect-Oriented Programming)** и динамических прокси.

#### **Алгоритм работы (Шаг за шагом):**
	
1. 🎭 При старте контекста Spring видит класс с аннотацией `@Transactional` и создает вокруг него **Proxy-объект** (*CGLIB или JDK Dynamic Proxy*).
    
2. 📥 При вызове метода запрос попадает в этот прокси (`TransactionInterceptor`).
    
3. 🔌 Прокси обращается к `TransactionManager`, который берет физическое `Connection` из пула (HikariCP), отключает автокоммит (`connection.setAutoCommit(false)`) и привязывает соединение к текущему потоку через **`ThreadLocal`**.
    
4. ⚙️ Выполняется реальный бизнес-код вашего метода.
    
5. ✅ Если метод завершился успешно, прокси делает **`connection.commit()`**.
    
6. 💥 Если метод выбросил исключение (по умолчанию только `RuntimeException` или `Error`), прокси делает **`connection.rollback()`**.
    
7. 🧹 Соединение очищается и возвращается в Connection Pool.

---
### 🎛️ Главные атрибуты аннотации

- ⏪ **`rollbackFor` / `noRollbackFor`:**
    
    - По умолчанию Spring откатывает транзакцию **только при Unchecked Exceptions** (`RuntimeException` и `Error`).
        
    - Если метод выбросит проверяемое исключение (например, `IOException`), транзакция **будет закоммичена**!
        
    - _Лучшая практика:_ Явно указывать `@Transactional(rollbackFor = Exception.class)`.
        
- 🌿 **`readOnly = true`:**
    
    - Подсказка для оптимизации.
        
    - В Hibernate она **отключает Dirty Checking** (не создаются снапшоты объектов, экономится RAM) и предотвращает случайные `UPDATE`/`INSERT`. На уровне БД может перевести сессию в режим _Read-Only_.
        
- ⏱️ **`timeout`:**
    
    - Максимальное время выполнения транзакции (в секундах). Если метод выполняется дольше — выбрасывается `TransactionTimedOutException` и транзакция откатывается.
        
- 🛡️ **`isolation`:**
    
    - Задает уровень изоляции БД для данной транзакции (`READ_COMMITTED`, `REPEATABLE_READ`, `SERIALIZABLE`).
        
- 🔗 **`propagation`:**
    
    - Задает логику распространения транзакций при вызове одного транзакционного метода из другого (`REQUIRED`, `REQUIRES_NEW`, `NESTED` и т.д.).

### 💣 Подводные камни и частые ошибки *(Топ вопросов на собеседовании)*

1. 🪞 **Вызов внутри одного класса (Self-Invocation):**
	    
    - _Проблема:_ Если обычный метод `methodA()` вызывает внутри себя `@Transactional methodB()`, **транзакция не откроется**.
        
    - _Причина:_ Вызов идет напрямую через `this`, в обход AOP-прокси.
        
    - _Решение:_ Вынести `methodB` в другой сервис, использовать программный `TransactionTemplate` или получить текущий прокси через `AopContext.currentProxy()`.
    
2. 🔒 **Приватные методы:**
	    
    - Аннотация `@Transactional` работает **только на `public` методах**!
        
    - Если повесить её над `private` или `protected` методом, Spring просто проигнорирует её без ошибок компиляции (*CGLIB-прокси не может переопределить приватный метод*). Транзакция не сработает.
    
3. 🪤 **Поглощение исключений (Try-Catch):**
	    
    - _Проблема:_ Вы обернули код внутри `@Transactional` метода в блок `try-catch(Exception e) { log.error(e); }` и не пробросили исключение дальше.
        
    - _Итог:_ Прокси получит успешное завершение метода (раз исключение поглощено) и сделает **`COMMIT`** вместо ожидаемого `ROLLBACK`.
    
4. 🧵 **Многопоточность внутри транзакции:**
	    
    - _Проблема:_ Если внутри `@Transactional` метода вы создаете новый поток (через `CompletableFuture` или `@Async`), этот **новый поток не будет участвовать в транзакции**.
        
    - _Причина:_ Контекст транзакции привязан к текущему потоку через `ThreadLocal`. Новый поток получит свое собственное новое соединение без активной транзакции старого потока.

## 1. Records vs Generics (Java Core)

#### Record vs Обычный класс
- **Record (Java 16+)** 📦 — неизменяемый (immutable) прозрачный переносчик данных (Value Object / DTO).
    
- **Сгенерированный под капотом байт-код:**
    - Все поля становятся `private final`.
    - Класс автоматически объявляется `final` и наследуется от `java.lang.Record`.
    - Создается канонический конструктор, инициализирующий все поля.
    - Генерируются методы доступа (геттеры) **без префикса `get`** (`id()`, `name()`), а также `equals()`, `hashCode()` и `toString()`.

#### Ограничения Record
	
- 🧬 **Наследование:**
    - Record **не может наследоваться** от других классов (так как уже неявно наследует `java.lang.Record`).
    - Record является `final` — **от него нельзя наследоваться**.
    - Record **может реализовывать интерфейсы**.
    
- 🧱 **Поля:**    
    - Нельзя добавлять дополнительные instance-поля (все поля описываются строго в заголовке `record User(Long id, String name)`).        
    - Можно объявлять `static`-поля и константы.
    
- 🏗️ **Конструкторы:**    
    - Любой кастомный дополнительный конструктор **обязан первично вызывать канонический конструктор** через `this(...)`.
    - **Компактный конструктор (Compact Constructor):** Используется для валидации и трансформации аргументов без дублирования присвоения полей:
```Java
public record User(Long id, String email) {
	public User {
		Objects.requireNonNull(email, "Email mandatory");
		email = email.toLowerCase();
	}
}
```

#### Дженерики: Generics, Wildcards и Стирание типов

- 🧹 **Стирание типов (Type Erasure):**    
    - Механизм обратной совместимости. Во время компиляции компилятор проверяет типизацию, а затем **стирает сведения о дженериках** в байт-коде.
    - `<T>` заменяется на upper bound (например, `Object` или `Number`).
    - Специфичные сведения обобщений не доступны в runtime (нельзя сделать `new T()` или `instanceof List<String>`).
    
- 📐 **Bounded Types (Ограниченные типы):**
    - `<T Number extends>` — ограничение сверху. Параметром может быть только `Number` или его наследники.
    
- 🔀 **Wildcards (`?`) и Принцип PECS:**
    - **`? extends T` (Upper Bounded Wildcard / Producer Extends):**        
        - Коллекция выступает **производителем** (Producer). Из неё можно только **читать** элементы как тип `T`.            
        - _Ограничение:_ Записывать в неё новые элементы нельзя (кроме `null`), так как компилятор не знает точный конкретный подтип.
        
    - **`? super T` (Lower Bounded Wildcard / Consumer Super):**
        - Коллекция выступает **потребителем** (Consumer). В неё можно **записывать** элементы типа `T` или его подтипов.            
        - _Ограничение:_ Читать из неё можно только как объект типа `Object`, так как точный уровень предка неизвестен.

## 2. CompletableFuture и асинхронность

#### Future vs CompletableFuture

- ⏳ **`Future` (Java 5):**    
    - Представляет результат асинхронной задачи.        
    - **Блокирующий API:** Получение результата требует вызова `get()`, который блокирует текущий поток до завершения задачи.        
    - Не поддерживает колбэки, ручное завершение, композицию нескольких `Future` или отслеживание ошибок.
    
- 🚀 **`CompletableFuture` (Java 8+):**
    - Реализует `Future` и `CompletionStage`.        
    - **Событийно-ориентированный неблокирующий API:** Позволяет строить асинхронные графы выполнения на колбэках (`thenApply`, `thenAccept`).        
    - Можно завершать принудительно из любого потока (`completableFuture.complete(value)`).

#### Обработка исключений в цепочке

- 🛑 **`exceptionally(fn)`:**
    - Перехватывает исключение из предыдущих шагов и возвращает дефолтное/резервное значение (Fallback).
    
- 🔄 **`handle((result, ex) -> ...)`:**
    - Вызывается **всегда** (и при успехе, и при ошибке).
    - Принимает и результат, и исключение. Позволяет трансформировать любой исход в новый результат.
    
- 🔔 **`whenComplete((result, ex) -> ...)`:**
    - Вызывается всегда для выполнения побочных эффектов (логирование, метрики).
    - **Не изменяет** итоговый результат или исключение, передавая их дальше по цепочке.

#### Параллельные запросы и объединение

- 🔗 **`CompletableFuture.allOf(f1, f2, f3)`:**
    - Принимает массив `CompletableFuture`.
    - Возвращает `CompletableFuture<Void>`, который завершается только тогда, когда **все переданные задачи успешно или со сбоем завершены**.
    
- ⚡ **`CompletableFuture.anyOf(f1, f2, f3)`:**
    - Возвращает `CompletableFuture<Object>`, который завершается, как только **любая первая задача из списка вернет результат**.

#### Блокирующие vs Неблокирующие операции

- 🛑 **Блокирующие вызовы:**
    - `future.get()` (выбрасывает проверяемые `InterruptedException`, `ExecutionException`).
    - `future.join()` (выбрасывает непроверяемый `CompletionException`).
    - Переводят текущий поток в состояние ожидания (`WAITING`), просаживая пропускную способность.
    
- ⚡ **Неблокирующие цепочки:**
    - `thenApply()` / `thenApplyAsync()` — трансформацией результата ($1 \rightarrow 1$).
    - `thenCompose()` / `thenComposeAsync()` — связывание зависимых асинхронных операций (аналог `flatMap`).
    - `thenCombine()` — параллельное выполнение двух независимых `CompletableFuture` и обработка их совместного результата.        
    - Выполняются асинхронно в пуле по умолчанию `ForkJoinPool.commonPool()` или в кастомном переданном `Executor`.

### 3. ООП и SOLID

#### Базовые принципы ООП

- 🔒 **Инкапсуляция:** Сокрытие внутренних деталей реализации класса и ограничение прямого доступа к его состоянию за счет модификаторов доступа (`private`) и предоставления контролируемого API.
    
- 🧬 **Наследование:** Возможность создания нового класса на основе существующего с унаследованием его полей и методов для повторного использования кода.
    
- 🎭 **Полиморфизм:** Способность объектов с одинаковой сигнатурой выполнять разную реализацию. Позволяет использовать один интерфейс для разных типов данных (через переопределение методов `@Override` или перегрузку).
    
- 🧱 **Абстракция:** Выделение только главных характеристик объекта, значимых для текущей системы, с отбрасыванием нерелевантных деталей.

#### Принципы SOLID

- 🎯 **Single Responsibility Principle (SRP — Принцип единственной ответственности):**
    - У класса должна быть **ровно одна причина для изменения**. Класс должен решать ровно одну задачу бизнеса или инфраструктуры.
    
- 🔓 **Open/Closed Principle (OCP — Принцип открытости/закрытости):**
    - Программные сущности должны быть **открыты для расширения, но закрыты для изменения**. Новая функциональность добавляется путем создания новых классов/интерфейсов, а не правкой старого работающего кода.
    
- 📐 **Liskov Substitution Principle (LSP — Принцип подстановки Барбары Лисков):**
    - Объекты дочерних классов должны быть взаимозаменяемы с объектами базовых классов, **не ломая логику и контракты системы**.
    
- ✂️ **Interface Segregation Principle (ISP — Принцип разделения интерфейса):**
    - Клиенты не должны зависеть от методов, которые они не используют. Лучше создавать много специализированных узких интерфейсов, чем один «всемогущий» жирный интерфейс.
    
- 🔄 **Dependency Inversion Principle (DIP — Принцип инверсии зависимостей):**
    - Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба типа модулей должны зависеть от **абстракций** (интерфейсов).

### 4. Микросервисная архитектура

#### SAGA (Распределенные транзакции)

Паттерн управляет транзакциями сквозь несколько микросервисов с помощью цепочки локальных транзакций с обязательным объявлением **компенсирующих транзакций** на случай сбоев.

- 🎺 **Choreography (Хореография):**
    - Сервисы обмениваются событиями асинхронно через шину (Kafka). Каждое событие триггерит следующий локальный шаг.
    - _Плюсы:_ Нет единой точки отказа, слабая связанность.
    - _Минусы:_ Сложность отслеживания цепи событий, риск циклических зависимостей.
    
- 🎼 **Orchestration (Оркестрация):**
    - Центральный сервис-оркестратор (Camunda, Temporal) берет на себя управление потоком: сам вызывает сервисы по REST/gRPC и инициирует шаги отмены при ошибках.
    - _Плюсы:_ Простой контроль и мониторинг графа выполнения.
    - _Минусы:_ Риск превращения оркестратора в «монолит» и единую точку отказа.

#### Circuit Breaker (Resilience4j)
Паттерн защиты системы от каскадных сбоев при вызове нестабильных внешних сервисов.

- **Состояния:**
    - `CLOSED` (Замкнут): Все вызовы пролетают во внешний сервис.
    - `OPEN` (Разомкнут): Внешний сервис считается недоступным. Запросы отсекаются мгновенно (Fast Fail) без выполнения сетевого вызова, возвращая `fallback`-значение.
    - `HALF_OPEN` (Полуразомкнут): По истечении таймаута пропускается тестовая порция запросов. При успехе замок закрывается в `CLOSED`, при ошибке — снова открывается в `OPEN`.

#### Service Discovery (Eureka / Consul)
Динамический реестр сетевых адресов (IP и портов) экземпляров сервисов.
- Экземпляры сервисов при старте регистрируются в Service Discovery и периодически отправляют heartbeat.
- Другие сервисы запрашивают у Discovery актуальный список IP-адресов для балансировки вызовов.

#### API Gateway (Spring Cloud Gateway / Kong)
Единая точка входа (Reverse Proxy) для внешних клиентов системы:
- Маршрутизация (Routing) входящих HTTP-запросов на внутренние микросервисы.
- Аутентификация и проверка JWT-токенов на внешнем периметре.
- Ограничение частоты запросов (Rate Limiting) и защита от DDOS.
- Централизованная обработка CORS и TLS-терминация.

#### Шардирование и Масштабирование
- 📈 **Вертикальное vs Горизонтальное масштабирование:**    
    - _Vertical Scaling (Scale Up):_ Увеличение вычислительных ресурсов одного сервера (CPU, RAM, SSD).        
    - _Horizontal Scaling (Scale Out):_ Добавление новых экземпляров приложений или серверов БД в единый кластер.
- 🧩 **Шардирование (Sharding):**
    - Горизонтальное разделение крупных таблиц БД по разным физическим серверам/узлам на основе ключа шардирования (**Shard Key**).

### 5. Hibernate / JPA

#### Проблема N+1

- **Суть:** Происходит, когда при выборке $N$ родительских сущностей JPA для каждой из них делает отдельный дополнительный SQL-запрос для вычитки связанной коллекции или сущности. В итоге вместо 1 запроса база выполняет $N+1$ запрос.
    
- **Способы решения:**
    1. Использование `JOIN FETCH` в JPQL/HQL.        
    2. Аннотация **`@EntityGraph`** (директивная указание графа загрузки).        
    3. Настройка `@Fetch(FetchMode.SUBSELECT)` или `batch_size` (загрузка связанных данных батчами через `IN (...)`).        
    4. Переход на DTO-проекции (Spring Data JPA Projections).
#### LAZY vs EAGER Загрузка
- 💤 **`FetchType.LAZY` (Ленивая):**
    - Данные связанной сущности не вычитываются из БД сразу. JPA генерирует CGLIB-прокси. Запрос в БД уходит только при первом вызове геттера.
    - _Дефолт для:_ `@OneToMany`, `@ManyToMany`.
    
- ⚡ **`FetchType.EAGER` (Быстрая):**
    - Связанная сущность загружается мгновенно вместе с родителем (за один `JOIN` или мгновенным вторым SQL-запросом).
    - _Дефолт для:_ `@ManyToOne`, `@OneToOne`.
    - _Опасность:_ Нарушает производительность, провоцирует проблему N+1 и декартово произведение.

#### Состояния жизненного цикла Entity
- 🐣 **Transient:** Объект создан через `new`, не имеет ID в БД, не отслеживается Hibernate.
    
- 🟢 **Persistent (Managed):** Объект связан с сессией `EntityManager` и имеет ID. Изменения его полей отслеживаются механизмом **Dirty Checking**.
    
- 🟡 **Detached:** Объект имеет ID, но его сессия закрыта. Изменения полей не транслируются в БД.
    
- 🔴 **Removed:** Объект помечен на удаление вызовом `em.remove()`, удалится из БД при сбросе сессии (`flush`).

#### Уровни кэширования в Hibernate

- 📦 **L1 Cache (Первый уровень):**
    - Кэш на уровне **сессии (`EntityManager`)**. Включен всегда, его нельзя отключить.
    - Хранит ссылки на все `Managed`-объекты в рамках одной текущей транзакции/сессии. Гарантирует повторное чтение без запросов к БД внутри сессии.
    
- 🏭 **L2 Cache (Второй уровень):**
    - Кэш на уровне **`SessionFactory`**. Разделяется между всеми сессиями и потоками приложения.
    - Отключен по умолчанию. Требует внешнего провайдера (Ehcache, Hazelcast). Хранит данные в разобранном виде (дегидрированные кортежи).
    
- 🔍 **Query Cache (Кэш запросов):**    
    - Хранит результаты вызовов JPQL/HQL запросов (массив ключей/ID сущностей). Работает строго в связке с L2-кэшем.

#### Dirty Checking (Отслеживание грязных состояний)
- **Механика:** При загрузке сущности в состояние `Managed` Hibernate создает в памяти скрытый базовый снапшот (копию) всех её полей.
- При вызове `flush()` или коммите транзакции Hibernate сравнивает текущее состояние объекта с его исходным снапшотом.
- Если найдены расхождения, Hibernate **автоматически генерирует и выполняет SQL-запрос `UPDATE`** для измененных полей без необходимости явного вызова каких-либо методов сохранения.

## 📦 SAGA, Circuit Breaker, Service Discovery, API Gateway, шардирование и масштабирование

### SAGA (распределённые транзакции)

**Проблема:** В микросервисах одна бизнес-операция (например, оформление заказа) затрагивает несколько сервисов, каждый со своей БД. Классические ACID-транзакции тут не работают — нет единого координатора, который мог бы откатить всё сразу.

**Решение:** SAGA разбивает распределённую транзакцию на **цепочку локальных транзакций**. Каждая локальная транзакция выполняется в своём сервисе и коммитится. Если на каком-то шаге происходит сбой — запускаются **компенсирующие транзакции**, которые «откатывают» уже выполненные шаги в обратном порядке.

**Две реализации:**

1. **Хореография (Choreography):** Сервисы обмениваются событиями. Каждый сервис слушает событие, выполняет свою часть и публикует следующее. Нет центрального координатора.
    
2. **Оркестрация (Orchestration):** Есть **центральный координатор (Orchestrator)**, который вызывает сервисы по очереди и решает, что делать при сбое. Сервисы не знают друг о друге.
    

### Circuit Breaker (Предохранитель)

**Проблема:** Если один сервис начинает тормозить или падать, вызывающий его сервис будет ждать, тратить потоки и ресурсы. По цепочке это может привести к **каскадному отказу (雪崩效应 / avalanche effect)**[](https://raw.githubusercontent.com/Snailclimb/JavaGuide/main/docs/high-availability/fallback-and-circuit-breaker.md#1#1).

**Решение:** Circuit Breaker оборачивает вызов к внешнему сервису и отслеживает результаты. Если количество ошибок превышает порог — он **разрывает цепь** и сразу возвращает ошибку или fallback, не пытаясь вызвать проблемный сервис.

**Три состояния:**

- **Closed:** Всё нормально, запросы проходят, ошибки считаются.
    
- **Open:** Слишком много ошибок — все запросы сразу отклоняются. Ждём `waitDurationInOpenState`.
    
- **Half-Open:** Пробуем пропустить несколько запросов. Если успешно — возвращаемся в Closed. Если снова ошибки — обратно в Open[](https://guosy.blog.csdn.net/article/details/147597605)[](https://raw.githubusercontent.com/Snailclimb/JavaGuide/refs/heads/main/docs/high-availability/fallback-and-circuit-breaker.md#1).
    

**Fallback:** Метод-«заглушка», который возвращает безопасное значение, когда цепь разомкнута. Важно: fallback не должен возвращать `null` (это вызовет NPE у клиента) и должен быть **быстрым и простым**[](https://raw.githubusercontent.com/Snailclimb/JavaGuide/main/docs/high-availability/fallback-and-circuit-breaker.md#1#1).

### Service Discovery (Обнаружение сервисов)

**Проблема:** В микросервисах экземпляры сервисов динамически создаются и умирают. Клиент не может знать фиксированные IP-адреса.

**Решение:** Есть **Service Registry** (Consul, Eureka, etcd, Zookeeper) — хранилище, где сервисы регистрируются при старте и удаляются при остановке[](https://developer.aliyun.com/article/1535031)[](https://www.kloia.com/service-discovery).

**Два паттерна:**

1. **Client-Side Discovery:** Клиент сам запрашивает реестр, получает список IP и сам выбирает, куда идти (своя логика балансировки). Пример: Netflix Eureka + Ribbon.
    
2. **Server-Side Discovery:** Клиент идёт на **Load Balancer / API Gateway**, который сам запрашивает реестр и маршрутизирует запрос. Клиент ничего не знает о реестре. Пример: Kubernetes Service, AWS ELB[](https://www.kloia.com/service-discovery)[](https://bbs.huaweicloud.com/blogs/458647#1).
    

### API Gateway

**Что это:** Единая точка входа для всех клиентов. Gateway принимает все запросы и маршрутизирует их к нужным сервисам.

**Зачем:** Скрывает внутреннюю структуру микросервисов, берёт на себя аутентификацию, rate limiting, логирование, CORS, circuit breaker. Клиенту не нужно знать про десятки сервисов — он общается только с Gateway.

### Шардирование и масштабирование

**Шардирование (Sharding):** Горизонтальное разделение данных по разным узлам. Каждый шард содержит часть данных (например, пользователи с ID 1-1000 — шард A, 1001-2000 — шард B). Решает проблему, когда данные не влезают на один сервер.

**Масштабирование:**

- **Вертикальное (Scale Up):** Увеличиваем мощность сервера (больше CPU, RAM). Просто, но имеет предел.
    
- **Горизонтальное (Scale Out):** Добавляем новые серверы. Сложнее (нужна синхронизация), но масштабируется почти бесконечно.

## 📦 Подготовка к пятнице

### 1. Когерентность кэшей (Cache Coherence)

**Что это:** Согласованность данных между несколькими кэшами (например, L1/L2 процессора или кэшами приложений).

**Проблема:** Если один поток изменил данные в своём кэше, а другой поток читает устаревшее значение из своего — получаем **stale data**.

**В Java:** `volatile` и `synchronized` обеспечивают **happens-before** — гарантию, что изменения одного потока будут видны другому.

**В распределённых системах:** Кэши на разных сервисах могут рассинхронизироваться. Решения: TTL, event-driven инвалидация, write-through/write-behind паттерны.

### 2. Виды синхронизаторов

**Semaphore:** Счётчик разрешений. Ограничивает количество потоков, одновременно работающих с ресурсом. `acquire()` забирает разрешение, `release()` возвращает[](https://wiki.rice.edu/confluence/download/attachments/55836943/comp322-s16-lec30-slides-v2.key.pdf?api=v2#1#1).

**CountDownLatch:** «Защёлка» с обратным отсчётом. Поток ждёт (`await()`), пока счётчик не дойдёт до нуля. Используется, когда нужно дождаться завершения N задач. **Одноразовый** — счётчик нельзя сбросить[](https://raw.githubusercontent.com/HabenChan/toBeBetterJavaer/60adeb865fbb6878f4f832745ee67106f85f8228/docs/thread/CountDownLatch.md#1).

**CyclicBarrier:** «Барьер», который ждёт, пока все потоки достигнут точки сбора. В отличие от CountDownLatch, **можно сбросить** (`reset()`) и использовать повторно[](https://raw.githubusercontent.com/HabenChan/toBeBetterJavaer/60adeb865fbb6878f4f832745ee67106f85f8228/docs/thread/CountDownLatch.md#1).

**Exchanger:** Обмен данными между двумя потоками. Оба потока блокируются, пока оба не вызовут `exchange()`[](https://raw.githubusercontent.com/HabenChan/toBeBetterJavaer/60adeb865fbb6878f4f832745ee67106f85f8228/docs/thread/CountDownLatch.md#1).

**Phaser:** Более гибкая версия CyclicBarrier с поддержкой динамического добавления/удаления участников.

### 3. Виды Executors

- **FixedThreadPool:** Фиксированное количество потоков. Очередь неограниченная.
    
- **CachedThreadPool:** Создаёт потоки по мере необходимости, переиспользует свободные (60 сек). Очередь — SynchronousQueue.
    
- **SingleThreadExecutor:** Один поток, последовательное выполнение.
    
- **ScheduledThreadPool:** Для отложенных и периодических задач.
    
- **WorkStealingPool:** На основе ForkJoinPool, воровство задач.
    
- **VirtualThreadPerTaskExecutor:** Для виртуальных потоков (Java 21+)[](https://ualberta.scholaris.ca/server/api/core/bitstreams/638816bf-717b-497a-af3c-512b0a418b6c/content#6#2)[](https://developer.aliyun.com/article/1726125#1).
    

### 4. CAS (Compare-And-Swap)

**Что это:** Атомарная инструкция процессора. «Сравни значение в памяти с ожидаемым. Если совпадает — замени на новое. Если нет — ничего не делай и верни текущее».

**Где используется:** `AtomicInteger`, `AtomicReference`, `ConcurrentHashMap`, `ReentrantLock` (внутри AQS).

**Почему быстрее synchronized:** Не блокирует поток — при неудаче просто повторяет попытку (spin-loop). Но при высокой конкуренции может впустую жечь CPU.

### 5. Потокобезопасные коллекции

**ConcurrentHashMap:** Сегментированная блокировка (или CAS для корзин). Не блокирует всю мапу при записи[](https://raw.githubusercontent.com/shivkumar98/OCP-Java-Examples/refs/heads/main/src/chapter_7/c_7_4_usingConcurrentCollections/README.md)[](https://raw.githubusercontent.com/Compile-N-Run/Compile-N-Run/refs/heads/main/docs/language/java/9-java-multithreading/6-java-concurrent-collections.mdx#1).

**CopyOnWriteArrayList:** При каждой записи создаётся новая копия массива. Чтение — без блокировок. Идеально для сценариев «много чтений, мало записей»[](https://raw.githubusercontent.com/Compile-N-Run/Compile-N-Run/refs/heads/main/docs/language/java/9-java-multithreading/6-java-concurrent-collections.mdx#1).

**BlockingQueue:** Очереди для producer-consumer. `put()` блокируется, если очередь полна, `take()` — если пуста. Реализации: ArrayBlockingQueue, LinkedBlockingQueue, PriorityBlockingQueue[](https://raw.githubusercontent.com/Compile-N-Run/Compile-N-Run/refs/heads/main/docs/language/java/9-java-multithreading/6-java-concurrent-collections.mdx#1).

**ConcurrentSkipListMap/Set:** Потокобезопасные отсортированные коллекции на основе skip list[](https://raw.githubusercontent.com/shivkumar98/OCP-Java-Examples/refs/heads/main/src/chapter_7/c_7_4_usingConcurrentCollections/README.md).

### 6. Thread Lock (локи)

**ReentrantLock:** Явная блокировка. Даёт `tryLock()` с таймаутом, `lockInterruptibly()`, честный режим. Требует `unlock()` в `finally`.

**ReentrantReadWriteLock:** Разделяет чтение (shared) и запись (exclusive). Много читателей или один писатель[](https://www.cleverence.com/articles/oracle-documentation/lock-java-platform-se-8-4927/#1).

**StampedLock:** Оптимистичное чтение без блокировки. Если данные не изменились — читаем без блокировки. Если изменились — берём обычный read lock[](https://www.cleverence.com/articles/oracle-documentation/lock-java-platform-se-8-4927/#1)[](https://www.javaspecialists.eu/talks/pdfs/2014%20JavaLand%20in%20Germany%20-%20%22Java%208%20From%20Smile%20To%20Tears%20-%20Emotional%20StampedLock%22%20by%20Heinz%20Kabutz.pdf#2#1).

**Deadlock (взаимоблокировка):** Два потока ждут лок, который держит другой. Решение: **единый порядок захвата локов**[](https://www.cleverence.com/articles/oracle-documentation/lock-java-platform-se-8-4927/#1).

**Livelock (живая блокировка):** Потоки постоянно меняют состояние в ответ на действия друг друга, но прогресса нет. Решение: рандомизированный back-off[](https://www.cleverence.com/articles/oracle-documentation/lock-java-platform-se-8-4927/#1).

### 7. Race Condition (Состояние гонки)

**Что это:** Два потока одновременно читают и изменяют общие данные, и результат зависит от порядка выполнения.

**Пример:** `count++` — это три операции (чтение, инкремент, запись). Между ними может вклиниться другой поток.

**Решение:** `synchronized`, `AtomicInteger` (CAS), `ReentrantLock`, иммутабельные объекты.

### 8. Virtual Threads (Виртуальные потоки)

**Что это:** Легковесные потоки, управляемые JVM, а не ОС. Несколько виртуальных потоков работают на одном **carrier-потоке** (платформенном). При блокировке виртуальный поток «размонтируется» с carrier, освобождая его для других задач[](https://developer.aliyun.com/article/1726125#1).

**Зачем:** Позволяют создавать **миллионы потоков** без огромного расхода памяти (≈1 КБ vs ≈1 МБ для платформенного). Возвращают простую модель «один запрос — один поток», убирая сложность реактивного программирования[](https://zenodo.org/records/20588007/files/18-JSEE3788.pdf?download=1#1#1).

**Ограничения:**

- **Пиннинг (до Java 24):** Если виртуальный поток входит в `synchronized` и блокируется внутри — он «прибивается» к carrier-потоку и не может быть снят. Это может привести к дедлоку, как в кейсе Netflix[](https://habr.com/ru/companies/naumen/articles/953262/#1)[](https://habr.com/ru/companies/naumen/posts/946070/#publication-comments#1). **Исправлено в JDK 24 (JEP 491)**[](https://habr.com/ru/companies/naumen/posts/946070/#publication-comments#1)[](https://zenodo.org/records/20588007/files/18-JSEE3788.pdf?download=1#1#1).
    
- **CPU-bound задачи:** Виртуальные потоки не ускоряют вычисления. Они для I/O-bound задач.
    
- **Backpressure:** Раньше пул потоков был неявным ограничителем. Теперь нужно явно ставить `Semaphore` или rate limiter[](https://habr.com/en/articles/1037932/#1).
    

**Рекомендации:**

- Не пулить виртуальные потоки — они дешёвые, создавай по одному на задачу.
    
- Использовать `Executors.newVirtualThreadPerTaskExecutor()`.
    
- Для передачи контекста использовать **Scoped Values** вместо ThreadLocal (стабильны в JDK 25)[](https://habr.com/ru/companies/naumen/posts/946070/#publication-comments#1)[](https://habr.com/en/articles/1037932/#1).

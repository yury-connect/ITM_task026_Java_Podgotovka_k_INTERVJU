### 1. IoC и DI в целом 🔄

- **IoC (Inversion of Control — Инверсия управления):** Архитектурный принцип, при котором управление созданием объектов и их жизненным циклом передается от кода приложения внешнему фреймворку (Spring IoC-контейнеру).
    
- **DI (Dependency Injection — Внедрение зависимостей):** Конкретный паттерн проектирования, реализующий IoC. Вместо того чтобы класс сам создавал свои зависимости через `new`, контейнер «внедряет» готовые экземпляры снаружи (через конструктор, сеттеры или поля).
    

### 2. Варианты инжекта бинов и почему через конструктор — топ 💉

Существует 3 способа:

1. **Field Injection (`@Autowired` на поле):** Самый простой, но худший способ (скрывает зависимости, усложняет тесты без контекста).
    
2. **Setter Injection:** Для необязательных зависимостей.
    
3. **Constructor Injection (Рекомендуемый):**
    

**Почему он приоритетен:**

- **Неизменяемость (Immutability):** Позволяет объявлять поля как `final`.
    
- **Гарантия целостности (Fail-fast):** Невозможно создать объект в невалидном состоянии без переданных зависимостей еще на этапе компиляции.
    
- **Легкое Unit-тестирование:** Объект тестируется в Plain Java через `new MyService(mockDep)` без поднятия Spring TestContext и Reflection.
    
- **Защита от сбоев:** Явно подсвечивает плохой дизайн (если у конструктора 10+ параметров — класс нарушает SRP).
    

### 3. Плюсы и минусы микросервисной архитектуры 🏢

- **Плюсы:**
    
    - Независимый деплой и масштабирование отдельных сервисов.
        
    - Технологическая гетерогенность (разные стеки и БД под разные задачи).
        
    - Изоляция сбоев (падение одного сервиса не валит всю систему).
        
    - Небольшие кодовые базы, сфокусированные команды.
        
- **Минусы:**
    
    - Высокая операционная сложность (K8s, Service Mesh, CI/CD, Distributed Tracing).
        
    - Сложность распределенных транзакций (отказ от ACID в пользу SAGA / Eventual Consistency).
        
    - Сетевые задержки (Network Latency) при межсервисных вызовах.
        
    - Трудности сквозной отладки и мониторинга.
        

### 4. REST (Representational State Transfer) 🌐

Архитектурный стиль взаимодействия компонентов распределенного приложения over HTTP.

**6 ключевых ограничений (Constraints):**

1. **Client-Server:** Разделение ответственности между клиентом и сервером.
    
2. **Stateless:** Сервер не хранит состояние сессии клиента между запросами.
    
3. **Cacheable:** Ответы должны явно помечаться как кэшируемые или некэшируемые.
    
4. **Uniform Interface:** Единый интерфейс (использование стандартных HTTP-методов `GET`, `POST`, `PUT`, `DELETE` и понятных URI).
    
5. **Layered System:** Клиент не знает, общается он напрямую с сервером или с промежуточным прокси/балансировщиком.
    
6. **Code on Demand (Опционально):** Передача исполняемого кода (например, JavaScript) клиенту.
    

### 5. Circuit Breaker (Resilience4j) ⚡

Паттерн защиты системы от каскадных сбоев при вызове нестабильных внешних сервисов.

**3 состояния автомата:**

1. **`CLOSED` (Замкнут):** Нормальный режим. Все запросы пролетают к внешнему сервису. Если процент ошибок превышает порог (`failureRateThreshold`), переходит в `OPEN`.
    
2. **`OPEN` (Разомкнут):** Запросы **не отправляются** во внешний сервис, а мгновенно возвращают ошибку (Fast Fail) или `fallback`-значение.
    
3. **`HALF_OPEN` (Полуразомкнут):** По истечении таймаута пропускает тестовую порцию запросов. Если они успешны — возвращается в `CLOSED`, если нет — снова в `OPEN`.
    

### 6. В чем разница между интерфейсом и абстрактным классом 🧬

- **Абстрактный класс:** Концепция **«is-a»**. Имеет состояние (instance-поля), конструкторы, модификаторы доступа (`protected`, `private`) и одиночное наследование (`extends`).
    
- **Интерфейс:** Концепция **«can-do»**. Не имеет состояния экземпляра (только `public static final` константы), не имеет конструкторов, поддерживает множественную реализацию (`implements`).
    
- **Методы в интерфейсах (по версиям Java):**
    
    - _Java 8:_ Появились **`default`** (методы с дефолтной реализацией, которые можно переопределять) и **`static`** утилитарные методы.
        
    - _Java 9:_ Появились **`private`** (и `private static`) методы для переиспользования внутреннего кода между default-методами самого интерфейса.
        

### 7. Record (Java 16+) 📦

Специальный тип класса для использования в качестве неиммутабельного (immutable) DTO / Value Object.

Java

```
public record UserDto(Long id, String email) {}
```

- **Автогенерация:** Компилятор создает `private final` поля, канонический конструктор, геттеры без префикса `get` (`id()`, `email()`), `equals()`, `hashCode()` и `toString()`.
    
- **Ограничения:** Неявно является `final` (нельзя наследоваться), не может наследоваться от других классов (уже унаследован от `java.lang.Record`), нельзя добавлять новые instance-поля. Можно реализовывать интерфейсы и создавать статические методы/поля.
    

### 8. ClassLoader (Виды и механика) 🚚

Компонент JVM, загружающий `.class`-файлы в оперативную память. Работает по **модели делегирования (Delegation Model):** запрос на загрузку сначала передается родителю, и только если родитель не нашел класс, текущий ClassLoader ищет его сам.

**Иерархия загрузчиков:**

1. **Bootstrap ClassLoader:** Базовый загрузчик нативно на C++. Загружает ключевые классы JDK (`rt.jar`, `java.lang.*`).
    
2. **Platform / Extension ClassLoader:** Загружает расширения Java и модули платформы.
    
3. **Application / System ClassLoader:** Загружает классы вашего приложения и библиотеки из `classpath`.
    

### 9. Happens-Before (JMM) ⏱️

**Happens-Before** — это отношение/гарантия в Java Memory Model: если операция A находится в отношении Happens-Before с операцией B, то все изменения памяти, сделанные операцией A, **гарантированно видны** операции B.

**Ключевые правила:**

- **`volatile`:** Запись в `volatile`-переменную Happens-Before последующему чтению из этой же переменной.
    
- **`synchronized`:** Освобождение монитора (unlock) Happens-Before последующему захвату (lock) этого же монитора.
    
- **Threads:** Вызов `thread.start()` Happens-Before первой операции внутри этого потока.
    

### 10. Жизненный цикл бина в Spring (Bean Lifecycle) 🔄

1. **Instantiation:** Вызов конструктора (создание объекта).
    
2. **Populate Properties:** Внедрение зависимостей (DI).
    
3. **Aware Interfaces:** Вызов `setBeanName()`, `setApplicationContext()` и др.
    
4. **BeanPostProcessor (Before):** Обработка `@PostConstruct`.
    
5. **Initialization:** Вызов `afterPropertiesSet()` из `InitializingBean` или кастомного `initMethod`.
    
6. **BeanPostProcessor (After):** **Создание AOP-прокси** (для `@Transactional`, `@Async`).
    
7. **Ready:** Бин готов к работе.
    
8. **Destruction:** Вызов `@PreDestroy` / `destroy()` при закрытии контекста.
    

### 11. Скоупы бинов (включая @RefreshScope и Application) 🎯

- **`singleton`** (дефолт): Один объект на весь контекст Spring.
    
- **`prototype`:** Новый объект при каждом запросе из контекста.
    
- **`request`:** Один объект на каждый HTTP-запрос.
    
- **`session`:** Один объект на HTTP-сессию.
    
- **`application`:** Один объект на весь жизненный цикл `ServletContext` (в веб-приложении).
    
- **`@RefreshScope` (Spring Cloud):** Обертка-прокси. При вызове `/actuator/refresh` инвалидирует бин в кэше и создает его заново, обновляя свойства из `@Value` без перезапуска приложения.
    

### 12. Приоритетность конструкторского внедрения 🥇

_(Сводка ключевых тезисов для четкого ответа)_

1. **Гарантия неизменяемости:** Поля можно сделать `final`.
    
2. **Безопасность во время компиляции:** Нельзя создать объект без обязательных полей (нет `NullPointerException` в runtime).
    
3. **Простота тестирования:** Тестируется без поднятия Spring-контекста и reflection.
    
4. **Подсветка запаха кода (Code Smell):** Если конструктор раздувается, фреймворк визуально намекает на нарушение SRP.
    

### 13. Циклическая зависимость и как её решить 🔄

**Суть:** Бин A зависит от B, а Бин B зависит от A.

_При инъекции через поля/сеттеры_ Spring резолвит это через 3-уровневый кэш (Early Singleton Objects). _При инъекции через конструктор_ Spring падает с `BeanCurrentlyInCreationException`.

**Решения:**

1. **Аннотация `@Lazy`** над параметром конструктора (Spring внедрит прокси-заглушку).
    
2. **Рефакторинг (Рекомендуемый):** Вынос общей зависимости в отдельный Бин C.
    
3. Переход на инъекцию через сеттеры.
    

### 14. Lazy-инициализация 💤

Откладывает создание бина до момента первого фактического обращения к нему (вместо создания при старте приложения).

- **Настройка:** Аннотация `@Lazy` над бином или свойство `spring.main.lazy-initialization=true`.
    
- **Плюсы:** Быстрый старт приложения, экономия RAM.
    
- **Минусы:** Скрывает ошибки конфигурации до runtime, первый запрос к бину будет выполняться с высокой задержкой (latency).
    

### 15. Минусы Spring Boot ⚠️

1. **«Магия» автоконфигурации:** Сложно отлаживать и понимать, почему поднялся конкретный бин, если не знать кишок `@ConditionalOn...`.
    
2. **Тяжеловесность (Heavy Footprint):** Высокое потребление оперативной памяти и долгий холодный старт (Cold Start) приложения.
    
3. **Конфликты транзитивных зависимостей:** При подключении нештатных стартеров возможны конфликты версий библиотек.
    

### 16. Как Spring понимает, что стартер — это стартер 🔮

Spring Boot ищет специальные конфигурационные файлы внутри подключенных JAR-библиотек:

- В современных версиях (Spring Boot 2.7+ / 3.x): **`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`**, где списком перечислены `@Configuration`-классы.
    
- В старых версиях: файл `META-INF/spring.factories` под ключом `EnableAutoConfiguration`.
    

### 17. Когда используются прокси в Spring 🎭

Spring создает CGLIB или JDK Dynamic Proxy для добавления сквозной функциональности (AOP) над вызовами методов:

- Управление транзакциями (`@Transactional`).
    
- Асинхронность (`@Async`).
    
- Кэширование (`@Cacheable`).
    
- Валидация аргументов (`@Validated`).
    
- Безопасность (`@PreAuthorize`).
    
- Специфичные скоупы (`@RequestScope`, `@RefreshScope`).
    

### 18. Обработка ошибок в Spring 🛠️

Глобальная обработка реализована через связку **`@RestControllerAdvice` + `@ExceptionHandler`**:

Java

```
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(UserNotFoundException.class)
    public ProblemDetail handleNotFound(UserNotFoundException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    }
}
```

_Преимущество:_ Централизованная обработка ошибок для всего приложения, единообразный формат ответа (RFC 7807) без boilerplate-кода в контроллерах.

### 19. QueryDSL 🔍

Фреймворк для построения строго типизированных SQL/JPQL запросов на базе сгенерированных Q-классов (например, `QUser`).

- **Зачем нужен:** Избавляет от опечаток в строковых запросах (ошибки проверяются на этапе компиляции), поддерживает автодополнение в IDE и позволяет легко собирать сложные динамические фильтры.
    

### 20. Флоу Spring Security 🛡️

1. Входящий `HttpServletRequest` перехватывается сервлетным мостом **`DelegatingFilterProxy`**.
    
2. Вызов передается в **`FilterChainProxy`**, который запускает активный **`SecurityFilterChain`**.
    
3. Фильтр аутентификации (например, `BearerTokenAuthenticationFilter`) извлекает учетные данные и формирует `AuthenticationToken`.
    
4. **`AuthenticationManager`** (через `AuthenticationProvider`) проверяет токен и возвращает заполненный объект `Authentication`.
    
5. Успешный токен сохраняется в **`SecurityContextHolder`**.
    
6. Финальный **`AuthorizationFilter`** проверяет права/роли и либо пропускает запрос в `@RestController`, либо выбрасывает 401/403.
    

### 21. CORS (Cross-Origin Resource Sharing) 🌐

Механизм безопасности веб-браузеров, запрещающий веб-странице делать AJAX-запросы к другому домену/порту (Origin), отличному от того, с которого она была загружена.

- **Preflight Request:** Для «непростых» запросов браузер автоматически отправляет предварительный HTTP-запрос с методом **`OPTIONS`**, проверяя заголовки сервера:
    
    - `Access-Control-Allow-Origin`
        
    - `Access-Control-Allow-Methods`
        
    - `Access-Control-Allow-Headers`
        
- Если сервер разрешает Origin, браузер отправляет реальный запрос.
    

### 22. Компоненты Kafka (включая Connect и Streams) ⚙️

- **Core:** Broker, Topic, Partition, Producer, Consumer, Consumer Group, Offset, KRaft / ZooKeeper.
    
- **Kafka Connect:** Фреймворк для готовой бескодовой интеграции Kafka со сторонними системами (БД, S3, Elasticsearch) при помощи Source и Sink коннекторов.
    
- **Kafka Streams:** Клиентская Java-библиотека для потоковой обработки и трансформации данных из топиков в реальном времени (aggregations, joins, windowing) прямо внутри вашего приложения.
    

### 23. At-Least-Once vs Exactly-Once 📩

- **At-Least-Once (Хотя бы раз):** Сообщение гарантированно доставляется, но возможны дубликаты из-за повторных попыток (retries) при сбоях сети. _(Требует идемпотентных консюмеров)_.
    
- **Exactly-Once (Строго один раз / EOS):** Гарантирует доставку без дублей.
    
    - _Как настроить в Kafka:_
        
        1. На продюсере: `enable.idempotence=true` + задать `transactional.id`.
            
        2. На консюмере: `isolation.level=read_committed`.
            
        3. Использовать метод `sendOffsetsToTransaction()` для связывания оффсетов и отправки в единую транзакцию.
            

### 24. Dead Letter Topic (DLT) ☠️

Специальный топик Kafka, куда перенаправляются сообщения ("poison pills"), обработка которых завершилась сбоем после исчерпания всех заданных попыток (retries).

- **Зачем нужен:** Защищает основную партицию от зависания и блокировки оффсета, позволяя инженерам асинхронно проанализировать битые сообщения и переотправить их позже.

### 🐙 1. Git Clone vs Git Fork

- 👥 **`git clone`:** Команда Git CLI для скопирования существующих данных репозитория с удаленного сервера (GitHub/GitLab) на ваш локальный компьютер.
    
- 🍴 **`Git Fork`:** Операция на стороне Git-хостинга (не команда Git). Создает персональную копию чужого публичного репозитория в вашем аккаунте GitHub, позволяя вам вносить изменения и отправлять Pull Request автору оригинального проекта.
    

### 🏛️ 2. Паттерн Facade (Фасад)

- 🧩 **Суть:** Структурный паттерн проектирования.
    
- 🎯 **Назначение:** Предоставляет простой, верхнеуровневый и понятный интерфейс к сложной подсистеме из десятков взаимодействующих классов.
    
- 💡 **Пример:** Вызов метода `orderService.placeOrder(id)` под капотом обращается к `InventoryService`, `PaymentGateway`, `NotificationService` и `DeliveryService`, скрывая всю эту кухню от клиента.
    

### 🔔 3. Паттерн Observer (Наблюдатель)

- 🧩 **Суть:** Поведенческий паттерн проектирования.
    
- 🎯 **Назначение:** Создает механизм подписки «один-ко-многим». Когда главный объект (**Subject**) меняет свое состояние, он автоматически уведомляет всех зарегистрированных слушателей (**Observers**).
    
- 💡 **Пример:** Изменение статуса заказа генерирует событие, на которое подписаны сервисы отправки Email, SMS и обновления аналитики (`ApplicationEventPublisher` в Spring).
    

### 🧱 4. Ключевые паттерны проектирования микросервисов

- 🎼 **Saga:** Управление распределенными транзакциями через цепочку локальных транзакций с компенсирующими шагами.
    
- ⚡ **Circuit Breaker:** Защита системы от каскадных сбоев при падении смежных сервисов (Resilience4j).
    
- 🚪 **API Gateway:** Единая точка входа для клиентов (маршрутизация, CORS, авторизация, rate-limiting).
    
- 📬 **Transactional Outbox:** Атомарное сохранение бизнес-данных и событий для Kafka в единую БД-транзакцию.
    
- 📊 **CQRS:** Разделение моделей на запись (Command) и чтение (Query).
    
- 🔍 **Service Discovery (Eureka/Consul):** Динамическое обнаружение сетевых адресов микросервисов.
    

### 🔄 5. Компенсирующие транзакции

- 💳 Логическое действие в паттерне **SAGA**, явно отменяющее эффект ранее успешно закоммиченной локальной транзакции.
    
- **Зачем нужны:** Поскольку в распределенных системах нет глобального ACID и `ROLLBACK`, при сбое на шаге N для ранее завершенных шагов 1..N-1 последовательно вызываются компенсирующие операции (например: шаг 1 — списание денег, шаг 2 — ошибка бронирования склада $\rightarrow$ вызов компенсации шага 1: возврат денег клиенту).
    

### 🔀 6. Git Merge vs Git Rebase

- 🔀 **`git merge`:**
    
    - Соединяет две ветки, создавая специальный **Merge Commit** с двумя родителями.
        
    - Сохраняет абсолютную правдивость истории разработок (со всеми ответвлениями и датами).
        
- 📏 **`git rebase`:**
    
    - Переносит ("переписывает") ваши локальные коммиты, переставляя их основание поверх вершины целевой ветки.
        
    - Создает абсолютно чистую, **линейную историю** без лишних Merge-коммитов.
        
    - ⚠️ _Опасность:_ Нарушает правило "не переписывать публичную историю", если применять к расшаренным веткам.
        

### 🍒 7. Git Cherry-Pick

- 🎯 Команда (`git cherry-pick <commit-hash>`), позволяющая точечно применить изменения конкретного коммита из любой другой ветки в вашу текущую ветку.
    
- **Применение:** Перенос срочного хотфикса из рабочей ветки в продакшн без подтягивания всей ветки целиком.
    

### 🏭 8. Factory Method vs Abstract Factory

- ⚙️ **Factory Method (Фабричный метод):**
    
    - Наследуется и делегирует создание **одного конкретного** продукта дочерним классам через переопределенный метод.
        
- 🏛️ **Abstract Factory (Абстрактная фабрика):**
    
    - Использует композицию и предоставляeт интерфейс для создания **целых семейств** взаимосвязанных продуктов (например, семейство кнопок, чекбоксов и окон под темную или светлую тему) без привязки к их конкретным классам.
        

### 📚 9. Три группы паттернов GoF (Gang of Four)

1. 🏗️ **Порождающие (Creational):** Отвечают за безопасное и гибкое создание объектов (`Singleton`, `Factory Method`, `Abstract Factory`, `Builder`, `Prototype`).
    
2. 🧱 **Структурные (Structural):** Отвечают за сборку классов и объектов в более крупные структуры (`Adapter`, `Proxy`, `Decorator`, `Facade`, `Composite`, `Bridge`).
    
3. ⚙️ **Поведенческие (Behavioral):** Отвечают за эффективное алгоритмическое взаимодействие и распределение обязанностей между объектами (`Strategy`, `Observer`, `Command`, `Chain of Responsibility`, `State`, `Iterator`).
    

### 🎭 10. Паттерн Proxy (Заместитель)

- 🧩 **Суть:** Структурный паттерн.
    
- 🎯 **Назначение:** Подменяет реальный объект объектом-заменителем, контролируя доступ к нему.
    
- 💡 **Применение:** Ленивая инициализация (Lazy Loading), проверка прав доступа, кэширование, перехват вызовов в Spring (`@Transactional`, `@Async`).
    

### 👷 11. Паттерн Builder (Строитель)

- 🧩 **Суть:** Порождающий паттерн.
    
- 🎯 **Назначение:** Позволяет пошагово конструировать сложные объекты с большим количеством опциональных параметров.
    
- 💡 **Плюс:** Избавляет от телескопических конструкторов (`new User(a, b, c, null, null, true)`) и обеспечивает читаемыйFluent-API (`User.builder().name("A").age(20).build()`).
    

### 🧰 12. Lombok @UtilityClass

- 🛠️ Аннотация Lombok для создания утилитарных классов.
    
- **Что делает под капотом:**
    
    1. Делает класс `final`.
        
    2. Генерирует `private` конструктор, выбрасывающий исключение при вызове через Reflection.
        
    3. Автоматически помечает все методы, поля и внутренние классы как **`static`**.
        

### 🔓 13. Как избежать создания 2 синглтонов при десериализации

1. 💡 **Реализовать метод `readResolve()`:**
    
    В классическом синглтоне объявить специальный метод `private Object readResolve()`, который при десериализации вернет существующий экземпляр `INSTANCE` вместо создания нового объекта из потока байт.
    
2. 🚀 **Использовать `Enum` (Рекомендуемый способ):**
    
    Реализовать синглтон через `public enum Singleton { INSTANCE; }`. JVM нативном уровне гарантирует защиту Enum от дублирования при сериализации и атаках через Reflection.
    

### 📐 14. Liskov Substitution Principle (LSP / SOLID)

- 📜 **Принцип подстановки Барбары Лисков:** Объекты дочерних классов должны свободно заменять объекты базовых классов, не ломая поведение программы и соблюдая контракты базового класса.
    
- ⚠️ **Принцип нарушен, если:** Дочерний класс переопределяет метод так, что тот кидает `UnsupportedOperationException`, ослабляет предусловия или усиливает постусловия родителя. _(Классический антипример: Квадрат, наследующийся от Прямоугольника)_.
    

### 📦 15. Git Stash, Git Revert, Git Reset

- 📥 **`git stash`:** Временно убирает незакоммиченные изменения из рабочей директории в стек, позволяя получить чистый `HEAD` без коммита.
    
- ↩️ **`git revert <commit>`:** Безопасный откат. Создает **новый коммит**, который выполняет строго противоположные изменения указанному коммиту. История не переписывается.
    
- 💥 **`git reset <commit>`:** Опасный откат. Перемещает указатель ветки назад:
    
    - `--soft`: Сохраняет изменения в индексах (Staging Area).
        
    - `--mixed` (дефолт): Сохраняет изменения в рабочей директории.
        
    - `--hard`: Безвозвратно удаляет все изменения и коммиты!
        

### 🚦 16. Git Add vs Git Status

- 🔍 **`git status`:** Выводит отчет о текущем состоянии рабочей директории (показывает измененные, неотслеживаемые и подготовленные к коммиту файлы).
    
- 📥 **`git add`:** Переносит изменения из рабочей директории в **Индекс (Staging Area)**, подготавливая их к включению в следующий коммит.
    

### 🔄 17. Можно ли сделать revert другого revert коммита?

- **Да, абсолютно.**
    
- Запуск `git revert <hash-of-revert-commit>` отменит предыдущую отмену и повторно накатит исходные изменения назад в ветку.
    

### 🎯 18. Паттерн Strategy (Стратегия)

- 🧩 **Суть:** Поведенческий паттерн.
    
- 🎯 **Назначение:** Выносит семейство родственных алгоритмов в отдельные классы и делает их взаимозаменяемыми во время выполнения (Runtime) через общий интерфейс.
    
- 💡 **Пример:** Класс `OrderProcessor` принимает интерфейс `PaymentStrategy` (`CardPayment`, `SbpPayment`, `CryptoPayment`) и вызывает `pay()`, не ведая о деталях конкретного способа оплаты.
    

### 🔌 19. Паттерн Adapter (Адаптер)

- 🧩 **Суть:** Структурный паттерн.
    
- 🎯 **Назначение:** Оборачивает объект с некорректным или несовместимым интерфейсом, приводя его к интерфейсу, который ожидает клиент (работает как переходник с европейской розетки на американскую).
    

### 🕹️ 20. Паттерн Command (Команда)

- 🧩 **Суть:** Поведенческий паттерн.
    
- 🎯 **Назначение:** Превращает запрос/действие в самостоятельный объект, содержащий сам запрос и все его аргументы.
    
- 💡 **Плюсы:** Позволяет передавать команды как параметры методов, ставить их в очереди, логировать и поддерживать отмену операций (Undo/Redo).
    

### 🎨 21. Decorator vs Proxy

- 🎨 **Decorator (Декоратор):** Динамически **добавляет новые обязанности и поведение** существующему объекту, расширяя его функциональность без изменения интерфейса.
    
- 🎭 **Proxy (Заместитель):** **Контролирует доступ** к существующему объекту (права, ленивая загрузка, кэширование, логирование), **не добавляя новой бизнес-логики** и не меняя его бизнес-контракт.
    

### 💋 22. Принцип KISS (Keep It Simple, Stupid)

- 🧼 Принцип проектирования, призывающий делать код и архитектуру **максимально простыми и прямолинейными**.
    
- Избегайте преждевременной оптимизации, избыточных уровней абстракции и овер-инжиниринга. Простой код легко читать, тестировать и поддерживать.
    

### 💧 23. Принцип DRY (Don't Repeat Yourself)

- 🔄 Каждый фрагмент бизнес-логики или знаний должен иметь **единственное и недвусмысленное представление** в системе.
    
- Избегайте дублирования кода. Если логика повторяется, выносите ее в общие методы, компоненты или библиотеки.
    

### 🔓 24. Нарушение Open/Closed Принципа (OCP)

Принцип гласит: _«Программные сущности должны быть открыты для расширения, но закрыты для изменения»_.

- 🔴 **Как выглядит нарушение:** Чтобы добавить новую доменную сущность или тип оплаты, разработчик вынужден идти в существующий рабочий класс и **модифицировать его код** (например, дописывать новые `if-else` или `switch-case` блоки).
    
- 🟢 **Как исправить:** Использовать полиморфизм, интерфейсы и паттерн Strategy, чтобы новые варианты добавлялись созданием новых классов-наследников без правки старого кода.

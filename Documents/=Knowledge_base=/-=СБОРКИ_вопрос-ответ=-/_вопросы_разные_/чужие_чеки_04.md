### 🔍 1. Отличие HAVING от WHERE

Обе секции служат для фильтрации данных в SQL, но работают на абсолютно разных этапах выполнения запроса:

- 🛠️ **`WHERE`:**
    
    - Фильтрирует **отдельные строки** **ДО** того, как будет выполнена группировка (`GROUP BY`) или агрегация.
        
    - **Не может** содержать агрегатные функции (`WHERE SUM(price) > 1000` вызовет ошибку).
        
    - Использует обычные и составные индексы.
        
- 📊 **`HAVING`:**
    
    - Фильтрирует **сгруппированные группы и результаты агрегации** **ПОСЛЕ** выполнения `GROUP BY`.
        
    - Работает строго с агрегатными функциями (`HAVING COUNT(order_id) > 5`).
        

### 🔄 2. Состояния объектов в Hibernate (Entity Lifecycle States)

В Hibernate объект сущности находится в одном из 4 состояний жизненного цикла:

1. 🐣 **Transient (New):**
    
    - Объект создан через оператор `new`.
        
    - Не имеет присвоенного Primary Key (ID) и не связан с текущей сессией (`EntityManager`).
        
    - В базе данных записи нет, Hibernate про него ничего не знает.
        
2. 🟢 **Persistent (Managed):**
    
    - Объект связан с активной сессией и имеет Primary Key.
        
    - Находится в L1-кэше сессии. Включен механизм **Dirty Checking** — любые изменения полей через сеттеры автоматически сгенерируют `UPDATE` при сбросе сессии (`flush`).
        
3. 🟡 **Detached:**
    
    - Объект имеет ID в БД, но **сессия закрыта** (`close()`) или очищена (`clear()` / `evict()`).
        
    - Hibernate больше не отслеживает изменения объекта. При изменении полей `UPDATE` в БД не уйдет, пока объект не вернется в контекст через `merge()`.
        
4. 🔴 **Removed:**
    
    - Объект помечен на удаление вызовом `em.remove(entity)`.
        
    - Он еще находится в сессии, но при ближайшем `flush()` в БД будет отправлен SQL-запрос `DELETE`.
        

### 📚 3. Отличие JPA от Hibernate

- 📜 **JPA (Jakarta Persistence API):**
    
    - Это **спецификация** (стандарт) Java-платформы.
        
    - Представляет собой набор интерфейсов, контрактов и аннотаций (`@Entity`, `@Table`, `EntityManager`). Не содержит исполняемого кода бизнес-логики.
        
- ⚙️ **Hibernate:**
    
    - Это конкретная **библиотека и ORM-провайдер**, реализующая спецификацию JPA.
        
    - Помимо реализации стандарта JPA, Hibernate содержит собственные расширения: расширенный L2-кэш, аудирование (Hibernate Envers), кастомные типы данных, методы `Session` и `Criteria`.
        

### 🆔 4. Стратегии генерации ID (`@GeneratedValue`)

1. ⚙️ **`GenerationType.AUTO` (Дефолт):**
    
    - JPA сама выбирает стратегию в зависимости от вендора СУБД (в Hibernate 6+ для реляционных БД по умолчанию выбирает `SEQUENCE`).
        
2. 🆔 **`GenerationType.IDENTITY`:**
    
    - Использует автоинкрементную колонку таблицы БД (`AUTO_INCREMENT` в MySQL, `SERIAL` / `IDENTITY` в Postgres).
        
    - ⚠️ _Минус:_ Отключает батчинг вставок (`Insert Batching`), так как Hibernate вынужден делать мгновенный `INSERT` в БД при вызове `persist()`, чтобы узнать сгенерированный базой ID.
        
3. 🔢 **`GenerationType.SEQUENCE` (Рекомендуемый):**
    
    - Использует специальный объект последовательности в СУБД (`CREATE SEQUENCE`).
        
    - 🚀 _Плюс:_ Поддерживает пакетную генерацию ID (параметр `allocationSize`). Hibernate вычитывает диапазон ключей заранее за 1 запрос к БД и не отключает batching.
        
4. 📑 **`GenerationType.TABLE`:**
    
    - Использует отдельную служебную таблицу для эмуляции генерации ключей. Очень медленный вариант, создает блокировки строк, на практике не используется.
        
5. 🧬 **`UUID` (Hibernate-extension / Java 17+):**
    
    - Генерация 128-битных уникальных идентификаторов на стороне JVM без обращения к БД.
        

### 📐 5. Требования к Entity в JPA

Чтобы класс стал полноценной сущностью JPA, он должен соответствовать контракту:

1. Обязательна аннотация **`@Entity`** над классом.
    
2. Обязательно наличие **Primary Key** — хотя бы одно поле с аннотацией **`@Id`** (или `@EmbeddedId`).
    
3. Конструктор **без параметров (no-args constructor)** с модификатором доступа `public` или `protected` (нужен Hibernate для создания прокси через Reflection).
    
4. Класс **не должен быть `final`** (иначе невозможно сгенерировать CGLIB-прокси для Lazy-загрузки).
    
5. Поля и методы не должны быть `final`.
    
6. Рекомендуется реализовывать `Serializable` (для составных ключей — обязательно).
    

### 🛠️ 6. ddl-auto (`spring.jpa.hibernate.ddl-auto`)

Свойство управления автоматической генерацией схемы БД при старте приложения:

- 🚫 **`none`:** Ничего не делает со схемой БД (рекомендуемый дефолт для Production).
    
- 🔍 **`validate`:** Проверяет соответствие структура аннотированных `@Entity` таблицам в БД. Если есть расхождения — валит старт приложения. (Идеально для PROD в связке с Flyway/Liquibase).
    
- 🔄 **`update`:** Изменяет схему БД под структуру сущностей (добавляет новые колонки/таблицы), но **не удаляет** устаревшие колонки.
    
- 💥 **`create`:** При старте удаляет существующие таблицы и создает схему заново.
    
- 🧹 **`create-drop`:** Создает схему при старте приложения и полностью удаляет ее при закрытии `SessionFactory` (для integration-тестов).
    

### 🔌 7. Основные интерфейсы JPA

- 🏭 **`EntityManagerFactory`:** Тяжеловесный потокобезопасный синглтон-объект, создающий экземпляры `EntityManager`.
    
- 💼 **`EntityManager`:** Ключевой интерфейс контекста персистентности (L1-кэш, Dirty Checking, выполнение операций CRUD).
    
- 💳 **`EntityTransaction`:** Управление границами транзакций при ручном управлении (`begin()`, `commit()`, `rollback()`).
    
- 📜 **`Query` / `TypedQuery`:** Выполнение JPQL, HQL и нативных SQL-запросов.
    

### ⚡ 8. 2 типа триггеров в БД (по уровню выполнения)

1. 📄 **FOR EACH STATEMENT (Операторные):**
    
    - Выполняется **ровно один раз на весь SQL-запрос**, независимо от того, сколько строк было изменено (даже если модифицировано 0 или 1 000 000 строк).
        
2. 📝 **FOR EACH ROW (Строчные):**
    
    - Выполняется **индивидуально для каждой затронутой строки**.
        
    - Позволяет обращаться к старым и новым значениям колонок конкретной строки через переменные `OLD` и `NEW`.
        

### ⚙️ 9. Хранимая процедура vs Хранимая функция

- 🧮 **Хранимая функция (Function):**
    
    - **Обязана** возвращать значение определенного типа.
        
    - Можно вызывать напрямую внутри SQL-запросов: `SELECT calculate_tax(salary) FROM employees`.
        
- 📜 **Хранимая процедура (Procedure):**
    
    - Может не возвращать значений вообще либо возвращать их через `OUT`-параметры.
        
    - Вызывается как самостоятельная команда через `CALL my_procedure()`.
        
    - **Нельзя** вызывать внутри выражений `SELECT`.
        

### 👁️ 10. Отличие View от Materialized View

- 🪟 **View (Виртуальное представление):**
    
    - **Не хранит данные** на диске. Это просто зафиксированный SQL-запрос.
        
    - При каждом обращении СУБД выполняeт исходный SQL-запрос заново. Данные всегда на 100% свежие.
        
- 💾 **Materialized View (Материализованное представление):**
    
    - **Физически сохраняет результат** выполнения запроса на диск в виде обычной таблицы.
        
    - Выборки работают мгновенно, но данные могут устаревать. Требуют обновления через команду `REFRESH MATERIALIZED VIEW`.
        

### 📖 11. Индексация

Механизм создания специальных вспомогательных структур данных (чаще всего B-Tree или Hash) для колонок таблицы.

- 🚀 **Плюс:** Позволяет находить записи за $O(\log N)$ вместо полного сканирования таблицы $O(N)$ (`Seq Scan`).
    
- ⚖️ **Плата:** Индексы занимают RAM и диск, а также **замедляют операции записи** (`INSERT`, `UPDATE`, `DELETE`), так как СУБД обязана перестраивать деревья индексов при любых изменениях.
    

### 🛠️ 12. Как создать индекс

- **В нативном SQL:**
    
    SQL
    
    ```
    CREATE INDEX idx_users_email ON users (email);
    ```
    
- **В JPA (через аннотации сущности):**
    
    Java
    
    ```
    @Table(name = "users", indexes = {
        @Index(name = "idx_users_email", columnList = "email", unique = true)
    })
    ```
    

### 🛑 13. Отличие DELETE от TRUNCATE

- 📝 **`DELETE` (DML-операция):**
    
    - Удаляет строки **поочередно**, записывая каждую операцию в журнал транзакций (WAL).
        
    - Поддерживает секцию **`WHERE`**.
        
    - Поддерживает полные откаты (`ROLLBACK`).
        
    - Вызывает **строчные триггеры** (`FOR EACH ROW`).
        
    - **Не сбрасывает** счетчик автоинкремента (`SERIAL`).
        
- 💥 **`TRUNCATE` (DDL-операция):**
    
    - Мгновенно освобождает дисковые страницы таблицы целиком.
        
    - **Не поддерживает `WHERE`** (очищает таблицу полностью).
        
    - Не генерирует детальных логов удаляемых строк (работает в разы быстрее).
        
    - **Не вызывает** строчные триггеры.
        
    - **Сбрасывает счетчики** автоинкремента в начальное значение.
        

### 💾 14. save vs persist (flush & merge)

- 📥 **`persist()` (JPA):**
    
    - Метод возвращает `void`. Делает переданный `Transient`-объект `Managed`.
        
    - Не выполняет мгновенного SQL `INSERT` (если генератор ID не `IDENTITY`), откладывая запрос до этапа `flush`.
        
- 💾 **`save()` (Hibernate Legacy):**
    
    - Возвращает сгенерированный `Serializable` ID.
        
    - Принудительно генерирует и выполняет SQL `INSERT` незамедлительно, чтобы вернуть ключи.
        
- 💧 **`flush()`:**
    
    - Синхронизирует состояние L1-кэша с базой данных — физически отправляет все накопленные SQL-запросы (`INSERT`, `UPDATE`, `DELETE`) в сетевой сокет БД, но **не завершает транзакцию** (`COMMIT` еще не сделан).
        
- 🔀 **`merge()` (JPA):**
    
    - Принимает `Detached`-объект, находит или создает его копию в `Managed`-контексте, копирует туда все поля и возвращает **новый управляемый экземпляр**. Исходный переданный объект остается `Detached`!
        

### 💳 15. ACID

Фундаментальные требования к транзакционной системе:

- **A (Atomicity — Атомарность):** «Все или ничего».
    
- **C (Consistency — Согласованность):** Сохранение валидности данных и правил БД.
    
- **I (Isolation — Изолированность):** Параллельные транзакции не мешают друг другу.
    
- **D (Durability — Долговечность):** Закоммиченный результат гарантированно сохранен на диск.
    

### 🔗 16. @JoinColumn

Аннотация, указывающая **имя конкретной колонки внешнего ключа (Foreign Key)** в текущей таблице БД при настройке связей `@ManyToOne` или `@OneToOne`.
```Java
@ManyToOne
@JoinColumn(name = "department_id", nullable = false)
private Department department;
```

### ⚡ 17. FetchType (EAGER vs LAZY)

Стратегия загрузки связанных сущностей:

- 💤 **`FetchType.LAZY` (Ленивая):**
    
    - Данные связанной сущности или коллекции **не загружаются** сразу из БД. Вместо них подставляется CGLIB-прокси.
        
    - Реальный SQL-запрос отправляется только при первом вызове геттера поля.
        
    - _Дефолт для:_ `@OneToMany`, `@ManyToMany`.
        
- ⚡ **`FetchType.EAGER` (Быстрая):**
    
    - Загружает связанные сущности мгновенно вместе с родителем за один `JOIN` или через немедленный второй SQL-запрос.
        
    - _Дефолт для:_ `@ManyToOne`, `@OneToOne`.
        
    - _Опасность:_ Провоцирует проблему N+1 и создание огромных декартовых произведений при `JOIN`.
        

### 💼 18. EntityManager vs DataManager

- 🔧 **`EntityManager`:** Стандартный низкоуровневый JPA-интерфейс. Работает напрямую с контекстом персистентности, требует контроля транзакций и ручной обработки состояний сущностей.
    
- 🚀 **`DataManager`:** Высокоуровневая абстракция, встречающаяся в корпоративных фреймворках (например, Jmix / CUBA). Оборачивает `EntityManager`, автоматически проверяет права доступа пользователя (Security), управляет транзакциями «под капотом» и генерирует события сущностей.
    

### 📦 19. Второй уровень кэша Hibernate (L2 Cache)

- 🏭 **Скоуп:** Живет на уровне **`SessionFactory`** и разделяется между **всеми сессиями и потоками** приложения.
    
- 🥩 **Формат хранения:** Хранит данные не в виде Java-объектов, а в виде разобранных массивов базовых значений (дегидрированные кортежи).
    
- 🔌 **Провайдеры:** Вынесен во внешние библиотеки (Ehcache, Hazelcast, Infinispan).
    
- 🛡️ **Стратегии согласованности:** `READ_ONLY`, `NONSTRICT_READ_WRITE`, `READ_WRITE`, `TRANSACTIONAL`.
    

### ⚡ 20. Отличие кэша от БД

- 🚀 **Кэш (RAM):**
    
    - Хранит данные в оперативной памяти.
        
    - Сверхбыстрая скорость чтения/записи (на порядки быстрее диска).
        
    - Энергозависим — данные стираются при перезагрузке приложения/сервера.
        
- 💾 **База данных (Disk/SSD):**
    
    - Физически хранит данные на энергонезависимом накопителе.
        
    - Гарантирует долговечность (Durability), поддерживает сложный синтаксис SQL, транзакции и индексы.
        

### 🧬 21. Стратегии наследования в Hibernate (`@Inheritance`)

1. 📄 **`SINGLE_TABLE` (По умолчанию):**
    
    - Все классы иерархии хранятся в **одной общей таблице**. Нужна колонка-дискриминатор (`@DiscriminatorColumn`).
        
    - 🚀 _Плюс:_ Высокая скорость, нет `JOIN`.
        
    - ⚠️ _Минус:_ Поля дочерних классов обязаны разрешать `NULL`.
        
2. 🔗 **`JOINED`:**
    
    - Базовый класс хранит общие поля в своей таблице, дочерние классы — в своих отдельных таблицах с FK на базовую.
        
    - 🚀 _Плюс:_ Нормализованная БД без лишних `NULL`.
        
    - ⚠️ _Минус:_ Медленные выборки из-за изобилия `JOIN`.
        
3. 📚 **`TABLE_PER_CLASS`:**
    
    - Для каждого конкретного класса создается полная самостоятельная таблица.
        
    - ⚠️ _Минус:_ Полиморфные выборки делают тяжелый и медленный `UNION`.
        
4. 🧱 **`@MappedSuperclass`:**
    
    - Не является стратегией отображения иерархии сущностей. Родительский класс не сущность (нельзя делать `SELECT` по нему), его поля просто копируются в таблицы дочерних сущностей.
        

### 🔀 22. UNION vs UNION ALL

Оба оператора объединяют результаты двух и более SQL-выборок:

- 🧹 **`UNION`:**
    
    - Объединяет результаты и **удаляет дубликаты строк**.
        
    - ⚠️ Требует выполнения ресурсоемкой сортировки или хэширования в памяти СУБД, из-за чего работает медленнее.
        
- ⚡ **`UNION ALL`:**
    
    - Объединяет результаты **без проверки на дубликаты** (склеивает все строки как есть).
        
    - 🚀 Работает значительно быстрее, рекомендуется использовать по умолчанию, если точно известно, что дублей нет или они допустимы.

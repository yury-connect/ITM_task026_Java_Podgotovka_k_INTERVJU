### ⚡ 1. `@Cacheable` в Spring

Аннотация Spring Cache Abstraction для прозрачного кэширования результатов выполнения методов.

- ⚙️ **Как работает под капотом:**
    
    - Метод, помеченный `@Cacheable`, оборачивается в AOP-прокси.
        
    - При вызове метода Spring перехватывает запрос, формирует кэш-ключ (по умолчанию на основе переданных аргументов) и запрашивает значение у настроенного `CacheManager` (Redis, Caffeine, Ehcache).
        
    - **Cache Hit (Попадание):** Если значение найдено в кэше, выполнение реального тела метода **пропускается**, и результат отдается напрямую из кэша.
        
    - **Cache Miss (Промах):** Если значения нет, метод физически выполняется, его результат сохраняется в кэш и возвращается вызывающему коду.
        
- 📌 **Ключевые атрибуты:**
    
    - `value` / `cacheNames` — имя области/структуры кэша.
        
    - `key` — SpEL-выражение для формирования кастомного ключа (например, `key = "#user.id"`).
        
    - `condition` — SpEL-условие **до** вызова метода (кэшировать только если `condition = "#id > 100"`).
        
    - `unless` — SpEL-условие **после** вызова метода (НЕ кэшировать если `unless = "#result == null"`).
        

### 🔄 2. Стратегии и механизмы обновления кэша

#### Основные паттерны

- 📥 **Cache-Aside (Lazy Loading / Ленивая загрузка):** Приложение сначала ищет данные в кэше. При отсутствии — читает из БД, сам пишет в кэш и возвращает результат. (Дефолтная модель Spring `@Cacheable`).
    
- 📤 **Write-Through (Сквозная запись):** Приложение пишет данные в кэш, а сам модуль кэша синхронно сохраняет их в БД.
    
- ⏳ **Write-Behind / Write-Back (Отложенная запись):** Приложение пишет в кэш, а кэш асинхронно батчами сбрасывает данные в БД. Огромная скорость записи, но есть риск потери данных при сбое кэша.
    

#### Аннотации Spring для управления кэшем

- 🔄 **`@CachePut`:** **Всегда** принудительно выполняет реальный метод и обновляет/перезаписывает содержимое кэша свежим результатом работы метода.
    
- 🧹 **`@CacheEvict`:** Удаляет данные из кэша при вызове метода (например, при удалении сущности):
    
    - `allEntries = true` — очищает всю область кэша целиком.
        
    - `beforeInvocation = true` — удаляет из кэша до выполнения метода (даже если метод выбросит исключение).
        

### 🔀 3. JOIN при Шардировании и Партиционировании

#### При партиционировании (Partitioning на одном узле)

- Если запрос делает `JOIN` по полям, совпадающим с ключом партиционирования (**Partition Key**), СУБД делает **Partition Pruning** (отсечение) и соединяет только нужные физические партиции.
    
- Если `JOIN` идет по неиндексированным/неключевым полям, СУБД вынуждена делать полный проход по всем партициям обоих таблиц, что снижает производительность.
    

#### При шардировании (Sharding по разным серверам/узлам)

Выполнение `JOIN` между таблицами, находящимися на разных физических шардах — самая дорогая и сложная операция:

- 📍 **Co-located JOINs (Совмещенное шардирование):** Идеальный сценарий. Связанные таблицы шардируются по единому ключу (например, `user_id`). Данные пользователя из всех таблиц живут на одном и том же физическом шарде. `JOIN` выполняется локально без сетевых прыжков.
    
- 📡 **Broadcast / Reference Tables:** Маленькие справочные таблицы (например, справочник стран или статусов) полностью дублируются (реплицируются) на каждый шард. `JOIN` происходит локально на каждом шарде.
    
- 💥 **Scatter-Gather / Two-Phase JOINs:** Самый медленный вариант. Координатор (или прокси) отправляет запросы на все шарды, скачивает гигабайты сырых данных по сети к себе в память и выполняет `JOIN` локально на узле-координаторе.
    

### 🌐 4. Репликация, партиционирование, шардирование, прокси и наследование таблиц

- 🔄 **Репликация vs Партиционирование vs Шардирование:**
    
    - **Репликация:** Создание полных копий всей БД (Primary/Leader для записи, Replicas/Followers для чтения). Повышает отказоустойчивость и скорость чтения.
        
    - **Партиционирование:** Разделение одной крупной таблицы на мелкие физические куски в рамках **одного сервера БД**.
        
    - **Шардирование:** Горизонтальное разделение данных одной таблицы по **разным независимым серверам (узлам)**.
        
- 🔌 **Роль прокси-сервера (Citus, Vitess, PgBouncer, ProxySQL):**
    
    - Клиентское приложение работает с прокси как с единой монолитной БД.
        
    - Прокси берет на себя маршрутизацию запросов (разделение Read/Write вызовов), пул соединений, разбор SQL, выбор конкретного шарда по Shard Key и объединение результирующих ответов.
        
- 📜 **Наследование таблиц в PostgreSQL (`INHERITS`):**
    
    - Исторический механизм партиционирования до появления декларативного секционирования (до PG 10).
        
    - Дочерние таблицы наследуют схему родительской.
        
    - **Проблемы и ограничения:** Уникальные ограничения (`UNIQUE`), первичные ключи (`PRIMARY KEY`) и внешние ключи (`FOREIGN KEY`) **не наследуются автоматически** на дочерние таблицы и не работают сквозь иерархию без сложных кастомных триггеров.
        

### 🧹 5. Vacuum в PostgreSQL

Из-за архитектуры MVCC операции `UPDATE` и `DELETE` оставляют в дисковых страницах «мертвые кортежи» (Dead Tuples).

- ⚙️ **Механика работы `VACUUM`:**
    
    - Сканирует страницы таблиц, находим мертвые версии строк и удаляет ссылки на них из индексов и страниц.
        
    - Помечает высвободившееся место в картограмме свободного пространства (**FSM — Free Space Map**) и карте видимости (**VM — Visibility Map**).
        
    - Обновляет статистику планировщика запросов (`ANALYZE`).
        
- 🛑 **Чего НЕ делает обычный `VACUUM`:**
    
    - **Не блокирует** параллельные чтения и записи (`SELECT`, `INSERT`, `UPDATE` продолжают работать).
        
    - **Не возвращает** физическое дисковое пространство операционной системе (размер файла таблицы на диске не уменьшается; освобожденное место просто переиспользуется для новых `INSERT`).
        
- 💥 **`VACUUM FULL`:**
    
    - Полностью переписывает содержимое таблицы и её индексов в **новый сжатый файл на диске**.
        
    - **Возвращает неиспользуемое место ОС**.
        
    - ⚠️ Захватывает жесткую блокировку `ACCESS EXCLUSIVE` — полностью блокирует любые чтения и записи в таблицу до окончания своей работы.
        

### 🤖 6. Autovacuum в PostgreSQL

Фоновый демонический процесс PostgreSQL, который автоматически запускает `VACUUM` и `ANALYZE` по мере накопления изменений.

- 📊 **Формула срабатывания:** Очистка таблицы запускается, когда количество мертвых кортежей превышает порог:
    
    $$\text{Threshold} = \text{autovacuum\_vacuum\_threshold} + (\text{autovacuum\_vacuum\_scale\_factor} \times \text{number\_of\_tuples})$$
    
- ⚙️ **Настройка и тюнинг:**
    
    - `autovacuum_max_workers` — количество параллельных потоков автовакуума.
        
    - `autovacuum_vacuum_cost_limit` — лимит ресурсов (I/O), при достижении которого процесс засыпает, чтобы не просаживать производительность основной БД.
        
    - Для интенсивно изменяемых ("горячих") таблиц параметры `scale_factor` переопределяются персонально на уровне конкретной таблицы.
        
- 🛡️ **Защита от Wraparound (Зацикливания ID транзакций):** Принудительный `autovacuum` запускается вне зависимости от настроек при приближении к порогу `autovacuum_freeze_max_age` (заморозка старых `xmin`), чтобы предотвратить потерю данных из-за исчерпания 32-битного счетчика транзакций.
    

### 🔀 7. Проблема «А-В-С» / Неупорядоченность событий в SAGA Choreography

В SAGA Хореографии нет центрального оркестратора — сервисы реагируют на события асинхронно через шину (Kafka).

- 🔴 **Суть проблемы (Out-of-Order Events & Race Conditions):** Из-за сетевых задержек или сбоев партиционирования событие $C$ (например, `OrderCancelled`) может прийти в сервис раньше, чем событие $B$ (`PaymentCompleted`) или $A$ (`OrderCreated`). Сервис пытается отменить то, чего у него еще нет в базе.
    
- 🟢 **Методы решения:**
    
    - **Идемпотентный консюмер (Idempotent Consumer):** Фиксация уже обработанных ID событий в специальной таблице дедупликации (`processed_events`).
        
    - **Версионирование и оптимистичные блокировки:** Каждое событие содержит возрастающий номер версии/штамп времени. Если приходит событие с версией $V_{event} > V_{current} + 1$, обработка откладывается или отправляется в отложенную очередь (Retry/Delay Topic).
        
    - **Машина состояний (State Machine):** Четкое определение допустимых переходов. Если статус заказа `NEW`, а пришла команда отмены — устанавливается статус `CANCELLED`. Когда с задержкой долетит событие успешной оплаты, машина состояний увидит текущий статус `CANCELLED` и отклонит платеж, вызвав компенсацию.
        

### 📬 8. Transactional Outbox

Паттерн для атомарного обновления БД и публикации сообщений в брокер ( Kafka / RabbitMQ ) без применения двойной записи (Dual-Write Problem).

- 🛠️ **Схема работы:**
    
    1. В рамках **единой локальной ACID-транзакции** БД сохраняется бизнес-сущность (например, запись в `orders`) и создается запись события в служебной таблице `outbox`.
        
    2. Транзакция коммитится. Данные гарантированно сохранены.
        
- 🚚 **Два способа вычитки из таблицы Outbox в Kafka:**
    
    - 🔄 **Polling Publisher (Опрос по расписанию):** Фоновый процесс (`@Scheduled`) периодически выполняет `SELECT ... FROM outbox WHERE processed = false FOR UPDATE SKIP LOCKED`, отправляет сообщения в Kafka и удаляет/помечает обработанные строки. _Минус:_ Дополнительная нагрузка на БД.
        
    - ⚡ **CDC (Change Data Capture / Debezium):** Коннектор вычитывает изменения таблицы `outbox` напрямую из **бинарного лога предзаписи БД (WAL)** и мгновенно стримит их в Kafka без нагрузки на ресурс выполнения SQL-запросов.
        

### 🛡️ 9. Безопасность в микросервисной архитектуре

- 🚪 **Edge Security (Внешний периметр / API Gateway):**
    
    - Клиент аутентифицируется на внешнем Сервере Авторизации (Keycloak / Auth0 / Spring Authorization Server) по протоколу **OAuth 2.0 / OIDC** и получает Signed JWT.
        
    - API Gateway валидирует подпись JWT, проверяет срок жизни и отсекает невалидные запросы.
        
- 🔄 **Internal Security (Межсервисное взаимодействие — East-West Traffic):**
    
    - **Token Relaying (Прокидывание токена):** Gateway прокидывает исходный JWT дальше во внутренние сервисы в заголовке `Authorization: Bearer <token>`. Сервисы де декодируют токен и извлекают `roles`/`claims`.
        
    - **mTLS (Mutual TLS):** Безопасность на сетевом уровне (часто через Service Mesh: Istio/Linkerd). Сервисы проверяют TLS-сертификаты друг друга с обоюдным шифрованием трафика.
        
    - **Internal JWT / Session Tokens:** Gateway обменивает внешний токен пользователя на короткоживущий внутренний доверенный токен сервисов.
        

### 🧰 10. Свой Spring Boot Starter для Spring Security и прокидывания JWT

Модуль для автоматического подключения единой безопасности во все микросервисы.

- 🏗️ **Составные части стартера:**
    
    1. **`JwtProperties`:** Класс конфигурации свойств с аннотацией `@ConfigurationProperties(prefix = "app.security.jwt")` (секретный ключ, время жизни).
        
    2. **`JwtTokenFilter` (`OncePerRequestFilter`):** Извлекает токен из заголовка `Authorization`, валидирует подпись, конструирует `UsernamePasswordAuthenticationToken` и помещает его в `SecurityContextHolder.getContext().setAuthentication(...)`.
        
    3. **`JwtSecurityAutoConfiguration`:** Автоконфигурационный класс с `@AutoConfiguration`, который поднимает `SecurityFilterChain`, отключает CSRF, переводит сессии в `SessionCreationPolicy.STATELESS` и добавляет `JwtTokenFilter` в цепочку.
        
    4. **Token Relay (Прокидывание во внешние вызовы):** Конфигурация `Feign` / `RestClient` перехватчика (`RequestInterceptor`), который извлекает текущий JWT из `SecurityContextHolder` и автоматически подставляет его в заголовок исходящего HTTP-запроса к другим микросервисам.
        
    5. **Файл импорта:** Сведения об автоконфигурации прописываются в `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
        

### 📞 11. External Call (Внешние интеграционные вызовы)

Паттерны и практики надежного выполнения сетевых запросов к сторонним системам:

- ⏱️ **Управление таймаутами:** Обязательная настройка `Connect Timeout` (время установки TCP-соединения, $\sim 1\text{--}3\text{ с}$) и `Read Timeout` (время ожидания ответа, $\sim 3\text{--}5\text{ с}$). Отсутствие таймаутов утилизирует все потоки пула при зависании внешнего сервиса.
    
- ⚡ **Circuit Breaker (Resilience4j):** Автоматическое размыкание цепи. Если процент ошибок внешнего сервиса превышает порог, вызовы мгновенно завершаются ошибкой (Fast Fail) без выполнения сетевого запроса, давая стороннему сервису восстановиться.
    
- 🔄 **Retry with Exponential Backoff + Jitter:** Повторные попытки запросов при сетевых сбоях с экспоненциальным увеличением паузы ожидания и случайной задержкой (Jitter), чтобы предотвратить "Thundering Herd Problem" (залповый наплыв повторных запросов).
    
- 🛡️ **Bulkhead (Изоляция ресурсов):** Ограничение количества параллельных вызовов к конкретному внешнему сервису (через отдельные пулы потоков или семафоры), чтобы падение одной интеграции не утянуло за собой остальное приложение.
    
- 🛠️ **Инструментарий:** Использование современного неблокирующего `WebClient` или `RestClient` вместо устаревшего `RestTemplate`.
    

### 🚀 12. CI/CD (Continuous Integration / Continuous Delivery & Deployment)

- 🧪 **CI (Continuous Integration — Непрерывная интеграция):**
    
    - Автоматический процесс сборки и проверки кода при каждом коммите/пулле в Git.
        
    - **Этапы:** Скачивание кода $\rightarrow$ Компиляция $\rightarrow$ Запуск Unit и Integration тестов $\rightarrow$ Статический анализ кода (SonarQube) $\rightarrow$ Сборка Docker-образа и публикация в Registry.
        
- 🚚 **CD (Continuous Delivery — Непрерывная доставка):**
    
    - Автоматизация подготовки релиза. После прохождения CI артефакт/контейнер автоматически разворачивается на Test/Staging окружение.
        
    - Выкатка на Production происходит **вручную по нажатию кнопки** авторизованным сотрудником.
        
- 🚀 **CD (Continuous Deployment — Непрерывное развертывание):**
    
    - Полностью автоматический цикл без ручного участия. Если весь конвейер CI и автотесты прошли успешно, изменения **автоматически выкатываются прямо на Production**.
        

### 🎯 13. Стратегии деплоя приложений (Deployment Strategies)

- 🛑 **Recreate (Пересоздание):** Старая версия приложения полностью останавливается, после чего запускается новая версия.
    
    - _Плюс:_ Простота, нет параллельного сосуществования разных версий.
        
    - _Минус:_ Наличие простоя сервиса (Downtime).
        
- 🔄 **Rolling Update (Постепенное обновление):** Экземпляры приложения обновляются поочередно или небольшими группами (батчами).
    
    - _Плюс:_ Отсутствие Downtime.
        
    - _Минус:_ Во время обновления в кластере одновременно работают две разные версии кода (требуется обратная совместимость API и БД).
        
- 🔵🟢 **Blue-Green Deployment:** В наличии два идентичных боевых окружения. "Blue" обрабатывает весь текущий трафик, на "Green" деплоится новая версия. После проведения Smoke-тестов балансировщик мгновенно переключает весь трафик на "Green".
    
    - _Плюс:_ Нулевой Downtime, мгновенный откат (Rollback) переключением балансировщика назад.
        
    - _Минус:_ Двойные затраты на инфраструктуру.
        
- 🐤 **Canary Deployment (Канареечный деплой):** Новая версия выкатывается на один экземпляр, и балансировщик направляет на нее небольшой процент пользователей (например, 5%). Выполняется мониторинг ошибок и метрик. При отсутствии сбоев процент трафика постепенно наращивается до 100%.
    

### 🧪 14. Типы тестов (Пирамида тестирования)

- 🧱 **Unit Tests (Модульные):** Проверяют изолированную работу одного класса/метода. Внешние зависимости подменяются моками (Mockito). Выполняются за миллисекунды. Составляют базис пирамиды (70–80% всех тестов).
    
- 🔗 **Integration Tests (Интеграционные):** Проверяют корректность взаимодействия нескольких компонентов: работу сервиса с реальной базой данных (через Testcontainers), кэшем или Kafka, поднятие Spring-контекста.
    
- 🤝 **Contract Tests (Контрактные — Spring Cloud Contract, Pact):** Проверяют совместимость API между сервисом-продюсером и сервисом-консьюмером на основе зафиксированного контракта без запуска тяжелой распределенной системы.
    
- 🌐 **End-to-End Tests (E2E / Сквозные):** Проверяют полное пользовательское поведение сквозь всю цепочку систем (от Frontend до БД и сторонних сервисов) в реальном окружении. Самые медленные, дорогие и хрупкие тесты.
    

### 🧩 15. Component Testing (Компонентное тестирование)

Тестирование отдельного микросервиса целиком как «черного ящика» в полной изоляции от окружающего мира.

- 🛠️ **Механика проведения:**
    
    - Сервис запускается полностью (поднимается реальный Spring Boot контекст, контроллеры, бизнес-логика и слои доступа к данным).
        
    - **Внутренние инфраструктурные зависимости** (PostgreSQL, Redis) поднимаются в реальном виде через **Testcontainers**.
        
    - **Все внешние сетевые зависимости** (соседние микросервисы, сторонние REST API) **подменяются заглушками-заменителями** (WireMock, MockServer).
        
- 🎯 **Цель:** Убедиться, что конкретный микросервис корректно обрабатывает входящие HTTP/MQ запросы, валидирует данные, сохраняет их в БД и формирует правильные исходящие вызовы, изолировав тест от нестабильности реальной сети.

### Serial GC
	
- **Как работает:** Использует один поток для всей процедуры сборки. На время очистки полностью останавливает работу приложения (пауза Stop-the-World).
    
- **Когда выбрать:** Для микросервисов в контейнерах с ограничениями в 1 ядро процессора, небольших CLI-утилит или приложений с объемом памяти до 100 MB.    

### Parallel GC
	
- **Как работает:** Многопоточный вариант Serial GC. Задействует все доступные ядра процессора для максимально быстрой очистки памяти. Нацелен на предельную пропускную способность (Throughput), но делает ощутимые паузы при сборке.
    
- **Когда выбрать:** Для фоновых расчетов, пакетной обработки данных (Batch processing) и аналитики, где важна итоговая скорость вычислений, а временные задержки не критичны.    

### CMS (*Concurrent Mark Sweep*)
	
- **Как работает:** Выполняет поиск и удаление мусора параллельно с работой основных потоков приложения, снижая длительность пауз. Не умеет сжимать (компактизовать) память, из-за чего со временем возникала фрагментация.
    
- **Когда выбрать:** Исторический сборщик (устарел в Java 9, полностью удален в Java 14). В современных проектах не используется.    

### **G1** (*Garbage-First*)
	
- **Как работает:** Делит всю память на сотни равных областей (регионов). В первую очередь очищает регионы с наибольшим количеством мусора (Garbage-First). Выполняет сжатие памяти на лету и позволяет задавать целевое время паузы.
    
- **Когда выбрать:** Универсальный выбор по умолчанию (с Java 9) для большинства веб-приложений и микросервисов с объемом памяти от 4 GB до 64 GB.    

### ZGC (Z Garbage Collector)
	
- **Как работает:** Сборщик с ультранизкими паузами (менее 1 миллисекунды). Выполняет практически все этапы сборки и перемещения объектов параллельно с работой приложения. Время паузы не зависит от объема оперативной памяти.
    
- **Когда выбрать:** Для высоконагруженных систем с жесткими требованиями к задержкам (Low Latency) и огромными объемами памяти (от 16 GB до нескольких терабайт).    

### Shenandoah
	
- **Как работает:** Как и ZGC, производит компактное перемещение объектов в памяти параллельно с рабочими потоками программы, исключая длинные остановки приложения.
    
- **Когда выбрать:** Для приложений с высокими требованиями к предсказуемости отклика, когда нужно избежать длинных пауз на средне-крупных объемах памяти.    

### Epsilon
	
- **Как работает:** «Заглушка», а не полноценный сборщик. Выделяет память под новые объекты, но никогда ее не очищает. Когда выделенный объем заканчивается, приложение завершается с ошибкой `OutOfMemoryError`.
    
- **Когда выбрать:** Для нагрузочного тестирования (чтобы измерить чистую производительность без влияния GC), а также для короткоживущих Serverless-функций (AWS Lambda), завершающих работу до заполнения памяти.    

### Generational ZGC
	
- **Как работает:** Эволюция ZGC с добавлением гипотезы поколений («молодые» объекты умирают чаще «старых»). Сохраняет паузы до 1 мс, но тратит значительно меньше ресурсов процессора и лучше справляется с высокой скоростью создания новых объектов.
    
- **Когда выбрать:** Главный выбор для высоконагруженных Low-Latency систем на Java 21+.    

### Generational Shenandoah
	
- **Как работает:** Расширение Shenandoah разделением памяти на молодое и старое поколения. Это сокращает расход CPU на сборку мусора и устраняет задержки при интенсивном выделении памяти.
    
- **Когда выбрать:** Для сервисов с приоритетом на минимальные задержки при активном потоке короткоживущих объектов на Java 24+.

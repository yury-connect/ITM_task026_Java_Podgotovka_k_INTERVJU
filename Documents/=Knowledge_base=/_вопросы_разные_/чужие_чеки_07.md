### 🌐 1. Блокирующий I/O (BIO) vs Неблокирующий I/O (NIO)

- 🛑 **Блокирующий I/O (BIO / `java.io`):**
    
    - **Механика:** Поток вызывает операцию чтения или записи (например, `socket.read()`) и **полностью блокируется** (переходит в состояние `BLOCKED`/`WAITING`), пока операционная система не завершит сетевой прыжок или чтение с диска.
        
    - **Архитектурный подход:** Модель «один поток на одно соединение» (Thread-per-connection).
        
    - **Минусы:** При высоком параллелизме (10 000+ одновременных подключений) приложение падает или тормозит из-за гигантского расхода оперативной памяти на стеки потоков и оверхеда на переключение контекста процессора (Context Switching).
        
- ⚡ **Неблокирующий I/O (NIO / `java.nio`):**
    
    - **Механика:** Поток запрашивает операцию I/O. Если данные еще не готовы, поток **не блокируется**, а мгновенно получает ответ, что данных нет, и может выполнять другую работу.
        
    - **Архитектурный подход:** Модель «Event Loop» и мультиплексирование через **`Selector`**. Один или несколько системных потоков непрерывно опрашивают сотни и тысячи сетевых каналов (`SocketChannel`) на предмет готовности данных.
        
    - **Где используется:** Netty, Spring WebFlux, Nginx, Node.js.
        

### 🧵 2. Виртуальные потоки (Virtual Threads / Java 21+)

Легковесные потоки, управляемые виртуальной машиной (JVM), а не ядрами операционной системы (Project Loom).

- ⚖️ **Отличие от системных потоков (Platform Threads):**
    
    - Системный поток имеет фиксированный стек размером $\sim 1 \text{ МБ}$ памяти и жестко привязан к потоку ОС.
        
    - Виртуальный поток занимает в памяти Heap всего **несколько сотен байт** и может создаваться миллионами экземпляров без риска перегрузки системы.
        
- ⚙️ **Как работают под капотом:**
    
    - Виртуальные потоки исполняются поверх небольшого пула системных **потоков-носителей (Carrier Threads)**.
        
    - В момент, когда виртуальный поток доходит до блокирующего вызова I/O (запрос в БД, `Thread.sleep()`, сетевой вызов), JVM перехватывает этот вызов, **отмонтирует (unmounts)** виртуальный поток от Carrier Thread и сохраняет его стек в Heap.
        
    - Освободившийся Carrier Thread мгновенно берет в работу другой виртуальный поток.
        
- ⚠️ **Главное ограничение:** Виртуальные потоки **не ускоряют CPU-bound вычисления** (математику, криптографию), так как физические ядра CPU не становятся быстрее. Они предназначены исключительно для I/O-bound задач с частыми ожиданиями.
    

### ⚛️ 3. CAS и Атомики

- ⚙️ **CAS (Compare-And-Swap / Сравнение с обменом):**
    
    - Атомарная инструкция на аппаратном уровне процессора (например, `CMPXCHG` на архитектурах x86).
        
    - Принимает три параметра: `(адрес_памяти, ожидаемое_старое_значение, новое_значение)`.
        
    - Если текущее значение в памяти совпадает с ожидаемым — процессор атомарно меняет его на новое и возвращает `true`. Если значение успел изменить другой поток — инструкция возвращает `false`, не меняя данные.
        
- ⚛️ **Атомики (`java.util.concurrent.atomic`):**
    
    - Классы (`AtomicInteger`, `AtomicReference` и др.), реализующие **Lock-free (неблокирующую)** потокобезопасность.
        
    - Под капотом они исполняют операцию CAS в бесконечном цикле (**spin-lock**): поток пытается обновить значение; если CAS вернул `false` (был конфликт), поток не уходит в тяжелую блокировку ОС, а мгновенно перечитывает свежее значение и повторяет попытку CAS заново, пока она не завершится успехом.
        

### 🌐 4. Принципы REST (6 REST Constraints)

Архитектурный стиль взаимодействия систем над HTTP, описанный Роем Филдингом:

1. 💻 **Client-Server (Клиент-Сервер):** Строгое разделение ответственности между клиентом (UI/пользовательский интерфейс) и сервером (хранение и обработка данных).
    
2. 🚫 **Stateless (Отсутствие состояния сессии):** Сервер не хранит никаких данных о состоянии сессии клиента между запросами. Каждый запрос от клиента обязан содержать всю необходимую информацию для своей обработки (например, JWT-токен).
    
3. 💾 **Cacheable (Кэшируемость):** Все ответы сервера должны быть явно помечены как кэшируемые или некэшируемые (через заголовки `Cache-Control`), чтобы клиент мог повторно использовать данные.
    
4. 🔌 **Uniform Interface (Единый интерфейс):**
    
    - Идентификация ресурсов через понятные URI (`/api/v1/users/42`).
        
    - Манипуляция ресурсами через стандартные HTTP-методы (`GET`, `POST`, `PUT`, `DELETE`).
        
    - Самоописываемые сообщения (заголовки `Content-Type`).
        
    - HATEOAS (гипермедиа как средство управления состоянием приложения).
        
5. 🧱 **Layered System (Многоуровневая система):** Клиент не знает, общается он напрямую с финальным сервером или с промежуточными слоями (балансировщики, прокси, CDN, API Gateway).
    
6. 📜 **Code on Demand (Код по запросу — опционально):** Сервер может временно расширять функционал клиента, передавая ему исполняемый код (например, JavaScript-скрипты).
    

### 🧪 5. @Mock vs @MockBean

- 🤖 **`@Mock` (Mockito Framework):**
    
    - Создает чистый виртуальный мок-объект средствами самой библиотеки Mockito без поднятия Spring-контекста.
        
    - Используется в изолированных **Unit-тестах** (`@ExtendWith(MockitoExtension.class)`). Работает мгновенно.
        
- 🍃 **`@MockBean` (Spring Boot Test):**
    
    - Создает мок-объект и **внедряет его напрямую в Spring ApplicationContext**, принудительно заменяя настоящий реальный бин этим моком.
        
    - Используется в **интеграционных тестах** (`@SpringBootTest`, `@WebMvcTest`), когда нужно проверить взаимодействие компонентов Spring-контекста, подменив конкретный внешний сервис (например, отправку SMS или вызов внешней БД).
        

### 🔑 6. ReentrantLock

Явная реализация блокировки из пакета `java.util.concurrent.locks`, пришедшая на смену встроенному `synchronized`:

- 🔄 **Reentrant (Повторная входимость):** Если поток уже захватил блокировку, он может повторно зайти в любой другой метод, защищенный этой же блокировкой, без возникновения дедлока (внутренний счетчик удерживаний просто увеличивается на 1).
    
- 🛡️ **Гибкие механизмы управления:**
    
    - `tryLock()` — неблокирующая попытка забрать замок (возвращает `false`, если замок занят, или ждет указанный таймаут).
        
    - `lockInterruptibly()` — позволяет прервать поток через `Thread.interrupt()`, пока он ждет освобождения блокировки.
        
    - **Честность (Fairness):** Конструктор `new ReentrantLock(true)` организует справедливую FIFO-очередь ожидания потоков, исключая проблему голодания (Starvation).
        
    - **Condition:** Позволяет создавать несколько независимых условий ожидания сигналов для одной блокировки (методы `await()` / `signal()`).
        

### 📊 7. Отличие Hashtable от HashMap

- 📜 **`Hashtable` (Legacy):**
    
    - Появилась в Java 1.0. Устаревшая потокобезопасная коллекция.
        
    - Потокобезопасность реализована грубо: над **каждым методом** висит ключевое слово `synchronized`, блокирующее всю таблицу целиком при любой операции.
        
    - **Категорически запрещает `null`** как в качестве ключей, так и в качестве значений (выбрасывает `NullPointerException`).
        
- 🚀 **`HashMap` (Modern):**
    
    - Появилась в Java 1.2. Не является потокобезопасной.
        
    - Разрешает хранить **один `null` ключ** и любое количество `null` значений.
        
    - Работает в разы быстрее. Начиная с Java 8, при коллизиях умеет трансформировать односвязные списки бакетов в Красно-Черные деревья (при достижении 8 элементов в бакете).
        

### 🌐 8. Что такое gRPC (и JRPC)

- 🚀 **gRPC (Google Remote Procedure Call):**
    
    - Высокопроизводительный фреймворк для межсервисного взаимодействия (RPC), работающий поверх транспортного протокола **HTTP/2**.
        
    - Использует **Protocol Buffers (.proto)** в качестве строго типизированного языка описания контрактов и бинарной сериализации данных (работает намного быстрее и компактнее текстового JSON).
        
    - Поддерживает 4 типа вызовов: Unary (обычный), Server Streaming, Client Streaming и Bidirectional Streaming (двунаправленный стриминг).
        
- 📄 **JSON-RPC (JRPC):**
    
    - Простой легкий протокол вызова удаленных процедур, использующий в качестве формата передачи данных базовый **JSON** (`{"jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 1}`). Работает поверх любого транспорта (HTTP, WebSocket).
        

### 🛡️ 9. Уровни изоляции транзакций

Определяют degree (степень) изолированности параллельно выполняющихся транзакций на стороне СУБД:

1. 🔓 **Read Uncommitted:** Самый слабый уровень. Транзакция видит незакоммиченные изменения других транзакций. **Допускает грязное чтение (Dirty Read)**.
    
2. 🔒 **Read Committed (Дефолт в Postgres/Oracle):** Транзакция видит только закоммиченные изменения. Защищает от Dirty Read. **Допускает неповторяемое чтение (Non-Repeatable Read)**.
    
3. 🛡️ **Repeatable Read:** Повторный `SELECT` той же строки внутри транзакции всегда гарантированно вернет идентичные данные. Защищает от Non-Repeatable Read. _(В PostgreSQL этот уровень также защищает от фантомных чтений Phantom Read)_.
    
4. 🏰 **Serializable:** Полная изоляция параллельных транзакций (эмуляция их строго последовательного выполнения). Защищает от всех известных аномалий, включая искажение записи (**Write Skew**).
    

### 👵 10. Young Generation и Old Generation в JVM Heap

Память Heap в Java разделена на области в соответствии с **слабой гипотезой о поколениях (Weak Generational Hypothesis)**: большинство объектов умирают практически сразу после создания.

- 🐣 **Young Generation (Молодое поколение):**
    
    - Зона для размещения свежесозданных объектов.
        
    - Состоит из 3 регионов: **Eden** (куда изначально попадают все объекты через `new`) и двух регионов выживших **Survivor 0 (S0)** и **Survivor 1 (S1)**.
        
    - Очищается быстрой сборкой мусора — **Minor GC**. Выжившие объекты перекладываются из Eden в S0/S1 и инкрементируют свой возраст (Age).
        
- 👴 **Old Generation (Tenured / Старое поколение):**
    
    - Хранит долгоживущие объекты и крупные массивы.
        
    - Если объект выживает в Young Gen в течение $N$ сборок мусора (параметр `-XX:MaxTenuringThreshold`, по умолчанию обычно 15), он **продвигается (promoted) в Old Gen**.
        
    - Очищается более тяжелой сборкой мусора — **Major GC / Full GC**, которая сопровождается длительными паузами Stop-The-World (STW).
        

### ⚠️ 11. Проблема Atomic при высоконагруженных средах (High Contention)

- 🔴 **Суть проблемы:**
    
    - Классы вроде `AtomicLong` работают на одиночной CAS-переменной.
        
    - При экстремальной конкуренции (сотни параллельных потоков одновременно делают `incrementAndGet()`) удачно выполнить CAS получается только у одного потока.
        
    - Остальные 99 потоков терпят неудачу, сваливаются в затяжные циклы `spin-lock` и массово повторно запрашивают CAS.
        
    - **Результат:** Процессор выжигается на $100\%$ бесполезными циклами ожидания, а шина памяти перегружается постоянной инвалидацией кэшей CPU (Cache Coherence Traffic).
        
- 🟢 **Решение (`LongAdder` / `LongAccumulator`):**
    
    - В Java 8 появились спец-классы `LongAdder`.
        
    - Вместо одной переменной `LongAdder` внутри держит динамический **массив ячеек (`Cell[]`)**.
        
    - При высокой конкуренции потоки случайным образом распределяются по разным ячейкам массива и атомарно обновляют только свою ячейку, не мешая остальным!
        
    - Когда требуется получить итоговый результат, метод `sum()` просто суммирует значения всех ячеек.
        

### 🔄 12. Как заинжектить Prototype в Singleton (Scope Mismatch)

Проблема возникнет из-за того, что `Singleton`-бин создается один раз при старте контекста и навсегда фиксирует заинжекченный в него экземпляр `Prototype`-бина.

**Три правильных способа решения:**

1. 🎭 **Scoped Proxy (Самый декларативный вариант):**
    
    Пометить Prototype-класс аннотацией с созданием CGLIB-прокси:
```Java
    @Component
    @Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE, proxyMode = ScopedProxyMode.TARGET_CLASS)
    public class MyPrototypeBean {}
```
    
_Spring внедрит прокси. При каждом обращении к методам прокси он будет запрашивать у контекста свежий экземпляр Prototype-бина._
    
2. 📦 **Использование `ObjectProvider<T>`:**        
```Java
    @Service
    public class MySingletonService {
        @Autowired
        private ObjectProvider<MyPrototypeBean> prototypeProvider;
    
        public void doWork() {
            MyPrototypeBean freshInstance = prototypeProvider.getObject(); // Всегда новый экземпляр
        }
    }
```
    
3. 🔍 **Использование аннотации `@Lookup`:**
    
    Объявить внутри синглтона абстрактный или пустой метод-заглушку:
```Java
    @Lookup
    public MyPrototypeBean getPrototypeBean() {
        return null; // Spring переопределит этот метод через CGLIB
    }
```
    

### 🧵 13. String Pool (Пул строк)

Специальная область памяти внутри **Heap** (кучи), предназначенная для оптимизации расхода RAM путем сохранения только уникальных экземпляров строковых литералов.

- 💡 **Как работает:**
    
    - При объявлении строки через литерал `String s = "hello";` JVM ищет строку `"hello"` в String Pool. Если она там есть — возвращается ссылка на существующий объект. Если нет — создается новый объект в пуле.
        
    - При явном создании через конструктор `String s = new String("hello");` JVM **принудительно создаст новый объект в общем Heap**, минуя String Pool (что приводит к перерасходу памяти).
        
- 🔍 **Метод `intern()`:**
    
    - Вызов `str.intern()` ищет строку в String Pool. Если строка найдена — возвращает ссылку из пула. Если нет — добавляет текущую строку в String Pool и возвращает ссылку на нее.
        
- 🧹 **GC в String Pool:** Начиная с Java 7 (когда String Pool перенесли из PermGen в основную Heap), неиспользуемые строки из String Pool полноправно удаляются сборщиком мусора, если на них больше нет живых ссылок.

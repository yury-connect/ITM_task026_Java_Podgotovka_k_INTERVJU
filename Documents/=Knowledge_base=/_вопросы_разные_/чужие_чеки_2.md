### ✂️ 1. Spring AOP: Концепция и сквозное логирование

**Что такое AOP (Aspect-Oriented Programming):**

Парадигма, позволяющая вынести сквозную системную логику (Cross-Cutting Concerns: логирование, транзакции, безопасность, кэширование) из основного бизнес-кода в отдельные модули — **Аспекты**.

**Ключевые понятия AOP:**

- 🧩 **Aspect:** Класс с аннотацией `@Aspect`, объединяющий срез и советы.
    
- 📍 **JoinPoint:** Точка в программе (вызов метода), где может быть применен аспект.
    
- 🎯 **Pointcut:** Выражение-фильтр (синтаксис AspectJ), определяющее, к каким именно методам применится аспект (например, `execution(* com.example.service.*.*(..))`).
    
- 💡 **Advice:** Действие, выполняемое аспектом: `@Before`, `@After`, `@AfterReturning`, `@AfterThrowing` или `@Around`.
    

**Как реализуется сквозное логирование через `@Around`:**

Аннотация `@Around` дает полный контроль над выполнением метода и позволяет замерить время работы или залогировать входящие/исходящие данные:

```Java
@Aspect
@Component
@Slf4j
public class LoggingAspect {

    @Around("execution(* com.example.service..*.*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        String methodName = joinPoint.getSignature().toShortString();
        Object[] args = joinPoint.getArgs();
        log.info("▶️ Вызов метода {} с аргументами: {}", methodName, Arrays.toString(args));

        long start = System.currentTimeMillis();
        try {
            Object result = joinPoint.proceed(); // Вызов реального метода
            long executionTime = System.currentTimeMillis() - start;
            log.info("✅ Метод {} успешно выполнен за {} мс. Результат: {}", methodName, executionTime, result);
            return result;
        } catch (Throwable ex) {
            log.error("❌ Исключение в методе {}: {}", methodName, ex.getMessage());
            throw ex;
        }
    }
}
```

### 🍃 2. Spring vs Spring Boot: Отличия, плюсы и минусы

- 🌿 **Spring Framework:** Базовый фреймворк, предоставляющий IoC/DI контейнер, абстракции над JDBC/ORM, MVC и AOP.
    
    - _Особенность:_ Требует явной ручной конфигурации (XML или Java Config) и сборки приложения в WAR-архив для деплоя во внешний Сервлет-контейнер (Tomcat/WildFly).
        
- 🧰 **Spring Boot:** Инструмент надстройка **над** Spring Framework, ориентированный на быстрый запуск (Convention over Configuration).
    
    - _Ключевые фичи:_ Автоконфигурация, стартеры (`spring-boot-starter-*`), встроенный веб-сервер (Embedded Tomcat/Netty) и Actuator для метрик.
        

**Плюсы Spring Boot:**

- 🚀 Мгновенный старт разработки без написания версий зависимостей и тяжелых XML.
    
- 📦 Сборка в автономный исполняемый **Fat JAR** (запуск через `java -jar`).
    
- ⚙️ Огромное экосистемное сообщество и нативные механизмы профилей (`application-dev.yml`).
    

**Минусы Spring Boot:**

- 🪄 **«Магия» автоконфигурации:** Неопытному разработчику сложно понять, почему поднялся конкретный бин, если не знать работу `@ConditionalOn...`.
    
- 🐘 **Тяжеловесность:** Потребляет больше оперативной памяти и имеет более долгий холодный старт (Cold Start) из-за багажа автоконфигураций.
    

### 🌐 3. @Controller vs @RestController

- 🖥️ **`@Controller`:** Классический стереотип Spring MVC для веб-приложений.
    
    - Возвращает **`String`** — имя шаблона View (Thymeleaf, JSP). `DispatcherServlet` передает это имя в `ViewResolver`, который рендерит HTML-страницу для браузера.
        
- 🔌 **`@RestController`:** Аннотация-комбинация **`@Controller` + `@ResponseBody`**.
    
    - Предназначена для создания **REST API**.
        
    - Возвращает **Java-объекты (DTO)**. Аннотация `@ResponseBody` под капотом отключает поиск View-шаблонов и задействует **`HttpMessageConverter`** (например, `MappingJackson2HttpMessageConverter`), который напрямую сериализует Java-объект в JSON/XML и пишет его в тело HTTP-ответа.
        

### 🗄️ 4. @Component vs @Repository

- 🧩 **`@Component`:** Базовый аннотация-стереотип. Помечает класс как Spring-бин, отдавая его под управление IoC-контейнера.
    
- 🗄️ **`@Repository`:** Специализированный стереотип для классов слоя доступа к данным (DAO / Repositories), который наследуется от `@Component`.
    

**Главное отличие под капотом:**

Помимо сканирования компонентов, `@Repository` активирует постобработчик **`PersistenceExceptionTranslationPostProcessor`**.

Этот компонент автоматически перехватывает специфичные для конкретных вендоров СУБД или ORM исключения (например, нативные `SQLException`, `HibernateException`, `PersistenceException`) и **транслирует их в единую иерархию непроверяемых исключений Spring — `DataAccessException`** (например, `DataIntegrityViolationException`). Это изолирует бизнес-код от деталей конкретной БД.

### 🌊 5. Почему Stream API является «ленивым» (Lazy Evaluation)

Стримы работают по принципу **конвейера (pipeline)**:

- 🛠️ **Промежуточные операции (Intermediate):** `map()`, `filter()`, `flatMap()`, `sorted()`.
    
    - При их вызове **никакая обработка элементов не происходит**. Вызов промежуточной операции лишь конструирует новый объект `Stream`, записывая шаг обработки во внутреннюю цепочку.
        
- ⚡ **Терминальные операции (Terminal):** `collect()`, `forEach()`, `reduce()`, `count()`.
    
    - Вызов терминальной операции **запускает фактическое выполнение** всего конвейера и проход по источнику данных.
        

**Зачем нужна ленивость (Плюсы производительности):**

1. 🏎️ **Слияние циклов (Loop Fusion):** Стрим делает **ровно один проход** по коллекции. Если написать `.filter().map().filter()`, элементы будут прогоняться через весь цепочку поштучно за один цикл, а не создавать промежуточные коллекции на каждом этапе.
    
2. 🛑 **Короткое замыкание (Short-Circuiting):** Операции вроде `findFirst()`, `anyMatch()` или `limit(n)` останавливают обработку источника сразу при выполнении условия, не обрабатывая оставшиеся миллионы элементов.
    

### 🔄 6. Внедрение Prototype-бина в Singleton (Scope Mismatch)

**Проблема:** Бин со скоупом `Singleton` создается контейнером **один раз** при старте приложения. Если инжектить в него `Prototype`-бин напрямую через конструктор или поле, Spring создаст экземпляр Prototype-бина ровно один раз во время сборки синглтона. В результате Prototype-бин «застрянет» внутри синглтона и сам станет фактически синглтоном.

**Три решения задачи:**

1. 🎭 **Scoped Proxy (Самый декларативный способ):**
    
    Добавить над `Prototype`-бином аннотацию с режимом прокси:
    
    
```Java
    @Component
    @Scope(value = ConfigurableBeanFactory.SCOPE_PROTOTYPE, proxyMode = ScopedProxyMode.TARGET_CLASS)
    public class PrototypeBean {}
```
    
    _Spring внедрит CGLIB-прокси. При каждом вызове метода этого прокси он будет обращаться к контексту и генерировать новый экземпляр._
    
2. 📦 **Использование `ObjectProvider<T>`:**
```Java
    @Service
    public class SingletonService {
        @Autowired
        private ObjectProvider<PrototypeBean> prototypeProvider;
    
        public void process() {
            PrototypeBean freshInstance = prototypeProvider.getObject(); // Каждый раз новый
        }
    }
```
    
3. 🔍 **Использование `@Lookup`:**
    
    Объявить внутри синглтона метод-заглушку, который Spring переопределит через CGLIB:    
 ```Java
    @Lookup
    public PrototypeBean getPrototypeBean() { return null; }
 ```


### 💥 7. @PreDestroy в Prototype-бине

**Вызывается ли `@PreDestroy` для бинов со скоупом `Prototype`?**

**НЕТ, не вызывается!** ❌

**Почему так устроено:**

Контейнер Spring полностью берёт на себя управление жизненным циклом только для **`Singleton`**-бинов.

Для бинов со скоупом **`Prototype`** Spring выполняeт только создание, внедрение зависимостей и вызов методов инициализации (`@PostConstruct` / `afterPropertiesSet`), после чего **отдает объект клиенту и полностью забывает про него**. Контейнер не хранит ссылки на Prototype-бины, поэтому при закрытии контекста методы уничтожения (`@PreDestroy` / `DisposableBean`) для них **не вызываются**. Освобождение их ресурсов лежит на разработчике.

### 📊 8. EXPLAIN vs EXPLAIN ANALYZE

- 📑 **`EXPLAIN`:**
    
    - Возвращает **расчетный (теоретический) план выполнения** SQL-запроса, построенный Cost-Based оптимизатором СУБД на основе накопленной статистики.
        
    - **Запрос при этом физически НЕ выполняется!** Работает мгновенно.
        
- ⏱️ **`EXPLAIN ANALYZE`:**
    
    - **Физически выполняет** SQL-запрос в базе данных.
        
    - Возвращает реальные метрики: фактическое время выполнения каждого узла (`actual time`), количество прочитанных строк (`actual rows`), проходы по кэшу и диску (`Buffers: shared hit/read`).
        

⚠️ **Опасность `EXPLAIN ANALYZE`:**

Если запустить `EXPLAIN ANALYZE` для команд `UPDATE` или `DELETE`, **запрос реально модифицирует или удалит данные в вашей БД**! Для безопасной проверки модифицирующих запросов их обворачивают в транзакцию с последующим откатом (`BEGIN; EXPLAIN ANALYZE UPDATE...; ROLLBACK;`).

### 📦 9. Что такое Spring Starter и как он устроен

**Spring Boot Starter** — это скомпонованный модуль (JAR-архив), содержащий набор транзитивных зависимостей и логику автоконфигурации под конкретную задачу (например, `spring-boot-starter-data-jpa`).

**Как устроен механизм автоконфигурации под капотом:**

1. Starter привносит конфигурационный класс с аннотацией **`@AutoConfiguration`**.
    
2. Внутри класса описываются `@Bean`-методы, обернутые условными аннотациями семейства **`@ConditionalOn...`**:
    
    - `@ConditionalOnClass(DataSource.class)` — активируется, если класс есть в classpath.
        
    - `@ConditionalOnMissingBean(MyService.class)` — активируется, только если пользователь сам не создавал такой бин.
        
    - `@ConditionalOnProperty(name = "feature.enabled", havingValue = "true")` — проверяет `application.yml`.
        
3. **Регистрация:** Сведения об автоконфигурациях регистрируются в служебном файле `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (в Spring Boot 3.x). Spring Boot читает этот файл при старте и поднимает бины.
    

### 🛡️ 10. Optional.ofNullable

`Optional.ofNullable(T value)` — фабричный метод класса `Optional`, который создаёт контейнер, безопасно обрабатывающий возможный `null`:

- Если переданный объект **не-null** — возвращается `Optional`, содержащий данное значение.
    
- Если передан **`null`** — возвращается пустой контейнер **`Optional.empty()`** (без выбрасывания `NullPointerException`).
    

**В чем отличие от `Optional.of(T value)`:**

Вызов `Optional.of(null)` **сразу выбросит `NullPointerException`**. Метод `of()` используется только тогда, когда вы на 100% уверены, что объект не равен `null`.

**Ключевые методы работы с `Optional`:**

- `orElse(defaultValue)` — возвращает значение или дефолтный объект (дефолтный объект вычисляется **всегда**, даже если Optional не пуст).
    
- `orElseGet(() -> fetchDefault())` — ленивый вариант `orElse` (Supplier вызывается **только** если Optional пуст).
    
- `orElseThrow(() -> new NotFoundException())` — выбрасывает кастомное исключение, если значение отсутствует.
    
- `map(Function)` / `flatMap(Function)` — безопасная трансформацией внутри контейнера.
    

### ☠️ 11. Kafka Dead Letter Queue (DLQ / DLT)

**Dead Letter Queue (Dead Letter Topic)** — специальный служебный топик в Kafka, предназначенный для изоляции сообщений, обработка которых завершилась критической ошибкой ("poison pills").

**Зачем нужен и как работает:**

1. Консюмер вычитывает сообщение из основной партиции и пытается его обработать (например, распарсить JSON или записать в БД).
    
2. Происходит сбой. Консюмер делает $N$ повторных попыток (Retries) с заданными паузами (Backoff).
    
3. Если все попытки исчерпаны, а ошибка не устранена, механизм `DefaultErrorHandler` в Spring Kafka отправляет сбойное сообщение в **DLT-топик** (обычно с именем `<original_topic>.DLT`) и **коммитит оффсет** в основной партиции.
    

**Главный профит:** Основная партиция не застревает в бесконечном цикле ошибок, а продолжит вычитку свежих сообщений. Битые данные из DLT инженеры могут разобрать и переотправить вручную.

### 📩 12. Kafka семантики доставки (Глубокое погружение)

#### 1. At-Most-Once (Максимум один раз)

- **Гарантия:** Сообщение будет доставлено 0 или 1 раз. Потери возможны, дубликаты исключены.
    
- **Как настраивается:** Консюмер коммитит оффсет **ДО** того, как бизнес-логика реально обработает сообщение (`enable.auto.commit=true`). Если консюмер упадет во время обработки, при перезапуске он пропустит это сообщение.
    

#### 2. At-Least-Once (Хотя бы один раз)

- **Гарантия:** Сообщение гарантированно доставится, но возможны дубликаты.
    
- **Как настраивается:**
    
    - Продюсер шлет с `acks=all` и повторными попытками (`retries > 0`).
        
    - Консюмер коммитит оффсет strictly **ПОСЛЕ** успешного завершения бизнес-обработки сообщения.
        
    - _Если консюмер упал после бизнес-логики, но до коммита оффсета — при перезапуске он вычитает сообщение повторно (требуется идемпотентность бизнеса!)._
        

#### 3. Exactly-Once Semantics (EOS / Строго один раз)

- **Гарантия:** Сообщение обрабатывается ровно 1 раз без потерь и дубликатов на всём маршруте _Producer $\rightarrow$ Kafka $\rightarrow$ Consumer_.
    

**Как реализуется под капотом:**

1. **Идемпотентный продюсер (`enable.idempotence=true`):** Брокер присваивает продюсеру `Producer ID (PID)` и с каждым сообщением ждет монотонно растущий Sequence Number. Если брокер получает дубликат sequence number — он отбрасывает его на уровне хранилища.
    
2. **Транзакционный продюсер (`transactional.id=my-tx-id`):** Использует координатор транзакций и 2PC (двухфазный коммит) внутри самой Kafka.
    
3. **Связка Read-Process-Write:** Продюсер отправляет результирующее сообщение и **коммитит вычитанный оффсет входящего топика в единой транзакции Kafka**:
    
    
    
 ```Java
    kafkaTemplate.executeInTransaction(kt -> {
        kt.send("output-topic", resultData);
        kt.sendOffsetsToTransaction(offsets, consumerGroupId);
        return null;
    });
 ```
    
4. **Консюмер:** Настраивается параметром **`isolation.level=read_committed`** — он видит сообщения только из успешно закоммиченных транзакций Kafka.
    

### 🧪 13. Юнит и интеграционные тесты. Spying в Mockito

**Unit-тесты (Модульные):**

- Тестируют один конкретный класс в полной изоляции от внешнего мира.
    
- Не поднимают Spring-контекст, работают мгновенно. Все внешние зависимости подменяются заглушками (`@Mock` / `Mockito.mock()`).
    

**Integration-тесты (Интеграционные):**

- Тестируют связку нескольких компонентов системы: работу сервисов с реальной базами данных (через Testcontainers), веб-слоем (`MockMvc`) или Kafka.
    
- Поднимают контекст Spring (`@SpringBootTest`).
    

#### Mock (`@Mock` / `@MockBean`) vs Spy (`@Spy` / `@SpyBean`)

- **Mock (`@Mock`):** Полный фейк. Все методы объекта по умолчанию возвращают `null`, `0` или пустые коллекции, пока их поведение явно не зададут через `when(mock.method()).thenReturn(...)`.
    
- **Spy (`@Spy`):** **Частичный мок (Partial Mock)**. Оборачивает **реальный существующий объект**:
    
    - По умолчанию вызов любого метода объекта выполнит его **настоящую реальную логику**.
        
    - Мы можем избирательно перехватить ("замокать") только _один конкретный метод_ этого объекта, оставив остальные работать как обычно.
        

**Правильный синтаксис для Spy:**

При работе со Spy нужно использовать форму записи `doReturn().when(spyObject).method()`, а не `when(spyObject.method()).thenReturn()`, иначе в момент настройки `when()` сработает настоящий метод объекта!

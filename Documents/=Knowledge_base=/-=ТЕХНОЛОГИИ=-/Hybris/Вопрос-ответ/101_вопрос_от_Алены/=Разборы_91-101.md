**91. Можно ли синхронизировать данные из online в stage? Можно ли отображать на сайте данные из stage?**

- **Синхронизация `Online` $\rightarrow$ `Staged`:** Да, это технически возможно. В Hybris синхронизация задается конфигурацией `CatalogVersionSyncJob`, где указываются `source` (источник) и `target` (приемник). Можно создать джобу, где `source = Online`, а `target = Staged` (используется при аварийных фиксах данных прямо на проде).
    
- **Отображение `Staged` на сайте:** Да, возможно. По умолчанию витрина читает каталог `Online`, но в режиме предпросмотра (**SmartEdit / CMS Cockpit**) или программно через `catalogVersionService.setSessionCatalogVersions(...)` сессия пользователя переключается на чтение `Staged`-версии.
    

**92. Что такое HAC? Какие возможности чаще всего использовали?**

**HAC (Hybris Administration Console)** — служебный веб-интерфейс (`/hac`) для разработчиков и системных администраторов.

**Часто используемые функции:**

- `Platform -> Init/Update` — обновление структуры и инициализация базы данных.
    
- `Console -> FlexibleSearch` — составление, проверка и анализ сгенерированного SQL-кода.
    
- `Console -> ImpEx Import` — экспресс-загрузка скриптов данных.
    
- `Console -> Scripting Languages` — выполнение **Groovy**-скриптов прямо на работающей JVM.
    
- `Monitoring -> Cache` — точечный сброс кэша платформы (`Region Cache`).
    
- `Support -> Log4j` — динамическое переключение уровня логирования (например, перевод пакета в `DEBUG`) без перезапуска.
    

**93. Что такое ImpEx? Какие параметры (галочки) используются при выполнении скриптов? Для чего Enable Code Execution и Legacy Mode?**

**ImpEx** — текстовый CSV-подобный инструмент/язык для работы с базами данных Hybris.

**Параметры при импорте:**

- _Validation Mode:_ `Strict` (падать при любой ошибке) или `Relaxed` (пропускать битые строки).
    
- _Max Threads:_ Настройка многопоточности для ускорения за빅загрузок.
    
- _Enable Code Execution:_ Разрешает выполнение embedded-скриптов на **Groovy / BeanShell**, прописанных прямо внутри CSV-строк.
    
- _Enable Legacy Mode:_ Переключает импорт со стандартного `ServiceLayer` на устаревший слой `JALO`. Данные пишутся напрямую в БД в обход валидаторов и интерцепторов Hybris (используется для ускорения заливки гигантских дампов данных).
    

**94. Какие операции поддерживает ImpEx (insert, update, remove)? Как указывается уникальный атрибут?**

**Поддерживаемые операции (директивы):**

- `INSERT` — только создание новых записей (упадет, если запись существует).
    
- `UPDATE` — только обновление существующих записей.
    
- `INSERT_UPDATE` (Upsert) — универсальный режим: создает новую запись или обновляет существующую.
    
- `REMOVE` — физическое удаление найденных записей из БД.
    

**Уникальный атрибут:**

Задается добавлением модификатора **`[unique=true]`** в колонке заголовка ImpEx-файла.

Фрагмент кода

```
INSERT_UPDATE Product; code[unique=true]; name[lang=ru]
; prod_100; Ноутбук
```

**95. Использовались ли deployment manager, Liquibase?**

Для управления основной базой данных Hybris **Liquibase и Flyway НЕ используются**.

- Единственным источником правды для структуры БД в Hybris являются файлы **`items.xml`**.
    
- Миграция и создание таблиц выполняется штатными Ant-командами (`ant updatesystem` / `ant initialize`).
    
- _Примечание:_ Liquibase или Flyway могут использоваться отдельно только во внешних изолированных Spring Boot микросервисах, не связанных с ядром Hybris.
    

**96. Как работает жизненный цикл модели в сервисном слое? Какие вызываются интерцепторы?**

```
1. modelService.create(ProductModel.class)
   └──> Вызывается InitDefaultsInterceptor (заполнение дефолтов из items.xml)

2. Изменение полей через сеттеры
   └──> Модель переходит в состояние Dirty (изменена в память)

3. modelService.save(model)
   ├──> 1. PrepareInterceptor (подготовка/трансформация данных)
   ├──> 2. ValidateInterceptor (проверка бизнес-правил)
   └──> Выполнение SQL INSERT / UPDATE в БД

4. modelService.remove(model)
   ├──> Вызывается RemoveInterceptor
   └──> Выполнение SQL DELETE из БД
```

**97. Как сохранить объект, созданный через new, в базу данных?**

Объект, созданный через обычный Java-оператор `new`, сохраняется стандартным методом:

Java

```
ProductModel product = new ProductModel();
product.setCode("custom_code");
product.setCatalogVersion(catalogVersionModel);

// Сохранение в БД
modelService.save(product);
```

- **Что произойдет:** При вызове `modelService.save()` Hybris определит, что у модели нет `PK`, автоматически сгенерирует его, прогонит объект через `PrepareInterceptor` и `ValidateInterceptor` и выполнит SQL `INSERT`.
    
- _Нюанс:_ Для объекта, созданного через `new`, **не вызывается** `InitDefaultsInterceptor`. Поэтому правильным стандартом Hybris является создание моделей через `modelService.create(ProductModel.class)`.
    

**98. Как создаются свои интерцепторы?**

1. **Создать Java-класс**, реализовав один из интерфейсов (например, `PrepareInterceptor<ProductModel>`):
    
    Java
    
    ```
    public class CustomProductPrepareInterceptor implements PrepareInterceptor<ProductModel> {
        @Override
        public void onPrepare(ProductModel product, InterceptorContext ctx) throws InterceptorException {
            if (product.getName() != null) {
                product.setName(product.getName().trim());
            }
        }
    }
    ```
    
2. **Зарегистрировать класс как Spring-бин** в `*-spring.xml`.
    
3. **Связать с типом сущности** через `InterceptorMapping`:
    
    XML
    
    ```
    <bean id="customProductPrepareMapping" class="de.hybris.platform.servicelayer.interceptor.impl.InterceptorMapping">
        <property name="interceptor" ref="customProductPrepareInterceptor"/>
        <property name="typeCode" value="Product"/>
    </bean>
    ```
    

**99. В чем разница между синхронными и асинхронными событиями? Как они работают в кластере?**

|**Характеристика**|**Синхронные события**|**Асинхронные события**|
|---|---|---|
|**Поток**|Выполняются в **том же потоке**, что и вызов `publishEvent()`.|Выполняются в **фоновом потоке** из пула задач.|
|**Блокировка**|Основной поток ждет завершения всех слушателей.|Основной поток не ждет выполнения слушателей.|
|**Транзакции**|Ошибка в слушателе откатывает общую транзакцию.|Ошибка в слушателе не влияет на основную транзакцию.|

**Работа в кластере:**

Если класс события наследуется от `ClusterAwareEvent`, платформа при его публикации автоматически сериализует его и рассылает по сети на все соседние ноды кластера через сетевой транспорт (JGroups / UDP / TCP).

**100. Пример события, которое раскидывается на все ноды (инвалидация кэша).**

**`EntityCacheInvalidationEvent`** (или `CatalogVersionSyncCompletedEvent`).

- **Как работает:** Когда Нода А обновляет данные товара в базе данных, она публикует в кластер `EntityCacheInvalidationEvent`, передавая `PK` измененного объекта.
    
- **Результат:** Все остальные ноды кластера (Нода Б, Нода В) получают это событие и мгновенно сбрасывают кэш данного объекта в своей локальной оперативной памяти (`Region Cache`), исключая отдачу устаревших данных пользователям.
    

**101. Как корзина (cart) соотносится с заказом (order)? Как происходит процесс checkout?**

- **Соотношение:** Сущности `CartModel` и `OrderModel` являются "братьями" — они обе наследуются от одного базового класса **`AbstractOrderModel`**.
    

**Процесс Checkout:**

1. Пользователь подтверждает оформление заказа на фронтенде.
    
2. Вызывается сервис `CommerceCheckoutService.placeOrder(cart)`.
    
3. Под капотом выполянется `OrderService.createOrderFromCart()`, который **глубоко клонирует** объект `CartModel` со всеми его строками (`OrderEntryModel`), адресами и способами оплаты в новый объект `OrderModel`.
    
4. Заказу присваивается уникальный номер (`Order.code`), и для него запускается фоновый бизнес-процесс **`BusinessProcess`** (`order-process`).
    
5. Исходная корзина (`CartModel`) либо физически удаляется, либо переводится в статус неактивной (`calculated = false`).

**61. Как принимали участие в тестировании? Как готовились тестовые сценарии?**

- **Модульное и интеграционное тестирование:** Написание тестов на Java (JUnit) или Groovy (Spock Framework). Для интеграционных тестов использовались встроенные базовые классы Hybris (`ServicelayerTransactionalTest`), которые поднимают под контекст базу данных в памяти.
    
- **Подготовка данных:** Написание ImpEx-скриптов для генерации специфичных тестовых наборов данных (крайние случаи для скидок, сложных структур B2B-юзеров).
    
- **Совместная работа с QA:** Участие в ревью тест-кейсов с QA-инженерами на этапе планирования задач, а также оперативный локальный багфиксинг в QA-окружении.
    

**62. Был ли этап приемочного тестирования заказчиком? Проводились ли демо?**

**Да, обязательно.** В рамках Agile/Scrum процессов:

- **Демо (Sprint Demo):** В конце каждого 2-недельного спринта команда проводила демонстрацию работоспособного функционала для Бизнес-владельцев (Product Owner, стейкхолдеры) на `STAGE`-стенде.
    
- **UAT (User Acceptance Testing):** Приемочный этап перед каждым крупным релизом. Представители заказчика тестировали новые сценарии. Возникающие замечания заводились в Jira как `UAT Bug` или `Change Request`.
    

**63. Что такое Prometheus и Grafana? Как настраивались метрики?**

- **Prometheus:** Система сбора и хранения метрик (pull-модель).
    
- **Grafana:** Инструмент визуализации метрик в виде наглядных дашбордов.
    

**Как настраивались метрики в Hybris:** Платформа экспортирует данные через **Micrometer / Spring Boot Actuator** или **JMX Exporter**:

- _Метрики JVM:_ Нагрузка на CPU, задействованная Heap-память, паузы Garbage Collector.
    
- _Метрики Hybris:_ Размеры пулов соединений с БД, время выполнения CronJobs, скорость ответа Solr, количество активных веб-сессий и заказов в минуту.
    

**64. Какие консоли и cockpit'ы знаете в Hybris? Для чего используются?**

1. **HAC (Hybris Administration Console):** Техническая консоль для разработчиков/DevOps. Сборка, инициализация БД, управление кэшем, выполнения Groovy и FlexibleSearch.
    
2. **Backoffice (ранее Admin Cockpit, Product Cockpit, CS Cockpit):** Единый бизнес-интерфейс на базе фреймворка ZK. Испольуется менеджерами для PIM (товары), OMS (заказы), поддержки клиентов и управления пользователями.
    
3. **SmartEdit (ранее CMS Cockpit):** Визуальный редактор витрины WCMS. Позволяет контент-менеджерам в режиме Drag-and-Drop менять слоты, баннеры и компоненты прямо на странице.
    

**65. Как реализована модель данных в Hybris?**

Модель данных объявлена декларативно в XML-файлах `items.xml`.

```
[ items.xml ] ──(ant all)──> [ Java Models в gensrc ] + [ SQL Schema в БД ]
```

- **ORM Layer:** Hybris использует собственный ORM-движок (Persistence Layer).
    
- **Идентификация:** Каждая запись в базе получает уникальный системный 64-битный первичный ключ — **`PK` (Primary Key)**, а также поле `typepkstring`, определяющее тип сущности.
    

**66. Какие типы товаров есть в коробке Hybris?**

- **`ProductModel`:** Базовая сущность любого товара.
    
- **`VariantCategoryModel` & `VariantTypeModel`:** Для описания вариативных характеристик (размер, цвет).
    
- **`GenericVariantProductModel` / `ApparelProductModel`:** Товар с вариантами (например, футболка определенного цвета и размера).
    
- **Configurable / Bundle Products:** Составные и комплектуемые товары (например, ПК из комплектующих).
    

**67. Какие бывают каталоги? Сколько версий у товарного каталога? Как происходит синхронизация?**

**Виды каталогов:**

- **Product Catalog:** Товары, цены, категории.
    
- **Content Catalog:** WCMS-страницы, компоненты, навигационные меню.
    
- **Classification Catalog:** Неструктурированные характеристики.
    

**Версии товарного каталога (2 штатные):**

1. `Staged` (для редактирования).
    
2. `Online` (публичная для покупателей).
    

**Синхронизация:** Выполняется джобой `CatalogVersionSyncJob`. Она сравнивает объекты из `Staged` и `Online` по их уникальным PK/атрибутам и копирует измененные поля из черновика в боевую версию.

**68. Для чего нужен классификационный каталог?**

**Classification Catalog (`ClassificationSystemCatalog`)** служит для добавления динамических технических характеристик товарам без пересборки системы и изменения `items.xml`.

- _Пример:_ У ноутбуков есть "Объем ОЗУ", у футболок — "Состав ткани". Вместо добавления сотни новых колонок в таблицу товаров `Product`, создаются атрибуты классификации, которые динамически привязываются к выбранным категориям.
    

**69. Что такое медиа-объекты и медиаконтейнеры? Как загружались изображения товаров?**

- **`MediaModel`:** Метаданные файла в БД (URL, mime-type, имя) + ссылка на бинарный файл в Media Storage (диск / S3).
    
- **`MediaContainerModel`:** Контейнер, объединяющий один и тот же исходный файл в разном разрешении (например: `100x100 thumbnail`, `500x500 medium`, `1200x1200 zoom`).
    

**Загрузка:** Через Backoffice (ручная загрузка), по REST API, либо автоматически пачками через **ImpEx**.

**70. Что такое ImpEx? Как через него загружаются изображения?**

Для импорта медиа-файлов в ImpEx используется специальный транслятор, принимающий ZIP-архив или папку с картинками:

Фрагмент кода

```
$importFolder=jar:de.hybris.platform.impex.jalo.ImpExManager;

INSERT_UPDATE Media; code[unique=true]; realfilename; @media[translator=de.hybris.platform.impex.jalo.media.MediaDataTranslator]; mime
; prod_image_01.jpg ; photo.jpg ; /images/photo.jpg ; image/jpeg
```

ImpEx считывает физический файл по указанному пути, сохраняет его в Media Storage и создает соответствующий `MediaModel` в БД.

**71. Какие типы пользователей есть в системе? Как они описываются на уровне модели данных?**

Базовый абстрактный тип для всех участников — **`PrincipalModel`**.

```
                   [ PrincipalModel ]
                           │
       ┌───────────────────┴───────────────────┐
       ▼                                       ▼
  [ UserModel ]                         [ UserGroupModel ]
       │                                       │
  ┌────┴───────────────┐                  ┌────┴───────────────┐
  ▼                    ▼                  ▼                    ▼
[CustomerModel]  [EmployeeModel]   [B2BUnitModel]   [UserGroupModel]
 (Покупатель)     (Менеджер)       (Компания B2B)    (Группы прав)
```

**72. Что такое BaseStore, BaseSite, Point-of-Service?**

- **`BaseSiteModel`:** Точка входа веб-сайта (домен, привязка к WCMS-каталогу контента, языки, валюты).
    
- **`BaseStoreModel`:** Коммерческая конфигурация (привязанные товарные каталоги, склады, каналы оплаты, правила расчета налогов и скидок).
    
- **`PointOfServiceModel` (POS):** Физическая точка (магазин, ПВЗ, склад) с географическими координатами для самовывоза и проверки остатков.
    

**73. Как связаны корзина и заказ? Каков срок жизни корзины?**

**Связь:** И `CartModel`, и `OrderModel` наследуются от абстрактного класса **`AbstractOrderModel`**. При чекауте метод `OrderService.createOrderFromCart()` полностью клонирует данные корзины в новую сущность заказа.

**Срок жизни корзины:**

- Корзина незарегистрированного гостя хранится ограниченное время и удаляется фоновым CronJob (`OldCartRemovalCronJob`, обычно через 14–30 дней неактивности).
    
- При авторизации пользователя его анонимная корзина объединяется (merge) с его сохраненной корзиной.
    

**74. Что такое Promotion Engine? Где настраиваются акции?**

**Promotion Engine** — это штатный модуль расчета скидок в Hybris, работающий на базе движка правил **Apache Drools**.

- **Где настраиваются:** В **Backoffice** (`Marketing -> Promotion Rules`).
    
- **Как работает:** Бизнес-пользователь через конструктор условий и действий задает правило (например: _«Если в корзине 2 товара из категории X, дать скидку 10%»_). Движок компилирует это правило в Drools-скрипт (`.drl`) и выполняет его при пересчете корзины.
    

**75. Что такое фасетный поиск? Где он настраивается?**

**Фасетный поиск (Faceted Search)** — это динамическая фильтрация каталога по атрибутам с отображением количества совпадений для каждого значения (например: _Бренд: Apple (12), Samsung (8)_).

**Где настраивается:** В **Backoffice** или через **ImpEx** на уровне `SolrIndexedType`. Выбранному свойству (`SolrIndexedProperty`) выставляется флаг `facet = true` и задается тип фасета (`MultiSelectAnd`, `Refinable` и т.д.). После проведения индексации Solr начинает отдавать фасеты вместе с результатами поиска.

**76. Как устроено хранение и управление ценами?**

В Hybris цены управляются через подсистему **Europe1 (PDT Engine — Price, Discount, Tax)**:

- **`PriceRowModel`:** Базовая таблица хранения цен в БД. Позволяет задавать цену с гибкой привязкой к товару, валюте, минимальному количеству (шкала цен), группе клиентов (`UserPriceGroup`), группе товаров (`ProductPriceGroup`) и диапазону дат.
    
- **Динамические цены (B2B):** В B2B-сегменте цены часто не хранятся в `PriceRow`, а запрашиваются на лету через REST/SOAP из внешних систем (например, SAP S/4HANA) в момент рендеринга страницы или расчета корзины.
    

**77. Что такое экстеншены и акселераторы?**

- **Extension (Расширение):** Базовый изолированный модуль платформы Hybris, содержащий свою модель данных, Spring-бины, сервисы и контроллеры.
    
- **Accelerator (Акселератор):** Готовый шаблон интернет-магазина «из коробки» (B2C Accelerator, B2B Accelerator, Financial Accelerator), поставляемый SAP. Содержит преднастроенные верстку, дизайн, структуру каталогов, логику чекаута и личный кабинет.
    

**78. Был ли опыт с Assisted Service Module? Кто его использовал?**

**Assisted Service Module (ASM)** — это штатный модуль Hybris для сотрудников поддержки и менеджеров продаж.

- **Кто использовал:** Операторы call-центра и менеджеры по продажам.
    
- **Как работает:** Оператор поверх витрины магазина вызывает специальную панель ASM, ищет клиента и эмулирует его сессию («заходит под учеткой пользователя»). В этом режиме оператор может наглядно помогать клиенту наполнять корзину, применять индивидуальные скидки и оформлять заказ от его имени в режиме реального времени.
    

**79. Как собирался проект? Какие инструменты сборки использовались (Ant, Gradle)?**

- **Основной инструмент:** **Apache Ant** (стандарт сборки ядра Hybris).
    
- **Процесс:** Выполнялась инициализация переменных среды (`source setAntEnv.sh`), после чего сборка запускалась командой `ant clean all`.
    
- **Gradle / Maven:** Могут использоваться внешне для сборки отдельных фронтенд-приложений (например, Spartacus / Node.js) или внешних микросервисов, но само ядро Hybris собирается исключительно через Ant.
    

**80. Что делают команды ant clean и all? Как инициализируется база данных?**

- **`ant clean`:** Удаляет результаты прошлых сборок — скомпилированные `.class` файлы, сгенерированные классы моделей в `gensrc` и временные веб-ресурсы.
    
- **`ant all`:** Полный цикл сборки — читает `items.xml`, генерирует Java-классы в `gensrc`, компилирует весь Java-код и собирает веб-модули.
    
- **Инициализация БД (`ant initialize`):** Полностью сносит схему базы данных (Drop Tables), пересоздает таблицы с нуля и накатывает стартовые данные из ImpEx-скриптов. Также может запускаться через HAC (`Platform -> Init/Update`).
    

**81. Какие еще таргеты Ant использовались?**

- `ant updatesystem` — обновляет структуру БД (добавляет новые таблицы и колонки) без удаления существующих данных.
    
- `ant extgen` / `ant modulegen` — генерация структуры новых кастомных расширений из шаблонов.
    
- `ant production` — сборка готового архива (дистрибутива) проекта для деплоя на прод.
    
- `ant yunit` — запуск Unit и Integration тестов.
    
- `ant addoninstall` — автоматическая интеграция UI-аддона в модули витрины.
    

**82. В чем разница между extension и addon extension? Где прописываются extension? Можно ли влиять на порядок сборки?**

- **Разница:** Extension — это независимый модуль логики/БД. AddOn — это особый тип расширения, чьи UI-ресурсы (JSP, JS, CSS, контроллеры) при сборке автоматически инжектятся (копируются) в целевое веб-расширение (Storefront).
    
- **Где прописываются:** В файле `${HYBRIS_CONFIG_DIR}/localextensions.xml`.
    
- **Порядок сборки:** Напрямую изменять порядок строк в XML бесполезно. Hybris автоматически высчитывает порядок компиляции на основе графа зависимостей, прописанных в тегах `<requires-extension>` файла `extensioninfo.xml` каждого модуля.
    

**83. Как происходит сборка проекта под капотом?**

```
1. Чтение localextensions.xml + extensioninfo.xml всех модулей
   │
   ▼
2. Построение графа зависимостей (Топологическая сортировка)
   │
   ▼
3. Парсинг и объединение всех XML-файлов (items.xml, spring.xml)
   │
   ▼
4. Генерация Java-моделей на основе items.xml в папки gensrc
   │
   ▼
5. Компиляция Java-кода (src + gensrc) в .class файлы
   │
   ▼
6. Инжект ресурсов AddOns и компиляция Web-модулей
```

**84. Как подключаются внешние зависимости? Как указываются зависимости между extension? Что происходит при циклических зависимостях?**

- **Внешние JAR:** Прописываются в `external-dependencies.xml` (в формате Maven `<dependency>`) или закидываются напрямую в папку `lib/` расширения.
    
- **Зависимости между модулями:** Прописываются в `extensioninfo.xml`:
    
    XML
    
    ```
    <requires-extension name="commercefacades"/>
    ```
    
- **Циклические зависимости:** Категорически запрещены. При обнаружении цикла (A $\rightarrow$ B $\rightarrow$ A) Ant прервет сборку с ошибкой `BuildException` на этапе построения графа сборок.
    

**85. Какие типы можно определять в items.xml? Для чего используется модификатор deployment?**

- **Типы данных:** `<atomictypes>` (примитивы), `<enumtypes>` (перечисления), `<collectiontypes>` (списки), `<maptypes>` (Map), `<relationtypes>` (связи 1:N, N:M), `<itemtype>` (сущности/таблицы).
    
- **Модификатор `deployment`:** Указывает Hybris создать для данного `<itemtype>` **отдельную физическую таблицу в SQL БД**. Содержит атрибуты `table` (имя таблицы) и `typecode` (уникальный системный ID типа $> 10000$).
    

**86. Как хранятся типы и наследники в базе данных?**

- **C `deployment`:** Под класс-наследник создается отдельная SQL-таблица в БД.
    
- **Без `deployment`:** Используется паттерн **Table Per Hierarchy**. Данные наследника хранятся в таблице его родителя, новые поля становятся `NULLable`-колонками родительской таблицы, а тип конкретной строки определяется системным полем `typepkstring`.
    

**87. Как хранятся relation и collection type? Как реализуется отношение one-to-many?**

- **Relation:** Создает честные реляционные связи в SQL.
    
    - _Many-to-Many:_ Создает отдельную промежуточную Link-таблицу.
        
    - _One-to-Many:_ Добавляет колоночный Foreign Key (FK) в таблицу на стороне "Many".
        
- **Collection:** Упаковывает элементы списка в единую строку (через запятую) или в бинарный `BLOB` прямо внутри одной колонки родительской таблицы.
    

**88. Когда лучше использовать relation, а когда collection?**

- **Relation:** Всегда, когда элементами являются сущности Hybris (`ItemType`), когда элементов много или по ним требуется проводить поиск/фильтрацию в `FlexibleSearch`.
    
- **Collection:** Только для простых примитивов (`String`, `Integer`), при заведомо малом фиксированном количестве элементов (2–5 штук) и при отсутствии необходимости производить по ним SQL-поиск.
    

**89. Какие каталоги использовались на проекте? Как происходит синхронизация stage и online каталогов?**

- **Виды каталогов:** Product Catalog (товары, категории), Content Catalog (WCMS-страницы), Classification Catalog (динамические характеристики).
    
- **Версии:** `Staged` (черновик) и `Online` (публичный сайт).
    
- **Синхронизация:** Запускается джобой `CatalogVersionSyncCronJob`. Она находит измененные или созданные объекты в `Staged` и копирует их состояние в `Online`. Правила фильтрации переноса можно настраивать с помощью `FlexibleSearch`.
    

**90. Как хранятся медиафайлы (картинки продуктов)? Что такое медиаконтейнеры?**

- **Хранение медиа:** Запись `MediaModel` в БД содержит только метаданные (URL, Mime-type, имя файла), а сам бинарный файл картинки лежит в **Media Storage** (на локальном диске сервера или в S3 / Azure Blob).
    
- **`MediaContainerModel`:** Логическая сущность, группирующая одну и ту же картинку в разных форматах и разрешениях (например: `100x100 thumbnail`, `500x500 detail`, `1200x1200 zoom`). На витрину отдается нужная картинка из контейнера в зависимости от устройства пользователя.

**31. Что возвращает perform() custom Job?**

Метод `perform()` возвращает объект **`PerformableResult`**, который содержит две характеристики выполненной задачи:

Java

```
return new PerformableResult(CronJobResult.SUCCESS, CronJobStatus.FINISHED);
```

- **`CronJobResult` (Результат):** `SUCCESS` (успешно), `ERROR` (была ошибка, но работа завершена), `FAILURE` (критический сбой).
    
- **`CronJobStatus` (Состояние):** `FINISHED` (завершен), `PAUSED` (приостановлен), `ABORTED` (прерван пользователем).
    

**32. Что будет, если CronJob запущен на нескольких nodes кластера? Как избежать двойного выполнения?**

Если не настроить ограничение, параллельный запуск на разных нодах приведет к состояниям гонки (Race Conditions) и дублированию обработки данных.

**Как избежать:**

1. **Настройка `nodeGroup`:** В настройках `CronJob` или `Trigger` указывается конкретная группа серверов (например, `background_group`), на которой разрешен запуск фоновых задач.
    
2. **Встроенное блокирование (Built-in Locking):** При старте Hybris блокирует запись `CronJobModel` в БД, выставляя статус `RUNNING` и привязывая `runningOnNode`. Если другая нода попытается запустить этот же CronJob, она увидит активный статус и пропустит выполнение.
    

**33. Чем SAP Commerce Event System отличается от Spring Events?**

Платформенная Event System построена **поверх** Spring Events, но добавляет ключевую возможность — **работа в кластере (Cluster Awareness)**.

- **Spring Events:** Работает строго в рамках **одной JVM** (одной ноды).
    
- **Hybris Event System:** Позволяет публиковать события типа `ClusterAwareEvent`, которые автоматически рассылаются на **все ноды кластера** через сетевой транспорт (JGroups / UDP / TCP).
    

**34. Как вы публикуете собственное событие в Hybris?**

1. **Создать класс события**, унаследованный от `AbstractEvent` (или `ClusterAwareEvent` для кластера):
    
    Java
    
    ```
    public class OrderCancelledEvent extends AbstractEvent {
        private final String orderCode;
        public OrderCancelledEvent(String orderCode) { this.orderCode = orderCode; }
        // getter
    }
    ```
    
2. **Внедрить `EventService` и опубликовать:**
    
    Java
    
    ```
    @Autowired
    private EventService eventService;
    
    public void cancelOrder(String code) {
        // логика отмены
        eventService.publishEvent(new OrderCancelledEvent(code));
    }
    ```
    

**35. Как вы решаете проблему “event пришёл дважды”?**

Проблема повторной доставки решается через **паттерн Идемпотентности (Idempotency)**:

1. Каждому событию присваивается уникальный идентификатор (`eventId` или `transactionId`).
    
2. Слушатель события (`EventListener`) перед выполнением проверяет наличие `eventId` в БД или кэше Redis.
    
3. Если ID найден — событие игнорируется как дубликат.
    
4. Если ID нет — бизнес-логика выполняется в транзакции, а `eventId` сохраняется в базу.
    

**36. Чем Workflow в SAP Commerce отличается от Business Process Engine?**

|Характеристика|Workflow System|Business Process Engine (`processengine`)|
|---|---|---|
|**Назначение**|Ручные процессы согласования с участием **людей**.|Автоматические технические **системные процессы**.|
|**Интерфейс**|Задачи приходят сотрудникам в интерфейс Backoffice (Inbox).|Выполняется фоново Java-сервисами без участия человека.|
|**Пример**|Контент-менеджер создал товар → Редактор утвердил описание.|Оформлен заказ → Списание средств → Резерв склада → Email.|

**37. Как выглядит business process definition?**

Это XML-файл (в папке `resources/process/`), описывающий граф состояний (State Machine):

XML

```
<process xmlns="http://www.hybris.de/xsd/processdefinition" name="order-process" start="checkOrder">
    <action id="checkOrder" bean="checkOrderAction">
        <transition name="OK" to="authorizePayment"/>
        <transition name="NOK" to="cancelOrder"/>
    </action>
    <action id="authorizePayment" bean="authorizePaymentAction">
        <transition name="OK" to="waitForDelivery"/>
    </action>
    <wait id="waitForDelivery" then="shipOrder">
        <event>DeliveryConfirmedEvent</event>
    </wait>
    <end id="cancelOrder" state="ERROR">Order cancelled</end>
</process>
```

**38. Если process остановился на WAIT, как он продолжит выполнение?**

Процесс находится в состоянии `WAITING`, пока в систему не поступит внешнее событие.

**Как возобновить:** В коде вызывается метод `BusinessProcessService`, куда передается имя события, привязанное к данному процессу:

Java

```
businessProcessService.triggerEvent("order-process-12345_DeliveryConfirmedEvent");
```

Получив событие, Process Engine снимает паузу и переходит к следующему шагу `<action>`.

**39. Вы пишете “Workflows согласования через Process Engine”. Это один механизм или два разных?**

Это **два разных механизма**, которые могут быть технически интегрированы друг с другом:

- **Process Engine** ведет общий автоматический процесс.
    
- На определенном шаге Process Engine создает задачу в **Workflow System** для человека и уходит в ожидание (`<wait>`).
    
- Когда человек нажатием кнопки в Backoffice завершает Workflow, генерируется событие, которое пробуждает Process Engine для дальнейшего движения.
    

**40. Что такое ModelService? Назовите операции, которыми постоянно пользовались.**

**ModelService** — ключевой Spring-сервис Hybris для управления жизненным циклом Java-моделей (POJO, представляющих строки из БД).

**Основные операции:**

- `modelService.create(ProductModel.class)` — создание нового объекта с дефолтными значениями.
    
- `modelService.save(model)` / `saveAll(models)` — сохранение/обновление в БД.
    
- `modelService.remove(model)` — физическое удаление из БД.
    
- `modelService.refresh(model)` — сброс изменений в памяти и перезагрузка состояния из БД.
    
- `modelService.isDirty(model)` — проверка, были ли изменены поля объекта.
    

**41. Что такое interceptors в SAP Commerce? Какие бывают?**

**Interceptors (Интерцепторы)** — это перехватчики жизненного цикла моделей, вызываемые сервисом `ModelService`.

**5 видов интерцепторов:**

1. **`InitDefaultsInterceptor`:** Вызывается при `modelService.create()`, заполняет дефолтные значения.
    
2. **`PrepareInterceptor`:** Вызывается перед сохранением `save()`, позволяет дозаполнить или отформатировать данные.
    
3. **`ValidateInterceptor`:** Проверяет валидность полей перед сохранением (бросает `InterceptorException` при ошибках).
    
4. **`LoadInterceptor`:** Вызывается в момент загрузки модели из БД в память.
    
5. **`RemoveInterceptor`:** Вызывается перед удалением модели из БД (для проверок или каскадной очистки).
    

**42. Чем interceptor отличается от event listener?**

- **Interceptor:** Синхронный, жестко встроен в цепочку вызова `ModelService`. Моет **изменить** модель до записи или **заблокировать** операцию (откатив транзакцию через Exception).
    
- **Event Listener:** Слушатель событий. Обычно работает **после** того, как действие уже совершилось. Не используется для модификации сохраняемого объекта перед записью в БД.
    

**43. Что такое ServiceLayer в SAP Commerce? Почему не следует напрямую писать SQL UPDATE в commerce tables?**

**ServiceLayer** — это архитектурный каркас бизнес-логики Hybris (Models, Services, DAOs, Interceptors).

**Почему нельзя делать прямой SQL UPDATE в БД:**

1. **Инвалидация кэша:** Платформа использует `Region Cache`. Прямой SQL-запрос изменит БД, но Hybris продолжит отдавать устаревшие данные из оперативной памяти.
    
2. **Обход бизнес-логики:** Не вызовутся `Prepare` и `Validate` интерцепторы, правила безопасности и триггеры событий.
    
3. **Нарушение структуры:** Риск повредить служебные поля Hybris (например, генерацию `PK`, `typepkstring` или `modifiedtime`).
    

**44. Как устроено Spring dependency injection внутри SAP Commerce?**

1. Каждое расширение имеет свой XML-файл конфигурации Spring (`resources/<extname>-spring.xml`).
    
2. При старте Hybris объединяет конфигурации всех активных расширений из `localextensions.xml` в один единый иерархический **`ApplicationContext`**.
    
3. За счет последовательной загрузки дочерние расширения могут **переопределять (override)** бины базовых расширений, просто объявив бин с таким же `id`.


**45. Что такое Populator и Converter в Commerce?**

Паттерн для конвертации тяжелых сущностей БД (`Model`) в легкие DTO-объекты (`Data`) для передачи на фронтенд:

```text
[ProductModel] ──> (Converter) ──> [ProductData]
                         │
        ┌────────────────┴────────────────┐
        ▼                                 ▼
[ProductBasicPopulator]       [ProductPricePopulator]
(Заполняет Code, Name)        (Заполняет Цены, Валюту)
```

- **Converter:** Spring-бин, создающий пустой DTO-объект (`Target`) и последовательно прогоняющий его через список популяторов.
    
- **Populator:** Класс с единственным методом `populate(source, target)`, выполняющий маппинг конкретной группы полей.

**46. Controller → Facade → Service → DAO: насколько типична такая архитектура в Hybris?**

Это **абсолютный стандарт** классической архитектуры Hybris (4-слойная модель):

```
[ HTTP Request ]
       │
       ▼
[ Controller ] ──> Принимает DTO/Request, вызывает Facade.
       │
       ▼
[ Facade ]     ──> Оркеструет бизнес-логику, маппит Model <-> Data (DTO) через Converters.
       │
       ▼
[ Service ]    ──> Транзакционная бизнес-логика, работа с ModelService и EventService.
       │
       ▼
[ DAO ]        ──> Доступ к БД через FlexibleSearchService (возвращает Models).
```

- **Разделение ответственности:** Контроллер не знает про БД и `Model`, а Сервис не знает про DTO и HTTP-запросы.
    

**47. Как бы вы сделали REST API в SAP Commerce?**

1. **Создать DTO в `beans.xml`:** Описать структуру возвращаемого JSON.
    
2. **Написать Facade:** Внедрить нужные сервисы и с помощью `Converter` превратить `Model` из БД в `Data` (DTO).
    
3. **Написать Controller (`@RestController`):**
    
    - Разместить его в кастомном OCC-расширении (`ycommercewebservices`).
        
    - Использовать стандартный `DataMapper` (или `FieldSetBuilder`) Hybris для автоматической фильтрации полей в JSON по параметру `fields` (`DEFAULT`, `FULL`).
        

**48. Почему в вашем проекте REST был написан на Spring MVC, а не через стандартный OCC?**

Типовые причины на собеседовании:

- **Кастомная специфика бизнеса:** Необходимость реализовать специфичные B2B-эндпоинты (например, согласование лимитов или сложный расчет графиков поставок), которых нет в коробке OCC.
    
- **Корпоративный стандарт API:** Строгие требования компании к структуре JSON, заголовкам или аутентификации, несовместимые со штатным OCC.
    
- **Оптимизация производительности:** Легковесный Spring Controller работает быстрее тяжелого OCC-пайплайна, когда нужно быстро отдать легковесные данные (например, статус склада или цены на лету).

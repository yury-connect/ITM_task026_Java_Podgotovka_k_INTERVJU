
# 🧠 1. Самая полезная аналогия

Представь обычный Java/**Spring** проект:
```text
my-shop/
│
├── controller/
├── service/
├── repository/
├── entity/
├── dto/
└── configuration/
```

В Hybris вместо этого ты увидишь примерно:
```text
hybris/
│
├── bin/
│   │
│   ├── platform/
│   │
│   ├── modules/
│   │
│   └── custom/
│       │
│       ├── mycore/			-> Models  
│       ├── myfacades/		-> DTO/Facade
│       ├── myocc/			-> REST
│       └── mybackoffice/
│
└── config/
```

И **extension** — одна из ключевых строительных единиц.

SAP прямо описывает extension как единицу, которая может содержать бизнес-логику, определения типов, web-приложение или конфигурацию Backoffice.

# 🧩 2. Что такое Extension

Очень грубо:
> **Extension ≈ самостоятельный модуль SAP Commerce.**

Например:
```text
mycore
myfacades
myocc
```

Можно представить так:
```text
                         SAP COMMERCE
                              │
             ┌────────────────┼────────────────┐
             │                │                │
             ▼                ▼                ▼
          mycore          myfacades          myocc
             │                │                │
             │                │                │
             ▼                ▼                ▼
          Models           DTO/Facade        REST
```

### `mycore`
Основная бизнес-логика:
```text
items.xml
services
DAOs
models
interceptors
events
```

### `myfacades`
Публичный слой между *backend* и *внешним API*:
```text
Facade
Converter
Populator
DTO
```

### `myocc`
REST API:
```text
Controller
DTO
OCC
```

Это уже очень похоже на привычный тебе Spring:
```
Controller
   ↓
Facade
   ↓
Service
   ↓
DAO
   ↓
DB
```

# 🔥 3. Но здесь есть очень важный нюанс

В обычном Spring Boot ты сам выбираешь архитектуру.

Например:
```
Controller
    ↓
Service
    ↓
Repository
    ↓
JPA
```

В *SAP Commerce* большая часть архитектуры **уже задана платформой**.

Тебе говорят:
> Вот так правильно работать с данными.

Например:
```
items.xml
     ↓
Type System
     ↓
Model
     ↓
ModelService
     ↓
Persistence
     ↓
DB
```

И вот это надо будет очень хорошо понять.

# 🧬 ЭТАП 1. Type System

Это **первая фундаментальная тема**, которую я хочу тебе поставить в голову.
В обычном Java проекте ты можешь написать:
```java
public class Product {

    private String code;
    private String name;
}
```

И затем:
```
Java class
     ↓
Hibernate/JPA
     ↓
Database
```

В *SAP Commerce* немного иначе.
Ты описываешь тип через:
```
items.xml
```

SAP прямо указывает: `items.xml` определяет типы *extension* и позволяет создавать новые типы или расширять существующие; файл находится в `resources` соответствующего extension.

---
# 🧬 4. items.xml

Условно:
```xml
<itemtype code="MyProduct"
          extends="Product">
    <attributes>
        <attribute qualifier="myField"
                   type="java.lang.String">
        </attribute>
    </attributes>
</itemtype>
```

То есть ты говоришь платформе:
> Создай мне новый тип `MyProduct`, который наследуется от `Product`, и добавь ему поле `myField`.

Получается:
```
                items.xml
                    │
                    ▼
               Type System
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Product   MyProduct   Category
          │
          ▼
        Model
          │
          ▼
         DB
```

# ☕ 5. Аналогия с Hibernate

Вот эту аналогию **запомни**.

### JPA
```java
@Entity
public class Product {

    @Id
    private Long id;
    private String code;
}
```

### SAP Commerce
```
items.xml
       ↓
Product
       ↓
ProductModel
       ↓
DB
```

То есть:

|Обычный Java|SAP Commerce|
|---|---|
|`@Entity`|`itemtype`|
|Java field|`attribute`|
|Entity|Model|
|JPA/Hibernate|Persistence Service|
|Repository/JPQL|FlexibleSearch|
|DB schema|Type System + deployment|
|Entity lifecycle|Model lifecycle|

Это **не полная техническая эквивалентность**, но для понимания — отличная карта.

# ⚠️ 6. Очень важный момент: Model ≠ Entity

В Hybris ты увидишь:
```
ProductModel
CustomerModel
OrderModel
CartModel
```

Не надо воспринимать их просто как обычные JPA Entity.

SAP описывает Model как POJO-подобное представление Commerce item, с автоматически генерируемыми getter/setter.

То есть:
```
ProductModel product;
```

— это **представление Commerce item через Service Layer**.

# 🎯 8. Вопрос интервьюера №1

### ❓ Что такое `items.xml`?

### ❌ Плохой ответ
> Это XML, где описываются сущности Hybris.

Слишком поверхностно.

### 🟢 Хороший Middle
> `items.xml` — это описание Type System SAP Commerce. В нём определяются item types, их атрибуты, наследование, relations, collections и другие характеристики модели данных. На основе этих определений SAP Commerce генерирует соответствующие Model-классы, а при обновлении системы изменения применяются к runtime data model и базе данных.

Вот **это уже нормальный ответ**.

# 🔗 11. Теперь Extension Dependencies

Допустим:
```
myocc
  │
  ▼
myfacades
  │
  ▼
mycore
```

`myocc` использует классы `myfacades`.
`myfacades` использует `mycore`.

Значит:
```
myocc
  ↓
myfacades
  ↓
mycore
```
— это dependency graph.

Если сделать:
```
mycore
  ↓
myfacades
  ↓
mycore
```

получаем:
```
      ┌──────────────┐
      │              │
      ▼              │
    mycore ───────► myfacades
      ▲              │
      └──────────────┘
```
**циклическую зависимость.**

И вот именно это интервьюер проверял вопросом:
> Что будет при циклических зависимостях между extension?

# 🏗️ 12. `localextensions.xml`

Еще одна вещь, которую нужно запомнить.

В проекте есть конфигурация extension'ов.

Концептуально:
```
<extension name="mycore"/>
<extension name="myfacades"/>
<extension name="myocc"/>
```

Именно здесь ты говоришь:
> Эти extension должны участвовать в проекте.

SAP в документации для Service Layer прямо напоминает: после создания extension нужно добавить его в `localextensions.xml`.

# 🔨 14. `ant clean`

Условно:
```
ant clean
```

означает:
> очистить результаты предыдущей сборки.

А:

```
ant all
```

— выполнить основную сборку SAP Commerce, в том числе обработать изменения модели и сгенерировать необходимые классы.

Ключевая связка:
```
items.xml
    │
    ▼
ant all
    │
    ▼
generated Model classes
```

И именно поэтому интервьюер задал:
> Что делают `ant clean` и `all`?

# 🎯 Первый мини-чек

После этого этапа ты должен уметь ответить без подсказки:

### 1️⃣ Что такое SAP Commerce?

> Enterprise e-commerce платформа SAP, внутри которой разработчики расширяют функциональность через extensions и используют платформенные механизмы Type System, Service Layer, ImpEx, FlexibleSearch и т.д.

### 2️⃣ Что такое Extension?

> Модуль SAP Commerce, содержащий определённую функциональность: бизнес-логику, типы данных, web-компоненты, Backoffice-конфигурацию и т.д.

### 3️⃣ Что такое `items.xml`?

> Описание Type System extension: типы, атрибуты, relations, collections, inheritance и т.д.

### 4️⃣ Что такое Model?

> POJO-подобное представление SAP Commerce item, используемое Service Layer.

### 5️⃣ Как `items.xml` связан с Model?

```
items.xml
   ↓
Type System
   ↓
generated Model
```

### 6️⃣ Что такое `localextensions.xml`?

> Конфигурация, определяющая extensions, участвующие в конкретной SAP Commerce-системе.

### 7️⃣ Зачем `ant all`?

> Основная сборка SAP Commerce, в том числе обработка model definitions и генерация необходимых классов.

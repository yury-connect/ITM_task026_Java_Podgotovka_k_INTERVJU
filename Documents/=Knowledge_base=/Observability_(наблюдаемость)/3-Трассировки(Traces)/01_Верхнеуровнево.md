Трассировка (*или распределенная трассировка*) — это инструмент, который показывает **путь одного конкретного запроса** через все сервисы и компоненты системы. Если метрики говорят «что-то сломалось», а логи — «почему сломалось», то трассировка отвечает на вопрос **«где именно в цепочке микросервисов произошел затык»**[](https://learn.microsoft.com/cs-cz/power-platform/architecture/key-concepts/distributed-tracing-details#1)[](https://learn.microsoft.com/ru-ru/power-platform/architecture/key-concepts/distributed-tracing-details#1).

### 🧩 Три ключевых понятия: `Trace`, `Span`, `Context`

Представь, что пользователь нажимает кнопку «Оформить заказ» в интернет-магазине.
	
1. **Trace (*Трассировка*)**: Это **вся история** этого запроса от начала до конца. От нажатия кнопки в браузере, через API Gateway, сервис заказов, сервис оплаты, до записи в базу данных. У всей этой истории есть один уникальный идентификатор — `Trace ID` (например, `4bf9f3577b34da6a3ce929d0e0e4736`)[](https://opentelemetry.io/docs/concepts/signals/traces/)[](https://datatracker.ietf.org/meeting/115/materials/slides-115-netconf-context-tracing-00#1#1).
    
2. **Span (*Спан*)**: Это **один конкретный шаг** внутри истории. Например:
	    
    - Span 1: «HTTP-запрос пришел на API Gateway» (длительность 5 мс).
        
    - Span 2: «Сервис заказов обрабатывает запрос» (длительность 120 мс).
        
    - Span 3: «Сервис заказов вызывает сервис оплаты» (длительность 3000 мс — вот здесь проблема!).
        
    - Span 4: «Запись в БД» (длительность 15 мс).  
        У каждого Span есть свой уникальный `Span ID`, а также `Parent Span ID`, который показывает, какой шаг его породил. Это создает иерархию (дерево), которую ты видишь в виде «водопада» (waterfall chart) в Jaeger или Grafana Tempo[](https://opentelemetry.io/docs/concepts/signals/traces/)[](https://middleware.io/blog/what-is-grafana-tempo/#core-features-of-grafana-tempo).
    
3. **Context Propagation (*Передача контекста*)**: Это **самое важное** для распределенных систем. Чтобы все эти шаги в разных сервисах объединились в одну историю, информация о `Trace ID` должна передаваться между сервисами. Делается это через HTTP-заголовки. Стандарт **W3C Trace Context** определяет заголовок `traceparent`, который выглядит так:  
    `00-4bf9f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`  
    Где `4bf9...` — это Trace ID, а `00f0...` — Span ID родителя[](https://datatracker.ietf.org/meeting/115/materials/slides-115-netconf-context-tracing-00#1#1)[](https://docs.cloud.google.com/trace/docs/trace-context?hl=ko#context-propagation-protocols)[](https://docs.cloud.google.com/trace/docs/trace-context).

### ⚙️ Как это выглядит в **Spring Boot**

В Spring Boot 3 на смену старому *Spring Cloud Sleuth* пришла библиотека ***Micrometer Tracing***[](https://docs.guance.com/en/best-practices/monitoring/springboot3_webflux/#2-testing)[](https://stackoverflow.com/questions/79733423/how-to-correctly-log-traceid-and-spanid-in-springboot-3-in-every-log-message/79733586#79733586#1). Она работает вместе с уже знакомым тебе *Micrometer* (*для метрик*).
д
Схема потока данных:  
**Spring Boot App (с Micrometer Tracing) → OTLP / Zipkin / Jaeger → Backend (Jaeger / Tempo) → Grafana**
	
1. **Автоматическая инструментация**: Ты просто добавляешь зависимости (например, `micrometer-tracing-bridge-brave` или `micrometer-tracing-bridge-otel`) и настраиваешь экспортер. Spring Boot автоматически создает Span’ы для входящих HTTP-запросов, исходящих вызовов (RestTemplate, WebClient, Kafka), запросов к базе данных и т.д.[](https://docs.guance.com/en/best-practices/monitoring/springboot3_webflux/#2-testing)[](https://stackoverflow.com/questions/79733423/how-to-correctly-log-traceid-and-spanid-in-springboot-3-in-every-log-message/79733586#79733586#1).
    
2. **Связь с логами**: Micrometer Tracing автоматически прокидывает `traceId` и `spanId` в MDC (Mapped Diagnostic Context). Тебе достаточно добавить в `logback.xml` паттерн с `%X{traceId}` и `%X{spanId}`, и ты сможешь связать любой лог с конкретным трейсом[](https://docs.guance.com/en/best-practices/monitoring/springboot3_webflux/#2-testing)[](https://stackoverflow.com/questions/79733423/how-to-correctly-log-traceid-and-spanid-in-springboot-3-in-every-log-message/79733586#79733586#1).

### 🗄️ Куда складывать трейсы (*Backend*)

Трейсы — это тяжелые данные (много span’ов), поэтому их хранят недолго и часто сэмплируют. Основные варианты бэкендов[](https://uptrace.dev/tools/distributed-tracing-tools)[](https://gitlab.ow2.org/discobole/doc/-/blob/ff5d631a17996522317e161caedc42ffddbd1e2f/docs/architecture/decisions/0022-observability-traces-backend-service.md?blame=1):

| Бэкенд            | Особенности                                                                                            | Для кого                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------- |
| **Jaeger**        | Индустриальный стандарт, graduated в CNCF. Богатый функционал, хорошая интеграция с OTel.              | Энтерпрайз, сложные системы, нужна надежность. |
| **Grafana Tempo** | Самый дешевый в хранении (использует S3/GCS). Идеально сочетается с Prometheus и Loki в стеке Grafana. | Те, кто уже использует Grafana.                |
| **Zipkin**        | Простой и старый. Хорош для базовых задач, но UI ограничен.                                            | Legacy-системы, простые сценарии.              |

### 💡 Главная фишка: Связь с метриками и логами (*Exemplars*)

Самое мощное в трассировке — это **Exemplars**. Представь, что на графике в Grafana (метрики) ты видишь всплеск задержки. Exemplar — это ссылка на **конкретный Trace ID**, который вызвал этот всплеск. Ты кликаешь на график и мгновенно попадаешь в трейс, где видно, какой именно вызов (Span) тормозил. А оттуда, по тому же Trace ID, можно перейти в логи (Loki) и увидеть текст ошибки[](https://middleware.io/blog/what-is-grafana-tempo/#core-features-of-grafana-tempo).

Это превращает расследование инцидента из «переключения между тремя разными инструментами» в один бесшовный клик.

Чтобы уменьшить коллизии, нужно **максимально разбросать** хэш-коды по всему диапазону `int` (от -2¹³¹ до 2¹³¹-1). Вот 7 золотых правил и техник:

---
### 1. Используйте простые числа (особенно 31, 37, 97)

В классической формуле `result = 31 * result + field.hashCode()` число 31 выбрано не случайно:
- Оно нечетное (четные множители приводят к потере битов).
- Оно простое (меньше коллизий при переполнении `int`).
- JVM оптимизирует умнож-е на 31 как сдвиг и вычитание: `31 * i == (i << 5) - i`.

**Но есть нюанс:** для коротких строк (до 5 символов) 31 дает мало коллизий, но для длинных — лучше **37** или **97**.
```java
// Плохо (только одно поле)
return name.hashCode();

// Хорошо (комбинация полей с простым числом)
@Override
public int hashCode() {
    int result = 17;
    result = 31 * result + name.hashCode();
    result = 31 * result + age;
    result = 31 * result + (address != null ? address.hashCode() : 0);
    return result;
}
```

---
### 2. Перемешивайте биты (Bit Mixing) — самый мощный прием

Если у вас поля имеют предсказуемые паттерны (например, даты, IP-адреса, ID из базы), простого умножения недостаточно. Нужно принудительно **перемешать биты** старших и младших разрядов.

Самый известный пример — метод из `HashMap` (Java 8+):
```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**Как это работает:**
- Берем 32-битный хэш.
- Сдвигаем вправо на 16 бит (старшие биты становятся младшими).
- Делаем XOR (исключающее ИЛИ) с оригиналом.
- В результате младшие 16 бит получают "примесь" старших.

Это критично, потому что в коллекциях индекс вычисляется как `hash & (n-1)` (где n — степень двойки). При такой операции **используются только младшие биты**! Без перемешивания все объекты с разными старшими битами, но одинаковыми младшими, попадут в одну корзину.

**Ваш метод может выглядеть так:**
```java
@Override
public int hashCode() {
    int result = Objects.hashCode(name, age); // стандартный
    result = result ^ (result >>> 16); // добавляем перемешивание
    return result;
}
```

---
### 3. Для чисел — используйте битовые операции, а не просто сумму

Допустим, у вас класс `Point(int x, int y)`.
- `x + y` — УЖАСНО (для (1,2) и (2,1) коллизия).
- `x * 31 + y` — лучше.
- `x ^ (y << 16)` — еще лучше (сдвиг разрядов).

```java
@Override
public int hashCode() {
    // Перемешиваем координаты в разные битовые позиции
    return x * 31 + y * 37;  // или x ^ (y << 16) ^ (y >>> 16);
}
```

---
### 4. Для строк — используйте встроенные алгоритмы или кэшируйте

У класса `String` в Java **уже идеальный** хэш-код (он кэшируется в поле `hash` после первого вычисления).

Но если вы пишете свой класс, который часто используется как ключ в `HashMap`, применяйте **полиномиальный хэш** (как у String), а не просто `Objects.hashCode()`:
```java
// Полиномиальный хэш для строки (как в Java)
public int hashCodeForString(char[] chars) {
    int h = 0;
    for (char c : chars) {
        h = 31 * h + c; // Каждый символ влияет на все последующие
    }
    return h;
}
```

---
### 5. Используйте `Objects.hash()` (но с осторожностью)

Java предоставляет утилиту:
```java
@Override
public int hashCode() {
    return Objects.hash(field1, field2, field3);
}
```

**Плюс:** Простота, автоматическая обработка `null`.  
**Минус:** Внутри создается массив `Object[]` для каждого вызова (плохо для производительности) и коллизий больше, чем у ручной формулы. Используйте только для редких объектов.

---
### 6. Для сложных объектов — комбинируйте по методу Эфтимиадиса (Efthymiades)

Если у вас много полей (10+), используйте проверенную формулу:
```java
@Override
public int hashCode() {
    long bits = Double.doubleToLongBits(value);
    int result = (int)(bits ^ (bits >>> 32));
    
    // Добавляем каждое поле с уникальным множителем
    result = 31 * result + (field1 != null ? field1.hashCode() : 0);
    result = 31 * result + (field2 != null ? field2.hashCode() : 0);
    // ...
    result = 31 * result + (fieldN != null ? fieldN.hashCode() : 0);
    
    // Финальное перемешивание
    return result ^ (result >>> 16);
}
```

---
### 7. Избегайте "слабых" полей в расчете

Если у вас есть поле, которое:
- Часто равно `null`.
- Принимает только 2 значения (`boolean`).
- Почти всегда одинаковое.

То его включение в `hashCode()` **увеличивает коллизии**, а не уменьшает. Лучше использовать только уникальные поля (ID, имя, дата создания).
```java
// Плохо: много объектов с status = ACTIVE
result = 31 * result + status.hashCode(); 

// Хорошо: используем только уникальные поля
result = 31 * result + userId.hashCode();
result = 31 * result + creationTimestamp.hashCode();
```

---
### Бонус: Как проверить, что ваши правила работают?

Напишите простой тест:
```java
Set<Integer> hashes = new HashSet<>();
for (int i = 0; i < 100_000; i++) {
    MyObject obj = new MyObject(i, i * 2);
    hashes.add(obj.hashCode());
}
System.out.println("Коллизий: " + (100_000 - hashes.size()));
```
Если коллизий больше 0.1% (100 штук) — ваш хэш-код плох.

---
### Самое главное резюме:

|Правило|Эффективность|
|---|---|
|Умножение на простое число (31)|⭐⭐⭐|
|Перемешивание битов `^ (h >>> 16)`|⭐⭐⭐⭐⭐ (обязательно!)|
|Использование сдвигов для чисел|⭐⭐⭐⭐|
|Исключение статических/постоянных полей|⭐⭐⭐⭐|
|Ручная формула вместо `Objects.hash()`|⭐⭐⭐⭐⭐ (для высоконагруженных систем)|

**Золотой стандарт** для любого класса-ключа в `HashMap`:
```java
@Override
public int hashCode() {
    int result = Objects.hashCode(id); 
    result = 31 * result + Objects.hashCode(name);
    result = result ^ (result >>> 16); // защита от плох. распред-я в HashMap
    return result;
}
```

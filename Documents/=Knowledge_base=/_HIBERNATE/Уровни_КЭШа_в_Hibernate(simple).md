## Уровни кэша в Hibernate (простыми словами)

Hibernate использует кэширование, чтобы реже обращаться к базе данных и тем самым ускорять работу приложения. Представьте себе три уровня кэша как три этажа хранения данных.

---
### Уровень 1. Кэш первой сессии — L1 (самый быстрый, но самый короткий)

**Что это:** Это кэш, который живет внутри одной **транзакции** или одной **сессии** (EntityManager).

**Как работает:** Представьте, что вы работаете с документами на своем рабочем столе. Пока вы не закрыли сессию, все документы лежат у вас под рукой.
	
- Если вы запросили пользователя по ID один раз — Hibernate сходил в базу.
    
- Если вы запросили **того же пользователя** второй раз в той же транзакции — Hibernate **не пойдет в базу**, а возьмет его со своего "рабочего стола" (из L1-кэша).

#### **Особенности:**
- Включен **всегда**, его нельзя отключить.
- Живет только пока жива сессия (транзакция).
- **НЕ потокобезопасен** — разные пользователи имеют свои собственные сессии, поэтому у каждого свой L1.

---
### Уровень 2. Кэш второй сессии — L2 (общий для всего приложения)

**Что это:** Это кэш, который живет на уровне **фабрики сессий** (SessionFactory). Он общий для **всех** сессий и транзакций.

**Как работает:** Представьте, что это **общий склад**, куда кладут копии документов. Если вы запросили пользователя по ID и его нет в вашем L1 (на вашем столе), Hibernate сначала проверит L2 (склад). Если пользователь там есть — он скопирует его к себе на "стол" (в L1). Если его нет на складе — тогда сходит в базу данных, положит копию на склад (L2) и на свой стол (L1).

#### **Особенности:**
- **Выключен по умолчанию** — его нужно включать специально.    
- **Потокобезопасен** — один склад для всех пользователей.    
- **Требует стороннего провайдера** — например, Ehcache, Hazelcast или **Redis**.    
- Работает **только** для загрузки по ID (метод `get()` или `find()`).    
- Настраивается над сущностями через аннотацию **`@Cacheable`**.    

**Почему не всегда используют:** Если сущность часто меняется, L2-кэш нужно постоянно обновлять (инвалидировать). Это сложно и может дать обратный эффект. Поэтому L2 используют для редко меняющихся данных — справочников, списка стран, городов, статусов.

---
### Уровень 3. Кэш запросов (Query Cache) — кэширует не данные, а списки ID

**Что это:** Это отдельный кэш, который хранит не сами объекты, а **идентификаторы (ID)** объектов, которые вернул ваш запрос.

**Как работает:** Вы выполнили сложный запрос: "Найти всех пользователей старше 18 лет, отсортированных по имени". Вместо того чтобы каждый раз выполнять этот запрос, Hibernate запоминает **только ID** подходящих пользователей.
	
1. Если такой запрос уже был — Hibernate достает список ID из Query Cache.
    
2. Затем для каждого ID он идет **сначала в L1, потом в L2**, и только если их там нет — в базу данных.

#### **Особенности:**
- Работает **только вместе с L2**.
    
- Если L2 выключен, то после получения списка ID Hibernate сделает по одному запросу к базе для каждого ID — это будет **медленнее**, чем один большой запрос.
    
- Включается отдельно через настройку.

---
## А теперь про **Redis**

**Redis** — это не уровень кэша Hibernate, это **внешнее хранилище**, которое может использоваться как **провайдер для L2-кэша** (и для Query Cache тоже).

### Какое отношение Redis имеет к этим трем уровням?

**Прямое:** Redis может быть тем самым "сторонним провайдером" для **L2-кэша**. Вместо Ehcache (который хранит данные в памяти JVM) вы можете использовать Redis, который хранит данные отдельно — на другом сервере.

### Когда используют **Redis** вместо **Ehcache**?
1. **Распределенные системы (микросервисы):** Если у вас 5 экземпляров одного микросервиса, у каждого свой L2-кэш в памяти (Ehcache). Они **не синхронизированы**. Если один сервис обновил сущность, другие об этом не узнают.
    
2. **Redis — общий кэш для всех экземпляров.** Один сервис обновил данные — они обновились в Redis — все остальные сразу видят новую версию.
    
3. **Перезапуск приложения:** Если вы перезапустили сервис, Ehcache очищается — все данные нужно грузить заново из базы. Redis хранит данные независимо от приложения — перезапуск не теряет кэш.

### Сравнение провайдеров для L2-кэша

|Провайдер|Где хранится|Распределенный|Переживает перезапуск приложения|Скорость|
|---|---|---|---|---|
|**Ehcache (встроенный)**|В памяти JVM|Нет|Нет|Очень высокая|
|**Hazelcast**|В памяти JVM кластера|Да|Нет|Высокая|
|**Redis**|На отдельном сервере|Да|Да|Ниже (из-за сети)|

### Пример настройки Hibernate L2 с Redis
```properties
# Включаем L2-кэш
spring.jpa.properties.hibernate.cache.use_second_level_cache = true

# Указываем Redis как провайдера
spring.jpa.properties.hibernate.cache.region.factory_class = org.hibernate.cache.jcache.JCacheRegionFactory

# Указываем JCache провайдера (в данном случае Redisson)
spring.jpa.properties.hibernate.javax.cache.provider = org.redisson.jcache.JCacheProvider

# Или для Spring Boot проще через зависимости и автоконфигурацию:
# spring.cache.type=redis
# spring.redis.host=localhost
```

### Итог
1. **L1** — ваш личный стол в сессии. Всегда включен.
2. **L2** — общий склад для всего приложения. Включить нужно явно.
3. **Query Cache** — запоминает списки ID, чтобы не вып. сложные запросы повторно.
4. **Redis** — может быть **складом (L2)** для распределенного приложения. Общий и независимый.

Если у вас монолит с одним экземпляром — Redis может быть излишним, и лучше использовать Ehcache (быстрее). Если у вас микросервисы с 3-5+ экземплярами — Redis оправдан, т.к. синхронизирует кэш между ними.

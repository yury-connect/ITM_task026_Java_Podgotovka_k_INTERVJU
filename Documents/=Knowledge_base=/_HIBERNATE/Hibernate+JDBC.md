Вот ответы по блоку **Hibernate + JDBC**, подготовленные в формате четкого и уверенного ответа кандидата на собеседовании на позицию Java Middle.

### 1. Уровни кэша в Hibernate

1. **First-Level Cache (L1):**
    
    - **Скоуп:** Кэш сессии (`Session` / `EntityManager`).
        
    - **Особенности:** Включен по умолчанию всегда, выключить нельзя. Гарантирует уникальность сущности в рамках одной сессии (Identity Map). Не потокобезопасен.
        
2. **Second-Level Cache (L2):**
    
    - **Скоуп:** Кэш фабрики сессий (`SessionFactory` / `EntityManagerFactory`).
        
    - **Особенности:** По умолчанию выключен. Разделяется между всеми сессиями приложения. Требует внешнего провайдера (Ehcache, Hazelcast). Хранит данные в виде дегидрированных массивов значений (без самих объектов-сущностей).
        
3. **Query Cache:**
    
    - Кэширует **результаты запросов** (списки ключей/ID). Работает только в связке с L2-кэшем.
        

### 2. Составной ключ (Composite Key)

Способы реализации в JPA:

1. **`@EmbeddedId` + `@Embeddable` (Рекомендуемый):** Создается отдельный класс для ключа, помечается `@Embeddable`, а в сущности поле помещатся как `@EmbeddedId`.
    
2. **`@IdClass`:** В сущности создаются обычные поля с аннотациями `@Id`, а над классом сущности указывается `@IdClass(MyKey.class)`.
    

**Требования к классу составного ключа:**

- Должен реализовывать `java.io.Serializable`.
    
- Обязан корректно переопределять `equals()` и `hashCode()`.
    
- Должен иметь no-args конструктор.
    

### 3. Наследование в Hibernate

1. **`SINGLE_TABLE` (По умолчанию):** Все классы иерархии отображаются в одну таблицу. Нужна колонка-дискриминатор (`@DiscriminatorColumn`).
    
    - _Плюс:_ Высокая скорость, нет `JOIN`.
        
    - _Минус:_ Поля дочерних классов обязаны быть `NULLable`.
        
2. **`JOINED`:** Базовый класс в своей таблице, дочерние — в своих с FK на базовую.
    
    - _Плюс:_ Нормализованная БД, нет лишних `NULL`.
        
    - _Минус:_ Тяжелые `JOIN` при полиморфных запросах.
        
3. **`TABLE_PER_CLASS`:** Для каждого конкретного класса создается отдельная полная таблица.
    
    - _Плюс:_ Нет `NULL` и обязательных `JOIN` для конкретного типа.
        
    - _Минус:_ Полиморфные выборки делают медленный `UNION`.
        
4. **`@MappedSuperclass`:** Не является стратегией отображения иерархии в полном смысле. Родительский класс не является сущностью (нельзя делать `SELECT` по нему), его поля просто наследуются дочерними таблицами.
    

### 4. Состояния объектов (Entity Lifecycle States)

- **Transient (New):** Объект создан через `new`, не привязан к сессии, не имеет ID в БД.
    
- **Persistent (Managed):** Объект связан с текущей сессией и имеет ID. Для него работает Dirty Checking (все изменения автоматически сохраняются в БД при `flush`).
    
- **Detached:** Объект имеет ID, но сессия закрыта или очищена (`clear()`). Изменения в объекте Hibernate больше не отслеживает.
    
- **Removed:** Объект помечен на удаление (вызван `remove()`). При `flush()` в БД уйдет `DELETE`.
    

### 5. JPA и Hibernate

- **JPA (Jakarta Persistence):** Это **спецификация** (стандарт, набор интерфейсов и аннотаций, таких как `EntityManager`, `@Entity`, `@Table`).
    
- **Hibernate:** Это конкретная **библиотека/реализация (ORM Provider)** этой спецификации, которая под капотом содержит всю реализацию JPA + собственные расширения (Envers, дополнительные типы кэширования, методы `Session`).
    

### 6. Отличие Orphan Removal от Cascade.REMOVE

- **`CascadeType.REMOVE`:** При удалении родительской сущности (`parent`) из базы удаляются и все связанные с ней дочерние сущности (`children`).
    
- **`orphanRemoval = true`:** Делает то же самое, что и `CascadeType.REMOVE`, но **дополнительно**: если удалить дочерний объект из коллекции родителя (`parent.getChildren().remove(child)`), Hibernate автоматически выполнит `DELETE` для этого объекта в БД.
    

### 7. Каскадирование (Cascading)

Автоматическая трансляция действий над родительской сущностью (переход состояния lifecycle) на связанные дочерние сущности.

**Основные типы:** `PERSIST`, `MERGE`, `REMOVE`, `REFRESH`, `DETACH`, `ALL` (применяет все вышеперечисленные).

### 8. Контекст персистентности (Persistence Context)

Это «кэш первого уровня» (L1 Cache) и среда управления сущностями внутри `EntityManager` / `Session`.

**Задачи:**

1. **Identity Map:** Гарантирует, что в рамках одной сессии одна строка таблицы соответствует ровно одному Java-объекту в памяти.
    
2. **Dirty Checking:** Автоматически отслеживает изменения полей Managed-объектов и генерирует `UPDATE` при сбросе сессии (`flush`).
    
3. **Write-Behind (Отложенная запись):** Оптимизирует и группирует SQL-запросы перед отправкой в БД.
    

### 9. HikariCP (Hikari Pool)

**HikariCP** — высокопроизводительный пул JDBC-соединений, используемый по умолчанию в Spring Boot.

**Почему он такой быстрый:**

- Оптимизация на уровне байт-кода и активное использование `invokevirtual`.
    
- Кастомные высокоэффективные коллекции (например, `FastList` вместо `ArrayList` для исключения проверок границ при обращении).
    
- Минимизация использования блокировок (`Lock-free` структуры данных).
    

### 10. Виды Statement в JDBC

1. **`Statement`:** Используется для статических SQL-запросов без параметров. Уязвим к **SQL-инъекциям**, не оптимизируется БД.
    
2. **`PreparedStatement`:** Используется для запросов с параметрами (`?`). Предкомпилируется СУБД, защищает от SQL-инъекций, работает быстрее при многократном вызове.
    
3. **`CallableStatement`:** Наследуется от `PreparedStatement`. Используется для вызова хранимых процедур и функций БД (поддерживает `IN`, `OUT` параметры).
    

### 11. Отличие процедуры от функции в СУБД

- **Хранимая функция (Function):** Обязана возвращать значение. Может быть вызвана напрямую внутри SQL-запроса `SELECT my_func(col) FROM table`.
    
- **Хранимая процедура (Procedure):** Может не возвращать значений вовсе или возвращать их через `OUT`-параметры. Вызывается отдельной командой (`CALL` / `EXEC`). Внутри SQL-запросов `SELECT` использоваться не может.
    

### 12. Методы PreparedStatement

- **`executeQuery()`:** Выполняет `SELECT`-запросы, возвращает `ResultSet`.
    
- **`executeUpdate()`:** Выполняет DDL/DML-запросы (`INSERT`, `UPDATE`, `DELETE`), возвращает `int` (число затронутых строк).
    
- **`execute()`:** Универсальный метод. Возвращает `boolean` (`true` — если результатом стал `ResultSet`, `false` — если число строк или результата нет).
    
- **`addBatch()` / `executeBatch()`:** Для батчинга (пакетной отправки нескольких запросов за один сетевой прыжок).
    

### 13. SessionFactory

Тяжеловесный, потокобезопасный объект-синглтон в Hibernate. Создается один раз при старте приложения на основе конфигурации и отвечает за создание экземпляров `Session`.

В JPA аналогом `SessionFactory` является **`EntityManagerFactory`**.

### 14. Как в Hibernate вызвать хранимую процедуру

1. **Через `@NamedStoredProcedureQuery` (JPA 2.1+):** Аннотируем сущность, а в коде вызываем:
    
    Java
    
    ```
    StoredProcedureQuery query = em.createNamedStoredProcedureQuery("my_proc");
    query.setParameter("param", val);
    query.execute();
    ```
    
2. **Через Native Query:**
    
    Java
    
    ```
    em.createNativeQuery("CALL my_procedure(:param)")
      .setParameter("param", val)
      .executeUpdate();
    ```
    

### 15. Как решить проблему N+1

1. **`JOIN FETCH` в JPQL / HQL:** `SELECT p FROM Parent p JOIN FETCH p.children`.
    
2. **`@EntityGraph`:** Декларативное указание связей для `LEFT JOIN` выгрузки.
    
3. **`@BatchSize`:** Группирует загрузку связанных коллекций/сущностей батчами (`WHERE id IN (?, ?, ?)`).
    
4. **DTO-проекции:** Запрос только нужных полей напрямую через SQL/JPQL.
    

### 16. Стратегии кэширования L2 (Cache Concurrency Strategies)

- **`READ_ONLY`:** Для справочников и данных, которые никогда не меняются.
    
- **`NONSTRICT_READ_WRITE`:** Если данные меняются крайне редко и допустима временная нерассогласованность.
    
- **`READ_WRITE`:** Использовать «мягкие блокировки» (Soft Locks). Для данных, которые периодически обновляются, при строгих требованиях к согласованности.
    
- **`TRANSACTIONAL`:** Полная поддержка JTA-транзакций (двухфазный коммит). Самый тяжелый режим.
    

### 17. Когда лучше использовать нативный SQL (Native Query)

1. Выполнение сложных аналитических запросов с **оконными функциями** (`OVER PARTITION BY`), CTE (`WITH ...`) или редкими операторами СУБД.
    
2. Специфические функции конкретной СУБД (например, работа с `JSONB` или PostGIS в PostgreSQL).
    
3. Массовые тяжелые DML-операции (`INSERT INTO ... SELECT`), когда загружать объекты в памяти JVM слишком затратно.
    

### 18. Виды LockModeType и @Version

**`@Version`:** Включает **оптимистическую блокировку**. При обновлении сущности проверяется совпадение версии.

**`LockModeType` (выставляются через EntityManager):**

- _Оптимистические:_
    
    - `OPTIMISTIC` (READ) — проверяет версионность в конце транзакции.
        
    - `OPTIMISTIC_FORCE_INCREMENT` — принудительно увеличивает версию даже без изменений сущности.
        
- _Пессимистические:_
    
    - `PESSIMISTIC_READ` — делает `SELECT ... FOR SHARE` (S-Lock).
        
    - `PESSIMISTIC_WRITE` — делает `SELECT ... FOR UPDATE` (X-Lock).
        
    - `PESSIMISTIC_FORCE_INCREMENT` — X-Lock + принудительное обновление версии.
        

### 19. Оконные функции в SQL

**Оконные функции** вычисляют результат по набору строк (окну), связанному с текущей строкой, **без группировки (схлопывания) строк** в одну (в отличие от `GROUP BY`).

_Пример:_ `ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC)`.

### 20. Как сделать свой Connection Pool (Упрощенная схема)

1. Создать класс, хранящий потокобезопасную очередь соединений, например `BlockingQueue<Connection>`.
    
2. При инициализации создать N реальных `DriverManager.getConnection()` и положить их в очередь.
    
3. Обернуть стандартный `Connection` через **Dynamic Proxy** или паттерн **Decorator**, переопределив метод `close()`.
    
4. В переопределенном `close()` вместо реального закрытия TCP-сокета возвращать соединение обратно в очередь (`queue.offer(connection)`).
    
5. Реализовать методы `getConnection()` (берут из очереди) и закрытия пула при завершении приложения.

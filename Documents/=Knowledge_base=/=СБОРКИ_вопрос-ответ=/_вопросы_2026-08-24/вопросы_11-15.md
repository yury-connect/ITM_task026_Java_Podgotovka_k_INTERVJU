### 🗺️ 11. HashMap, LinkedList, TreeNode и Изменяемые Ключи

#### Устройство HashMap под капотом

- **Структура:** Массив бакетов `Node<K,V>[]`.
    
- **Базовая коллизия (LinkedList):** Если несколько ключей попадают в один бакет (одинаковый индекс `(n - 1) & hash`), они связываются в односвязный список. Поиск в списке — $O(N)$.
    
- **Дереволизация (TreeNode):** Если число элементов в одном бакете достигает **8**, а общая емкость массива $\ge 64$, односвязный список трансформируется в **Красно-Черное дерево (Red-Black Tree / `TreeNode`)**. Поиск ускоряется до $O(\log N)$. При уменьшении числа элементов до 6 происходит дедереволизация назад в список.

#### Проблема Изменяемых Ключей (Mutable Keys)

Что произойдет, если добавить в `HashMap` объект в качестве ключа, а затем изменить его внутреннее состояние?

1. **Добавление:** Поток сохраняет запись `(Key1, Value)` в Бакет $X$, вычисленный на основе исходного `Key1.hashCode()`.
    
2. **Мутация:** Состояние объекта `Key1` меняется (например, изменили значение поля, участвующего в `hashCode()`).
    
3. **Результат:**    
    - При попытке вызвать `map.get(Key1)` HashMap заново считает `hashCode()` уже измененного ключа, который теперь указывает на совершенно другой Бакет $Y$.
    - Метод `get()` вернет **`null`**, хотя объект физически лежит в карте!
    - Метод `map.remove(Key1)` также **не сможет найти и удалить** объект.
    - **Итог:** Запись становится «фантомом» — данные невозможно извлечь или удалить обычными методами, что приводит к **утечке памяти (Memory Leak)**.
    - _Правило:_ Ключи в `HashMap` всегда должны быть **неизменяемыми (Immutable)** (`String`, `Long`, `Record`).

### 🧵 12. Многопоточность (Concurrency)

#### `synchronized` vs `volatile`
- ⚡ **`volatile`:**    
    - Гарантирует **видимость (Visibility)**: запись в переменную сразу сбрасывается в главную память (RAM), минуя L1/L2 кэши CPU, а чтение всегда происходит из RAM.        
    - Гарантирует **порядок (Ordering)**: предотвращает перестановку инструкций компилятором/процессором (Happens-Before).        
    - **НЕ гарантирует атомарность** (операция `count++` с `volatile` не является потокобезопасной!).
    
- 🔒 **`synchronized`:**    
    - Захватывает монитор объекта.        
    - Гарантирует **Атомарность, Видимость и Взаимное исключение (Mutual Exclusion)**. В защищенный блок кода одновременно может зайти только один поток.        

#### Atomic и CAS
- ⚙️ **CAS (Compare-And-Swap):** Аппаратная инструкция процессора. Принимает `(адрес_памяти, ожидаемое_значение, новое_значение)`. Меняет значение только если текущие данные в памяти равны ожидаемым.    
- ⚛️ **Atomic-классы (`AtomicInteger`, `AtomicReference`):** Реализуют потокобезопасность без блокировок (Lock-free) на базе CAS в бесконечном цикле (**spin-lock**).

#### Пулы потоков и типы Executors
- 🏭 **`ThreadPoolExecutor`:** Базовый класс пула. Главные параметры:    
    - `corePoolSize` — число постоянных рабочих потоков.        
    - `maximumPoolSize` — максимальное число потоков при переполнении очереди.
    - `workQueue` — очередь задач (`BlockingQueue`).
    
- 🧰 **Виды фабричных пулов (`Executors`):**
    - **`newFixedThreadPool(n)`:** Фиксированное число потоков, неограниченная очередь (`LinkedBlockingQueue`). Risk: OOM при всплесках нагрузки.
    - **`newCachedThreadPool()`:** Создает новые потоки по мере необходимости, удаляет простаивающие (таймаут 60 сек). Внутренняя очередь `SynchronousQueue`. Risk: исчерпание ресурсов CPU при миллионах запросов.
    - **`newSingleThreadExecutor()`:** Однопоточный пул с гарантией последовательного выполнения задач.
    - **`newScheduledThreadPool(n)`:** Пул для выполнения задач по расписанию или с задержкой.
    - **`newWorkStealingPool()`:** Пул на базе `ForkJoinPool`. Потоки «воруют» задачи из очередей соседних загруженных потоков.

#### Deadlock (Взаимная блокировка)
- 💀 Ситуация, когда два или более потоков навечно заблокированы, ожидая освобождения ресурсов, захваченных друг другом (Поток 1 держит Lock A и ждет Lock B; Поток 2 держит Lock B и ждет Lock A).
- _Решение:_ Строгий единый порядок захвата блокировок, использование `tryLock()` с таймаутом.

#### Virtual Threads (Виртуальные потоки / Java 21+)
- 🧵 Легковесные потоки JVM, монтируемые на системные потоки-носители (**Carrier Threads**).
- При блокирующем I/O виртуальный поток отмонтируется, освобождая Carrier Thread для обработки других задач. Позволяют масштабировать блокирующий код до миллионов параллельных операций.

### 🌊 13. Stream API

#### Промежуточные vs Терминальные операции
- 🛠️ **Промежуточные (Intermediate / Lazy):** Не выполняют обработку данных моментально, а лишь формируют конвейер шагов. Возвращают новый `Stream`. (`filter()`, `map()`, `flatMap()`, `distinct()`, `sorted()`).
- ⚡ **Терминальные (Terminal / Eager):** Запускают физический проход по данным и выполнение всего конвейера. Возвращают итоговый результат или `void`. После вызова терминальной операции стрим закрывается и **не может быть использован повторно**. (`collect()`, `forEach()`, `reduce()`, `count()`).

#### Методы `filter`, `map`, `collect`, `flatMap`
- 🔍 **`filter(Predicate)`:** Отбирает элементы, удовлетворяющие условию (1-в-1).    
- 🟢 **`map(Function)`:** Преобразует каждый элемент в другой объект (1-в-1).    
- 🟣 **`flatMap(Function)`:** Преобразует каждый элемент во вложенный стрим и сплющивает все вложенные стримы в один плоский стрим (1-ко-многим).    
- 📦 **`collect(Collector)`:** Собирает элементы стрима в итоговую структуру данных (Map, List, Set).    

#### Параллельные стримы (`parallelStream()`)
- Выполняют обработку элементов параллельно на общем пуле **`ForkJoinPool.commonPool()`**.
    
- ⚠️ **Проблемы и подвохи на практике:**    
    - **Забивание общего пула:** Блокирующий I/O (запросы в БД или внешнюю сеть) внутри `parallelStream()` блокирует потоки `ForkJoinPool.commonPool()`, парализуя все остальные параллельные стримы в приложении.        
    - **Потеря производительности на Stateful-операциях:** Операции `sorted()`, `distinct()`, `limit()` требуют синхронизации между потоками и сводят на нет весь профит от параллелизации.        
    - **Нарушение порядка:** Не гарантируют порядок элементов при `forEach()` (нужно использовать `forEachOrdered()`).        
    - **Оверхед на автоупаковку:** `Stream<Integer>` тратит колоссальное время на boxing/unboxing при параллелизации. Нужно использовать примитивные стримы (`IntStream`, `LongStream`).        

### ⚠️ 14. Exceptions (Исключения в Java)

#### Иерархия
```Plaintext
                  Throwable
                 /         \
            Error           Exception
                           /         \
          IOException ...             RuntimeException
          (Checked)                   (Unchecked)
```

- 💥 **`Error`:** Критические сбои самой JVM (`OutOfMemoryError`, `StackOverflowError`). Приложение не должно пытаться перехватывать ошибки этого типа.
- ⚠️ **Checked Exceptions (Проверяемые):** Наследуются от `Exception` (кроме `RuntimeException`). Компилятор заставляет обязательно обрабатывать их через `try-catch` или объявлять в сигнатуре метода `throws` (`IOException`, `SQLException`).
- 🔴 **Unchecked Exceptions / `RuntimeException` (Непроверяемые):** Ошибки логики программы (`NullPointerException`, `IndexOutOfBoundsException`, `IllegalArgumentException`). Не требуют обязательного объявления.

#### Try-with-resources и Suppressed Exceptions
- 🛠️ Конструкция автоматического закрытия ресурсов, реализующих `AutoCloseable`.
- **Suppressed Exceptions (Подавленные исключения):** Если исключение произошло и в блоке `try`, и при автоматическом вызове `close()`, главным выбрасывается исключение из `try`, а исключения закрытия прикрепляются к нему и доступны через **`ex.getSuppressed()`**.

### 🌐 15. REST и HTTP

#### Принципы REST (REST Constraints)
1. **Client-Server:** Разделение ответственности интерфейса и хранения данных.
2. **Stateless:** Сервер не хранит состояние сессии клиента между запросами.
3. **Cacheable:** Ответы должны явно помечаться как кэшируемые.
4. **Uniform Interface:** Единый формат URI и использование стандартных HTTP-методов.
5. **Layered System:** Использование промежуточных слоев (Gateway, Load Balancers) прозрачно для клиента.

#### Методы HTTP, Безопасность и Идемпотентность
- 🔍 **`GET`:** Чтение. **Safe** (не меняет данные), **Idempotent**.
- ➕ **`POST`:** Создание нового ресурса. **Not Safe**, **Not Idempotent** (повторный запрос создаст дубликат).
- 🔄 **`PUT`:** Полное замещение ресурса. **Not Safe**, **Idempotent** (повторные запросы оставляют ресурс в том же состоянии).
- 🧩 **`PATCH`:** Частичное изменение ресурса. **Not Safe**, **Not Idempotent** (по спецификации RFC 5789).
- ❌ **`DELETE`:** Удаление ресурса. **Not Safe**, **Idempotent**.

#### Группы HTTP Кодов Ответов
- ℹ️ **1xx (Informational):** Запрос принят (`100 Continue`).
- ✅ **2xx (Success):** `200 OK`, `201 Created` (успешный POST/PUT), `204 No Content` (успешный DELETE).
- 🔀 **3xx (Redirection):** `301 Moved Permanently`, `302 Found`.
- 🛑 **4xx (Client Error):** `400 Bad Request`, `401 Unauthorized` (не аутентифицирован), `403 Forbidden` (нет прав/роли), `404 Not Found`, `409 Conflict`.
- 💥 **5xx (Server Error):** `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

### 🍃 15. Spring & Spring Boot

**Конфигурации и профили**

- ⚙️ **`@Configuration` и `@Bean`:** Позволяют явно объявлять бины с помощью Java-кода.
    
- 📦 **`@ConfigurationProperties` vs `@Value`:** Аннотация `@Value` внедряет отдельные свойства по одному. `@ConfigurationProperties` связывает иерархическую группу свойств из YAML/properties в единый типобезопасный Java-объект.
    
- 🌐 **`@Profile`:** Позволяет активировать бины или конфигурации только при включении конкретного профиля (`spring.profiles.active=dev`). Используется для разграничения настроек между окружениями (dev, test, prod).
    

**Self-Invocation и `@Transactional`**

- 🔴 **В чем проблема:** Вызов метода с аннотацией `@Transactional` из другого метода того же класса (`this.methodB()`) **не откроет транзакцию**.
    
- 🔍 **Причина:** Spring реализует транзакционность через **AOP-прокси**. Внешний вызов из другого бина проходит через прокси-обертку, которая открывает транзакцию. Внутренний вызов через `this` идет в обход прокси напрямую к оригинальному объекту.
    

**Прокси и AOP (Aspect-Oriented Programming)**

- ✂️ **AOP:** Парадигма, выносящая сквозную системную логику (транзакции, логирование, безопасность) в отдельные модули — **Аспекты**.
    
- ☕ **JDK Dynamic Proxy:** Создает прокси на основе штатного Java Reflection. Работает только с классами, реализующими интерфейсы.
    
- ⚡ **CGLIB:** Генерирует дочерний класс-наследник на уровне байт-кода. Используется по умолчанию в Spring Boot. Не работает с `final`-классами и `final`-методами.
    

**Жизненный цикл бинов (Bean Lifecycle)**

1. 🏗️ **Instantiation:** Вызов конструктора (создание сырого объекта).
    
2. 💉 **Populate Properties:** Внедрение зависимостей (DI).
    
3. 🔔 **Aware Interfaces:** Вызов методов `setBeanName()`, `setApplicationContext()` и т.д.
    
4. ⚙️ **BeanPostProcessor (Before Initialization):** Обработка аннотации `@PostConstruct`.
    
5. 🛠️ **Initialization:** Вызов метода `afterPropertiesSet()` или кастомного `init-method`.
    
6. 🎭 **BeanPostProcessor (After Initialization):** **Оборачивание бина в AOP-прокси** (для `@Transactional`, `@Async`).
    
7. 🟢 **Ready:** Бин полностью готов к работе.
    
8. 🧹 **Destruction:** Вызов `@PreDestroy` или `destroy()` при закрытии контекста.
    

**Dependency Injection (DI)**

- 🥇 **Constructor Injection (Рекомендуемый):** Позволяет делать поля `final` (неизменяемость), гарантирует целостность объекта при создании и прост для unit-тестов без Spring.
    
- 🥈 **Setter Injection:** Используется для необязательных зависимостей, которые могут меняться во время работы.
    
- 🥉 **Field Injection (`@Autowired` на поле):** Антипаттерн. Скрывает зависимости, усложняет тестирование без рефлексии и провоцирует нарушение принципа единственной ответственности (SRP).

### 📦 17. Коллекции Java

**Иерархия и сложности (Big O)**

- 📝 **`List` (Списки):**
    
    - `ArrayList`: Динамический массив. Быстрый доступ по индексу $O(1)$, но медленная вставка/удаление из середины $O(N)$.
        
    - `LinkedList`: Двусвязный список. Быстрое добавление/удаление в начало и конец $O(1)$, но медленный доступ по индексу $O(N)$.
        
- 🎯 **`Set` (Множества уникальных элементов):**
    
    - `HashSet`: Построена на базе `HashMap`. Операции добавления, поиска и удаления работают за $O(1)$ в среднем. Порядок элементов не гарантирован.
        
    - `LinkedHashSet`: Сохраняет порядок вставки элементов за счет двусвязного списка поверх хэш-таблицы.
        
    - `TreeSet`: Построена на базе Красно-Черного дерева. Хранит элементы в строго отсортированном порядке. Операции за $O(\log N)$.
        
- 🗺️ **`Map` (Пары Ключ-Значение):**
    
    - `HashMap`: Поиск, вставка и удаление за $O(1)$ в среднем. При коллизиях бакеты с односвязными списками перестраиваются в Красно-Черные деревья $O(\log N)$ при достижении 8 элементов.
        
    - `TreeMap`: Хранит ключи отсортированными. Поиск и вставка за $O(\log N)$.
        

**ConcurrentHashMap**

- 🚀 Высококонкурентная потокобезопасная карта из `java.util.concurrent`.
    
- 📖 **Чтение (`get`):** Выполняется абсолютно без блокировок за счет `volatile`-ссылок на узлы.
    
- ✍️ **Запись (`put`):** Использует **CAS-операции** для первой вставки в пустой бакет и точечный **`synchronized` только на головной узел конкретного бакета** при коллизиях.
    
- 🚫 **Запрет `null`:** `null`-ключи и `null`-значения строго запрещены во избежание неоднозначности при многопоточной обработке.

### 🧠 18. Память JVM и Сборщик мусора (GC)

**Области памяти JVM**

- 🏔️ **Heap (Куча):** Общая область памяти для всех потоков. Хранит все создаваемые объекты. Управляется Garbage Collector-ом.
    
- 🌌 **Metaspace:** Хранится в нативной памяти ОС. Содержит метаданные классов, пулы констант и байт-код методов.
    
- 📚 **Thread Stack (Стек потоков):** Выделяется под каждый поток индивидуально. Хранит кадры вызова методов, примитивные локальные переменные и ссылки на объекты в Heap.
    
- 📍 **PC Register:** Содержит адрес текущей исполняемой инструкции JVM для конкретного потока.
    

**Поколения в Heap и Работа GC**

Память Heap разделена на основе _слабой гипотезы о поколениях_ (большинство объектов умирают сразу после создания):

- 🐣 **Young Generation (Молодое поколение):**
    
    - Состоит из региона `Eden` (куда попадают свежесозданные объекты через `new`) и двух регионов выживших `Survivor 0 (S0)` и `Survivor 1 (S1)`.
        
    - Очищается быстрой сборкой **Minor GC**. Выжившие объекты переносятся из `Eden` и текущего `S0` во второй `S1`, а старые регионы полностью очищаются.
        
- 👴 **Old Generation (Старое поколение):**
    
    - Хранит долгоживущие объекты (прошедшие заданное число сборок в Survivor) и крупные объекты.
        
    - Очищается тяжелой сборкой **Major / Full GC** (алгоритм Mark-Sweep-Compact), которая сопровождается паузами Stop-The-World (STW).

### 🧱 19. Паттерны проектирования (GoF)

**Singleton (Синглтон)**

- 🎯 **Назначение:** Порождающий паттерн. Гарантирует наличие **ровно одного экземпляра** класса на весь контекст приложения и предоставляет к нему глобальную точку доступа.
    
- 🛠️ **Реализация:** С использованием `Enum` (защищает от атак через Reflection и десериализацию) или `Bill Pugh Singleton` (на основе статического внутреннего класса).
    

**Factory Method (Фабричный метод)**

- 🎯 **Назначение:** Порождающий паттерн. Определяет интерфейс создания объекта, но делегирует выбор конкретного класса для создания дочерним классам.
    
- 💡 **Плюс:** Избавляет основной код от жесткой привязки к конкретным классам и вызовам `new ConcreteObject()`.
    

**Strategy (Стратегия)**

- 🎯 **Назначение:** Поведенческий паттерн. Выносит семейство родственных алгоритмов в отдельные классы и делает их взаимозаменяемыми во время выполнения (Runtime) под единым интерфейсом.
    
- 💡 **Пример:** Выбор способа оплаты (`CardPayment`, `SbpPayment`, `CryptoPayment`) внутри сервиса заказов.
    

**Builder (Строитель)**

- 🎯 **Назначение:** Порождающий паттерн. Позволяет пошагово конструировать сложные объекты с большим количеством опциональных параметров.
    
- 💡 **Плюс:** Избавляет от громоздких «телескопических» конструкторов с десятком аргументов и дает читаемый Fluent API.
    

**Prototype (Прототип)**

- 🎯 **Назначение:** Порождающий паттерн. Позволяет создавать новые объекты путем **клонирования уже существующего объекта-образца** вместо вызова `new` и повторной тяжелой инициализации.

### 🗄️ 20. SQL и Базы Данных

**Индексы**

- 📖 Вспомогательные древовидные структуры данных (чаще B-Tree) для ускорения поиска строк.
    
- 📈 **Плюс:** Ускоряют выполнение `SELECT`-запросов с $O(N)$ до $O(\log N)$.
    
- 📉 **Минус:** Занимают место на диске/RAM и **замедляют операции записи** (`INSERT`, `UPDATE`, `DELETE`), так как СУБД вынуждена перестраивать индексы при любых изменениях.
    

**Джойны (JOINs)**

- 🔗 **`INNER JOIN`:** Возвращает только те строки, для которых условие соединения истинно в обеих таблицах.
    
- 👈 **`LEFT JOIN`:** Возвращает все строки из левой таблицы и совпадающие строки из правой (если совпадения нет, подставляет `NULL`).
    
- 👉 **`RIGHT JOIN`:** Возвращает все строки из правой таблицы и совпадающие строки из левой.
    
- 🌐 **`FULL JOIN`:** Возвращает все строки из обеих таблиц, заполняя неспаренные места `NULL`.
    
- ✖️ **`CROSS JOIN`:** Создает декартово произведение (каждая строка первой таблицы связывается с каждой строкой второй).
    

**GROUP BY и HAVING**

- 📊 **`GROUP BY`:** Группирует строки с одинаковыми значениями в указанных колонках для последующего применения агрегатных функций (`COUNT`, `SUM`, `AVG`).
    
- 🔍 **`HAVING`:** Фильтрует сгруппированные данные **после** выполнения `GROUP BY` (работает с агрегатными функциями).
    
- ⚖️ **Отличие от `WHERE`:** `WHERE` фильтрует отдельные строки _до_ группировки, а `HAVING` фильтрует сформированные группы _после_ группировки.
    

**Views (Представления)**

- 🪟 **View (Обычное):** Виртуальная таблица на базе SQL-запроса. Данных на диске не хранит, выполняет исходный SQL-запрос заново при каждом обращении.
    
- 💾 **Materialized View:** Физически сохраняет результат выполнения SQL-запроса на диск. Выборки работают мгновенно, но данные требуют обновления через `REFRESH MATERIALIZED VIEW`.
    

**Constraints (Ограничения целостности)**

- 🔑 `PRIMARY KEY`: Уникальный идентификатор строки таблицы (`UNIQUE` + `NOT NULL`).
    
- 🔗 `FOREIGN KEY`: Внешний ключ для связи с первичным ключом другой таблицы и поддержания ссылочной целостности.
    
- 🛡️ `UNIQUE`: Гарантирует уникальность значений в колонке.
    
- 🚫 `NOT NULL`: Запрещает хранение `NULL`-значений в колонке.
    
- ⚙️ `CHECK`: Проверяет соответствие значений заданному условию (например, `CHECK (age >= 18)`).
    

**DateTime vs Timestamp / Timestamptz**

- 📅 **`TIMESTAMP` (without time zone):** Сохраняет дату и время «как есть», не привязываясь к часовому поясу сервера или клиента.
    
- 🌍 **`TIMESTAMPTZ` (with time zone):** При сохранении автоматически конвертирует время в UTC, а при чтении преобразует его в часовой пояс текущей сессии клиента. (Золотой стандарт для веб-приложений!).
    

**EXPLAIN**

- 📑 **`EXPLAIN`:** Выводит теоретический план выполнения SQL-запроса, построенный оптимизатором СУБД (расчетная стоимость `Cost`, тип сканирования `Index Scan` или `Seq Scan`). Запрос при этом **не выполняется**.
    
- ⏱️ **`EXPLAIN ANALYZE`:** Физически **выполняет** SQL-запрос и выводит как планируемые, так и фактические показатели времени и количества прочитанных строк.
